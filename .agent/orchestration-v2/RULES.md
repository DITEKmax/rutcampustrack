Решение владельца 2026-10-01, текущая продуктовая итерация: ВСЕ новые дочерние агенты и новые задания (исполнение, поиск, координация, независимое review) получают `gpt-6.1-sol` с effort `high`. Luna и предыдущий Sol для новых задач не используются; молчаливый fallback запрещён. Root остаётся `gpt-6-astra` medium. Это временно заменяет прежнюю модельную маршрутизацию данного проекта и сохраняется до явного нового решения владельца. Старые агенты не меняют модель от правки config: их безопасно останавливают и передают scope новому агенту с подтверждёнными runtime model/effort.

# RutCampusTrack — delivery policy

Решение владельца 2026-09-20. Этот файл — единый канон процесса проекта. Он заменяет несовместимые пункты предыдущего RULES, project/global routing, старых packets и skills только для rutcampustrackFULL. Предыдущие bytes: archive/2026-09-20-before-delivery-policy/. Продуктовый STOP снимается только новым явным GO на продукт; разрешение менять инструкции не является таким GO.

## 1. Общение и ответственность
Главный чат оркестратора — ЕДИНСТВЕННАЯ точка общения владельца с командой: вопросы, ответы, уточнения, отчёты, разрешения, STOP/GO. Тимлиды и исполнители сообщают главному; не требуют от владельца перехода в другие чаты. Главный отвечает за доставку функции, зависимости, ресурсы, приёмку и общую остановку. Не повторяет поиск или проверки исполнителя без конкретного пробела.

## 2. Модели и делегирование
Главный Astra medium. В текущей итерации implementation/search/coordinator/review — GPT-6.1 Sol high по решению владельца 2026-10-01. Каждый новый spawn явно передаёт model=gpt-6.1-sol, reasoning_effort=high, fork_turns=none. Роль с несовместимыми фиксированными runtime-настройками не использовать. Новое задание не отдавать старому Luna/Sol6.0 через followup. Reviewer остаётся независимым от автора. Terra NEVER; fast mode не меняется.
Основной маршрут: главный → назначенный исполнитель → приёмка. Тимлид подключается при полезной межзадачной координации или предметном решении; обязательного промежуточного слоя нет. Отдельный scout нужен только когда исходных locations недостаточно и его поиск сэкономит работу. Исполнитель сам читает известные связанные файлы. Не создавать агентов ради занятости.
Решение владельца 2026-09-30: конфигурационный потолок 8 дочерних агентов без root, включая scouts/reviewers/coordinators, в пределах фактически доступных runtime slots. Обычная загрузка 4–5; дополнительные слоты только для независимого scope или полезного review/завершения пакета, не обязательного запуска. Увеличение лимита не меняет модели, effort, независимость review и число heavy leases. Польза оценивается по времени доставки и ожиданию, а не заполнению слотов. Старый предел3 отменён. Config не меняет уже выданный лимит сессии: при меньшей runtime ёмкости использовать её, сообщить различие, не создавать обходной control plane. Параллелить независимые scopes с ясными входами и местом интеграции. Нет жёсткого ограничения «один исполнитель на проект». Leaves/reviewers не создают детей. Root и тимлиды не пишут продуктовый код; назначенный developer — sole writer. Документацию процесса пишет root.
Fresh spawn: явные model/effort, fork_turns=none, абсолютный RULES path + актуальный SHA и компактный scoped contract. Один исполнитель сохраняет ownership связанной реализации, исправлений и интеграции, пока доступен; свежий агент не требуется для каждого замечания. После compaction читать компактный CURRENT и свой handoff, не всю историю.

## 3. Единица работы
Планировать завершённое наблюдаемое действие пользователя со связанными Job Story/Screen/Requirement IDs: кто → что делает → что получает, какие данные меняются и какой существенный запрет сохраняется. Связанные малые изменения объединять, независимые задачи выполнять параллельно. Доводить текущий WIP до интеграции перед накоплением новых веток. Это не глобальный барьер: карты и независимые административные операции не ждут журнала/ДЗ; ждёт только задача с конкретной незакрытой зависимостью. Один автор ведёт пакет через реализацию, corrections и подготовку интеграции. До параллельных backend/frontend работ фиксировать минимальный API: методы, поля, ошибки, права и владелец контракта. Переиспользовать серверные операции и общие features PWA/TMA; платформенные adapters отдельно.
Девять полей contract остаются, но в краткой форме: Goal; Context/evidence; Relevant scope; Required behavior; Constraints; Existing patterns; Acceptance criteria; Verification; Do not. Не копировать RULES целиком; достаточно ссылки/hash и ограничений конкретной задачи. Scope включает base/worktree, пути, writer, интеграцию и достаточные проверки. Поиск и документирование не отдельные milestones без необходимости.
Решения владельца выше исторических документов/тестов. Источники читать адресно. Нет обязательной отдельной стадии переноса всех источников перед каждой реализацией.

## 4. Checkout и ресурсы
Один writer на worktree; параллельные writers только в независимых worktrees с известной baseline. Contracts/generated/lockfiles/configs имеют одного назначенного владельца. Product code располагается в services/frontends/proto внутри Git worktree, .agent хранит координацию/evidence и может содержать worktrees. .agents — skills, не место продуктовой реализации.
Не создавать новый worktree для каждого исправления. Повторно использовать сохранённый assigned worktree. Не работать по dirty original вместо принятой базы. Интегратор переносит только назначенный inventory, сохраняет чужие изменения.
Постоянное разрешение владельца от 2026-09-23 для этого проекта: «ты можешь переносить всегда в этом проекте без доп вопроса мне». Перенос готовых изменений в main (включая scoped cherry-pick/merge) заранее разрешён; повторное подтверждение владельца не требуется. Главный передаёт это разрешение исполнителю в packet и назначает единственного MAIN writer. Push и deploy остаются отдельными действиями, требующими разрешения. Отказ автоматической проверки не обходить: предъявить актуальное явное разрешение и правила как evidence; технический блокер сообщить главному.
Main имеет одного writer в каждый момент; роль интегратора передаётся явно после освобождения checkout. Готовые пакеты интегрируются по мере завершения, не после всех направлений. Не назначать main writer большую новую реализацию при очереди готовых пакетов. Если ждут интеграции два пакета, свободные слоты направлять на завершение/интеграцию вместо открытия новых scopes; независимую уже начатую работу не останавливать.
Тяжёлые Gradle/Docker операции по умолчанию имеют один lease у главного. Два одновременных lease допустимы после подтверждения свободной памяти/CPU и независимых ports/DB/queues/build/generated outputs; resource mapping записать в SLOTS. Не увеличивать heavy concurrency только вслед за числом агентов. Лёгкие проверки разных worktrees могут идти параллельно. Worktree не изолирует runtime resources. Переиспользовать выделенный стенд и собранные неизменённые artifacts; версии и данные проверочных сценариев должны оставаться известными. Не изменять чужие ресурсы.

## 5. Проверки по задаче
До реализации выбрать минимально достаточные проверки по изменяемому поведению и риску. Нет списка build/lint/typecheck/unit/integration «всё по умолчанию» и обязанности оправдывать каждую пропущенную категорию. Команды из build/scripts/CI конкретного worktree; известные команды повторно не искать. Обязательные repository/CI gates не обходить; запускать на соответствующей стадии, не после каждой мелкой правки.
Новые автоматические тесты — для сложных или значимых изменяемых правил: authz/изоляция, транзакции, история/потеря данных, конкуренция, идемпотентность, нетривиальные расчёты и существенный дефект без существующего покрытия. Для простых базовых операций, wiring, текста, CSS, очевидного mapping/делегирования новые unit-тесты по умолчанию не писать. Простая внешне операция с существенным риском оценивается по риску. Базовый результат подтвердить существующим тестом либо короткой проверкой пользовательского пути, а не новым suite.
Одно правило — достаточный уровень проверки результата. Второй уровень добавлять лишь для отдельного риска, который первый не проверяет; указать этот риск одной строкой. Не тестировать структуру кода, wording или mock-call как замену пользовательскому результату. Не повышать coverage ради числа. Не начинать массовую чистку старых тестов.
После пакета исправлений запускать затронутые проверки. После PASS повторять/расширять только из-за изменённой зависимости, конкретной ошибки или нерешённого риска. Полный набор — при соответствующей интеграции/release или обоснованном широком воздействии; не после каждой правки. Генерация только изменённых контрактов/назначенных consumers с явными путями; неизменённые outputs не регенерировать.
При повторной неудаче по той же причине остановить одинаковые попытки: изменить гипотезу/подход на основании новых данных. Исправление fixture/harness минимально для текущей задачи; новые возможности стенда — отдельный backlog, не неявное расширение. Не исправлять тест ослаблением реального требования.
Evidence: один компактный итог criteria → revision → command/result → log path. Логи запусков не перезаписывать, но не дублировать их пересказ в нескольких документах. Test count не показатель готовности.

## 6. Review и завершение
Для authz/транзакций/гонок/истории/риска потери данных — одно независимое Sol high review целостного изменения. Мелкие обратимые изменения не требуют отдельного review-агента. Автор сначала заканчивает связанный пакет и устраняет найденные им ошибки; reviewer получает цель, scope, стабильный diff и результаты без полного transcript.
Все подтверждённые findings одним пакетом: severity, file:line, наблюдение/воспроизведение, влияние. После corrections — независимая recheck затронутых мест и их влияния; весь diff заново только при изменении архитектуры/контракта или существенном расширении. Этот пункт отменяет прежнюю обязательную fresh full recheck после любого FAIL. Стиль и пожелание ещё одного теста без непокрытого существенного риска не блокируют DONE.
DONE: критерии пользовательского результата выполнены в согласованном scope, изменение интегрировано в назначенную базу, достаточные проверки приняты, важное review при необходимости завершено, blocking findings отсутствуют. Source-ready WIP обозначать отдельно. При документации runtime N/A. Для full-stack истории backend mocks не заменяют реальный путь; frontend подключать после стабилизации нужного API, не после всего backend.

## 7. Отчёт и готовность
Сначала: какое действие теперь доступно пользователю, ссылка/способ воспроизведения и короткая вырезка основной логики при её изменении. Затем точный список файлов: создан / изменён / удалён, абсолютная ссылка, что изменено; тесты и обвязку явно обозначать. Не выдавать перенесённый старый код за новый. При большом списке полный inventory в одном summary, в чате ключевые файлы и ссылка на полный список. Проверки — краткое подтверждение, не основной отчёт.
Готовность считать по принятому inventory Job Stories, экранов и целевых возможностей сервисов: docs/product/READINESS.md. Backend request IDs связывать с историями, а не суммировать повторно. Показывать числитель/знаменатель, unknown и незавершённое. Проценты тестов/строк/файлов не использовать. Общий production процент допустим только по утверждённому составу release и явной формуле; обязательные эксплуатационные блокеры показывать независимо от процента.
CURRENT содержит только активное состояние/точку STOP, владельцев, следующий шаг и ссылки. История хранится отдельно; не наращивать CURRENT бесконечными append. SLOTS/REGISTRY должны отражать текущее состояние, не старый GO.
Метрики процесса: docs/delivery-metrics.md и один ledger .agent/orchestration-v2/metrics/packages.csv. Запись при переходах start/ready/integrated/accepted/STOP, не на каждом tool call. Не создавать отдельного агента, daemon или новые тесты для измерений. Учитывать координацию, ожидание, проверки, исправления продукта/обвязки раздельно; неизвестные времена не выдумывать. Пользу оценивать по доставленному пользовательскому результату и времени до интеграции, а не числу агентов/тестов. Причина обязательна для повторного PASS и расширения проверки; обязательные gates не снимать ради метрик.

## 8. STOP и права
Главный принимает STOP в своём чате и передаёт всем активным направлениям/исполнителям; зарегистрированные направления подтверждают отсутствие дочерней работы. Новые работы не начинать. Текущую ограниченную операцию завершить безопасно или сохранить coherent WIP. Каждый ACK содержит оставшееся, состояние процессов/ресурсов и checkpoint. Главный объявляет STOP завершённым после сверки. Возобновление только по owner GO; не будить завершённых агентов автоматически.
Секреты не читать/печатать; no full access, no скрытый orchestrator/scheduler. Deploy, production migration, удаление данных/backup, firewall/rotation secrets требуют отдельного разрешения после конкретного diff/checks/rollback. Global config и другие проекты не менять без прямого задания владельца; разрешение 2026-09-21 касается agent concurrency config и настоящей delivery policy, не прав/секретов/моделей других проектов. Согласованная Figma остаётся источником UI; запись/публикация только по прямому заданию.

## Решение владельца 2026-10-01: окружения разработки
Параллельные frontend dev servers и небольшие сервисные окружения допускаются при конкретной экономии ожидания; один общий стенд принимает интегрированные сценарии. Worktree не изолирует ресурсы: назначать отдельные ports, DB/queues/volumes и synthetic data scopes. Общий API изменяет только владелец стенда; клиенты используют согласованный контракт. Не разворачивать полный стенд на каждый worktree и не расширять harness заранее. Heavy concurrency по-прежнему требует доказанного запаса ресурсов; измерять elapsed delivery/ожидание, не обещать ускорение без данных. Принятые неизменённые artifacts переиспользовать.

## Решение владельца 2026-10-01: backend-first
Текущий этап — полностью рабочая серверная часть А–Ж по принятым сценариям. Далее отдельные итерации frontend/Figma, ручная локальная приёмка и затем отдельно разрешённый deploy. Не запускать новые работы по внешнему виду, browser download/install/offline/TMA UI в текущем этапе; готовый клиентский WIP сохранить отдельно. Принимать серверные операции реальными API/БД/сообщениями на достаточном уровне риска. Генерация документов, auth/session/права, upload/download API, события и server recovery остаются текущими задачами. Ж означает серверную эксплуатационную подготовку; actual deploy не выполнять. Внешний Telegram/provider, требующий подключения владельцем, отмечать неподтверждённым, не исключать молча из итоговой готовности. Смена этапа не увеличивает старые смешанные проценты: backend и frontend остаток учитывать раздельно.
