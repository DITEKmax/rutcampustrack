### Сверка со сканом

- **ЗЕЛЁНОЕ:** переключатель ролей, круг профиля, кнопка «Добавить предмет», три кнопки типов занятий ЛК · ПЗ · ЛЗ внутри формы.
- **ЖЁЛТОЕ:** поповер профиля «Настройки / Выход», таблица предметов, **весь блок формы внизу страницы**.
- **КРАСНОГО на скане нет** — фиксированного отображения без взаимодействия на этом экране не выделено.
- **НЕ ОКРАШЕНО:** оба набора `MainNav`, иконка `⋮` в строке, поле названия и строки преподавателей внутри жёлтой формы.

**Форма (прим. 5) — условное содержимое:** по умолчанию свёрнута, раскрывается по «Добавить предмет» либо по «Редактировать» из меню `⋮`. Раскрывается **на самой странице**, не модалкой (§0 чат 3) — на скане она и нарисована внизу, а не поверх.

**Не нарисовано, но следует из заметок:** `h1`; кнопки «Сохранить» и «Отмена» у формы; состав меню `⋮` («Редактировать», «Удалить»); подтверждение удаления с вводом пароля и кода из бота (job 1); правило уникальности номера и названия предмета (прим. 1).

### Красный ≠ без взаимодействия

На этом скане красных блоков нет. Ближайший аналог — колонка «Количество пар пройдено / всего пар»: пользователь с ней не взаимодействует (прим. 4: «считается исходя из расписания и автоматически обновляется»), но у неё есть собственные `loading`, `future` и `error` — см. §5.

## 4. Потребности в данных

### 4.1 Предметы группы

- **Нужно:** сущность «предмет» — идентификатор, порядковый номер, название, привязка к группе и семестру; вложенный перечень **типов занятий**, у каждого — список преподавателей (идентификатор, ФИО, табельный номер) и пара счётчиков «пройдено / всего пар». Фильтров нет, сортировка по номеру, пагинации нет: 10–15 предметов на группу.
- **Сейчас:** `GET /academic/subjects` (HEADMAN — только своя группа, ADMIN — все); `GET /academic/assignments` — назначения «преподаватель / предмет / группа / семестр».
- **Пробел** `[уточнение по контракту]`: содержит ли представление предмета **перечень его типов занятий**. На ПК-103 уже действует правило «раскрываются только те типы, которые у предмета реально есть» (JS-HEADMAN-13) — значит связь где-то хранится; здесь она впервые становится **редактируемой**.
- **Пробел** `[предложение по бэкенду]` — **БЛОКИРУЮЩЕЕ:** и `POST /academic/subjects/{id}/teachers/{teacherId}`, и `assignments` связывают преподавателя с **предметом целиком**, без измерения «тип занятия». Скан (прим. 3 и строки таблицы) требует связи **«предмет × тип занятия × преподаватель»**: у одного предмета ЛК ведёт один преподаватель, ПЗ — другой, ЛЗ — двое сразу. **Без третьего измерения экран не строится вообще**, обходного пути на клиенте нет: сгруппировать по типу нечего, данные такой размерности не существует.
- **Пробел** `[предложение по бэкенду]`: счётчики «пройдено / всего пар» по паре «предмет × тип» — **агрегат сервера**. Клиент считать не должен: пришлось бы вытянуть расписание всего семестра и повторить правила знаменателя (отменённые не считаются, разовые и перенесённые считаются наравне). Это ровно тот расход и то расхождение цифр, которые запрещает JS-SYSTEM-16.

### 4.2 Подсказка названий предметов

- **Нужно:** список названий предметов, уже заведённых в системе, для подсказки при вводе. Поиск по фрагменту, ограничение по количеству. **Названия, не записи:** идентификаторы чужих предметов клиенту не нужны.
- **Сейчас:** `GET /academic/subjects` для старосты ограничен своей группой — как источник подсказки по системе он не подходит.
- **Пробел** `[предложение по бэкенду]`: операция подсказки названий. **Подтверждено владельцем:** список — это подсказка по уже заведённым в системе названиям, а не закрытый справочник; свободный ввод разрешён. Важное ограничение: отдавать **только строки названий**, без привязки к группам и преподавателям, иначе подсказка превращается в утечку структуры чужих групп.
- **Следствие для ПК-117:** там правило другое и более строгое — в расписание выбираются **только предметы, заведённые старостой для этой группы** (подтверждено владельцем). Два разных контрола, не путать.

### 4.3 Преподаватели

- **Нужно:** поиск преподавателя по фрагменту ФИО **или табельному номеру**, постранично, из общего пула вуза; в представлении — ФИО и табельный номер.
- **Сейчас:** `GET /academic/users/teachers` — список **без постраничной разбивки** и без поиска.
- **Пробел** `[предложение по бэкенду]`: поиск и пагинация. Иначе при каждом открытии формы фронт тянет всех преподавателей вуза целиком и фильтрует локально — over-fetching, растущий вместе с вузом, при том что выбирается один-два человека.
- **Пробел** `[уточнение по контракту]`: присутствует ли **табельный номер** в представлении преподавателя. JS-HEADMAN-12 строит сценарий поиска именно на нём, подпись на скане — тоже («вводить фио или номер»).

### 4.4 Создание и редактирование предмета

- **Нужно:** сохранить предмет целиком — название + набор типов занятий + преподаватели по каждому типу — **одной операцией**. Серверная проверка уникальности названия и номера в пределах группы и семестра (прим. 1), ошибка возвращается **на поле**.
- **Сейчас:** `POST /academic/subjects`, `PUT /academic/subjects/{id}` (полное обновление), `POST` / `DELETE /academic/subjects/{id}/teachers/{teacherId}` — по одному преподавателю за запрос.
- **Пробел** `[предложение по бэкенду]`: **атомарное сохранение предмета** с составом типов и преподавателей. Сейчас предмет с тремя типами и четырьмя преподавателями — это `1 + N` запросов; при обрыве на середине предмет остаётся в полусохранённом состоянии, и откатить его фронт не может.
- **Пробел** `[уточнение по контракту]`: что происходит при **снятии типа занятия, по которому уже проведены пары**. Предлагаю запретить снятие с текстовым пояснением, а не удалять пары молча: иначе правка формы каскадно уничтожает посещаемость, и пользователь об этом не предупреждён. **Требует подтверждения владельца.**
- **Пробел** `[уточнение по контракту]`: смена преподавателя (прим. 6) — добавляется новый, старый удаляется старостой, **и вся информация сохраняется**. Значит связь «преподаватель — тип занятия» должна иметь период действия либо проведённые пары должны хранить своего преподавателя. Иначе после смены весь семестр задним числом «вёл» новый человек.

### 4.5 Удаление предмета

- **Нужно:** необратимое каскадное удаление (job 1: удаляется вся информация — посещаемость, дз, всё связанное с предметом), доказательство намерения — **пароль + код из бота**, и **предварительный показ последствий**.
- **Сейчас:** `DELETE /academic/subjects/{id}` (HEADMAN/ADMIN). Механика кода существует: `POST /auth/otp/request`, `POST /auth/otp/verify-by-code`.
- **Пробел** `[предложение по бэкенду]`: операция удаления должна **принимать доказательство** (пароль + код), а у OTP появиться назначение вида `dangerous_action`. JS-SYSTEM-03 уже требует, чтобы код одного сценария не работал в другом — здесь это требование становится обязательным: кодом входа нельзя стирать семестр.
- **Пробел** `[предложение по бэкенду]`: **предпросмотр последствий** — сколько пар, отметок и заданий будет удалено. Образец в системе уже есть: `POST /academic/groups/promote/preview`. Без цифр диалог говорит «удалится всё», и староста подтверждает вслепую.
- **Пробел** `[уточнение по контракту]`: каскад выполняет **сервер целиком** (по цепочке в `schedule` и `attendance`) или часть данных остаётся сиротами. Фронт удалять по частям не может и не должен: это несколько межсервисных операций без транзакции.

### ⚠️ Фактура к решению о транспорте

| Что | Оценка |
|---|---|
| Запросов на входе в экран | **2–3**: предметы + назначения преподавателей + (возможно) типы занятий. Должно приходить одним ответом под форму экрана |
| Запись | **`1 + N`** на сохранение одного предмета: сам предмет плюс запрос на каждую привязку преподавателя. **Атомарности нет** — при обрыве остаётся полусохранённый предмет |
| Форма | typeahead по преподавателям — по запросу на ввод, это приемлемо. **Но при отсутствии серверного поиска это один тяжёлый запрос всего пула вуза** на каждое открытие формы |
| Не существует | измерение «тип занятия» в связи с преподавателем (**блокирует экран**), счётчики пройденных пар, подсказка названий, предпросмотр удаления, приём доказательства при удалении |

## 5. Состояния

**На бумаге состояний нет** — нарисован `success` с одним предметом на три типа занятий и раскрытая форма. Всё ниже добавлено при разборе.

### Автомат `SubjectForm`

| Состояние | Условие | Что показываем |
|---|---|---|
| `closed` | форма не вызвана | только таблица и кнопка «Добавить предмет» |
| `create` | нажата «Добавить предмет» | пустая форма, фокус в поле названия; типы не выбраны, **блоков преподавателей нет** |
| `edit` | «Редактировать» из `⋮` | та же форма, предзаполненная **предметом целиком** (прим. 2); заголовок различает режим |
| `types-empty` | название введено, ни один тип не выбран | блоки преподавателей не рендерятся, текстом объясняется, что сначала выбираются типы занятий (прим. 3) |
| `suggesting` | идёт ввод в поле названия | список подсказок, количество найденных **озвучивается**; свободный ввод при этом не блокируется |
| `saving` | отправка | `aria-busy`, кнопки заблокированы |
| `invalid` | сервер вернул конфликт названия или номера | ошибка **на поле**, не общим `FormError` (прим. 1: номер и название уникальны) |
| `error` | сбой сети или сервера | `FormError`, **введённые данные не теряются** |

### Автомат удаления (`ConfirmDialog` + `DangerousActionChallenge`)

| Состояние | Условие | Что показываем |
|---|---|---|
| `preview` | вызвано «Удалить» | что именно будет удалено, **с количествами** (§4.5), и что действие необратимо |
| `challenge` | предупреждение принято | поле пароля + поле кода из бота + `CountdownTimer` |
| `expired` | код истёк | действие «Запросить новый код», а не пустая форма (состояние введено в чате 3) |
| `rejected` | пароль или код неверны | ошибка текстом, `role="alert"`; данные предмета не тронуты |
| `deleting` | оба доказательства приняты | `busy`; **отмена уже невозможна**, и об этом сказано заранее, а не в момент нажатия |

**Без состояния `preview` экран врёт:** староста подтверждает уничтожение семестра посещаемости и всех домашних заданий, не зная объёма потерь.

### Остальные блоки

- **Таблица:** `loading` (скелетон строк), `empty` — «предметов ещё нет» + действие «Добавить предмет». Для начала семестра это **нормальное стартовое состояние**, а не ошибка, и текст должен это отражать (§6.2: `empty` различает будущее и прошедшее). `error` с повтором, независимо от формы.
- **`SubjectProgressCell`:** `future` — семестр ещё не начался, «0 из 16», где **ноль правдив** (в отличие от счётчиков на ПК-111, где ноль врал: там его заменяет `no-active-lesson`). `no-active-semester` — счётчики не рендерятся, вместо них пояснение: делить нечего.
- **Форма и таблица падают независимо:** ошибка подсказки названий не мешает сохранить предмет с введённым вручную названием.

### Общие

- `offline` — таблица показывается с пометкой об устаревании; форма и удаление **заблокированы**: сохранять предмет вслепую нельзя, а удалять тем более.
- `no-active-semester` — предметы привязаны к семестру (JS-HEADMAN-13); без активного семестра создание блокируется с пояснением, а не падает при отправке.
- `forbidden` — экран целиком, без утечки перечня предметов.

### По ролям

| Кто | Что видит и может |
|---|---|
| **Староста** | всё |
| **Помощник** | ⚠️ **в согласованном перечне прав** (`mark_attendance`, `manage_excuses`, `manage_homework`, `cancel_lessons`, `view_stats`) **права на предметы нет вообще.** Значит либо экран для помощника целиком `forbidden`, либо перечень прав расширяется. Вынесено в вопрос выделенной сессии |
| **student / teacher / admin** | `forbidden` |

Отдельное наблюдение к той же сессии: **удаление предмета с каскадом делегировать не следует ни при каком наборе прав** — это единственное действие в роли, которое уничтожает данные всей группы за семестр без возможности восстановления.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| «Добавить предмет» | Раскрывает `SubjectForm` в режиме `create` внизу страницы, фокус в поле названия. Подтверждения не требует |
| `⋮` → «Редактировать» | Раскрывает ту же форму в режиме `edit`, предзаполненную **предметом целиком**, а не одним типом занятия (прим. 2). Прокрутка к форме, фокус в первое поле |
| `⋮` → «Удалить» | `ConfirmDialog destructive` → предпросмотр последствий → пароль + код из бота (job 1). **Оптимистичного UI нет:** строка исчезает только после ответа сервера |
| Кнопка типа занятия (ЛК / ПЗ / ЛЗ) | Включает и выключает тип. Включение **добавляет блок преподавателей** (прим. 3), выключение — убирает его. Если по типу уже есть проведённые пары — снятие блокируется с пояснением (§4.4, требует подтверждения) |
| «+ добавить» | Добавляет ещё одного преподавателя к этому типу занятия (прим. 2, 6) |
| Удаление преподавателя из блока | Без `ConfirmDialog`: связь восстанавливается тем же действием. Прим. 6: смена преподавателя = добавить нового и удалить старого, **вся информация при этом сохраняется** |
| «Сохранить» | Отправляет предмет целиком одной операцией. На скане не нарисована — добавлена при разборе |
| «Отмена» | Сворачивает форму, фокус возвращается на вызвавшую кнопку. При несохранённых изменениях — `ConfirmDialog` |
| Строка таблицы | **Не кликабельна.** Раскрытия у этого экрана нет — вся правка идёт через `⋮` |
| `MainNav` → «Конструктор расписания» | Следующий шаг по порядку работы: заведённые здесь предметы становятся доступны для расписания |

### Нехватка прав

- **Неавторизованный** — редирект на ПК-001 с сохранением адреса возврата.
- **Авторизован, роль не headman** — `ForbiddenState` с пояснением, без утечки перечня предметов.
- **Помощник** — см. §5: подходящего права в перечне нет, вопрос открыт. До решения экран считается доступным только самому старосте.

### A11y (структурно)

- Один `h1` «Предметы». Skip-link на `#main`. Два `<nav>` с разными `aria-label`.
- Таблица настоящая: `<th scope="col">` в шапке; **№ и название — `<th rowspan scope="rowgroup">`**. Это тот случай, где `rowspan` семантически честен: структура реально двухуровневая, предмет объединяет свои типы занятий (в отличие от «визуального ритма» на ПК-112, который семантикой становиться не должен).
- Форма: **`<fieldset>` + `<legend>` на каждый тип занятия** («Преподаватели — лекции», «Преподаватели — практики»). Без этого три одинаковых поля «Преподаватель» на слух неразличимы — на скане они и выглядят одинаково.
- Типы занятий — группа переключателей в `fieldset` с `aria-pressed`, а не три безымянные кнопки; выбор объявляется, потому что он **меняет состав формы**.
- `SubjectNameField` — комбобокс: `role="combobox"`, `aria-expanded`, `aria-controls`, навигация стрелками, **количество найденных подсказок озвучивается**. Свободный ввод не блокируется — поле не `readonly`.
- `TeacherPicker` — тот же паттерн комбобокса; выбранные преподаватели — список с кнопкой удаления, доступное имя кнопки содержит ФИО («Удалить: Иванов И. И.»), а не голое «Удалить».
- Раскрытие формы объявляется через `role="status"`, фокус уходит в первое поле, при сворачивании возвращается на вызвавшую кнопку.
- `ConfirmDialog`: ловушка фокуса, Esc закрывает **только** на шаге `preview`; на шаге `deleting` закрытие блокируется. Ошибки пароля и кода — текстом, `role="alert"`.
- Все состояния (`loading`, `empty`, `error`, `forbidden`, `offline`) озвучиваемы.

## 7. Заметки на будущее

### Адаптив

На 1920 пять колонок плюс действия — запас есть, экран не тесный. На 1280 первым схлопывается «Количество пар» (уходит подписью под типом занятия); последними — «Тип» и «Преподаватель»: без них таблица перестаёт нести смысл.

Форма на узком десктопе становится одноколоночной, но **блоки преподавателей по типам нельзя сворачивать в один общий список** — потеряется привязка «кто ведёт какой тип», то самое измерение, которого не хватает и в API. В мобильной версии предмет разумно превращается в отдельный экран-карточку, а форма — в пошаговую (название → типы → преподаватели); сейчас не прорабатываем, PWA — отдельная поверхность.

### Открытые вопросы и риски

- **Связь «предмет × тип занятия × преподаватель» в API отсутствует — блокирующий пробел, экран без неё не строится.** Затрагивает и ПК-117: конструктор выбирает предмет и тип занятия и должен показать преподавателя.
- **Каскадное удаление:** объём последствий, атомарность, кто чистит `schedule` и `attendance`. Механика доказательства (пароль + код) в продукте появляется впервые — станет образцом для других необратимых действий.
- **Снятие типа занятия с проведёнными парами** — предлагаю запретить; требует подтверждения владельца.
- **Смена преподавателя не должна переписывать историю** (прим. 6: «вся информация сохраняется») — требует периода действия связи либо хранения преподавателя в самой паре.
- **Права помощника на этот экран** — подходящего права в перечне нет вообще; выделенная сессия.
- **Нумерация «№»** сквозная по предметам группы. Не определено, перенумеровываются ли предметы после удаления. Если да — номер нельзя использовать как ссылку ни на одном другом экране, только как порядок отображения.
- `SubjectProgressCell` и `LessonAttendanceCounter` сохраняются как самостоятельные компоненты; общая часть — отрисовка значения через `MetricValue` (K4). Сведение `LessonTypeToggleGroup` / `LessonTypePicker` выполнено (K3): один компонент с пропами `multiple` и `context`.
- Подсказка названий не должна раскрывать структуру чужих групп — отдавать только строки (§4.2).
