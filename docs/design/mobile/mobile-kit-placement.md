# Мобильный трек — размещение в ките и новые файлы

Дата: 31.08.2026. Относится к пакету `RutCampusTrack-mobile-UX-package`.

---

## 1. Куда положить пакет

```
kit/
  design/
    mobile/
      ux-guide.md              ← RutCampusTrack_PWA_TMA_UX_Guide.md
      ux-guide.pdf             ← для чтения владельцем
      build-checklist.md       ← Figma-build-checklist.md
      assets/svg/              ← 10 схем, редактируемые
      assets/png/              ← те же для просмотра
      research/                ← пять исследовательских записок
      reference-audit/         ← contact sheets 1920 dark
```

`docx` не кладите: он дублирует `md` и будет расходиться с ним. Если
нужен для правок — держите вне кита.

Шрифты из пакета в кит не кладите, они уже подключены в Figma.

## 2. Новые файлы, которые нужно завести

### 2.1. `design/figma-spec-mobile.md` — отдельно от основной спеки

Основная `figma-spec.md` уже около одиннадцати тысяч строк и описывает
веб-поверхность: восемь ширин, `AppHeader`, `MainNav`, `NavDrawer`,
десктопные мастера. Мобильный трек — другая оболочка, другие компоненты,
другие правила материалов. Смешивать их в одном файле значит сделать
неудобным и то, и другое.

В новый файл идут: `Mobile shell` и его варианты, нижняя навигация,
host action spec, материалы (glass, gradient, pattern), словарь форм,
компоновка телефона, типографическая шкала мобильного, состояния и
motion.

**Правила, общие для обеих поверхностей, не дублируются**, а остаются в
основной спеке: работа с осями, `layoutAlign`, `resize()`,
`ComponentSet.appendChild()`, read-before-write, снимки, аудит, R1–R7.
Новый файл ссылается на них, а не переписывает.

### 2.2. `design/mobile/token-requests.md`

Гайд запрашивает шестнадцать токенов: градиенты, материалы стекла,
поверхности данных, радиусы, формы, паттерн, motion, elevation, noise.
Ни один пока не существует.

Файл ведёт их как список с состоянием: запрошен → согласован → создан →
применён. Пока токен не создан, используется fallback из той же таблицы
гайда. Это не бюрократия: у вас уже висит долг по размерным токенам, и
без учёта мобильные добавят к нему ещё шестнадцать.

### 2.3. Записи в существующие файлы

`journal/DECISIONS.md` — четыре коррекции прежних решений, которые пакет
вводит явно и которые сейчас противоречат тому, что записано:

- «один дизайн и три platform difference» расширено до общего ядра и
  минимум восьми адаптеров;
- пять слотов остаются базой только для корневых маршрутов; detail,
  editor и task скрывают собственную навигацию;
- один канонический владелец экрана не запрещает контекстные deep links
  из «Сегодня», push и сообщений бота;
- mobile visual extension разрешает управляемые градиенты, fluid-формы,
  паттерн и glass-only chrome — это новое решение, в журнале его нет.

Каждую записать датированно, со ссылкой на раздел гайда.

`journal/to-owner.md` — открытые вопросы из раздела 16 гайда: student
check-in, exception attendance, mobile admin actions, map data. Плюс
отсутствующие свежие экспорты 1920 dark преподавателя и администратора.

## 3. Решение до первого кадра: где живут мобильные макеты

Документ сейчас 47 462 A. Мобильный трек добавит: четыре роли, около
пятидесяти экранов из бэклога, три ширины плюс stress 320, две
поверхности, четыре режима оболочки, шесть состояний. Даже при
экономной сборке это сопоставимо со всем веб-адаптивом или больше.

Раньше вопрос о разделении файла закрывался тем, что жёсткого лимита
Figma нет, а деградации не видно. Сейчас появились два новых
обстоятельства: транспортные отказы участились на записи, и мобильный
трек — это отдельная продуктовая поверхность со своей оболочкой,
компонентами и материалами, а не ещё одна ширина существующей.

Два варианта:

**A. Отдельный файл `ui-kit-rct-mobile`.** Веб-файл подключается как
библиотека, оттуда берутся токены цвета, типографики и базовые
компоненты. Мобильная оболочка и материалы живут в новом файле.

- плюс: веб-файл не растёт, транспорт легче, мобильный трек не мешает
  правкам веба;
- минус: правка общего мастера требует публикации библиотеки и
  обновления в мобильном файле — до сих пор вы работали без публикаций
  вообще, это новый процесс, и его надо освоить;
- минус: два файла нужно держать в синхронном состоянии.

**B. Та же книга, новые страницы.** Всё как сейчас, страницы 21+.

- плюс: ничего не меняется в процессе, общие мастера правятся один раз;
- минус: документ уйдёт заметно за 50 тысяч, транспортные отказы скорее
  всего участятся.

Я склоняюсь к A, но не настаиваю: цена варианта A — освоение публикации
библиотеки, и это реальная работа, а не формальность. Реши до того, как
агент начнёт, потому что перенос собранных страниц между файлами теряет
связи с мастерами.

## 4. Порядок работ

1. Разложить пакет по §1, завести файлы §2.
2. Принять решение §3.
3. **Партия 0 — основания**: `Mobile shell`, нижняя навигация, host
   action spec, материалы, токены. Промпт
   `part-17-mobile-foundations.md`.
4. **Партия 1 — студент**, начиная с трёх probes из §15.1 гайда.
   Промпт `part-17-student-mobile.md`.
5. Дальше староста, преподаватель, администратор — по тому же образцу,
   промпт под каждую роль пишется после закрытия предыдущей, с учётом
   найденного.

Роли идут в порядке студент → староста → преподаватель → администратор,
как вы и планировали. Староста вторым не случайно: он самый тяжёлый, и
если система выдерживает журнал на 27 студентов, остальные роли лягут
на готовое.
