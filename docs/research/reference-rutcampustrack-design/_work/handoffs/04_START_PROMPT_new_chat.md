# Стартовый промпт для нового чата

## Как использовать

1. Открой новый чат Claude.
2. **Прикрепи файлы:** `skills/screens-to-wireframe.md` и фото своих бумажных экранов.
3. Скопируй текст ниже (всё, что между линиями) и отправь первым сообщением.

Привет. Работаем над фронтендом моего проекта. Ниже весь нужный контекст — читай внимательно, дальше будем работать итеративно.

## Проект

**Репозиторий:** https://github.com/DITEKmax/rutcampustrack

RutCampusTrack — система учёта посещаемости и расписания для вуза (РУТ). Бэкенд уже написан и работает:

- Java 21 + Spring Boot 3.4, Gradle (Kotlin DSL), **микросервисы**: `auth-service`, `academic-service`, `schedule-service`, `attendance-service`, `notification-service`, `api-gateway`.
- **Contract-first**: публичные контракты в модулях `services/*/*-api-contract` — это источник правды по данным.
- REST через API Gateway (`/api/{service}/...`), ошибки в формате **RFC 9457 Problem Details**, HATEOAS.
- Между сервисами gRPC (`proto/`), события через RabbitMQ (`event-schemas/`).
- Хранилища: PostgreSQL (auth/academic/schedule), MongoDB (attendance/notification), Redis.
- **Роли пользователей:** `student`, `headman` (староста), `teacher`, `admin`.
- Есть `CLAUDE.md` с правилами проекта, ~234 теста, Testcontainers, ArchUnit, CI.

Существующие фронтенды: web-panel (Angular 19), pwa и mini-app (React 19 + Vite).
**Новый фронтенд делаем на Vue** — его ещё нет, начинаем с нуля.

При необходимости можешь склонировать репозиторий и свериться с реальными контрактами — описание выше может быть неточным.

## Два важных условия

**1. Бэкенд не заморожен.** Если экрану нужны данные, которых нет или которые неудобно доставать текущим API — НЕ подгоняй экран под API. Опиши, что реально нужно экрану, и пометь `[предложение по бэкенду]`. Я поменяю бэкенд под фронт, а не наоборот.

**2. Транспорт API под вопросом.** Возможно перейдём с REST на GraphQL — решение пока не принято. Поэтому описывай потребности в данных транспортно-нейтрально: сначала ЧТО нужно экрану (сущность, поля, фильтры, пагинация, связи), потом ГДЕ это лежит сейчас. Отдельно помечай экраны, где текущий REST явно неудобен (много запросов, over-fetching, N+1 на клиенте) — это будет фактурой для решения по GraphQL. Когда наберётся достаточно данных, я спрошу твоё мнение по GraphQL — не предлагай его сам заранее.

## Как работать

Я прикрепил скилл `screens-to-wireframe.md` — работай по нему. Кратко, по каждому экрану нужно:

1. Идентификация (название, роли, точка входа, цель)
2. Layout-регионы (зоны без стилей)
3. Компоненты (семантические имена + назначение)
4. Потребности в данных (транспортно-нейтрально, с пометками пробелов)
5. **Состояния**: loading, empty, error, success + различия по ролям
6. Навигация и действия (включая подтверждения деструктивных)
7. Заметки по адаптиву (без конкретных брейкпоинтов)

Итоговые файлы: по файлу на экран + `00_overview.md` (карта навигации, общие компоненты) + `figma-spec.md` (чеклист для Figma) + `backend-requests.md` (все пробелы и предложения по бэкенду).

## Важные правила

- Не выдумывай эндпоинты и данные — либо реальный контракт, либо явная пометка пробела.
- Не пропускай non-happy состояния — на бумаге их обычно нет, но это половина работы фронта.
- Учитывай, что один экран может выглядеть по-разному для разных ролей.
- Если экран на фото непонятен — задай ОДИН уточняющий вопрос, не домысливай.
- Работаем итеративно: разбираем по одному экрану или небольшой группе, я подтверждаю, идём дальше.
