# Этап 3 — блоки

Начинается после проверки этапа 2.

## Откуда берётся состав

Блоки уже описаны. Ничего не выводить из памяти о предыдущем этапе.

| Источник | Что там | Как читать |
|---|---|---|
| `design/figma-spec.md`, части 11–14 | блоки по ролям: 11 — student, 12 — headman, 13 — teacher, 14 — admin | по одной части за раз, не файл целиком |
| `design/figma-spec.md`, часть 10 | состояния: загрузка, пусто, пусто после фильтра, ошибка, нет доступа | один раз перед первой партией |
| `design/figma-spec.md`, часть 15 | экраны — что из каких блоков собирается | только для сверки границ блока |
| `specs/wireframes/<роль>/<экран>.md` | поведение блока на конкретном экране, порядок сжатия, источники данных | когда часть 11–14 отсылает к экрану |
| `design/COMPONENT_REGISTRY.md` | из каких компонентов блок собирается и кому они принадлежат | точечно, по имени компонента |

В каждой части 11–14 есть раздел «Каталог блоков роли» и раздел «Что переиспользовано» — начинать с них: они показывают, что уже собрано в предыдущей роли и повторно не создаётся.

Порядок ролей: **student → headman → teacher → admin.** Он не случайный: части 12–14 описаны как дельта к 11 и ссылаются на неё. Пойдёшь с админа — прочитаешь ссылки на то, чего ещё нет.

`block/AppHeader` — сквозной, собирается один раз в роли student; в остальных ролях у него варианты, а не новый блок.

## Что такое блок

Кусок экрана со **своим состоянием загрузки, пустоты и ошибки**.
Это и есть граница: если у куска нет своего запроса — он часть
соседнего блока, а не отдельный блок.

Практическое следствие: панель инструментов над таблицей — не блок.
Поиск не отрывается от таблицы, иначе читается как поиск по экрану.
Это же сказано в `figma-spec.md`, часть 14, раздел «Панель инструментов — не блок».

## Правила

- Блок собирается из компонентов этапа 2, новых слоёв не создаётся.
- Блок принадлежит экрану. Переиспользование живёт на уровне
  компонентов, а не блоков: один и тот же компонент на двух экранах
  получает данные из разных запросов — значит это разные блоки.
- Сквозных блоков в продукте мало: шапка и блоки настроек.
- У блока свои варианты ширины **1920 / 1440 / 1280**.
  Адаптив получается **переключением варианта**, а не растягиванием.
  Если для 1440 пришлось двигать руками — вариант собран неверно.
- Состав блока берётся из спеки, а не додумывается. Если части 11–14
  и спека экрана расходятся — назвать расхождение, не выбирать молча.

## По каждому блоку

- из каких компонентов собран
- что меняется между ширинами: число колонок, порядок, что сворачивается
- что не меняется никогда
- порядок сжатия, если он задан спекой экрана — не переизобретать
- пять состояний из части 10; где состояние невозможно — написать почему

## Работа партиями

Одна партия — одна роль или один экран, смотря по объёму. После партии
остановиться, показать список собранных блоков и что проверено по чек-листу,
дождаться подтверждения.

## Проверка

- [ ] Состав каждого блока сверен с частями 11–14, а не собран по памяти
- [ ] У каждого блока есть загрузка, пустота и ошибка
- [ ] Три ширины — варианты, а не три вёрстки
- [ ] Ни одного отсоединённого компонента
- [ ] Ни одного нового компонента: всё из этапа 2
- [ ] Расхождения между `figma-spec` и спеками экранов выданы отдельным списком
