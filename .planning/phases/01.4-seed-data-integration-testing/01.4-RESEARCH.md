## Summary

Phase 1.4 has an important finding: **V2__seed_test_data.sql already exists** in `services/academic-service/academic-app/src/main/resources/db/migration/`. It inserts admin/teacher/student users with BCrypt hash of "password", a test group (IVT-21-1), and test semester (Spring 2026), plus campus settings. The file is complete and correct per the schema.

The primary work of this phase is therefore **integration testing**: verifying the complete auth flow through Gateway. The correct approach is `@SpringBootTest` with Testcontainers for PostgreSQL and Redis, using `WebTestClient` or `TestRestTemplate` against the running auth-service, plus manual curl/Postman-style tests for the full Gateway flow (which requires both services running simultaneously).

For single-service integration tests (auth-service only), Testcontainers is the standard. For true end-to-end tests through Gateway, Docker Compose is required because Gateway fetches the public key from auth-service on startup — two services must be co-running. The plan must distinguish these two test levels.

**Primary recommendation:** Add Testcontainers to auth-service for `@SpringBootTest` integration tests covering all auth endpoints. The Gateway end-to-end test is a manual smoke test via curl against running Docker Compose stack — not an automated JUnit test (Gateway requires a live auth-service to fetch keys on startup).

## Architecture Patterns

### Recommended Test Structure for auth-service
```
services/auth-service/src/test/java/ru/rutcampustrack/auth/
├── integration/
│   ├── AuthIntegrationTest.java        # login, refresh, logout, public-key
│   └── OtpIntegrationTest.java         # otp/request, otp/verify
├── AbstractIntegrationTest.java        # @SpringBootTest + Testcontainers base class
└── config/
    └── TestJwtKeyConfig.java           # generate fresh RSA keys for tests (no filesystem dependency)
```

### Pattern 1: `@SpringBootTest` + Testcontainers with `@ServiceConnection`
**What:** Boot full Spring context with real PostgreSQL + Redis containers. Use `TestRestTemplate` to call auth endpoints.
**When to use:** All auth-service integration tests (login, refresh, OTP, change-password).

```java
// Source: Spring Boot 3.1+ Testcontainers documentation
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class AbstractIntegrationTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");

    @Container
    @ServiceConnection
    static GenericContainer<?> redis = new GenericContainer<>("redis:7-alpine")
            .withExposedPorts(6379);
}
```

**Critical:** `@ServiceConnection` requires `spring-boot-testcontainers` on classpath. It auto-overrides `spring.datasource.url` and `spring.data.redis.host/port`.

### Pattern 2: Flyway in tests — V1 + V2 run automatically
**What:** When `@SpringBootTest` boots academic-app (or auth-service with Flyway enabled for tests), Flyway runs all migrations including V2.

**Problem:** auth-service has `flyway.enabled: false`. For integration tests, we need either:
- Option A: Override Flyway to `enabled: true` in test `application-test.yml`, pointing at the Testcontainer PostgreSQL. This makes auth-service run V1 + V2 migrations in test context.
- Option B: Test only auth-service endpoints, pointing at a pre-seeded PostgreSQL Testcontainer (seed data inserted programmatically or via SQL script in `@BeforeAll`).

**Recommended: Option A** — create `src/test/resources/application-test.yml` that enables Flyway for tests only, pointing at the Testcontainer:

```yaml
# src/test/resources/application-test.yml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    # datasource auto-configured by @ServiceConnection
  jpa:
    hibernate:
      ddl-auto: validate
```

And copy (or symlink) the migration SQL files to `auth-service/src/test/resources/db/migration/` — same V1 + V2 scripts.

**Alternative (simpler):** Use a `@Sql` annotation to insert test users directly in the test class.

### Pattern 3: JWT key directory for tests
**What:** `JwtService` reads RSA keys from filesystem (`jwt.key-dir`). In tests, this causes issues because the path may not exist.

**Solution:** Set `jwt.key-dir` in `application-test.yml` to a temp dir:
```yaml
jwt:
  key-dir: ${java.io.tmpdir}/rct-test-keys
```
`JwtService.init()` generates a new key pair if files don't exist — this works automatically with the temp dir.

### Pattern 4: Gateway end-to-end test — curl against Docker Compose
**What:** The true end-to-end test requires both auth-service (port 9090) and api-gateway (port 8080) running together. Gateway fetches the public key from auth-service at `@PostConstruct`.

**Why not JUnit:** `PublicKeyConfig.fetchAndCachePublicKey()` calls `auth-service:9090` via `WebClient`. In a test environment, this requires a live auth-service. A full `@SpringBootTest` for both services simultaneously is complex — use Docker Compose + curl scripts instead.

**Recommended approach:** Document as a manual verification script:
```bash
# 1. Start infrastructure
docker compose up -d

# 2. Start auth-service
./gradlew :services:auth-service:bootRun --args="--spring.profiles.active=local"

# 3. Start api-gateway (set AUTH_SERVICE_URL to localhost:9090)
AUTH_SERVICE_URL=http://localhost:9090 ./gradlew :services:api-gateway:bootRun

# 4. Test login
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"login":"student","password":"password"}' | jq .

# 5. Test protected route (replace TOKEN)
curl -s http://localhost:8080/api/academic/groups \
  -H "Authorization: Bearer TOKEN"
```

### Anti-Patterns to Avoid
- **Do not mock PostgreSQL in integration tests:** Use Testcontainers, not H2. The schema uses PostgreSQL-specific types (`TIMESTAMPTZ`, `user_role` enum, exclusion constraints). H2 does not support these.
- **Do not share Testcontainer between unrelated test classes:** Use `@Container static` on a base class to share across the test suite.
- **Do not hardcode BCrypt hashes:** The hash in V2 was generated for "password" with cost 10. Do not regenerate — use the same hash.
- **Do not test Gateway JWT filter with `@SpringBootTest` against live auth-service:** The filter tests in phase 1.3 already use unit tests with a mocked `PublicKeyConfig`. Do not duplicate this.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Ephemeral PostgreSQL | Docker Compose test setup | Testcontainers PostgreSQL | Isolation, auto-teardown, no port conflicts |

| BCrypt hash generation | Hardcode in test | Use PasswordEncoder in @BeforeAll OR use V2 hash | Tests should use same hash as prod seed |
| JWT token for tests | Re-implement JWT building | Use `JwtService` bean directly from application context | No drift between test and prod JWT format |

## Common Pitfalls

### Pitfall 1: PostgreSQL custom ENUMs in H2
**What goes wrong:** Tests using H2 fail on `CREATE TYPE user_role AS ENUM (...)` — H2 does not support PostgreSQL-specific DDL.
**Why it happens:** Flyway runs V1__baseline.sql which creates custom PostgreSQL ENUMs.
**How to avoid:** Always use Testcontainers with `postgres:16` image, never H2 for this project.
**Warning signs:** `JdbcSQLSyntaxErrorException: Syntax error in SQL statement` mentioning `CREATE TYPE`.

### Pitfall 2: JwtService fails on startup — missing key directory
**What goes wrong:** `@SpringBootTest` fails with `NoSuchFileException` or `IOException` because `./keys` dir does not exist.
**Why it happens:** `JwtService.init()` tries `Files.createDirectories(keyDir)` — this works on the local machine but may create `./keys` relative to the test runner's working directory (not the service root).
**How to avoid:** Set `jwt.key-dir: ${java.io.tmpdir}/rct-test-keys` in `application-test.yml`. The `@PostConstruct` method will create it and generate a fresh key pair.

### Pitfall 3: auth-service Flyway disabled — no V2 data in test DB
**What goes wrong:** Integration test boots auth-service, connects to test PostgreSQL, but users table is empty. Login test returns 401.
**Why it happens:** `flyway.enabled: false` in auth-service's `application.yml`. No migrations run.
**How to avoid:** Either (a) enable Flyway for test profile and provide migration scripts in test resources, or (b) use `@Sql("classpath:test-data.sql")` on the test class to insert users before tests.

### Pitfall 4: `@ServiceConnection` requires `spring-boot-testcontainers` dependency
**What goes wrong:** `@ServiceConnection` annotation is not recognized — compile error or not auto-configured.
**Why it happens:** Missing `org.springframework.boot:spring-boot-testcontainers` in test dependencies.
**How to avoid:** Add the dependency explicitly; it is not pulled in by `spring-boot-starter-test`.

### Pitfall 5: Redis Testcontainer — `@ServiceConnection` support
**What goes wrong:** `@ServiceConnection` for `GenericContainer` with Redis image does not auto-configure `spring.data.redis.host/port`.
**Why it happens:** `@ServiceConnection` for Redis requires the container image to be recognized. `GenericContainer("redis:7-alpine")` is not automatically detected.
**How to avoid:** Override `spring.data.redis.host` and `spring.data.redis.port` manually via `@DynamicPropertySource`:

```java
@DynamicPropertySource
static void redisProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.data.redis.host", redis::getHost);
    registry.add("spring.data.redis.port", () -> redis.getMappedPort(6379));
}
```

Alternatively, use `com.redis:testcontainers-redis` which provides a `RedisContainer` with proper `@ServiceConnection` support.

### Pitfall 6: OTP integration test — OTP flow requires telegram_id
**What goes wrong:** `OtpService.requestOtp()` calls `userRepository.findByTelegramId(telegramId)`. The V2 seed data does not set `telegram_id` for any user.
**Why it happens:** V2 seed data only sets login/password/role — telegram_id is null for all test users.
**How to avoid:** For OTP integration tests, add a `telegram_id` to the student user via `@Sql` or update V2 to add one. Or test OTP with a 404 assertion (user not found by telegram_id).

### BaseIntegrationTest
```java
// Pattern: shared Testcontainers base class (auth-service tests)
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ActiveProfiles("test")
@Testcontainers
abstract class AbstractIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16")
            .withDatabaseName("academic_db")
            .withUsername("rct_user")
            .withPassword("rct_dev_pass");

    @Container
    static GenericContainer<?> redis = new GenericContainer<>("redis:7-alpine")
            .withExposedPorts(6379);

    @DynamicPropertySource
    static void overrideProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
        registry.add("spring.data.redis.host", redis::getHost);
        registry.add("spring.data.redis.port", () -> redis.getMappedPort(6379));
    }
}
```

## Project Constraints (from CLAUDE.md)

The following directives from CLAUDE.md apply to this phase:

- **No Lombok in contract modules** — auth-service has no api-contract module; Lombok is permitted in auth-service app layer.
- **Enums: PostgreSQL stores lowercase, Java uses UPPER_CASE** — test data in V2 uses lowercase ('admin', 'active') — correct.
- **ddl-auto: validate** — Flyway must create the schema before Hibernate validates it. In tests: Flyway must run BEFORE Spring context validation.
- **Flyway disabled in auth-service** (`flyway.enabled: false`) — must be overridden to `true` in test profile via `application-test.yml`.
- **BCrypt cost 10** — the V2 hash `$2a$10$...` is correct cost-10 BCrypt for "password".
- **PK: BIGSERIAL** — test users will get ids 1, 2, 3 (after group gets id=1, semester gets id=1). The `group_id = 1` in V2 references the groups row inserted in the same migration — correct.
- **RFC 7807 error responses** — integration tests should assert `Content-Type: application/problem+json` on 401 responses.
- **No plaintext secrets in code or config** — test passwords use BCrypt hashes; the plaintext "password" is only in test documentation, not in application code.
