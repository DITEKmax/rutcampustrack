## 4. Потребности в данных

### 4.1 Единый список заявок — главная проблема экрана

- **Нужно:** один список заявок группы с полями: тип тикета, ФИО автора, дата подачи, причина и комментарий (только «у»), **период покрытия** (возможно **с пропусками дней**, прим. 2), **количество пар**, **сколько пар уже имеют отметку**, наличие вложений, статус, дата решения, кто решил, причина отклонения. Фильтры: статус (активные / архив), тип, ФИО, дата. Сортировка: по дате подачи (активные), по дате решения (архив). **Пагинация обязательна для архива.**

- **Сейчас — два независимых источника:**

| Тип тикета | Список | Решение |
|---|---|---|
| на «у» | `GET /attendance/excuses/group/{groupId}` | `PATCH /attendance/excuses/{id}/status` |
| на «н» | `GET /attendance/late-checkin/pending`, `GET /attendance/late-checkin/group/{groupId}` | `POST /attendance/late-checkin/{requestId}/decision` |

- **Пробел** `[предложение по бэкенду]` — **высокий приоритет:** экран показывает **один список из двух подсистем**, и это ломается сразу в трёх местах:
  1. **пагинация невозможна корректно** — два курсора нельзя слить в одну страницу, не вытянув оба списка целиком;
  2. **сортировка по дате** между источниками выполняется на клиенте, то есть только в пределах загруженного;
  3. **фильтр «по типу тикета»** (прим. 4) вырождается в «не делать один из двух запросов», что снова ломает пагинацию.

  Нужен единый список заявок, где тип — **поле**, а не выбор эндпоинта.

- **Пробел** `[уточнение по контракту]`: **период покрытия хранится как период или выводится из набора пар.** Прим. 2 подчёркивает, что дни внутри периода могут быть пропущены — значит одно из другого не выводится, и показывать нужно и период, и количество пар.

### 4.2 Состав пар — по раскрытию (решение владельца)

- **Нужно:** список пар тикета — предмет, тип занятия, дата занятия, **текущая отметка по паре**. Загружается **при раскрытии карточки**, а не вместе со списком.
- **Сейчас:** `GET /attendance/excuses/{id}` — детали тикета.
- **Решение владельца:** «пусть будет по раскрытию, я думаю, так лучше». Это снимает N+1 из основного списка: очередь из двадцати заявок грузится одним запросом, а состав пар подтягивается только для тех карточек, которые староста реально открыл.
- **Пробел** `[уточнение по контракту]`: отдаёт ли детализация тикета **текущую отметку по каждой паре**. Без неё раскрытие не объяснит, какие именно пары исключены из эффекта одобрения (§4.4).
- **Пробел** `[уточнение по контракту]`: есть ли аналог детализации у тикетов **на «н»**. Там пара всегда одна (прим. 3), но она тоже должна показывать свою текущую отметку.

### 4.3 Фильтры и сортировка архива

- **Нужно:** фильтр по типу, по ФИО (поиск по подстроке), по дате — прим. 4 задаёт нетривиальную семантику: **дата попадает в фильтр, если входит в промежуток тикета**, а не совпадает с датой подачи. Сортировка по дате решения. Пагинация.
- **Сейчас:** параметров фильтрации, сортировки и пагинации у обоих списков нет.
- **Пробел** `[предложение по бэкенду]`: серверные фильтры, сортировка и пагинация; **фильтр по дате — по пересечению с периодом покрытия**. Клиентская реализация невозможна в принципе: фильтровать можно только загруженную страницу, а архив копится весь семестр.

### 4.4 Эффект одобрения — решение владельца

- **Правило (подтверждено владельцем): «+» не заменяется на «у».** Пары, где студенту уже проставлен «+», **исключаются из эффекта** одобрения и сохраняют свой «+». Тикет при этом остаётся неделимым: решение по-прежнему одно на весь тикет (§0), меняется только множество пар, к которым оно применяется.
- **Староста видит это до решения:** в карточке — предупреждение вида «2 из 5 пар уже отмечены», при раскрытии — какие именно.
- Одобрение тикета **на «н»** даёт «+» со способом получения **«заявка»** — эта градация уже есть в `StatsByStudentTable` (ПК-113).
- **Пробел** `[предложение по бэкенду]`: сервер должен возвращать **число пар, к которым решение реально применится**, — считать это на клиенте нельзя, отметки могли измениться между загрузкой очереди и нажатием кнопки.
- **Пробел** `[уточнение по контракту]`: поведение при уже проставленном «у» (повторная заявка на ту же пару) и при «н», выставленном вручную старостой, — второе как раз основной случай, и оно **должно** перезаписываться на «у».

### 4.5 Решение по тикету и его обратимость

- **Нужно:** одобрить или отклонить тикет **целиком**, с обязательной причиной при отклонении.
- **Сейчас:** две разные операции с разными контрактами (таблица в §4.1).
- **Пробел** `[предложение по бэкенду]`: **единая операция решения**. Сейчас одна кнопка интерфейса отображается в два разных вызова; любое расхождение в их поведении (валидация, ответ, права) вылезет как несогласованность на одном экране.
- **Пробел** `[уточнение по контракту]`: принимает ли решение **причину отклонения**. §8 реестра требует обязательности, `TicketCard archived` её показывает.
- **Пробел** `[уточнение по контракту]`: можно ли **переустановить** принятое решение. От ответа зависит конструкция:
  - решение обратимо → кнопки без `ConfirmDialog` (рутина: староста разбирает десятки заявок), в архиве появляется «Изменить решение»;
  - решение необратимо → `ConfirmDialog` на **одобрение** (оно меняет отметки задним числом), отклонение уже защищено обязательной причиной.

  По §0 отклонение **не окончательно для студента**: пары освобождаются, заявку можно подать снова. Это про повторную подачу, а не про правку решения — не путать.

- **Пробел** `[уточнение по контракту]`: тратит ли **отклонение** тикета на «н» попытку из лимита трёх на семестр, или попытка расходуется в момент подачи. Снятие блокировки живёт на ПК-116, и оба экрана обязаны говорить об одном счётчике.

### ⚠️ Фактура к решению о транспорте

| Что | Оценка |
|---|---|
| Запросов на вкладку | **2** минимум (два источника), и они не сливаются в одну страницу |
| N+1 | **снят решением владельца**: состав пар грузится по раскрытию, то есть для единиц карточек, а не для всей очереди |
| Мутации | **две разные операции на одну кнопку** интерфейса |
| Фильтрация и пагинация | серверных нет вовсе; на клиенте работали бы только по загруженному |
| Не существует | единый список, фильтры, сортировка, пагинация, единая операция решения, число реально затрагиваемых пар |

Это самый неудобный для REST экран раздела — не из-за количества запросов, а из-за того, что **одна пользовательская сущность разложена по двум подсистемам**.

## 5. Состояния

**На бумаге нарисован только `success`** с двумя активными карточками. Всё ниже добавлено при разборе.

### Автомат `TicketCard variant="incoming"`

| Состояние | Условие | Что показываем |
|---|---|---|
| `collapsed` | карточка не раскрыта | ФИО, тип, причина, период, количество пар, предупреждение об уже отмеченных |
| `expanding` | нажато раскрытие | скелетон списка пар; остальная карточка работает |
| `expanded` | детали пришли | список пар с текущими отметками |
| `expand-error` | детали не пришли | ошибка **внутри карточки**; решение по тикету при этом **остаётся доступным** — состав пар не обязателен для решения |
| `rejecting` | нажато «отклонить» | `TicketRejectForm`, фокус в поле причины |
| `invalid` | причина отклонения пуста | ошибка на поле, отправка заблокирована |
| `deciding` | решение отправляется | `aria-busy`, обе кнопки заблокированы |
| `decided` | сервер подтвердил | карточка уходит из «Активных»; результат объявляется через `role="status"` |
| `stale` | **заявку решил кто-то другой** — помощник или сам староста в другой вкладке | карточка помечается решённой **с пояснением, кем и когда**, кнопки блокируются |
| `error` | сбой решения | ошибка в карточке; **остальные карточки продолжают работать** |

**Состояние `stale` критично: у экрана есть второй легитимный оператор — помощник с `manage_excuses`.** Без него двое разбирают одну очередь и получают ошибку сервера вместо объяснения.

**Предупреждение об уже отмеченных парах — тоже критичное состояние.** Без него староста одобряет тикет и не понимает, почему у части пар отметка не изменилась: **экран врёт об эффекте собственного действия**.

### Остальные блоки

- **«Активные»:** `loading` (скелетоны карточек), **`empty` — «нет заявок на рассмотрении», и это хорошая новость, а не ошибка**: формулировка должна звучать нейтрально, без интонации сбоя. `error` с повтором.
- **«Архив»:** `empty` («решённых заявок пока нет») и **`filtered-empty`** («фильтры не оставили заявок» + сброс) — тексты обязаны различаться (§6.2).
- **Пагинация:** `loading-more`, `end-of-list`.

### Общие

- `offline` — список с пометкой об устаревании, **решения заблокированы**: одобрение меняет отметки и уходит студенту уведомлением.
- `no-active-semester` — вырожденный случай, заявок нет по определению.
- `forbidden` — экран целиком.

### По ролям

| Кто | Что видит и может |
|---|---|
| **Староста** | всё |
| **Помощник с `manage_excuses`** | тикеты **на «у»** — полный разбор |
| **Помощник и тикеты на «н»** | ⚠️ **подходящего права в перечне нет.** `manage_excuses` по названию относится к уважительным причинам. Либо тикеты на «н» помощнику недоступны, либо право расширяется — вопрос выделенной сессии |
| **Помощник без права** | по принципу §0: **блок данных не рендерится** — это чужие персональные данные и причины, а не просто заблокированное действие |
| **student / teacher / admin** | `forbidden` |

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| Вкладки «Активные» / «Архив» | Переключение разреза. Фильтры показываются **только в архиве** (прим. 4). Синхронизация активной вкладки с URL и предвыбор при входе с ПК-111 принадлежат `TicketsInboxPage`, не `Tabs` |
| Раскрытие карточки | Подгружает список пар (решение владельца). `aria-expanded`, повторное нажатие сворачивает |
| «Подтвердить» | Одобряет тикет **целиком** (§0). Пары с уже проставленным «+» **сохраняют свою отметку**. Подтверждение — по итогу §4.5. **Оптимистичного UI нет:** решение меняет отметки и уходит уведомлением студенту |
| «отклонить» | Раскрывает `TicketRejectForm` в карточке. Отправка — после заполнения причины. Текст поясняет, что отклонение **не окончательно**: пары освободятся для повторной подачи |
| Причина на карточке «у» | `ExcuseReasonPopover`, доступен с клавиатуры |
| Вложение | Открытие через `AttachmentList` |
| Фильтры и сортировка архива | Серверные; активные фильтры видны **текстом**, есть сброс |
| `PendingRequestsCounter` (ПК-111) | Входная точка сюда с предвыбранным типом |
| Блокировка студента за захват пар | Живёт на **ПК-116**; отсюда — только пояснение, где её снять |

### Нехватка прав

- **Неавторизованный** — редирект на ПК-001 с сохранением адреса возврата.
- **Авторизован, роль не headman** — `ForbiddenState` без утечки заявок.
- **Помощник** — см. §5; при отсутствии права блок данных не рендерится.

### A11y (структурно)

- Один `h1` «Заявки и тикеты». Skip-link на `#main`. Два `<nav>` с разными `aria-label`.
- Вкладки — `Tabs` с полной ARIA-механикой (стрелки, `aria-selected`, перевод фокуса в панель); **счётчик активных входит в доступное имя вкладки**, отдельного бейджа нет.
- Очередь — `<ul>` / `<li>`; каждая карточка — `<article>` с заголовком, включающим **тип тикета и ФИО**.
- Список пар внутри — вложенный `<ul>`, **не таблица**: три поля на строку не требуют табличной семантики.
- **Тип тикета передаётся текстом** («тикет на "у"»), а не только составом полей.
- Раскрытие состава пар — `aria-expanded` на триггере, появление объявляется через `role="status"`.
- Раскрытие формы отклонения — `aria-expanded`, фокус в поле причины, при отмене возврат на кнопку.
- **Исчезновение карточки из «Активных» объявляется через `role="status"`, а фокус переводится на следующую карточку**, а не теряется в конец документа: разбор очереди с клавиатуры — главный сценарий экрана.
- Ошибки — `role="alert"` внутри своей карточки, не общим баннером.
- Все состояния (`loading`, `empty`, `filtered-empty`, `error`, `forbidden`, `offline`) озвучиваемы.

## 7. Заметки на будущее

### Адаптив

Карточки на 1920 просторны: строка «ФИО · причина · период · количество пар» при сужении сложится в две, действия уйдут под содержимое. Терять нельзя: **тип тикета текстом**, ФИО, период покрытия, количество пар и **предупреждение об уже отмеченных парах** — по ним староста принимает решение, не раскрывая состав. Раскрываемый список пар при сужении не страдает — он и так вертикальный.

В мобильной версии карточка почти наверняка станет отдельным экраном решения, а очередь — компактным списком. Отдельная поверхность, отдельный цикл.

### Открытые вопросы и риски

- **Единая сущность разложена по двум подсистемам** (§4.1) — самый тяжёлый пробел экрана: бьёт по пагинации, сортировке и фильтрам одновременно.
- Обратимость решения (§4.5) — определяет наличие `ConfirmDialog`.
- Поведение при уже проставленном «у» и при ручном «н» (§4.4) — правило по «+» задано, края нет.
- Право помощника на тикеты «н» — в перечне отсутствует.
- Расход попытки при отклонении (§4.5) — общая механика с ПК-116.
- Фильтр-бары сведены в один `FilterBar` (K1) — вопрос закрыт.
- **`RowDetailTrigger` используется в третьем контексте и уже не про строку таблицы** — обобщение имени в калибровочный чат.
- `TicketCard` теперь имеет три варианта и живёт в двух ролях — при сборке в Figma проверить, что вариантами не подменяется различие «свои / чужие».

## Решения задачи 4 — внесено 01.08.2026

Источник — `02-backend/backend-conflicts.md`. Правила ниже имеют приоритет над более ранними формулировками этой спеки.

**Решение по тикету необратимо (Р-2, Р-14).** «Изменить решение» не проектируется: если староста ошибся, он перепроставляет отметки вручную. Поэтому **одобрение и отклонение требуют `ConfirmDialog`** — это необратимое действие, а по §2.3 `BRAND_DIRECTION.md` подтверждение необратимого и есть единственная модалка продукта.

**Кто решает (Р-14).** Только староста и помощник с правом `manage_excuses`. Преподаватель тикет **читает** в урезанном сервером представлении. Администратор в согласовании не участвует.

**Вложения (Р-9).** Файлы хранятся **год с момента загрузки**, независимо от судьбы тикета и статуса студента; вместе с тикетом файл не удаляется. После истечения срока карточка показывает состояние **«вложение удалено по сроку хранения»** — не битую ссылку и не пустоту.
