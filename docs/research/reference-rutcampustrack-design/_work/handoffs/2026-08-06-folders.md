## ЗАДАЧА

У меня две рабочие папки, и я в них запутался. Разберись и предложи, как их организовать.

- **`rutcampustrack-design`** — папка, где велась вся проектная работа: вайрфреймы, бэкенд-запросы, бренд, спеки, архив закрытых этапов.
- **`rutcampustrack-kit`** — обвязка для агента, собранная позже: скилл проекта, задания по этапам, конфигурация MCP, копии части файлов из первой папки.

Часть файлов существует в обеих папках, часть переименована, часть могла разойтись по содержимому.

## ЖЁСТКОЕ ПРАВИЛО

**НИЧЕГО НЕ УДАЛЯТЬ.** Только переносить. Переименовывать — редко и только когда имя реально вводит в заблуждение, с объяснением по каждому случаю.

Если два файла выглядят дублями — не удалять ни один: сравнить содержимое, сказать, какой свежее и чем именно они отличаются, и предложить, какой считать действующим. Решение за мной.

## ПОРЯДОК РАБОТЫ

Сначала **предложение**, потом действия. Не начинай раскладывать файлы, пока я не согласился.

1. **Инвентаризация.** Что есть в каждой папке, что дублируется, что расходится по содержимому, что осиротело (файл есть, а ссылок на него нет, или наоборот — ссылки есть, а файла нет).
2. **Предложение структуры** — с объяснением логики. Не просто «положить сюда», а почему именно так: по какому признаку разделены папки, что происходит при добавлении нового этапа, где будет искать человек и где будет искать агент.
3. **Разбор альтернатив.** Здесь нет единственно верного ответа. Покажи два-три варианта раскладки с честными плюсами и минусами: например, объединить всё в одну папку против сохранить разделение «архив проектирования» и «рабочая папка агента». Скажи, какой рекомендуешь и почему, но не выдавай рекомендацию за единственный вариант.
4. **После моего согласия** — план переноса: что откуда куда, построчно, с причиной по каждому пункту. Помеченное «под вопросом» — отдельным списком, я отвечу.

## О ЧЁМ ПОДУМАТЬ ОТДЕЛЬНО

- Часть файлов нужна **агенту** в рабочей папке проекта, часть — **мне** для планирования, часть — **истории**. Это три разных потребителя с разными требованиями к близости файлов.
- Дальше начинается работа в коде: Vue-проект, компоненты, экраны. Структура должна пережить появление кода рядом, а не рассыпаться от него.
- Большие файлы (реестр 279 КБ, спека Figma 354 КБ, job-stories 193 КБ) в контекст агента целиком не влезают. Учитывай это в раскладке.
- Скажи, где по-твоему единственный источник истины для каждого класса файлов, и назови места, где сейчас источников два.

# HANDOFF — что было сделано в предыдущей сессии

Это контекст, а не задание. Читать, чтобы понимать, почему файлы такие.

## Состояние проекта

RutCampusTrack — система учёта посещаемости и расписания для вуза РУТ (МИИТ). Личный проект, согласований нет, язык только русский. Бэкенд написан и работает: Java 21, Spring Boot 3.4, шесть микросервисов, gRPC, RabbitMQ. Фронтенд переписывается на **Vue**, визуал с нуля. Роли: student, headman, teacher, admin. Репозиторий продукта: https://github.com/DITEKmax/rutcampustrack

Закрыто: вайрфреймы всех четырёх ролей (27 уникальных экранов, 26 файлов спек), калибровка компонентов и реестр v1.0, расхождения бэкенда (Р-1…Р-24), транспорт (REST + BFF, gRPC вниз), бренд-направление «Табло», мудборд, гарнитура, брендбук v2, `figma-spec.md`.

## Что сделано в предыдущей сессии

README переписан целиком. Отчёт — `_work/handoffs/CLEANUP-2026-08-01.md`.

**Правки по содержанию.** В `BRAND_DIRECTION.md` перенесены §13 брендбука: тени разрешены точечно с правилом «дублирует, а не заменяет», введён §2.3.2 про цвет статусов посещаемости, в §2.2 добавлено исключение для крест-подсветки в журнале. **Сравнение моделей.** Два варианта экрана 101 в HTML, сверка скриптом против `tokens-v2.json`. Находки: один вариант схлопнул три слоя токенов в один (77 примитивов не заведены, правка примитива никуда не распространяется); второй сослался на несуществующий пункт брендбука и на этом основании выразил акцент контуром вместо заливки. **Решение по инструментам.** База компонентов — **shadcn-vue** с официальным MCP: исходники лежат в проекте, агент может их читать и рефакторить, что совпадает с рабочим процессом владельца. Скиллы: `emilkowalski/skills` (движение, выбор библиотек), `vercel-labs/agent-skills --skill web-design-guidelines` (аудит кода), плюс собственный `SKILL.md` проекта — единственное, что знает конкретную систему.
