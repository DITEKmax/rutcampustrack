# M17 — Decisions

Архитектурные решения, принятые в ходе milestone. Заполняется по мере
работы; на старте — пусто.

Формат: `### Dx (YYYY-MM-DD) — короткое название`, потом контекст /
решение / альтернативы / последствия.

---

## D1 (2026-04-28) — Формат файла = `.docx`, не PDF/Excel

**Контекст:** Деканат принимает отчёты в строгом формате. У старосты
есть готовый эталон, нарисованный в Word.

**Решение:** Генерируем `.docx`, используя готовый шаблон + подстановку
плейсхолдеров. PDF/Excel не делаем.

**Альтернативы:**
- Excel `.xlsx` — отвергнут: эталон в Word, деканат может потребовать
  именно doc.
- PDF — отвергнут: деканат в гос-учреждениях обычно требует
  редактируемый формат (для своих правок/штампов).

**Последствия:** Завязка на стек генерации docx (POI / docx4j /
docx-stamper). Шаблон должен лежать как ассет в репо.

---

## D2 (2026-04-28) — Только web-panel, не PWA (для первой версии)

**Контекст:** Староста скачивает отчёт для печати/email. На телефоне
docx неудобен.

**Решение:** Кнопка «Скачать» только в web-panel. PWA не получает
функционал.

**Альтернативы:** Дублировать в PWA — отвергнуто как лишняя работа без
явной пользы.

**Последствия:** Если кто-то всё-таки попросит на телефоне — добавим
позже. Эндпоинт уже будет готов.

---

## D3 (2026-04-28) — Не выделяем в отдельный сервис

**Контекст:** Пользователь спросил, стоит ли выносить генерацию
отчётов в отдельный микросервис.

**Решение:** Оставляем в `attendance-service`. Отдельного
`report-service` не делаем.

**Альтернативы:**
- Отдельный `report-service` (Spring Boot контейнер) — отвергнуто.
  Объём задачи 300-500 строк кода; данные уже у attendance (Mongo) или
  доступны через существующие gRPC-вызовы; выделение добавило бы лишний
  сетевой прыжок без выгоды; M18 (сводный отчёт) тоже про attendance.

**Триггеры для будущего refactor'а** (когда стоит выделить):
- ≥3 разных типов отчётов в системе.
- Долгая генерация (минуты) → нужна очередь / воркер.
- Batch-выгрузка (все группы факультета сразу) → пул процессов.
- 10+ шаблонов с UI редактирования.

**Последствия:** в attendance-service появится новый Spring `@Service`
+ контроллер + ресурс-папка `report-templates/` + зависимость на
docx-библиотеку. Код локализуется в пакете `report/template/` для
лёгкого выделения в будущем (если триггер сработает).

## D4 (2026-04-28) — Слияние недель: один многостраничный `.docx`, не ZIP

**Контекст:** Староста может выбрать несколько недель за раз. Варианты:
ZIP с N файлами / один многостраничный docx / только одна неделя.

**Решение:** Один многостраничный `.docx` с page-break между
неделями. Выбран вариант (ε).

**Альтернативы:**
- ZIP (δ) — отвергнуто как менее удобное для пользователя.
- Только одна неделя (ζ) — отвергнуто, не покрывает реальный сценарий.

**Последствия:** Реализация чуть сложнее (нужен docx-merger или
template-loop). Плюс — пользователь получает один файл, который сразу
можно отправить или распечатать.

---

## D5 (2026-04-28) — Имя файла включает дату конца недели

**Решение:** Формат имени:
`понедельный-{group_name}-{дата_начала}-{дата_конца}.docx`,
где конец = календарное воскресенье (даже если пар в выходные нет).

При слиянии: `понедельный-{group_name}-{первая_дата}-{последняя_дата}.docx`.

---

## D6 (2026-04-28) — Превышения лимитов → 422, не silent truncate

**Решение:** При >5 пар в день у группы или >35 студентов в группе
— эндпоинт возвращает 422 с описанием проблемы. Не пытаемся
обрезать или подвинуть.

**Обоснование:** Деканат должен знать о расхождении между шаблоном и
реальностью; молчаливая потеря данных хуже явной ошибки.
