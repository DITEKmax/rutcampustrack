Результаты, HTML и статус складывать в PR. Этот главный чат — будущий

Не публиковать шумный комментарий после каждой правки отступа.

Спорные продуктовые решения, найденные ошибки/разногласия PWA/TMA:

### Код, оболочка и reuse

Vue3, strict TypeScript, существующий Vite/toolchain и проектные conventions.
Читаемый форматированный код, не сжатый в одну строку. Разделить transport,
state/domain rules и композицию экранов. Не складывать всё в App.vue.

Общая shell/layout: навигация, header, role selector, notifications host и
область вложенных страниц. Не копировать их на каждом экране. Термин владельца
«микрофронтенды» описывает переиспользуемую вложенность; не внедрять независимо
развёртываемые bundles/Module Federation без архитектурной необходимости.

Reuse: общие Onest/font tokens, цвета, типографика, spacing/radius и прочая
дизайн-основа. Web имеет свои shared UI blocks; мобильные dock/Telegram
adapters не переносить в web. Подходящие SVG/иконки брать из PWA/TMA/Figma;
при необходимости выносить в общий пакет. Новые SVG делать в едином стиле
и едином каталоге, не размножать inline копии по страницам.

Стили — отдельные PCSS/PostCSS; размеры rem и семантические токены по
frontends/AGENTS.md. Figma px переводить по принятой базе, не менять root
font ради соответствия. Tailwind/shadcn из generated reference не внедрять.

### Миксины, общая типографика и переменные

Перед параллельной реализацией подготовить общую стилевую основу:
responsive mixins/брейкпоинты и типовые перестроения shell, grid/stack,
контента, форм и таблиц; text mixins для используемых семантических стилей.
Согласовать общий API миксинов, чтобы авторы не изобретали несовместимые
медиазапросы и размеры текста на каждом экране. Все требуемые widths
проверяются, но не обязательно являются отдельными breakpoints.

Переиспользовать существующие postcss-mixins и rct-type-* / rct-focus-ring
из mobile-core/src/styles/tokens.pcss. Один источник Onest и типографических
токенов для web/PWA/TMA, подключение шрифта однократно на приложение.
В текущем коде PWA/TMA импортируют mobile-core/src/styles/base.pcss,
который загружает @fontsource-variable/onest и tokens.pcss.
Общую font/token/mixin основу при необходимости выделяет один владелец,
не перенося в web все mobile-specific глобальные стили.

Предупреждение об источнике: frontends/shared/styles/fonts.css содержит
старые Clash Display/General Sans/DM Sans imports, не актуальную Onest основу.
Не считать этот файл каноном только из-за названия shared.

Цвета и theme mappings находятся вне компонентов в общей token foundation:
примитивы → семантика → компонентные aliases. Компонент выбирает token по
назначению, не копирует hex из соседнего блока. Менять общую палитру и темы
можно в одном месте без ручной правки всех страниц. Не заводить отдельные
несогласованные палитры и font-size наборы для каждой роли.

### Разрешённая доработка дизайна

Разумно убирать лишние границы, пустоты, дублирующий текст; унифицировать
warning/error blocks, поля, иконки, spacing; сжимать/перекомпоновывать формы,
таблицы и содержание; добавлять ясную иерархию без потери действий/данных.
Главную администратора владелец разрешил фактически передизайнить заново:
сейчас не устраивают GPT-подписи, расположение и вёрстка.

Использовать DESIGN-PREFERENCES-FROM-PWA-TMA.md с конкретными прежними
замечаниями. Общие дефекты исправлять в компоненте, не вручную по кадрам.
Не спрашивать про каждый отступ. В спорном случае менять обычную визуальную
композицию можно; менять роли/семантику записи/историю без решения нельзя.

Короткий текст и очевидный результат: не дублировать назначение кнопок,
не добавлять служебные «запрос выполнен», «данные доступны», «сервер отвечает»
после каждого действия. Результат виден в изменившихся данных и состоянии.
Ошибки, необходимая валидация и опасные действия должны оставаться понятными,
с доступными названиями controls; запрет лишних подписей не отменяет a11y.

### Темы и сохранение устройства — RESOLVED

Все экраны web/PWA/TMA имеют light/dark/system.
Выбор сохраняется за устройством и переживает logout и повторный login.
Переключение другого устройства не должно перезаписывать текущий выбор.
В browser context «устройство» — отдельный профиль/хранилище браузера;
очистка site data/private browsing может сбросить его, fingerprinting не нужен.

Ручной light/dark приоритетнее host/system.
TMA system следует Telegram, PWA/web system — ОС.
При system изменения host/ОС применяются без перезагрузки страницы.
Обе темы имеют одинаковые композицию и адаптив, меняются семантические
значения; проверить графики, overlays, focus, disabled и контраст.

Учесть указание владельца о backend сохранении: проверить существующие
device/session/preferences contracts, дополнить при необходимости.
Сохранение только в уничтожаемой auth session недостаточно. Локальное
нечувствительное preference может обеспечивать применение до входа/без сети;
серверный и клиентский выбор должны иметь понятное правило согласования.
Тема не является credential; logout не должен стирать её вместе с аккаунтом.
Конкретный storage/API выбрать по существующей архитектуре, не строить
отдельную сложную систему идентификации устройств ради переключателя.

### Реальные данные и realtime

Все штатные действия и экранные данные подключены к реальному backend
изолированного dev-стенда, без production secrets/data.
Изменение через web появляется у открытого PWA/TMA и наоборот без ручного
refresh. Сначала исследовать существующие event/SSE/WebSocket/query invalidation
механизмы и использовать их. Не дублировать query owner/store и не обновлять
всю страницу ради одной записи.

Проверить reconnect и догрузку пропущенных изменений, session/role switches,
одновременные клиенты и отсутствие чужих данных/дублей. Не подменять realtime
частым бесконтрольным polling и не показывать успешную запись до её подтверждения.
Не повторять неопределённую mutation автоматически. Контроль прав остаётся
на backend. Backend не рефакторить только ради UI, если нужный контракт уже есть.

Если нужного endpoint нет: сначала описать пользовательскую операцию,
проверить существующие endpoints/DTO/права; оценить переиспользование одного
или нескольких вызовов, затем совместимое расширение существующей операции,
и только после этого обосновать новый endpoint. Несколько запросов чтения
можно составить на клиенте, если это даёт нужные данные и приемлемую загрузку;
связанную запись не разбивать на хрупкую цепочку, теряющую атомарность.
Не дублировать серверные domain/authz правила в UI.

Каждое API изменение кратко фиксировать в отслеживаемом API-CHANGES.md:
endpoint/метод, причина, что изменилось, обратная совместимость, потребители
web/PWA/TMA и результат нужных проверок. Отдельно записывать найденные web
возможности для последующего переноса в PWA/TMA. Журнал короткий, пригодный
для внешнего review, а не отдельная массовая кампания документации.

### Уведомления

В открытом приложении верхний overlay host со стеком realtime уведомлений,
ориентир показа каждого — 10 секунд. Несколько сообщений отображаются
последовательно/стеком; вышедшие за видимую область и истёкшие уходят из
overlay, но остаются доступны в полной ленте через верхний колокольчик.
Не раздвигать content и не перекрывать экран неконтролируемо. Порядок,
прочитанность, адресация роли и переход к действию согласованы с существующей
лентой. Не терять события при очистке временного показа.

Владелец в этом уточнении описал in-app notifications, не новый запрос на
переработку фонового системного Web Push. Действующую background delivery
PWA/TMA сохранить; не засчитывать toast как подтверждение системного push.

### Адаптив и аналитика

Все восемь widths из макетов плюс промежуточные значения, обе темы.
Высота может меняться из-за улучшения композиции. Не делать отдельную
копию страницы на каждую ширину. Каждый автор отвечает за адаптив своего
пакета, не откладывать его на независимую массовую переделку в конце.

Живые состояния взаимодействия: понятные hover для подходящего pointer,
pressed/active/focus-visible, disabled/pending, переходы раскрытия/выбора,
плавное обновление progress bar, loading и skeleton. Использовать общий
motion/state язык, не делать новую анимацию для каждой роли. Движение
поддерживает понимание результата; не задерживает действие, не меняет данные
под курсором и не подменяет реальный progress выдуманным процентом.
Соблюдать prefers-reduced-motion и touch/keyboard сценарии без hover.

Владелец хочет совместимость со всеми браузерами; практическая проверка —
Chromium/Firefox/WebKit и responsive/touch/keyboard. Все версии всех браузеров
не объявлять проверенными; ограничения и unavailable проверки записать.
Не вводить browser-specific фундамент без необходимости.

Таблицы/списки без лишних кнопок «открыть всё/следующая страница», когда
данные можно показать в общем потоке с автоподгрузкой. Не загружать всю БД
одним запросом ради формального «всё на странице». Не терять столбцы,
выбор, поиск, доступность и контекст при перестройке.

Графики — интерактивная аналитика с настоящими метриками/периодами,
разумной осью, выбором точки/среза и деталями. Не картинка и не fake numbers.
Сохранить принятые особенности PWA: типы могут влиять только на график,
а подробные блоки оставаться видимыми; не менять согласованное правило
ради унификации. Легенды и пояснения добавлять только при реальной пользе.

### Состояния и HTML

Инвентарь применимых состояний: loading/skeleton, empty/data, network/retry,
validation, forbidden/expired session, read-only/partial/stale/uncertain
outcome, pending/success/error, notification, menus/focus/hover/selection.
Не строить бессмысленное произведение всех состояний любого компонента.

Галерея из скриншотов работающего Vue, а не из PNG макетов вместо интерфейса.
У каждого кадра постоянный semantic ID, краткое название, роль, тема,
viewport, состояние и отметка проверки. Не использовать меняющийся номер
кадра как единственную ссылку. Общий индекс + небольшие HTML по ролям/
пакетам; для мобильных PWA слева/TMA справа, для web сравнение dark/light.
Самодостаточный HTML+assets/ZIP открывается без запущенного backend.

Владелец собирает замечания в отдельном файле по ID. Встроенный редактор
заметок/экспорт комментариев не нужен. Артефакты доступны из PR для владельца
и обозревателя; пользовательская презентация/ожидание ответа не блокируют работу.
Контролируемые ошибки сети/synthetic state отмечать явно. Проверку настоящего
backend отдельно подтверждать реальным пользовательским путём.

## 5. Constraints

Сейчас только локальная подготовка, без отправки/новой задачи/PR.
При будущем GO — одна цель/новый PR, автономная работа и GitHub delivery;
никакого merge/deploy/production migrations/firewall/secrets rotation,
сообщений реальным пользователям или удаления production/backups.

Figma read-only. Подключение remote MCP не требует открытого редактора,
но доступ именно из нового cloud сначала проверить. PAT не передавать
в чате/репозитории/логах; при необходимости secret read-only для REST,
не путать его с OAuth MCP. Browser/Computer Use cloud не обещать; headless
screenshot route отдельно проверить при разрешённом setup.

Старую cloud среду не чистить вслепую. Сначала найти незакоммиченный source,
нужные evidence/artifacts/owners, сохранить handoff. Предпочесть свежую
workspace с проверенными dependencies; без global prune и чужих volumes.

## 6. Existing patterns / агенты

Разрешено распределение по ролям, предметным областям и самостоятельным
семействам экранов. Если API готов и зависимости понятны, не ждать
ненужного backend рефакторинга. Подзадачи/подагенты допустимы, когда они
ускоряют независимый scope; соблюдать актуальную project routing policy,
один coordinator layer и фактические runtime slots, не скрытый оркестратор.
Модели/effort — по решению владельца и актуальным правилам, не менять
его выбор молча. Число исполнителей не искусственно фиксировано на4–5.

Общие tokens/icons, shell/routes/session/API types/lockfiles/configs/docs
имеют назначенного sole owner. Параллельные writers в разных worktrees,
стабильная baseline и минимальный контракт заранее. Тяжёлый стенд один,
пока ресурсами и раздельными DB/queues/ports не обоснован второй.
Worktree не изолирует runtime. Независимое review не выполняет исправления
своего автора и не получает скрытое reasoning вместо проверяемого diff.

## 7. Acceptance criteria

- Карта screen/action/API/state показывает все роли и реальные сценарии.
- Нет неработающих кнопок/декоративных backend функций; нужные endpoint
  дополнения совместимы с PWA/TMA и прежней авторизацией.
- Light/dark/system работают на всех трёх поверхностях; выбор переживает
  logout/login этого устройства, manual override и Telegram/OS policy соблюдены.
- Realtime между клиентами, reconnect и notification history проверены.
- Все размеры/темы и значимые состояния имеют честную visual/runtime evidence.
- Angular убран после функциональной замены из активных sources/dependencies/
  build/CI/deployment wiring; полезные проверки возможностей перенесены.
  Историю Git не переписывать. Сам deploy не выполнять.
- PR содержит читаемый summary, достаточные результаты проверок, HTML
  evidence/ссылки и durable вопросы. Непроверенное не объявлено PASS.

## 8. Verification / тесты

Тест ловит сломанную функциональность, а не заставляет сохранять реализацию.
После рефакторинга без изменения поведения тест проходит.
Не писать новые тесты layout/formatting/UI wording/DOM shape, mock call-count/
order, копии реализации, дубли одного сценария без отдельного риска.
Не повышать coverage ради процента. Не выбрасывать полезный дешёвый unit test,
который защищает значимое правило/алгоритм. Конкретное ожидаемое значение
нормально; magic number/source hash без бизнес-смысла — не oracle.

Backend изменения: endpoint integration tests с отдельной тестовой БД и
настоящим persistence. Проверить значимые результат/права/чужие данные/
валидацию, по риску transaction/history/idempotence/concurrency.
Frontend: достаточные реальные операции через dev backend и соответствующие
negative cases. Минимально достаточный scope на пакет; не гонять весь тяжёлый
suite после каждого CSS. Новые E2E не обязательны для каждого экрана и визуальной
правки, могут вообще не требоваться, если риск уже защищён дешевле. Не создавать
хрупкую E2E кампанию как самостоятельную цель. Полезные старые проверки не
ослаблять ради PASS.

Последнее решение владельца: в этой ветке на время разработки приостановить
автоматические CI/Coverage/Security и OpenAPI. Branch versions четырёх workflow
оставляют только workflow_dispatch; main/другие PR не отключаются. Jobs не
удаляются, локальные применимые build/typecheck/runtime остаются. Включение
после готовности фронта и просмотра — только отдельным решением владельца,
не автоматически по завершению агентом. Не merge с временной паузой.
Подробности, исходные triggers и активация — CI-DEVELOPMENT-POLICY.md
и WORKFLOW-ORIGINAL-TRIGGERS.json. PAUSED/Expected/Pending не равны PASS.

Visual QA и screenshot inspection нужны, но новые CI pixel/wording snapshots
не требуются. Для runtime отчёта — точный revision, команда/среда/результат,
не ручные хрупкие хеши исходников в тестовой обвязке.
SHA256 входных PNG/архива здесь служит только целостности передачи файлов.

## 9. Do not

Не запускать реализацию по этому файлу до GO владельца.
Не отправлять его другим чатам сейчас. Не merge/deploy/менять production.
Не делать отдельную массовую кампанию чистки всех старых тестов.
Не скрывать незавершённый путь за зелёным build/mock API.
Не выдавать snapshot дизайна за работающий экран или synthetic state за
реальную проверку сервера. Не считать отсутствие ответа согласием на
изменение продукта. Не оставлять вопросы только в потеряемом контексте чата.
