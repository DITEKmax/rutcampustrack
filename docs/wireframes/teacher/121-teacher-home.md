# ПК-121 — Преподаватель, Главная

> Этап 1, чат 6. Веб-десктоп 1920. Структура и логика, без визуала.
> Цветовые группы по скану: ЗЕЛЁНЫЙ — управляющие элементы,
> ЖЁЛТЫЙ — условное/наложенное, КРАСНЫЙ — фиксированное отображение.

## 1. Идентификация

| | |
|---|---|
| **Название** | ПК-121 «Преподаватель — Главная», страница `TeacherHomePage` |
| **Роли** | teacher (в том числе совмещённый с admin — при активной роли teacher). **Не доступен** student, headman и admin в активной роли admin |
| **Поверхность** | веб-десктоп 1920 |
| **Точка входа** | редирект после входа (базовая роль — teacher, §0 чат 1); пункт «главная» в `MainNav` |
| **Цель** | Две задачи в одном экране: **навигационный хаб по назначениям** (свои группы и свои пары «предмет × тип занятия») и **оперативный срез дня** — какие пары у меня сегодня и что было на любой другой день семестра |

**Расхождение с историями**

- **JS-TEACHER-01** обещает «выпадающий список групп, внутри — выпадающий список предметов». На 121 это **не селекторы, а списки-ссылки**. Селекторы существуют, но живут на 122 и 123. Противоречия нет — уточняется точка входа: 121 задаёт контекст **навигацией**, 122/123 — **фильтрами**.
- **JS-TEACHER-04 подтверждён владельцем (чат 6):** преподаватель **не ставит и не правит отметки**, посещаемость ведёт староста. Возможность может появиться в будущем, но сейчас не проектируется. Следствие для 121: карточка пары ведёт в **просмотр** посещаемости, а не в отметку.
- **JS-TEACHER-05 изменён владельцем (чат 6):** Telegram у преподавателя **опционален** — привязку по запросу делает администратор; привязанный преподаватель пользуется ботом наравне со студентом. Базовый путь восстановления доступа — администратор: ссылка смены пароля или регенерация пароля. Прежняя формулировка «Telegram-бота нет вовсе» неверна.
- **JS-TEACHER-06** («процент по каждому предмету и группе») на 121 не выполняется: на скане и после правок — **ни одного числа**. Проценты и тренд живут на 123.
- **Оперативный срез добавлен решением владельца (чат 6)**, на скане его нет. Изначально экран был чисто навигационным; блок «пары на день» — правка, а не прочтение рисунка.
- **Прим. 1 скана** (генерация логина, «не сразу давать данные», база юзеров) — админская механика выдачи учётных данных, к структуре 121 не относится. Учтено в правке JS-TEACHER-05 и в `backend-requests`.
- **Прим. 2 скана:** карта «абсолютно аналогичная» → **ПК-105 = ПК-115 = карта преподавателя**, отдельной страницы не заводим. `CampusMapPage` остаётся `domain` (map), третья роль-потребитель.

**Сверка со сканом.** ЗЕЛЁНЫЕ: переключатель ролей, круг профиля, строки «УИТ-311» / «УИТ-211» в «Моих группах», строки «УИТ-211 · Предмет 1 · ЛК» и «УИТ-211 · Предмет 2 · ЛЗ» в «Моих предметах». ЖЁЛТОЕ: только поповер профиля «Настройки / Выход». КРАСНОЕ: два контейнера-панели с заголовками и строка шапки колонок. НЕОКРАШЕНО: `MainNav` (главная · посещаемость · статистика · карта) и фон страницы. **Не нарисовано, но следует:** `<h1>`, skip-link, все non-happy состояния, принадлежность к активному семестру. **Не нарисовано, добавлено правкой владельца:** весь регион `TeacherDayPanel`.

В «Моих группах» на скане две группы, в «Моих предметах» — строки только по одной. Читаю как незаконченность эскиза, **не** как фильтрацию второго блока первым: у «Моих предметов» есть собственная колонка «Группа», значит список самодостаточен и оба блока независимы.

**Красный ≠ без взаимодействия.** Оба красных контейнера содержат интерактивные строки (прим. 3 и 4) — красным помечена рамка панели, не содержимое. Красная шапка колонок «Моих предметов» интерактивной **не является**: сортировки и фильтров нет (согласуется с прим. 1 скана 122 — «нет сортировки и фильтров»).

## 4. Потребности в данных

### 4.1. Мои назначения (питает «Мои группы» и «Мои предметы»)

**Нужно:** сущность «назначение» = `id` · `semesterId` · `groupId` + **название группы** · `subjectId` + **название предмета** · **`lessonType`** (ЛК / ПЗ / ЛЗ). Фильтр — активный семестр. Пагинация не нужна (десятки строк), сортировка клиентская.

**Сейчас:** `GET /academic/assignments/my` (TEACHER) — единственный профильный эндпоинт роли.

**Пробел `[предложение по бэкенду]` — блокирующее.** В текущей модели назначение = преподаватель × предмет × группа × семестр, **измерения «тип занятия» нет**. Скан требует его отдельной колонкой. Это **тот же блокирующий пункт**, что уже открыт в §9 реестра («связь предмет × тип занятия × преподаватель», блокирует 116.1 и 117) — 121 становится третьим потребителем, и здесь он критичнее: без типа занятия две строки одного предмета неразличимы, а прим. 3 обещает переход в журнал **именно с этим фильтром**. Обходного пути на клиенте нет — данных не существует ни в каком виде.

**Пробел `[уточнение по контракту]`.** Возвращает ли `assignments/my` **названия** группы и предмета или только идентификаторы. Если только id — на экран добавляется N резолвов (`/academic/groups/{id}`, `/academic/subjects/{id}`) или batch-догон: N+1 ради двух списков.

### 4.2. Мои группы

**Нужно:** уникальные группы из моих назначений: `id` + `name`.

**Сейчас:** `GET /academic/groups` помечен ADMIN/TEACHER, но это **список всех групп системы** с поиском и фильтром по статусу. Для 121 непригоден: over-fetching и выдача преподавателю справочника чужих групп при том, что экрану нужны его две.

**Решение:** блок строится из ответа 4.1 (`distinct` по `groupId`), отдельного запроса нет. `GET /academic/groups` на экране **не используется** — уйдёт в раздел «не используется фронтом» в `backend-requests`.

### 4.3. Контекст семестра

**Нужно:** активный семестр — по нему фильтруются и назначения, и границы листания дня.

**Сейчас:** `GET /academic/semesters` (список); явного «активный» в дайджесте нет, есть `PATCH /academic/semesters/{id}/activate` (ADMIN).

**Пробел `[уточнение по контракту]`.** Отфильтрованы ли назначения по активному семестру на сервере, или фильтровать должен клиент. Без ответа экран покажет прошлогодние назначения как текущие, и преподаватель уйдёт в журнал закрытой группы. Селектора семестра на экране нет — значит фильтрация обязана быть серверной по умолчанию. Границы семестра (`min` / `max`) нужны `DatePager`.

### 4.4. Пары преподавателя за выбранный день (подтверждено владельцем, чат 6)

**Нужно:** сущность «пара» за **одну дату**, отобранная **по преподавателю, а не по группе**. Поля: `lessonId` · дата и время начала/окончания · `groupId` + название · `subjectId` + название · **тип занятия** · аудитория · происхождение (`regular` / `one-off` / `перенесена`, с указанием источника переноса) · статус пары (`отменена` + причина). Фильтр — дата и текущий преподаватель. Сортировка — по времени начала. Пагинации не нужно (единицы строк в дне).

**Сейчас:** `GET /schedule/groups/{groupId}/lessons` — расписание **группы** за диапазон дат. Аналога «расписание преподавателя» нет.

**Пробел `[предложение по бэкенду]` — высокий приоритет.** Нужен `расписание моих пар за диапазон дат` (одна сущность, один запрос, любой транспорт). Обходной путь на клиенте плох дважды:

1. **Веерный запрос.** Для N групп — N запросов, слияние и сортировка по времени на клиенте. Уже при трёх группах день стоит трёх запросов и не кэшируется как целое.
2. **Отфильтровать чужие пары нечем.** Ответ группы содержит **все** пары группы, включая предметы других преподавателей. Чтобы оставить свои, нужно сопоставление «пара → предмет → **тип занятия** → преподаватель», а третьего измерения в модели нет (см. 4.1). То есть без бэкенд-правки клиент физически не может определить, какие пары дня — его. **Это делает блок неработающим, а не медленным.**

**Пробел `[уточнение по контракту]`.** Несёт ли представление пары признаки «перенесена» и «разовая» с указанием источника — владелец просит показывать примечание в строке. По реестру это свойства сущности (термины «разовая пара», «перенесённая пара»), но подтверждения в дайджесте нет.

### 4.5. Что экран **не** запрашивает

Ни отметок, ни списков студентов, ни тикетов, ни дз. **Персональных данных студентов на 121 нет вообще** — ни ФИО, ни процентов, ни учётных данных. Первый экран роли полностью безопасен по границам данных: преподаватель видит только собственные назначения и собственное расписание.

### ⚠️ Фактура к решению о транспорте

| | |
|---|---|
| Запросов при обогащённых контрактах | **2** (назначения + пары дня) |
| Запросов сейчас, в лучшем случае | 1 + **N по числу групп** на каждое переключение дня |
| Запросов сейчас, при контракте «только id» | 1 + N (пары) + M (резолв названий групп и предметов) — **два независимых N+1 на одном экране** |
| Over-fetching | `GET /academic/groups` вернул бы все группы вуза вместо двух; `groups/{id}/lessons` возвращает все пары группы, из которых нужна меньшая часть |
| Невозможные данные | «тип занятия» в назначении; отбор пар по преподавателю — **не медленно, а невозможно** |

Экран задумывался как самый лёгкий в роли, а после правки владельца стал первым, где REST мешает предметно: листание дня — частое действие, а стоит оно N запросов.

## 5. Состояния

На бумаге нарисован **только `success` двух панелей-хабов**. Регион дня на бумаге отсутствует целиком (правка владельца), все его состояния добавлены при разборе. Остальное — тоже добавлено при разборе.

### `TeacherDayPanel` — автомат состояний

| Состояние | Условие | Что показываем |
|---|---|---|
| `loading` | пары дня грузятся | скелетон списка, `aria-busy`; `DatePager` остаётся активным |
| `success` | в дне есть мои пары | список по времени: время · группа · предмет · тип занятия · аудитория · примечание |
| `empty` (прошедший день) | пар не было | «в этот день у вас не было пар» |
| `empty` (будущий день) | пар не запланировано | «в этот день пар не запланировано». **Один текст на оба случая — дефект (§6.2)**: прошедший пустой день и будущий пустой день значат разное |
| `out-of-range` | вышли за границы семестра | стрелка недоступна **с пояснением**, а не пустой список |
| `no-active-semester` | активного семестра нет | пары не запрашиваем, показываем пояснение |
| `error` | запрос упал | `ErrorState` + повтор. **Падение дня не роняет хаб назначений** — блоки независимы |
| `offline` | нет сети | `OfflineState` с пометкой о возможной устарелости |

Внутри `success` строка пары имеет собственные признаки:

| Признак строки | Условие | Что показываем |
|---|---|---|
| обычная | пара идёт по плану | строка-ссылка в посещаемость этой пары |
| `one-off` | разовая пара | пометка «разовая» **текстом** |
| перенесена | пара переехала с другой даты или на другую | пометка с указанием источника, **текстом** |
| **отменена** | пара отменена | **строка показывается, но ссылкой не является**: при отмене отметки стираются (§0 чат 5), смотреть нечего. Причина отмены — текстом. **Без этого преподаватель кликает в пустой журнал и решает, что данные потеряны** |
| `future` | пара сегодня ещё не началась | отметок нет — переход допустим, но открывает пару **без данных**, а не «0 из 25» |

### `MyAssignmentsTable` — автомат состояний

| Состояние | Условие | Что показываем |
|---|---|---|
| `loading` | запрос назначений в полёте | скелетон таблицы, `aria-busy` |
| `success` | ≥1 назначение в активном семестре | строки-ссылки, порядок «группа → предмет → тип» |
| **`no-assignments`** | **запрос успешен, назначений нет вообще (новый преподаватель)** | **пояснение «назначения выдаёт староста группы или администратор» + к кому обратиться. Пустая таблица с шапкой здесь — дефект: преподаватель решит, что система сломана. Уровень вырожденности — как `no-subjects` на 117.** В этом состоянии регион дня тоже бессмысленен: пояснение показывается **один раз на страницу**, а не трижды |
| `past-semester-only` | назначения есть, но все в закрытых семестрах | «в текущем семестре назначений нет». **Без этого состояния экран неотличим от `no-assignments`, а причины у них разные** |
| `no-active-semester` | активного семестра нет (JS-ADMIN-09) | назначения не запрашиваем |
| `error` | запрос упал | `ErrorState` (`title` / `detail`, RFC 9457) + повтор |
| `forbidden` | у пользователя нет роли teacher | `ForbiddenState` без утечки данных |
| `offline` | нет сети | `OfflineState` |

### Остальные блоки

`MyGroupsPanel` и `MyAssignmentsTable` строятся **из одного ответа** — грузятся и падают вместе. Это осознанное отступление от §6.2: делить один ответ на два запроса ради независимости падений хуже, чем один понятный `error`. Но состояние должно быть **одно и объяснённое**, а не два разных пустых прямоугольника.

`TeacherDayPanel` — **независимый** блок со своим запросом: падение дня не убирает хаб, падение хаба не убирает день (кроме `no-assignments`, где пусто по определению).

### Общие

- Пустой `MyGroupsPanel` при непустой таблице невозможен по построению; если такое пришло — дефект данных, показываем `error`, не пустой список.
- `offline`: назначения кэшируем охотно (меняются раз в семестр), пары дня — осторожно, с явной пометкой об устарелости.
- Смена дня не должна ронять страницу: при ошибке одного дня остаёмся на нём с `error` и возможностью вернуться к сегодня.

### По ролям

- Преподаватель без admin — шапка **без** `RoleSwitcher`.
- **Совмещённый teacher + admin:** после входа активна базовая роль **teacher** (§0 чат 1), то есть попадает именно сюда, а не в админку. `RoleSwitcher` виден; переключение в admin уводит в админский раздел, и 121 при активной роли admin отдаёт `forbidden`, а не «пустого преподавателя». Обратное переключение возвращает контекст экрана, но **не** выбранный день — панель стартует с сегодня.
- Student и headman в маршрут не попадают: 121 отсутствует в их `MainNav`.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| Строка в «Мои группы» [ЗЕЛЁНЫЙ, прим. 4] | → **ПК-123** с предустановленным фильтром «группа». Предмет и тип остаются невыбранными — 123 открывается в состоянии «предмет не выбран» (прим. 1 скана 123). Подтверждения нет |
| Строка в «Мои предметы» [ЗЕЛЁНЫЙ, прим. 3] | → **ПК-122** с предустановленными фильтрами «группа + предмет + тип занятия»; журнал открывается сразу заполненным. Подтверждения нет |
| Строка пары в дне (правка владельца) | → **ПК-122 в режиме одной пары**: посещаемость **именно этой пары за этот день**, а не журнал за период. Переход несёт `lessonId`. Отменённая пара ссылкой не является |
| `DatePager` ◀ ▶ | смена дня, запрос пар. На границах семестра стрелка недоступна с пояснением |
| `DatePager` «Сегодня» | возврат к текущей дате; вне сегодняшнего дня действие видимо, на сегодня — недоступно |
| `MainNav` → главная / посещаемость / статистика / карта | 121 / 122 (без контекста) / 123 (без контекста) / 105. Активный пункт — `aria-current="page"` |
| `RoleSwitcher` | смена активной роли и переход в её раздел. Подтверждения нет, действие обратимо |
| `ProfileMenu` → Настройки / Выход | ПК-108 / выход. Выход деструктивен для сессии, но подтверждения нет ни на скане, ни в других ролях — оставляем как есть |

Оптимистичного UI на экране нет: все действия — переходы и смена периода, менять на сервере нечего. Отметок преподаватель не ставит (JS-TEACHER-04).

**Контекст в URL.** Все три перехода несут контекст в адресе — **по идентификаторам, не по названиям** (правило чата 5): `groupId`, `subjectId`, тип занятия, `lessonId`. Выбранный день тоже живёт в URL. Следствия: ссылку можно переслать коллеге, F5 не сбрасывает состояние, «назад» возвращает в 121 на тот же день. **Между сессиями контекст не сохраняем:** 121 и так первый экран после входа, а «липкий» контекст опаснее — преподаватель откроет вчерашний журнал, не заметив.

**Поток на несколько групп (JS-TEACHER-02).** Одна лекция на потоке — это **несколько назначений и несколько пар**, по одной на группу. В «Моих предметах» они видны отдельными строками с разными группами, в дне — отдельными строками с указанием группы. Никакой склейки «поток» на 121 нет и быть не должно: владелец требует раздельного показа.

**Нехватка прав**

| Ситуация | Путь | Итог |
|---|---|---|
| Неавторизованный открыл `/teacher/home` | редирект на ПК-001 с сохранением адреса возврата | после входа возвращается сюда |
| Авторизован, роли teacher нет | `ForbiddenState` | без намёка, какие группы существуют |
| Преподаватель без назначений | `no-assignments` | не `forbidden` и не пустая таблица |
| Прямая ссылка на чужую группу или чужую пару (подмена id в URL) | сервер обязан проверять принадлежность по назначениям и отдавать 403 | `ForbiddenState`. **Клиентская проверка «этого нет в моём списке» — не защита, только UX.** `[уточнение по контракту]`: проверяют ли `reports/journal`, `reports/lesson/{lessonId}` и `schedule/groups/{groupId}/lessons` право преподавателя на группу |

**A11y (структурно)**

- `<h1>` «Главная»; три `<section>` с `<h2>`: «Мои группы», «Мои предметы», «Пары на <дата>». Заголовки первых двух на скане красные, но это **настоящие заголовки**, а не подписи.
- «Мои группы» — `<ul>` из `<a>`. «Мои предметы» — настоящая `<table>` с `<th scope="col">`: у неё три измерения и шапка колонок. «Пары на день» — `<ul>`, **не таблица**: это список событий во времени (совпадает с трактовкой `ScheduleList` на 101).
- **Строка целиком ссылкой не делается** — ломает семантику таблицы (правило `RowDetailTrigger`: `<tr>` кнопкой не делать). Основной клавиатурный путь — ссылка в ячейке предмета с полным доступным именем «Посещаемость: УИТ-211, Предмет 1, лекция»; клик по строке целиком — дополнительный путь для мыши.
- **Аббревиатуры ЛК / ПЗ / ЛЗ разворачиваются словом** в доступном имени: «лекция», «практическое занятие», «лабораторное занятие». Аббревиатура без расшифровки доступна только зрячему знающему.
- Доступное имя строки пары включает время и группу: «Посещаемость: 10:15, УИТ-211, Предмет 1, лекция, ауд. 3417». Пометки «разовая», «перенесена», «отменена» входят в него **текстом**.
- `DatePager` имеет собственный `aria-label` (на экране он один, но правило «несколько экземпляров — разные метки» соблюдаем заранее). **Смена дня объявляется через `role="status"`**: дата + количество пар, иначе для скринридера список молча подменяется.
- Порядок фокуса: skip-link → `RoleSwitcher` → `MainNav` → `ProfileMenu` → «Мои группы» → «Мои предметы» → `DatePager` → список пар.
- Списки маленькие (единицы строк) — roving tabindex не нужен, правило крупных сеток (§6.2) здесь не применяется.
- Ошибка — `role="alert"`, смена состояния блока — `role="status"`.
- Тач-таргеты ≥44×44; стрелки пейджера — самые мелкие цели экрана, за ними следить особо.
- `prefers-reduced-motion`: единственная потенциальная анимация — смена дня; переход делаем мгновенным при включённом флаге.

## 7. Заметки на будущее

**Адаптив.** На 1920 два блока-хаба стоят рядом, регион дня — под ними на всю ширину. На 1440/1280 хабы встают в колонку без потери смысла; список пар сжимается по ширине, но остаётся списком. **Критично не потерять при сужении:**

- колонку **«Тип занятия»** в «Моих предметах» — она несёт различение строк, а схлопнуть её соблазн первый;
- **название группы** в строке пары — без него кросс-групповой день теряет смысл;
- пометки «разовая» / «перенесена» / «отменена» — их тянет спрятать в иконку, а они текстовые носители смысла.

В мобильной версии «Мои предметы» станет списком карточек, а день, вероятно, отдельным экраном — но PWA это **отдельная поверхность и отдельный цикл**, здесь не проектируется.

**Открытые вопросы и риски**

1. **Режим «одна пара» на 122 порождён этим экраном.** До правки 122 был журналом за период; теперь у него две точки входа с разными контрактами — «группа + предмет + тип за период» и «одна пара за один день». Разграничение зафиксировать при разборе 122 и внести в §8 реестра.
2. **Отбор пар по преподавателю невозможен на клиенте** — блокирующее следствие отсутствия связи «предмет × тип занятия × преподаватель». Пункт уже открыт по 116.1 и 117; 121 переводит его из «мешает» в «роль не работает».
3. **Стоимость листания дня.** При текущем API каждое нажатие стрелки — N запросов по числу групп. Самая наглядная фактура к решению о транспорте из всей роли.
4. **Право преподавателя на группу** должно проверяться сервером на всех трёх эндпоинтах посещаемости и расписания — сейчас роли у них не указаны вовсе.
5. `GET /academic/groups` (ADMIN/TEACHER) отдаёт преподавателю справочник всех групп вуза — кандидат на сужение прав или на отдельное представление.
6. Переход «строка → 122» несёт **один** тип занятия, а на 123 фильтр типов **множественный** (прим. 2 скана 123). Проверить на 122, множественный ли фильтр там: если да, предустановка одним значением должна корректно ложиться в множественный контрол.
7. **Отметку преподавателем не проектируем** (JS-TEACHER-04 подтверждён), но владелец допускает её появление в будущем. Заложено структурно: строка пары ведёт в просмотр, и добавление права правки не потребует переделки навигации — только смены компонента ячейки на 122.
8. **Массовой отметки нет вообще** — решение чата 4 расширено владельцем со старосты на весь продукт. `POST /attendance/marks/batch` не используется ни одной ролью.
