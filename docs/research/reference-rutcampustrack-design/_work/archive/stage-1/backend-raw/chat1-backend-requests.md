## 1. attendance-service

### 1.1 `[нет API]` Рейтинг группы по посещаемости — ПК-103

**Нужно:** упорядоченный по % `+` за семестр список членов **своей** группы. Поля на элемент: позиция, отображаемое имя, процент присутствия, признак «это я». Курсорная подгрузка вверх и вниз с якорем на текущем пользователе — экран открывается сразу на моей позиции с соседями.

**Сейчас:** агрегата не существует. Есть `GET /academic/groups/my/members` (состав группы) и `GET /attendance/reports/journal` (сетка студенты × даты). Сборка на клиенте = вытянуть весь журнал группы ради одного числа на человека.

**Требования:**
- ФИО приходят **в самом ответе рейтинга**, а не догоняются через `GET /academic/users/by-ids` — иначе N+1 на каждую подгруженную страницу.
- Видимость ограничена своей группой: за пределы группы рейтинг не выходит.
- Решение владельца: рейтинг **не обезличен** — студент видит ФИО и проценты соседей.

### 1.2 `[нет API]` Средняя по группе для графика тренда — ПК-103

**Нужно:** вторая серия точек «средний % `+` по группе» с той же сеткой ключей, что и моя серия (номер недели / границы недели).

**Сейчас:** в существующих отчётах средней по группе нет. Недельный таймсерис есть только мой, внутри `dashboard`.

**Требование:** обе серии приходят одним ответом с одинаковыми ключами — иначе клиент сшивает их по датам.

### 1.3 `[нет API]` Агрегаты по предметам и типам занятий за семестр — ПК-103

**Нужно:** список предметов группы за активный семестр; на каждый предмет — количества и проценты по `+`, `н`, `у` и объединённое `+ и у`; вложенный уровень — те же агрегаты по каждому типу занятий, **который у предмета реально есть** (отсутствующие типы не показываются как «0%»).

**Сейчас:** `GET /attendance/reports/student/dashboard` отдаёт только «top missed subjects» — топ-N, а не полный список с разбивкой. `GET /academic/subjects` даёт названия без статистики.

**Требование:** сортировка по любой колонке на сервере, мультиколоночная с накоплением приоритета; дефолт — алфавит по названию предмета.

### 1.4 `[предложение по бэкенду]` Проценты считает сервер — ПК-103 (и сквозное)

Одни и те же показатели выводятся на 101, 102 и 103. Если каждый клиент считает и округляет сам, цифры разойдутся между экранами.

**Нужно:** проценты приходят **вместе с количествами**, посчитанные сервером.
**Единые правила знаменателя:** отменённые пары исключены полностью; будущие пары не считаются (по ним «нет данных», а не «0%»); разовые и перенесённые пары входят наравне с регулярными.

### 1.5 `[уточнение по контракту]` Разграничение `stats` и `dashboard` — ПК-103

Какой из двух эндпоинтов отдаёт разбивку по трём статусам **и в количествах, и в процентах**, и как каждый обходится с отменёнными парами:
- `GET /attendance/reports/student/stats`
- `GET /attendance/reports/student/dashboard`

Отдельно: `dashboard` в описании помечен «for the student PWA/Mini-App home screen» и содержит donut-разбивку и топ пропущенных предметов. На 1920 этот состав не используется — при обращении к нему получаем over-fetching.

## 2. academic-service

### 2.1 `[предложение по бэкенду]` Признак «выполнено мной» в списке заданий — ПК-104

**Нужно:** в элементе списка заданий — признак выполнения текущим студентом.

**Сейчас:** из описания `GET /academic/homeworks` не видно, приходит ли он. Переключение выполнения при этом есть: `POST` / `DELETE /academic/homeworks/{id}/complete`.

**Почему критично:** без признака переключатель не с чего инициализировать, а запрашивать деталь на каждое задание — N+1.

### 2.2 `[предложение по бэкенду]` Фильтр по диапазону дат у списка заданий — ПК-104

**Нужно:** выборка заданий за произвольный диапазон дат (день / неделя / месяц).

**Сейчас:** `GET /academic/homeworks` отдаёт список для группы и семестра целиком.

**Последствия без фильтра:** ради одного дня фронт тянет весь семестр (over-fetching); режим месяца разумно не реализуется.

### 2.3 `[предложение по бэкенду]` Привязка задания к паре или порядок предмета в дне — ПК-104

**Нужно:** у задания — ссылка на пару либо порядковый номер предмета в расписании этого дня.

**Зачем:** требование «невыполненные сверху, внутри — в порядке пар дня». Без этого клиент отдельно тянет расписание каждого дня и джойнит: ×7 в режиме недели, ×30 в месяце.

### 2.4 `[предложение по бэкенду]` Лёгкий агрегат для календаря месяца — ПК-104

**Нужно:** по каждой дате месяца — есть ли задания, сколько, краткие названия предметов.

**Зачем:** иначе календарь тянет полные тексты всех заданий месяца ради подписей под датами.

### 2.5 `[уточнение по контракту]` Ссылка в задании: одна или массив — ПК-104

Отдельное поле или внутри текста; одна ссылка или несколько. От этого зависит макет ячейки задания: иконка перехода против списка ссылок. Ссылка вводится старостой и ведёт вовне — открывается как внешняя, с видимым доменом.

### 2.6 `[уточнение по контракту]` Домашнее задание отменённой пары — ПК-104

Отменённая пара показывается, но не входит ни в один знаменатель. Что происходит с её заданием — правил нет.

### 2.7 `[уточнение по контракту]` Отметка выполнения при правке задания — ПК-104

Сбрасывается ли личная отметка выполнения, когда староста редактирует текст задания. Предполагается, что **не сбрасывается** — иначе правка запятой обнуляет прогресс всей группы. Требует подтверждения.

## 4. Экраны, где текущий REST неудобен

Фактура к решению REST / GraphQL. Направление владельца: **эндпоинты под форму экрана + кэшируемость**, а не клиентская агрегация.

| Экран | Запросов на отрисовку | В чём неудобство |
|---|---|---|
| ПК-103 Статистика | **4–6**, из них **3 не существуют** | Рейтинг, средняя по группе и агрегаты по предметам отсутствуют как контракты. `dashboard` отдаёт donut и топ-предметов, не используемые на 1920 → over-fetching. Каждое переключение «Семестр ↔ Неделя» и каждое листание недели — отдельный запрос за графиком |
| ПК-104 Домашнее задание | **1–3** в зависимости от режима | Без фильтра по диапазону дат любой режим тянет задания всего семестра. Порядок «по парам дня» без привязки к паре требует расписания на каждый день: ×7 в неделе, ×30 в месяце. Календарь месяца без лёгкого агрегата тянет полные тексты заданий ради подписей под датами |

**Наблюдения, зафиксированные при разборе:**

- У 103 два блока с **разной частотой инвалидации**: мои семестровые агрегаты и групповые данные (средняя по группе, рейтинг). Групповые заметно лучше кэшируются.
- На 104 переключение режима меняет не фильтр, а **форму ответа** (плоский список / группировка по дням / календарный агрегат + список дня).
- Ранее зафиксированная фактура для сравнения: 001 — 3–4 запроса, 101 — 6–8, 102 — 4–5 на каждое переключение.
