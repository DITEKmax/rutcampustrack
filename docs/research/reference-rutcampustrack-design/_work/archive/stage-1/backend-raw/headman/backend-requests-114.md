# backend-requests — ПК-114 (Староста, Домашнее задание)

> Этап 1, чат 3. Часть общего файла запросов к бэкенду — предназначена для слияния
> с аналогичными файлами других экранов.
> Транспортно-нейтрально: сначала ЧТО нужно, потом где это лежит сейчас.

---

## Сводка по экрану

| Тип | Кол-во | Критичность |
|---|---|---|
| **Изменение правила доступа** | 1 | **блокирующее** — экран расходится с API по существу |
| Новое поле в модели задания | 3 | высокая |
| Новый агрегат / признак | 2 | высокая |
| Новое поведение (автоперенос) | 1 | зависит от нереализованной операции |
| Повторные требования с других экранов | 3 | усиливают уже поданные |
| Уточнение контракта | 2 | средняя |

**Главное по экрану.** Продуктовое решение владельца («править дз может каждый, у кого есть право его выкладывать») **прямо противоречит** текущему ограничению API «только автор». Это не расширение и не удобство — без изменения экран будет показывать активные кнопки, на которые сервер ответит отказом.

## academic-service

### D-1. Снять ограничение «только автор» с редактирования и удаления
`[предложение по бэкенду]` · источник: ПК-114 §4.5, заметка 2 job · **подтверждено владельцем** · **блокирующее**

- **Сейчас:** `PUT /academic/homeworks/{id}` — «HEADMAN, только автор»; `DELETE /academic/homeworks/{id}` — «HEADMAN, только автор».
- **Нужно:** право на правку и удаление определяется **правом публиковать дз в этой группе** (`manage_homework` у помощника, либо роль старосты), а не авторством записи.
- **Формулировка владельца:** править может «все, у кого есть возможность выкладывать дз».
- **Почему блокирующее:** у группы несколько потенциальных авторов (староста + помощники). При текущем правиле помощник видит чужое задание с активными кнопками и получает отказ сервера — либо фронт вынужден блокировать действия, которые продукт разрешает.
- **Уточнить отдельно:** распространяется ли снятие на `DELETE`. В файле экрана применено по аналогии с `PUT`.
- **Следствие:** авторство перестаёт быть правилом доступа, но остаётся **значимой информацией** — см. `D-2` и `D-5`.

### D-2. Автор задания в модели
`[уточнение по контракту]` · источник: §4.5

- **Нужно:** `authorId` и отображаемое имя автора в представлении задания.
- **Зачем:** после `D-1` авторство не ограничивает права, но остаётся ответом на вопрос «кто выложил» — заметка 2 job прямо просит видеть, кто и как менял.

### D-3. Привязка задания к паре
`[уточнение по контракту]` · источник: §4.3, заметка 2 макета, заметка 1 job

- **Нужно:** у задания — `lessonId` **либо явный признак «без привязки к паре»**.
- **Зачем:** от этого поля зависят три механики сразу — ползунок в форме, автоперенос вместе с парой (`D-7`) и правило архивации (`D-4`).
- **Сейчас:** наличие поля в модели не подтверждено.

### D-4. Признак актуальности задания приходит с сервера
`[предложение по бэкенду]` · источник: §4.4 · **критерий подтверждён владельцем**

- **Правило (владелец):** задание уходит в архив, **когда прошла пара, на которую оно было создано**.
- **Отменённая пара:** задание уходит **в архив** — подтверждено владельцем. Закрывает вопрос, открытый в реестре §9 с чата 2.
- **Задание без привязки к паре:** пары нет, значит критерий — выбранная в календаре дата. Записано как необходимое дополнение, требует сверки.
- **Возврат из архива не проектируется:** «из архива не возвращаем, только создаём новое».
- **Почему нельзя на клиенте:** правило опирается на **время окончания пары и её статус отмены**, а не на одну дату в задании. Клиенту для вычисления пришлось бы тянуть расписание и джойнить — то же самое, чего уже избегаем в `AC-2`.
- **Нужно:** признак в представлении задания и **фильтр по нему** в списке.

### D-5. История изменений задания
`[предложение по бэкенду]` · источник: §4.6, заметка 2 job · **второй потребитель аудит-подсистемы**

- **Нужно:** по заданию — хронология: кто, когда, что изменил (текст, основная ссылка, дата, привязка к паре), включая факт первой публикации.
- **Сейчас:** нет.
- **Связь с `A-1` (ПК-111):** там требуется журнал действий по паре. Это **тот же механизм на другой сущности** — два независимых экрана просят одно и то же. Аргумент проектировать аудит как общую подсистему, а не точечно под каждый экран.
- **Усиление после `D-1`:** раз править может любой обладатель права, история перестаёт быть удобством и становится **единственным способом** установить, кто изменил задание.

### D-6. Основная ссылка отдельным полем
`[уточнение по контракту]` · источник: §4.3 · **подтверждено владельцем**

- **Нужно:** отдельное поле под **одну** основную ссылку (облако, репозиторий и т.п.), отдельно от текста описания.
- **Массива ссылок не требуется.** Прочие ссылки владелец размещает **внутри текста задания**; их кликабельность — задача отображения на фронте, хранить их отдельно не нужно.
- **Закрывает** открытый вопрос реестра «ссылка одна или массив».

### D-7. Несколько заданий на одну пару — детерминированный порядок
`[уточнение по контракту]` · источник: §4.9 · **подтверждено владельцем**

- **Факт:** на одну пару может приходиться несколько заданий, уникальности «пара → задание» нет.
- **Нужно:** стабильный порядок заданий внутри одной пары (например, по времени публикации), иначе список будет перетасовываться между запросами и на ПК-111, и здесь.

### D-8. Фильтр по диапазону дат в списке заданий
`[предложение по бэкенду]` · источник: §4.4 · **третий потребитель** · дубль `AC-1` (ПК-111) и JS-STUDENT-20 (ПК-104)

- **Нужно:** отбор заданий группы по диапазону дат, плюс фильтры по предмету и типу занятия, сортировка и пагинация.
- **Сейчас:** `GET /academic/homeworks` — за семестр целиком.
- **Замечание:** это требование поднимается уже на третьем экране подряд (студенческий 104, главная старосты 111, этот). Стоит закрывать один раз и полноценно.

### D-9. Конфигурируемый набор фильтров списка
`[предложение по бэкенду]` · источник: §3, заметка 3 макета · продолжение `AC-6` (ПК-113)

- **Заметка 3 макета:** «можно задать фильтры по предметам, по типам предметов, по датам **и т.д.**» — перечень открытый.
- **Нужно:** описание доступных фильтров приходит как данные, фронт их рисует. То же правило, что принято для таблиц статистики.

## schedule-service

### D-10. Перенос пары уносит связанные с ней данные
`[предложение по бэкенду]` · источник: §4.7, заметка 3 job · **сквозное, шире экрана**

- **Формулировка владельца:** «при переносе предмета данные все по паре (дз и, может, ещё какие-то) должны переноситься вместе с ней».
- **Нужно:** при переносе пары задания, привязанные к ней (`D-3`), автоматически переезжают на новые дату и время. Задания **без** привязки не двигаются.
- **Сейчас:** нет ни автопереноса, ни самой операции переноса пары — JS-HEADMAN-21 уже помечена как требующая решения бэкенда («есть только отмена и создание разовой пары»).
- **Повышение приоритета:** отсутствующая операция переноса теперь блокирует поведение **двух** экранов, а не одного.

### D-11. Ближайшая пара по предмету и типу занятия
`[предложение по бэкенду]` · источник: §4.2 · **второй потребитель** · дубль `S-6` (ПК-111)

- **Нужно:** «следующая пара по (предмет, тип занятия) после даты X».
- **Зачем здесь:** календарь в режиме привязки делает доступным **ровно один день** — день этой пары. Без эндпоинта клиент тянет расписание вперёд наугад, не зная глубины поиска.

### D-12. Реально существующие типы занятий у предмета
`[предложение по бэкенду]` · источник: §4.1 · **третий потребитель** · дубль `AC-4` (ПК-112)

- **Нужно:** у предмета приходит список фактически существующих типов занятий.
- **Зачем здесь:** без него форма предложит тип, которого у предмета нет, и следующая пара не найдётся никогда — пользователь упрётся в пустой календарь без объяснения причины.

## Замечание к слиянию файлов

Три требования этого экрана — повторные:

| Здесь | Впервые заявлено | Потребителей всего |
|---|---|---|
| `D-8` фильтр по датам | `AC-1` (ПК-111), JS-STUDENT-20 (ПК-104) | **3** |
| `D-11` следующая пара | `S-6` (ПК-111) | **2** |
| `D-12` типы занятий предмета | `AC-4` (ПК-112) | **3** |

При объединении файлов их следует свести в по одному пункту с перечнем экранов-потребителей — количество потребителей само по себе является аргументом приоритета.

Отдельно: `D-5` (история изменений задания) и `A-1` (журнал действий по паре, ПК-111) — **одна аудит-подсистема на двух сущностях**. Разводить их по разным задачам не стоит.
