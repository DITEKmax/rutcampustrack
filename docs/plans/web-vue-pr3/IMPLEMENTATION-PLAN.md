Для каждого экрана и действия записать в SCREEN-ACTION-MAP.csv:

## 4. Подготовить общую основу Vue и стилей

1. Определить место web Vue в существующем frontend workspace и читаемые
   scripts dev/typecheck/build. Учесть единый lockfile и действующие версии.
   Не держать второй конфликтующий менеджер пакетов для нового клиента.
2. Общая оболочка: навигация, header, role/session context, notification host,
   вложенный route outlet. Один каркас, содержимое экранов вкладывается в него.
   «Микрофронтенды» здесь не требуют Module Federation/отдельных deployments.
3. Отделить API transport/adapters, состояние и доменную логику от Vue views.
   Переиспользовать подходящие contracts/API types, не импортировать мобильную
   навигацию и Telegram globals во все web страницы.
4. Определить общий источник шрифта Onest, типографики, палитры, spacing,
   радиусов и focus. Существующие PWA/TMA подключают mobile-core/styles/base.pcss
   с Onest и tokens.pcss. Старые fonts.css с другими шрифтами не являются каноном.
5. Подготовить PCSS responsive mixins и семантические text mixins до массовой
   работы над экранами. Существующий postcss-mixins и rct-type-* переиспользовать.
   Определить правила shell/grid/stack/форм/таблиц, а не копировать медиазапросы.
6. Цвета вынести в общую foundation: примитивы → семантика → aliases компонентов.
   В страницах использовать назначение цвета, не копии hex для каждой роли.
7. Согласовать интерфейсы web controls: field, button, dialog/drawer, table,
   empty/error/loading, warning, badge, toast, chart. Не делать библиотеку
   из десятков неиспользуемых abstractions до первого рабочего сценария.
8. Иконки брать из общего каталога/Figma/PWA/TMA; новые SVG добавлять в единое
   место и стиле. Не плодить одинаковую inline геометрию по экранам.
9. Прочитать DESIGN-PREFERENCES-FROM-PWA-TMA.md: разумная плотность, меньше

Результат: компилируемый web shell и используемые общие стили/компоненты.
Конкретные имена новых файлов/пакетов выбирает исполнитель по репозиторию.

## 6. Завершать пользовательские сценарии всех ролей

Исполнитель сам группирует задачи по доступным API, общим компонентам,
ресурсам и риску. Каждый пакет — рабочая операция, а не только макет страницы.

Для каждого пакета:

1. Подтвердить актуальный read/write contract, права, ожидаемый результат.
2. Реализовать нужные списки/формы/подробности и все видимые действия.
   Если backend уже подходит — не рефакторить его без причины.
3. Подключить существующие API, query/state и обновление связанных экранов.
   Не оставлять production mock, фальшивую успешную кнопку или статичные числа.
4. Обработать загрузку, пустоту, валидацию, отказ доступа, сбой сети,
   повторное чтение, сохранение и восстановление. Не дублировать mutation
   вслепую после неизвестного результата запроса.
5. Довести light/dark и адаптив, hover/press/focus/disabled/loading,
   skeleton/progress, разумные анимации и reduced-motion.
6. Выполнить достаточную адресную проверку, приложить факты и обновить PR.

Таблицы и списки должны оставаться читаемыми с длинными значениями и большим
объёмом данных. Адаптировать колонки/приоритет/скролл/подгрузку без потери
доступа ко всем записям и без лишней кнопки только ради просмотра содержания.
Сохранить фильтры и контекст переходов там, где это ожидаемое поведение.

Графики показывают настоящие метрики, период, единицы и осмысленные данные,
подробности/легенду/состояния, по образцам PWA. Не заменять аналитику рисунком
и не выдавать отсутствие данных за нулевой результат.

Главная администратора: сначала реальные задачи/показатели/действия,
затем новая композиция. Убрать избыточные GPT-подписи и пустые высокие блоки.
Нельзя придумывать системные метрики, которых сервер не отдаёт.

## 7. Разбирать необходимые backend дополнения

Перед новым endpoint проверить существующие доступные операции, BFF и contracts:
можно ли переиспользовать один вызов, совместить независимые чтения или
обратно совместимо дополнить существующую операцию.

Не разбивать единую атомарную запись на несколько browser запросов ради
экономии endpoint. Не расширять права в обход принятых решений. Не менять
семантику полей/ошибок для PWA/TMA молча.

Каждую доработку кратко записать в API-CHANGES.md: ID, зачем, method/path,
до/после, права/ошибки, потребители, миграции/события, проверка совместимости.
Если меняются shared types, generated файлы обновлять штатным генератором
одним владельцем. Для изменения persistence/migrations соблюдать проектные
правила; production migration не разрешена.

Для затронутого endpoint — интеграционный тест с отдельной тестовой БД:
наблюдаемый результат и существенный запрет, по риску история/атомарность/
повторный запрос. Без новых endpoint и изменений backend расширение
backend test suite само по себе не нужно.

## 8. Реальные обновления и уведомления

Исследовать действующие SSE/WebSocket/event/query invalidation mechanisms.
Связать экранные данные с нужными событиями; не создавать параллельный
несогласованный event bus для нового web без необходимости.

Проверить на двух открытых клиентах web↔PWA и web↔TMA: изменение, получение
обновления, отсутствие чужих данных, reconnect и получение актуального
состояния после разрыва. Не терять unsaved форму при фоновом обновлении.
Явно объяснить fallback, если существующий transport какой-то путь не покрывает.

Уведомления поверх страницы вверху, несколько накапливаются; ориентир жизни
каждого около10 секунд. Ушедшие за видимую область/истёкшие не держат
бесконечную колонку, полный список доступен через bell/history. Новые
события не должны сбрасывать таймер старым и дублироваться при reconnect.
Существующий фоновый WebPush сохранить; toast не является его проверкой.

Не озвучивать служебный статус сервера после каждого клика. Результат действия
обычно виден в данных. Нужные ошибки, предупреждения и a11y labels сохранить.

## 9. Темы во всех клиентах

Состояние предпочтения: `light | dark | system`, отдельно от вычисленной темы.
Ручное light/dark важнее host; system в TMA следует Telegram, в web/PWA — ОС.
При смене system/Telegram применять значения без перезагрузки.

Выбор сохраняется для этого устройства/browser profile после logout/login,
не перетирается другим устройством. Не удалять preference вместе с auth tokens.
Существующий device/preferences API исследовать; при необходимости дополнить
совместимо. Не выдумывать fingerprint устройства. Локальное хранение может
давать тему до авторизации/без сети; правило согласования с сервером описать.

Пройти ВСЕ существующие PWA/TMA экраны: поля, таблицы, календари, charts,
модальные слои, notifications, disabled/focus/error/skeleton. Подключение
light variables не считается готовностью, пока конкретные экраны не читаются.
Новые web функции не переносить в мобильный UI в этой итерации: записать
в MOBILE-FOLLOWUPS.md, найденные спорные дефекты — в OPEN-QUESTIONS.md.

## 10. Адаптив и HTML для обозревателя

Целевые ширины 300/425/600/768/1024/1280/1440/1920 и промежутки между ними.
Высота может отличаться при разрешённой переработке. Для 28 видов нет140
узких light экспортов; брать композицию соответствующей dark темы,
менять семантические цвета. Не считать их потерянными входными файлами.

Проверить навигацию, переносы, длинные имена/данные, скролл страницы/таблиц,
диалоги, focus и отсутствие перекрытых действий. Целевые evergreen браузеры:
Chromium/Firefox/WebKit по доступной среде. Ограничения реальных Safari,
Telegram WebView/камеры/WebPush честно отметить, не обещать все версии браузеров.

Галерея — переносимый HTML с реальными скриншотами реализации, краткими
названием/описанием/ID роли, экрана, состояния, темы, viewport и revision.
Фильтр/индекс облегчит проверку; feedback редактор в галерее не требуется.
Пример ID: `WEB-STUDENT-ATTENDANCE--error--light--425`.
Не менять ID при смене файла/вёрстки; связать с API/state map.

Отдельно помечать исходный Figma, полученный runtime и синтетически вызванное
состояние. Искусственное offline/ошибка допустимы для visual QA, но не
доказывают реальный backend failure handling без соответствующего сценария.
Не записывать реальные секреты/персональные данные в screenshots, HTML и логи.

без запуска полного backend suite для каждого viewport. Значимые состояния
проверять там, где они отличаются по поведению, без декартова размножения.

Публиковать HTML и изображения/ZIP со ссылкой из PR. GitHub показывает HTML

## 11. Удалить Angular после функциональной замены

Сначала составить карту оставшихся Angular entrypoints/routes и связей:
workspace packages, dependencies/lockfiles, build scripts, Dockerfile,
compose/nginx/static hosting, CI jobs, deploy image paths, tests/docs.

Удалить активные Angular sources, зависимости и wiring после переноса
соответствующих возможностей. Старые специфичные Angular tests убрать
вместе с исчезнувшей реализацией; полезные проверки поведения перенести,
не оставлять заведомо красный тест ради сохранения файла.

Vue web должен собираться и упаковываться штатно, открывать deep links,
корректно обращаться к API и отдавать assets при новой конфигурации.
Исправить CI/deploy wiring под новый клиент, но не возвращать автозапуски
без владельца и не выполнять deploy. Не допустить, чтобы Security по старому
комментарию продолжил исключать новый web из итоговой проверки.

Сделать адресный поиск Angular/references; отличить исторические документы
от активной сборки. Не переписывать Git history и не удалять архивы оптом.
Финально показать перечень созданных/изменённых/удалённых файлов и заменённых
команд. Нет зависимости нового web от сохранившегося legacy bundle.

## 12. Проверять достаточно, без тестовой кампании ради числа

Правило владельца: тест нужен, если он дёшево ловит существенную поломку.
Если такую гарантию уже даёт существующая проверка/другой уровень, не дублировать.
Количество тестов, coverage и assertions не являются целью итерации.

| Изменение | Достаточная отправная точка проверки | Когда добавлять автоматизацию |
|---|---|---|
| Обычная вёрстка/цвета/адаптив | Typecheck/build по затронутому клиенту, реальный просмотр/скриншоты и keyboard/focus | Новые E2E и pixel/text snapshots для этого не требуются |
| Значимое правило frontend | Наблюдаемый результат на характерных входных данных | Небольшой устойчивый unit/component test, если даёт отдельную полезную гарантию |
| Backend endpoint/права/запись | Реальная endpoint integration с отдельной DB и существенными отрицательными случаями | Изменить существующий полезный test или добавить адресный integration test |
| Session/role/realtime cross-client | Реальная проверка основной цепочки и изоляции/восстановления | Минимальный устойчивый smoke/E2E только если риск остаётся без более дешёвой защиты |
| Удаление Angular/build wiring | Typecheck/build/package/config validation и запуск нового клиента на dev | Не писать source-string/hash tests, проверяющие тот же путь текстом |

Запрещённые новые проверки: форматирование/верстка/точный текст как oracle,
вызовы/порядок моков вместо результата, копии реализации, магические source
hashes, десять повторений одного сценария без отдельного риска. Конкретный
ожидаемый бизнес-результат допустим. Полезные дешёвые unit tests сохранять.

Новая большая Playwright/E2E инфраструктура не обязательный deliverable.
Открывать страницу браузером и получать screenshot — не то же самое, что
навешивать на каждую страницу хрупкий E2E gate. Число новых тестов может
быть нулевым для чисто визуального пакета с достаточной runtime evidence.

Во время разработки запускать локально только применимые проверки. Полный
тяжёлый suite не нужен после каждого CSS/коммита. Не удалять/ослаблять старые
проверки ради зелёного статуса; переработка нужна, когда проверяемое поведение
заменено/устарело, и это объяснено в diff. Не запускать массовую чистку старых
тестов, не связанную с заменой клиента.

Если проверка упала, разделить дефект продукта, теста и среды. Сохранить
краткое воспроизведение, исправление и адресную перепроверку, не повторять
одинаковые тяжёлые прогоны без новых фактов.

## 13. Вести PR и открытые решения

В отслеживаемых docs PR держать один актуальный комплект, не копии на каждого агента:

- `IMPLEMENTATION-PLAN.md` и `SCREEN-ACTION-MAP.csv`: scope/checklist и факты;
- `PROGRESS.md`: завершённые пользовательские операции и ближайший остаток;
- `API-CHANGES.md`: только реальные доработки контрактов;
- `OPEN-QUESTIONS.md`: Q-ID, решение, источник, варианты/рекомендация, что блокирует;
- `MOBILE-FOLLOWUPS.md`: новые web функции и предложения для будущего mobile;
- `VALIDATION.md` и gallery: выполненная команда/revision/среда/результат/evidence.

Пустые большие шаблоны необязательны: создавать файл при появлении записей.
Общие docs имеют одного владельца. После завершённого значимого пакета —
короткий PR отчёт: что работает, shared/API изменения, что проверено,
ссылка на HTML, что осталось и Q-IDs. Не ждать владельца после каждого экрана.

Различать `planned / in progress / implemented / verified / blocked`;
не выдавать presence файла за работающий сценарий. Если нужна доля готовности,
считать реальные принятые screen-client/story rows по READINESS, не число
скриншотов/агентов/тестов. Неотвеченные вопросы сохраняются для обозревателя.

## 14. Финальная передача и запуск GitHub-проверок владельцем

1. Подготовить законченную ветку: все роли/операции, две темы и нужные состояния,
   PWA/TMA совместимость, Angular removal, локальные достаточные проверки.
2. Собрать итоговый HTML/summary, точную revision, checklist готового/оставшегося,
   изменения API и вопросы. Указать: GitHub CI/Coverage/Security пока PAUSED.
3. Не снимать паузу автоматически по «я закончил». Дождаться отдельной команды
   владельца включить проверки; за ожидание не выдавать Pending за PASS.
4. По его команде вернуть нужные автоматические events четырём workflow,
   сохранить разработанные Vue job updates, проверить YAML, scope сканирования
   нового web и отсутствие deployment side effects. Не перетирать весь файл
   из старого main ради восстановления нескольких строк events.
5. Push разрешённой активации без skip-marker запускает применимые PR проверки.
   Разобрать реальные падения адресно, не объявлять оставшееся дефектом CI
   без фактов. Полный финальный набор и дальнейшую приёмку определяет владелец
   с учётом scope; merge/deploy всё ещё требуют отдельного решения.

Доставка этой итерации — проверяемый PR с рабочим новым клиентом и честными
ограничениями. Готовый фронт сам по себе не объявляет production/deploy готовым.
