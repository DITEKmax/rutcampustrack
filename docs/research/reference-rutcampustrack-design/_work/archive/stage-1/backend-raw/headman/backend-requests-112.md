## attendance-service

### B-1. Журнал должен быть сеткой по **парам**, а не по датам
`[предложение по бэкенду]` · источник: ПК-112 §4.1, заметка 1 макета · **блокирующее**

- **Нужно:** сетка «студенты × пары» с двухуровневой группировкой колонок: дата → пары внутри даты.
- **Сейчас:** `GET /attendance/reports/journal` описан как «Journal grid (students × dates)».
- **Подтверждено владельцем:** одна колонка = одна пара; над парами одного дня — объединённая ячейка с датой.
- **Почему блокирующее:** в дне у группы 2–4 пары, статусы у них разные. Одноуровневая сетка по датам физически не может нести эти данные — экран на ней не строится.
- **Состав колонки:** дата, день недели, порядковый номер пары в дне, предмет, тип занятия, статус пары, происхождение, аудитория.
- **Состав ячейки:** статус отметки, `source`, время отметки, ссылка на тикет для «у».

### B-2. Журнал с фильтром по предмету и типам занятий за семестр
`[предложение по бэкенду]` · источник: §4.4, заметка 4 макета

- **Нужно:** та же сетка «студенты × пары», отфильтрованная по предмету и набору типов занятий, за период **от начала семестра до текущей недели включительно**. Будущие пары не отдаются; отменённые отдаются.
- **Сейчас:** нет. Поддержка таких фильтров у `journal` неизвестна.
- **Подтверждено владельцем:** период — весь семестр одной простынёй, в будущее не заходим.
- **Объём:** 25–30 студентов × 30–40 пар ≈ 1000 ячеек в одном ответе. Нужно решение: отдавать целиком или пагинировать по колонкам.

### B-3. Снятие отметки
`[предложение по бэкенду]` · источник: §4.3 · **подтверждено владельцем** · дубль A-7 из ПК-111

- **Нужно:** операция возврата ячейки в состояние «отметки нет».
- **Сейчас:** `PUT /attendance/lessons/{lessonId}/students/{userId}` умеет только присвоить одно из трёх значений.
- **Механика, подтверждённая владельцем:** повторное нажатие на выбранный кружок снимает статус. Без операции снятия из отмеченного состояния «пусто» недостижимо, и описанное поведение невыполнимо.

### B-4. `source` отметки
`[предложение по бэкенду]` · источник: §4.3, заметка 2 макета · **подтверждено владельцем** · дубль A-6 из ПК-111

- **Нужно:** `source` (`student_geo` / `headman` / `auto_scheduler` / `teacher_override` / `late_checkin`), время отметки, кто изменил.
- **Формулировка владельца (заметка 2 макета):** «важно, поставил ли "н" староста или само проставилось, т.к. студент не отметился».
- **Почему критично:** после закрытия пары журнал автоматически заполняется `н`. Без источника староста не отличит автопростановку от собственного решения и от решения преподавателя.

### B-5. Причина «у» и комментарий в самой ячейке журнала
`[предложение по бэкенду]` · источник: §4.5 · **владелец: решаем на бэкенде**

- **Нужно:** тип уважительной причины, комментарий и `excuseId` приходят вместе с ячейкой.
- **Почему:** заметка 3 job требует показывать причину по наведению на «у». Если данных нет в ячейке, каждое наведение — отдельный запрос: **N+1 по числу «у» в таблице**, а их в неделе десятки.

### B-6. Доступ к файлу заявки из веба
`[предложение по бэкенду]` · источник: §4.5, заметка 3 job · **отменяет прежнее решение**

- **Нужно:** получение вложения заявки и его метаданных (имя, размер, тип) для показа в окне заявки.
- **Сейчас:** `POST /attendance/excuses/with-file` создаёт заявку с файлом; получения файла в дайджесте нет.
- **Подтверждено владельцем:** файл **теперь сохраняется отдельно**. Прежнее положение JS-STUDENT-WEB-07 («файлы уходят через бота без хранения у нас») отменено — иначе заметка 3 job невыполнима.
- **Потребители:** окно заявки одинаково нужно старосте и преподавателю (чат 4).

### B-7. Метаданные недели: номер и чётность
`[предложение по бэкенду]` · источник: §4.2, следствие JS-SYSTEM-05

- **Нужно:** границы недели, **порядковый номер недели от начала семестра**, чётность; границы семестра для ограничения листания.
- **Почему нельзя на клиенте:** JS-SYSTEM-05 уже постановил, что чётность и номер считает сервер — две реализации разойдутся на границах семестра и при переносах.

### B-8. Признак «пустой день»
`[предложение по бэкенду]` · источник: §4.1, заметка 1 макета

- **Нужно:** день без пар приходит явно, а не как отсутствие колонок.
- **Почему:** заметка 1 требует показывать такой день **неактивным в сетке** — он занимает место, а не исчезает.

### B-9. Перечень форматов выгрузки как данные
`[предложение по бэкенду]` · источник: §4.6 · **подтверждено владельцем**

- **Нужно:** список доступных форматов приходит клиенту как данные. Сейчас нужны docx, pdf, png; в планах html; перечень будет расширяться.
- **Подтверждено владельцем:** форматы и **шаблоны с placeholder'ами** — целиком задача бэкенда. Фронт рисует кнопки и передаёт выбранный формат.
- **Почему:** то же правило, что для типов уважительных причин (§0 реестра) — расширение перечня не должно требовать релиза фронта. Excel сейчас не нужен, но может появиться позже.

### B-10. Пакетная выгрузка роняет сервис
`[предложение по бэкенду]` · источник: §4.6, заметка 4 job · **сформулировано владельцем**

- **Проблема:** выгрузка нескольких недель одним действием кладёт сервис.
- **Направление владельца:** решать на бэкенде — хранить состояние отчёта либо считать **инкрементально по изменениям**, а не собирать данные заново на каждый запрос.
- **Следствие для фронта:** пока решения нет, нужен режим долгой операции (прогресс либо «пришлём, когда готово»). Синхронная кнопка на долгой генерации даёт зависший экран.

### B-11. Выгрузка разреза по предмету
`[предложение по бэкенду]` · источник: §4.6

- **Нужно:** выгрузка матрицы «предмет × типы занятий за семестр» во всех поддерживаемых форматах, с учётом активных фильтров.
- **Сейчас:** отчёты только недельные (`headman-weekly/*`).

## schedule-service

### S-7. Статус пары и признак переноса в представлении пары
`[предложение по бэкенду]` · источник: §4.1, заметка 1 макета · **подтверждено владельцем: «да, я бы добавлял»** · пересекается с S-1 из ПК-111

- **Нужно:** статус пары (`planned` / `active` / `closed` / `cancelled`) и происхождение (`regular` / `one-off` / **перенос**) — в том числе внутри ответа журнала, а не только в расписании.
- **Почему:** заметка 1 макета требует выделять отменённые и перенесённые пары, а также помечать «пара ещё не прошла» — без статуса ячейка не сможет отличить будущую пару от неотмеченной, и покажет кружки там, где отмечать нечего.

## academic-service

### AC-4. Реально существующие типы занятий у предмета
`[предложение по бэкенду]` · источник: §4.4, следствие JS-HEADMAN-13

- **Нужно:** у предмета приходит список типов занятий, которые у него **фактически есть**.
- **Сейчас:** `GET /academic/subjects` — состав полей неизвестен.
- **Почему:** правило реестра требует показывать недоступные типы **disabled с пояснением, а не скрывать**. Без явного списка фронт не отличит «типа у предмета нет» от «данные не пришли» — и либо соврёт, либо скроет то, что скрывать нельзя.

### AC-5. Права на чтение журнала и на выгрузку
`[уточнение по контракту]` · источник: §4.7 · **владелец: решаем после фронта**

- **Вопрос:** какое право помощника даёт чтение журнала и какое — выгрузку. В текущем перечне (`mark_attendance`, `manage_excuses`, `manage_homework`, `cancel_lessons`, `view_stats`) выгрузки нет вообще.
- **Связано с:** AC-3 из ПК-111 (эффективные права в сессии).

## Кросс-сервисное

### X-2. Единая форма ответа для двух разрезов
`[предложение по бэкенду]` · источник: §4.3

- **Ситуация:** правка отметки в одном разрезе обязана немедленно отражаться в другом (заметка 4 макета: «отображается без обновления и там, и там»).
- **Нужно:** оба разреза отдают ячейку в **одинаковой форме** с общим идентификатором `(lessonId, userId)`.
- **Почему:** если формы различаются, фронт держит две несовместимые копии данных, и они разойдутся при первой же правке.
