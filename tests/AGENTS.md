# Проверки RutCampusTrack

Канон: [RULES.md](../.agent/orchestration-v2/RULES.md), разделы 5–6, решение владельца 2026-09-20. Он отменяет прежний список build/lint/typecheck/unit/integration по умолчанию и обязательную полную recheck после каждой correction.

- Выбрать достаточные проверки изменённого поведения до реализации. Команды брать из scripts/Gradle/CI назначенного worktree и готового packet; не переоткрывать уже известный способ запуска.
- Известные особенности этого проекта: классы `*IT` запускаются задачей `integrationTest`, задача `test` их исключает. В Windows PowerShell dotted Gradle property передавать единым quoted аргументом, например `"-Popenapi.snapshot.update=true"`. При правке fixtures брать уже работающий matcher/mock pattern; `value(null)` не заменяет явный null matcher. Эти уточнения получены из сбоев2026-09-21, повторно выяснять их не нужно.
- Новые тесты писать для сложного или значимого правила/регрессии без существующего покрытия: права, транзакции, потеря истории, гонки, идемпотентность, нетривиальные расчёты. Для базового CRUD/wiring/mapping, текста/CSS новые unit-тесты по умолчанию не нужны; существенный риск важнее внешней простоты операции.
- Для текущего Windows multi-project Gradle стенда используй уже проверенный флаг `--system-prop=org.gradle.java.compile-classpath-packaging=true`: без него downstream `compileJava` может не видеть классы успешно собранного shared-модуля (например, `shared-web-api.ErrorResponse`). Это параметр команды, не повод менять зависимости или запускать полный suite. Сохраняй отдельный лог повторного запуска после такой ошибки.
- Проверять наблюдаемый результат. Не дублировать одно правило на mock/unit/HTTP/DB уровнях без отдельного непокрытого риска. Не тестировать wording или внутреннюю последовательность вызовов как самостоятельную цель. Существующее подходящее покрытие использовать.
- Исправления собирать пакетом и запускать затронутый набор один раз. После PASS расширение/повтор только при конкретном изменении зависимости, дефекте или риске. Полный suite при нужной интеграции/release, не при каждой мелкой правке; обязательные CI gates сохраняются.
- UI: проверить изменённый flow и затронутые состояния/viewport/keyboard. Не проходить все темы/экраны для локального изменения. Backend: проверить изменённый endpoint/правило; реальная БД нужна когда доказывается её транзакционное поведение. Для сквозного результата mocks недостаточно.
- Повтор той же неудачи требует новой гипотезы. Минимальный fixture/harness fix; улучшения стенда вне задачи в backlog. Не ослаблять требование ради PASS, не начинать массовую чистку тестов.
- Heavy leases по RULES раздел4: один по умолчанию, два только при подтверждённой ёмкости и изоляции ресурсов. Лёгкие проверки разных worktrees параллельны. Чужие/production ресурсы не трогать. Логи не содержат секретов. Evidence: criterion/revision/command/exit/environment/log, один компактный summary.
- В итог пакета включить время/число запусков, причину каждого повторного PASS и расширения scope, исправления продукта отдельно от fixture/harness. Это учёт по существующим логам для docs/delivery-metrics.md, не повод запускать дополнительные проверки или писать инструментацию.
- Документация: scoped diff и нужные ссылки/синтаксис. Продуктовые tests/runtime не запускать. Не нанимать отдельного reviewer для простого безопасного документа.
