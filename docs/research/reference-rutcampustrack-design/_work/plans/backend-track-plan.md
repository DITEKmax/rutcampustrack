# План действий — RutCampusTrack

Собран под твои две цели: (1) навести порядок в бэкенде через аудит/чистку/рефактор, (2) сделать новый Vue-фронт из бумажных экранов. Плюс общий рабочий процесс.

---

## Сначала — честная оценка твоего проекта

Твой проект уже **сильно выше среднего** по чату. У тебя есть то, о чём там только мечтают: contract-first, ~234 теста, Testcontainers, ArchUnit, jacoco-ratchet, RFC 9457, Flyway-дисциплина, пройденные аудиты M01–M16, CI/Trivy/Gitleaks, observability (OTel/Grafana). Это не «навайбкоженная поделка» — это инженерная система.

**Что это значит для тебя:**
- Тебе НЕ нужны «магические» вайбкод-скиллы. Тебе нужны **дисциплинирующие** инструменты (аудит, рефактор, ревью) — они в пакете.
- Главный риск — не «нет качества», а **энтропия при дальнейшем развитии**: новые фичи размывают contract-first, растут god-классы, копятся мелкие IDOR. Аудит + care-refactoring это ловят.
- Твой `CLAUDE.md` уже отличный. `AGENTS.md` из пакета его дополняет для Codex (Codex читает `AGENTS.md`, Claude — `CLAUDE.md`).

## Часть A. Бэкенд: аудит → чистка → рефактор

### Шаг 0. Подготовка (один раз)
1. Положи `AGENTS.md` из пакета в корень репо (Codex будет его читать).
2. Установи скиллы:
   ```bash
   for s in backend-audit-spring care-refactoring-java loop-code-review; do
     mkdir -p ~/.claude/skills/$s && cp skills/$s.md ~/.claude/skills/$s/SKILL.md
   done
   ```
3. Заведи ветку под работы по чистке: `git checkout -b cleanup/audit-round-1`.

### Шаг 1. Аудит — по одному сервису за раз
Не аудируй весь монорепо разом (перегрузка контекста, галлюцинации). Порядок по риску:

1. **auth-service** (самый критичный — JWT, роли, IDOR).
2. **attendance-service** (fraud посещаемости, ПДн, конкурентность отметок).
3. **academic / schedule** (бизнес-логика, данные).
4. **notification** (события, STOMP, MongoDB).
5. **api-gateway** (проксирование, RL, CSP).

Для каждого:
```
Сделай аудит через backend-audit-spring, scope: auth-service.
```
Получишь `_reports/auth-service/.../audit_master_summary.md` с приоритизированным списком.

**Дополнительно перед раскруткой** прогони `prompts/forensic-premortem.md` по auth + attendance — «злой» поиск дыр (но игнорируй любой «скор», смотри только подтверждённые находки).

### Шаг 2. Чистка/фиксы — по приоритету
Из отчётов бери CRITICAL/HIGH первыми (IDOR, authz, secrets, конкурентность). Для каждого бага:
1. Отладь через `prompts/root-cause-debug.md` (чинит корень, а не симптом, с production-wiring проверкой).
2. Пиши регрессионный тест, падающий до фикса (у тебя Testcontainers — используй `*IT`).
3. Закрывай изменение через `loop-code-review` (свежий ревьюер, лимит 3 раунда).

Сверяйся с уже закрытым: не трать время на то, что решено в M01–M16 (`docs/archive/report-before-v0.0.0/`).

### Шаг 3. Рефактор/наведение порядка
Когда критичное закрыто — прибирай код через `care-refactoring-java`:
```
Проведи care-refactoring, scope: attendance-service, найди god-классы и логику в контроллерах, вынеси в application/domain слой. Не меняй контракты и поведение.
```
Правила скилла не дадут сломать contract-first / enum-as-string / изоляцию доменов и остановятся на «No changes needed», если рефактор не нужен.

**Ритм:** не рефактори то, что работает и понятно. В чате прямо предупреждали — рефактор ради рефактора рождает +тысячи строк и оверинжиниринг. Бери 1–3 узких скоупа за раз.

### Правило экономии лимитов (из чата)
- Не запускай тяжёлый аудит/ревью на мелочи. Мелкие правки — `Direct` режим.
- Дорогой мультимодельный аудит (несколько школ моделей) — только для самого критичного (auth). Для остального хватит одного сильного аудитора.
- «Качество / быстро / дёшево — выбери два». Для auth выбирай качество, не экономь.

## Часть B. Фронтенд: бумага → wireframe → Figma → адаптив → Vue

Ты описал точный пайплайн — оформляю его по шагам.

### Шаг 1. Экраны → wireframe
1. Установи скилл:
   ```bash
   mkdir -p ~/.claude/skills/screens-to-wireframe && cp skills/screens-to-wireframe.md ~/.claude/skills/screens-to-wireframe/SKILL.md
   ```
2. Сфотографируй/отсканируй бумажные экраны, загрузи.
3. Запусти:
   ```
   Перенеси эти экраны в wireframe через screens-to-wireframe. Роли: student/headman/teacher/admin. Привязывай данные к нашим *-api-contract.
   ```
   Получишь структуру каждого экрана (зоны, компоненты, состояния loading/empty/error, навигация, данные из реального API) + `figma-spec.md`.

Ключевая ценность этого шага: он заставит тебя описать **состояния** (loading/empty/error) и **роли** — то, что на бумаге обычно не нарисовано, но составляет половину фронта.

### Шаг 2. Figma
- Перенеси wireframe в Figma по `figma-spec.md`: frame-структура экранов, переиспользуемые компоненты → Figma-компоненты, состояния → variants.
- Отредактируй, определи реальные брейкпоинты (mobile-first — у тебя PWA важна).
- Сделай адаптивы, потом раскрась (цвета/типографика/токены). Это ручной/дизайнерский этап — ИИ помогает структурой, не рисует за тебя финальный визуал.
- Опционально: `claude.ai/design` для быстрых итераций структуры, `21st.dev`/`reactbits.dev` — референсы компонентов.

### Шаг 3. Figma → Vue-код
1. Установи скилл:
   ```bash
   mkdir -p ~/.claude/skills/vue-frontend-build && cp skills/vue-frontend-build.md ~/.claude/skills/vue-frontend-build/SKILL.md
   ```
2. Заведи новый Vue-проект в `frontends/` (например `frontends/vue-app`, Vite + Vue 3 + TS).
3. Настрой типы из бэка: `openapi-typescript` (как уже сделано для web-panel/pwa) — не пиши DTO руками.
4. Реализуй по одному экрану:
   ```
   Реализуй экран "Расписание студента" через vue-frontend-build по Figma-спеке. Стили внутри компонентов, layout — снаружи. Ошибки в формате RFC 9457.
   ```

**Главное правило фронта (из чата, named-боль Сухарева):** визуальные стили живут ВНУТРИ компонента, снаружи только layout через wrapper и семантические пропы. Скилл это форсит — не дай агенту хардкодить стили на месте вызова, иначе получишь «вермишель», о которой жаловались.

### Про смешение стеков
У тебя уже web-panel (Angular), pwa/mini-app (React). Новый — Vue. **Не смешивай паттерны** между ними. Реши заранее: новый Vue-фронт заменяет какой-то из существующих или дополняет? Если заменяет — спланируй миграцию (что переносишь, что выключаешь), а не «два фронта параллельно навсегда».

## Часть C. Общий рабочий процесс и развитие

### Ежедневный цикл разработки
1. Новая задача → новое окно/сессия агента (не тащи контекст между несвязанными задачами — совет из чата).
2. Классифицируй: Direct / Investigation / TDD-first (см. `AGENTS.md`).
3. Для нетривиального — сначала тест, потом код (у тебя уже TDD-культура — держи её).
4. Закрывай через `loop-code-review`, коммить атомарно (Conventional Commits — у тебя уже CHANGELOG).
5. Не давай агенту «заодно отрефакторить соседнее» — out-of-scope в отдельную задачу.

### Раскрутка (ты упомянул «раскручивать»)
- Технически ты готов. Перед публичным ростом — прогони `forensic-premortem` по auth+attendance (ПДн студентов + fraud посещаемости — твои главные риски).
- ФЗ-152 (у тебя ru-проект, вуз, ПДн студентов): это отдельная юридическая тема. Есть чеклист-скилл fz-compliance из прошлых партий, НО — его юр-факты проверяй у живого юриста, не доверяй .md. Локализация БД в РФ, уведомление РКН, согласия — это уже про твой прод.
- Продукт/GTM важнее кода на этом этапе (мысль из чата): у тебя сильная техника, дальше вопрос — кто пользователи, как привлекаешь, чем отличаешься. Код уже не бутылочное горлышко.

### Развитие себя как инженера
- Ты уже пишешь на уровне выше чата. Чтобы расти дальше — вглубь: устройство систем (nand2tetris/SICP из `01_LINKS.md`), проектирование под нагрузку, ML/рекомендации (если посещаемость/аналитика будут расти).
- Мультимодельность как навык: держи под рукой 1-2 сильные модели + возможность аудитить чужой моделью (разные «школы» ловят разные баги).
- Веди `docs/` дисциплинированно (у тебя уже отлично) — это твоя реальная память, не «второй мозг» в обсидиане (который в чате единогласно назвали тратой токенов).
