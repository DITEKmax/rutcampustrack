# Измеримая готовность RutCampusTrack

Решение владельца 2026-09-20: готовность считать по Job Stories, экранам и целевому объёму сервисов. Этот документ определяет методику, не объявляет новую оценку готовности. Прежние приблизительные 45% и диапазоны ролей не являются измеренным baseline.

## Источники и единица учёта

- [job-stories.yaml](job-stories.yaml): 147 записей stories на 2026-09-20, stable IDs и роли. Canonical copied source — [knowledge/job-stories.md](../research/reference-rutcampustrack-design/knowledge/job-stories.md). Это подготовительный реестр 06.09, его delivery_status не считается актуальной приёмкой кода.
- [backend-delta.yaml](../implementation/backend-delta.yaml): 175 request IDs, отдельный backlog доработок. [story-backend-map.yaml](../implementation/story-backend-map.yaml) содержит связи; reconciliation candidates не выдавать за подтверждённые связи. 147+175 не равно322 независимым функциям.
- Экран: принятый Screen ID + целевой клиент/роль, со ссылкой на актуальный design packet/Figma. Повторные картинки, состояния и размеры одного экрана не отдельные готовые экраны. Число физических Figma nodes не число пользовательских страниц. Источники см. SOURCE-MAP ниже.
- Сервис: конечный перечень требуемых операций/инвариантов из историй, request IDs и принятых решений. Включить чтение/изменение/права, нужную межсервисную цепочку, события/восстановление и обязательные эксплуатационные требования. Не оценивать по числу классов/endpoints.

Текущие решения владельца накладываются на исходные реестры: отменённые требования исключаются только со ссылкой на отмену; заменённые считаются один раз; новые добавляются отдельной строкой. Например, исходный текст массового создания пользователей не возвращает отменённую владельцем массовую операцию. Пропущенные/неразобранные требования нельзя молча вычитать из знаменателя.

## Строка delivery matrix

Минимальные поля: `id`, `kind` (story/screen/service-capability/operations), `role`, `service`, `source_ref`, `release_scope`, `superseded_by`, `criteria`, `implementation_revision`, `changed_files`, `evidence_ref`, `status`, `blocker`, `updated_at`.

Статусы: `unassessed` (ещё не сверено), `not-started`, `in-progress`, `source-ready`, `integrated`, `accepted`, `blocked`, `excluded` (только с решением). Не заполнять unassessed как not-started и не приписывать accepted по наличию теста. Accepted означает выполненные критерии в целевой интегрированной версии и достаточное доказательство пользовательского результата; не требует нового автоматического теста для каждой строки.

Матрица ведётся по существующим IDs, без повторного переписывания требований. Обновлять затронутые строки при завершении задачи; уже имеющиеся evidence связывать без новых прогонов. Полную инвентаризацию не превращать в блокирующую кампанию перед продолжением продукта. До сверки показывать unknown, а не угадывать статус.

## Формулы

- Готовность историй роли = `accepted active stories / all active release stories ×100%`.
- Готовность экранов = `accepted screen-client rows / all required release screen-client rows ×100%`. Рядом можно показать «визуально реализовано», но оно не заменяет интеграцию API/прав/нужных состояний.
- Готовность сервиса = `accepted required capabilities / all required release capabilities ×100%`. Список capabilities фиксируется до оценки; не дробить выполненное ради увеличения процента.
- Всегда показывать X/Y, версию знаменателя, сколько unassessed и blocking requirements. Unknown остаются в утверждённом знаменателе; при неизвестном полном знаменателе писать «оценка пока не рассчитана». Частичному коду не присваивать произвольные0.5 или0.9.
- Это доля завершённых пунктов, не доля затраченного/оставшегося времени. Один сложный открытый пункт может занимать больше времени, чем несколько завершённых.

Истории/экраны/сервисы — разные срезы одной работы. Их нельзя складывать или усреднять как независимые задачи. Общий production показатель — по одному фиксированному release checklist: пользовательские stories и отдельные недублирующие эксплуатационные пункты. Без полного checklist общий процент не публиковать. Не закрытые обязательные права/backup restore/migration/recovery/release gates явно запрещают объявлять production-ready даже при высоком проценте.

## Публикация статуса

В summary: закрытые IDs за итерацию → наблюдаемый результат → конкретные файлы → X/Y по затронутому срезу → следующий открытый пункт. Количество PASS, assertions, строк кода, чатов, сборок и review не влияет на формулу. Сбой fixture/harness — стоимость исправления, а не новая функция.

После каждой продуктовой итерации обязательно публиковать одну и ту же таблицу: accepted / partial / unknown / excluded по ролям, закрытые ID за итерацию, изменение числителя и знаменателя с причиной. Partial не получает произвольный коэффициент. Если unknown остаётся, accepted/active — подтверждённый минимум, а не точная оценка всей фактической реализации. Частичный объём и unknown показывать рядом. Новые результаты обновляют строки существующей матрицы; не проводить полный аудит/прогон заново ради очередного отчёта. Общая production-ready оценка отдельно требует release/operations checklist, не подменяется этим минимумом.

Старый [implementation/readiness.md](../implementation/readiness.md) описывает подготовительные этапы09–10 от06.09. Он не является текущей production матрицей и не должен подменять описанный расчёт.
