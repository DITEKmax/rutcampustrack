# Промпты: консолидация реестра (этап 1.5)

Реестр — **248 КБ**. В один чат консолидация не влезет: 248 КБ ≈ 62k токенов, плюс 30 спек экранов по 15–27 КБ. Поэтому дробим на 5 чатов.

**Порядок строгий** — каждый следующий работает с результатом предыдущего.

---

## Перед началом: перенастроить базу знаний

Этап wireframe закончен, база знаний должна поменяться.

**Убрать из знаний:**
- `screens-to-wireframe.md` — методика разбора больше не нужна
- `job-stories.md` (80 КБ) — сверка со сценариями сделана, лежит в спеках
- `COMPONENT_REGISTRY.md` — 248 КБ будет душить каждый чат, прикладываем вручную там, где нужен

**Оставить:**
- `PROJECT_CONTEXT.md`
- `api-digest.md`
- `A11Y_REQUIREMENTS.md`

**Инструкции проекта:** замени раздел «Текущий этап» на:

```
## Текущий этап — консолидация (этап 1.5)

Wireframe десктопа 1920 завершён: 30 экранов, 4 роли.
Сейчас сводим реестр компонентов: убираем дубли, разводим конфликты имён,
проставляем финальное владение shared / domain / local.

Не разбирай экраны заново — спеки готовы и являются источником правды.
Не рисуй визуал, не пиши код.
```

## Чат A — «Сжатие реестра»

**Прикрепить:** только `COMPONENT_REGISTRY.md`. Больше ничего — файл на 248 КБ должен быть единственным крупным вложением.

```
Реестр компонентов разросся до 248 КБ за 7 чатов разбора экранов.
Он должен быть справочником имён, а стал вторым описанием экранов:
в него утекли подробности, которым место в спеках экранов.

Задача этого чата — сжать реестр, НЕ теряя информацию о различиях.

ЧТО СДЕЛАТЬ

1. Приведи реестр к компактному виду. Для каждого компонента оставь только:
   имя, назначение одной строкой, ключевые семантические пропы,
   владение (shared / domain / local), экраны где используется,
   статус (подтверждён / [кандидат на консолидацию с <имя>]).
   Всё остальное — подробные описания данных, состояний, поведения —
   выкидывай: это есть в спеках экранов.

2. Отдельным файлом собери инвентарь консолидации: все пометки
   [кандидат на консолидацию], сгруппированные по парам/группам.
   Для каждой группы: какие компоненты, на каких экранах, и что известно
   об их различиях из текущего реестра. Не решай, сводить или нет —
   только собери и опиши.

3. Отдельным списком — конфликты имён: разные компоненты с одинаковыми
   или почти одинаковыми именами, и одинаковые сущности под разными именами.

4. Скажи, какой объём получился и сколько компонентов осталось.

ЧЕГО НЕ ДЕЛАТЬ
- Не своди компоненты в этом чате — только инвентаризация.
- Не выдумывай компоненты, которых нет в реестре.
- Не удаляй компонент, если не уверен, что он дубль, — помечай.

ВЫДАЙ ФАЙЛАМИ
- COMPONENT_REGISTRY.md — сжатая версия
- consolidation-inventory.md — инвентарь кандидатов и конфликтов имён
```

**После чата:** архивируй старый реестр в `01-wireframes/registry/archive/registry-before-consolidation.md`, сжатый положи на его место.

## Чат B — «Семейство: Главная»

**Прикрепить:** сжатый `COMPONENT_REGISTRY.md`, `consolidation-inventory.md`, и спеки `101-student-home.md`, `111-headman-home.md`, `121-teacher-home.md`, `131-admin-home.md`.

```
Консолидируем семейство «Главная» — четыре экрана, по одному на роль:
ПК-101 (student), ПК-111 (headman), ПК-121 (teacher), ПК-131 (admin).

Спеки этих экранов приложены — они источник правды. Реестр и инвентарь
кандидатов тоже приложены.

ЗАДАЧА
По каждому компоненту, встречающемуся более чем на одном из этих экранов,
вынеси решение:

- ОДИН КОМПОНЕНТ — если различия сводятся к семантическим пропам
  (variant / size / state) или к разным данным при одинаковой структуре.
  Дай финальное имя, перечисли пропы, укажи владение shared или domain.

- РАЗНЫЕ КОМПОНЕНТЫ — если различаются структура, поведение или набор действий.
  Объясни чем именно, дай различающиеся имена, чтобы больше не путались.

- ОБЩИЙ ПРИМИТИВ + ОБЁРТКИ — если у них общее ядро, но разное обрамление.
  Опиши, что уходит в примитив, что остаётся в ролевых обёртках.

Решение принимай по спекам, а не по совпадению имён. Одинаковое имя
на разных экранах не означает один компонент, разные имена не означают разные.

ОСОБО ПРОВЕРЬ
- Каркас страницы: AppShell, AppHeader, MainNav, ProfileMenu, RoleSwitcher.
  У них у всех должно быть одно решение на весь продукт — это самый
  shared из shared. Если между ролями разошлись, сведи.
- Виджеты дашбордов: у student есть готовый dashboard-эндпоинт,
  у остальных ролей его нет. Проверь, не породило ли это ложных различий
  на уровне компонентов при одинаковой визуальной задаче.
- Селектор контекста преподавателя (группа/предмет) — его нет у других ролей.
  Убедись, что он не размазан по чужим компонентам.

ВЫДАЙ
1. Таблицу решений: было (имена по ролям) → стало (финальное имя) → тип решения
   → обоснование одной строкой.
2. Блок «Обновления для COMPONENT_REGISTRY.md» — только дельта.
3. Список вопросов, которые не смог решить по спекам, — я отвечу.

Не переписывай спеки экранов. Если решение требует правки спеки —
отметь это списком, править буду отдельно.
```

## Чат C — «Семейство: Посещаемость»

**Прикрепить:** актуальный реестр, инвентарь, спеки `102`, `112`, `122`.

Промпт тот же, что у чата B, с заменой первого абзаца:

```
Консолидируем семейство «Посещаемость» — три экрана:
ПК-102 (student), ПК-112 (headman), ПК-122 (teacher).

ОСОБО ПРОВЕРЬ
- Это семейство расходится сильнее всего: у студента личные записи и отметка,
  у старосты управление парами и обработка запросов, у преподавателя журнал

- Табличные компоненты: журнал преподавателя и списки старосты могут иметь
  общее ядро таблицы при разном наполнении. Проверь, стоит ли выделять примитив.
- Компоненты статусов отметки (+ / н / у) — они должны быть общими на весь
  продукт, включая статистику. Проверь, не расплодились ли.
- Пакетные операции (marks/batch) есть только у части ролей — убедись,
  что это отражено пропами, а не копией компонента.
```

## Параллельно: чат «Backend requests»

Не зависит от консолидации, можно вести одновременно.

**Прикрепить:** все файлы из `02-backend/raw/` + `api-digest.md`.

```
Собери из приложенных файлов единый backend-requests.md.

СТРУКТУРА
1. Сводка: сколько запросов всего, по сервисам, по типам
   ([предложение по бэкенду] / [уточнение по контракту]).
2. По каждому сервису (auth, academic, schedule, attendance, notification):
   - нужны новые эндпоинты: что, зачем, какие экраны блокирует;
   - нужны новые поля в существующих ответах;
   - нужны уточнения по контракту (есть поле или нет).
   Дубли из разных чатов объединяй, указывая все экраны-источники.
3. Приоритеты: что блокирует реализацию экранов, что улучшает,
   что косметика.
4. Отдельный раздел — фактура к решению о транспорте:
   таблица «экран → сколько запросов нужно → что запрашивается зря →
   где N+1 на клиенте». Отсортируй по тяжести.

Не предлагай решение REST vs GraphQL — только собери фактуру.
Решение принимаю я в отдельном разговоре.
```

Результат этого чата принеси в стратегический чат — обсудим GraphQL предметно.

## Что можно делать параллельно

| Трек | Зависит от консолидации? | Когда |
|---|---|---|
| Консолидация A→B→C→D→E | — | критический путь |
| Сводный backend-requests | нет | параллельно |
| Решение REST vs GraphQL | нет (нужен backend-requests) | после сводного файла |
| Бренд-направление: концепция, мудборд, 2–3 варианта | нет | параллельно, это про позиционирование |
| Брендбук v2 (компоненты) | **да** | только после E |
| `DESIGN.md` и Stitch | **да** | только после брендбука |

Бренд-направление — единственное, что можно начать хоть сейчас: оно про аудиторию, тон и визуальную идею, а не про список компонентов.
