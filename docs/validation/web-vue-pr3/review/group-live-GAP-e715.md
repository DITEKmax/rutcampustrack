# Group deletion: natural idle withdrawal — source gap подтверждён

**P2: на Root `e715bab97106c6f3b9d24f78d96c1cbc2d4b70ba` нет гарантированного пути, который сам уберёт уже открытую Student group page и обновит Teacher group projection после удаления группы на WEB/PWA/TMA.** Сервер отзывает доступ; уже загруженный DOM может оставаться до другого действия/запроса. Это новый незакрытый критерий доставки, не повторная оценка20 принятых backend cases и не причина выполнять destructive case ради обнаружения известного missing signal.

## Реальная цепь и место разрыва

1. `AuthGroupDeletionParticipant.java:130–147` очищает `active_role_grant_id` и повышает `session_version` **только** sessions, выбравших grant удаляемой группы, удаляет grants с exact `group_id`, пишет существующий identity catalog snapshot. Notification/outbox fact в этой transaction не создаётся. Важное уточнение: global `roles_version` не повышается; `V17__final_group_deletion.sql` явно сохраняет unrelated role sessions, а `append_auth_identity_catalog_snapshot` пишет каталог без RV bump. Поэтому Teacher/другая группа того же пользователя не должны терять свою действующую сессию.
2. `GroupDeletionStore.java:315–359` после canonical удаления публикует только `group.updated` и `dashboard.invalidated`. Первый обрабатывается cache eviction (`GroupCacheInvalidationListener:19–24`) и dashboard observation. Notification `EventConsumer:78–98` направляет dashboard hint только `/topic/admin/dashboard`; неизвестные catalog types игнорирует. `NotificationCatalog:383–402` знает `group.membership.changed`, headman/assistant/admin access facts, **не** `group.updated`. Group deletion не вызывает существующий personal notification publisher.
3. Существующий полноценный personal путь есть: accepted catalog event → audience/history persistence → after-commit `NotificationHistoryEventProcessor:141–165` → `/topic/user/{id}` hint; для поддержанных types возможен WebPush. Но membership event сейчас означает TRANSFERRED/old+new group (`AcademicPersonalNotificationEvent:15–21`), а не удаление. Его audience добавляет **только текущего ACTIVE STUDENT** (`NotificationAudienceResolver:181–184`): после удаления grant такого recipient может уже не быть; Teacher вообще не включается. Готовых `user.updated`, `subject.assignment.changed` или `authority_changed` types в NotificationCatalog нет. Нельзя выдать удаление за transfer или просто предположить появление personal hint из `group.updated`.
4. Даже добавление hint само не завершает retirement. `WsSessionAdmissionOutboundInterceptor:32–36,64` readmits только outgoing MESSAGE, heartbeat проходит без readmission. На denied authority `WsSessionBindingRegistry:143–155` закрывает socket и не доставляет MESSAGE. Здоровый молчащий socket вообще не обязан сделать этот read. Клиент `notifications-realtime.ts:219–221` при close только очищает subscriptions; при следующем ticket403 `:101–106` не вызывает owner refresh/reconciliation, а generic retry `:157–186` сохраняет старую authority. Поэтому «добавить событие/Notification» без client boundary correction недостаточно.
5. WEB `app/live.ts:74–95` делает bounded authority read только при active ADMIN. Student и Teacher получают domain refresh от пришедшего realtime/browser invalidation (`student-state.ts:53–72`, `teacher-state.ts:72–73`); естественного обязательного idle trigger нет. PWA/TMA realtime `App.vue:912–915` / `:767–770` меняет notification revision/unread, а не session authority или active domain query. `realtime-revision` передаётся только NotificationsScreen (`PWA:2287`, `TMA:1464`), не TeacherFeatureOwner/StudentFeatureOwner. У Teacher owner нет realtime prop, его reload watch зависит от api/semester/date/profilePort (`TeacherFeatureOwner.vue:190–215`). Foreground/online admission существует, но не заменяет событие для уже видимой молчащей страницы. PWA service-worker push handler (`public/sw.js:136–161`) показывает notification, не отзывает открытую page authority.

Следовательно реальный сценарий «Student смотрит ранее загруженные group data; группа удалена; больше запросов/сообщений/focus нет» оставляет cached private view без гарантированного retirement. Protected HTTP/WS admission при следующем эффекте остаётся fail-closed; server authorization bypass этим finding не утверждается.

## Минимальный совместимый выбор до actual delete

Рекомендуемый путь — существующий **group.updated + per-user socket invalidation**, с двумя локальными client bridges. Это конкретное предлагаемое additive изменение, а не утверждение, что такая поддержка уже работает:

1. В `GroupDeletionStore` перед удалением joins сохранить distinct exact affected users: eligibility user IDs, assistants student IDs, `assignments.teacher_id` и legacy `teacher_subject_groups.teacher_id`. Текущее `affectedUsers` включает лишь eligibility/assistants и используется для caches; Teacher assignment recipients нужно добавить. Передать frozen recipient IDs в уже существующий `GroupUpdatedEvent`/outbox одной canonical transaction; optional metadata согласовать в существующем `event-schemas/group.updated.json`. Нельзя искать recipients после удаления joins.
2. В `Notification EventConsumer` добавить специальную invalidation-ветку существующего `group.updated` по аналогии с dashboard: validated source/event/version, idempotency и exact supplied recipient set → существующий `/topic/user/{id}` hint. Не подменять событие ложным history/TRANSFERRED fact и не ослаблять outbound admission. Существующий event type/transport достаточны; нового websocket protocol или framework не нужно. Это branch до catalog history processing; подходящего готового Catalog type для Teacher-removal нет.
3. В shared `notifications-realtime.ts` связать transport denial/close с generation-bound owner re-admission. Retired Student не получит hint: outbound guard закроет его socket; client должен прочитать/reconcile текущую authority, а typed role403 ticket не должен бесконечно оставлять старый owner. Один normal refresh/re-auth с fences допускается для восстановления profile; repeated business commands запрещены. WEB/PWA/TMA уже имеют owner primitives; TMA простой `getProfileFor` сам не повышает generation на changed authority, поэтому adapter обязан использовать существующую authority identity/invalidation boundary.
4. Для still-admitted Teacher hint должен обновить **domain projection при неизменной Auth session**. WEB уже вызывает `useWebLiveRefresh` у Teacher/Student. В PWA/TMA `App.vue` нужен локальный bridge от realtime hint к active feature; shared `TeacherFeatureOwner.vue`/`StudentFeatureOwner.vue` должны получить scoped invalidation/reload revision либо существующий command-agnostic refresh callback. Проверить actual active catalog/list/detail query, включая удалённый selected group; notification unread refresh сам этого не делает. Не менять Teacher auth generation/other-group session ради domain refresh, не терять unknown mutation references и не повторять writes.

Минимальный inventory для назначения автора: Academic `GroupDeletionStore` + `GroupUpdatedEvent`/существующий schema; Notification `EventConsumer`; shared `notifications-realtime`; WEB `app/live` adapter при необходимости; PWA/TMA host callbacks и общие Student/Teacher feature owner adapters. Recipient/admission/feature ownership должны остаться едиными. Альтернативный bounded auth snapshot read сам закрывает лишь retired Student, **не обновляет Teacher domain при неизменной authority**; перенос5s на всех пользователей этой задачей не обоснован.

Изолированный group PREP10 не содержит Notification/Mobile BFF по Root packet; main Notification другого realm не является квалификацией этого пути. Для настоящего socket signal нужна своя realm Notification с существующей own Mongo DB/RS и квалифицированным source-identical c57 JAR; дополнительный Java ресурс (~415MB по Root packet) требует отдельного runtime resource admission. Это PREP dependency, а не выполненный запуск reviewer. Fake transport не доказывает actual socket delivery. WEB-only результат нельзя называть PWA/TMA PASS; WebPush delivery остаётся отдельной осью и не подменяет открытую page invalidation.

До actual destructive case нужен scoped code choice/fix существующей lifecycle. Затем достаточно предусмотренного конечного пользовательского наблюдения с открытой целевой страницей и retained other-role evidence; закрытые20 backend cases повторять не требуется. Reviewer выполнил только source reads/Git HEAD, без runtime/private/API/browser/tests, product writes или children; создан только этот отчёт. Requested Sol6.1/high; served-model telemetry недоступна.
