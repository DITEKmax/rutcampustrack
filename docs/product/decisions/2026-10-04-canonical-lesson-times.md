# Единое время пар — решение владельца 2026-10-04

Источник: прямое решение владельца в frontend чате, переданное backend оркестратору, и ответ владельца здесь о существующих тестовых данных.

## Принято

Единая серверная неизменяемая таблица задаёт номер пары и московское время:

| Номер | Начало | Конец |
|---|---|---|
| 1 | 08:30 | 09:50 |
| 2 | 10:05 | 11:25 |
| 3 | 11:40 | 13:00 |
| 4 | 13:45 | 15:05 |
| 5 | 15:20 | 16:40 |
| 6 | 16:55 | 18:15 |
| 7 | 18:30 | 19:50 |
| 8 | 20:00 | 21:20 |

Время не выбирается отдельно для каждой новой пары. Одна enum/value source на сервере используется при создании шаблонов, разовых занятий и новых целевых занятий при переносе. Клиенты получают каталог по API и времена конкретного занятия в существующих ответах; копии таблицы в клиентах и других сервисах не требуются.

## Существующие данные

Владелец подтвердил, что все нынешние записи являются тестовыми, и разрешил привести существующие занятия к этой таблице. Ограничение предыдущего предложения «существующие занятия сохранить без нормализации» отменено только для нынешних тестовых данных.

Если время пар впоследствии изменится, все будущие занятия должны получить новые значения. Время проведённых занятий реального использования сохраняется для истории. Предложение полностью убрать поля времени из БД было вариантом реализации, а не обязательным требованием: сохраняются снимки, необходимые планировщику, событиям и истории, при едином источнике новых значений.

## Границы исполнения

Нормализация выполняется только адресно на согласованном локальном тестовом стенде, после подготовки проверки источника, точного inventory/backup/rollback и атомарного плана. Это не разрешение на production migration, удаление записей, постоянное отключение immutable guards или произвольное редактирование истории. До фактического выполнения существующие записи не считаются нормализованными.

Новое правило не изменяет московскую часовую зону, согласованное окно геоотметки или авторизацию. Принятые ответы идемпотентных запросов остаются неизменными.

## Состояние

Правило принято. Каталог и каноническое время новых записей/переносов интегрированы в main `219146079e9e8d4180e92f408f8e7dc3231932c7`; независимое review, компиляция и выбранные проверки прошли. Новый Schedule JAR подключён к постоянному стенду, защищённый API подтвердил восемь интервалов. Readonly inventory: одна пара с правильным временем, ноль шаблонов и ноль расхождений. Переписывать текущие записи не требуется; DML и отключение guard не выполнялись.

Для нынешних тестовых данных сохранён узкий local maintenance operator: точный inventory и приватный backup, остановленные приложения этого стенда, одна транзакция с блокировками и временным изменением состояния только `lessons_history_guard_trg`. Исходное состояние guard восстанавливается до COMMIT; ошибка откатывает и строки, и DDL. Source review и readonly Inspect приняты; реальные Normalize/Rollback не выполнялись, потому что изменять нечего. Это не production tool или постоянный механизм обхода защиты истории.

В operator реализованы InspectFuture/NormalizeFuture/RollbackFuture: source3c61ad99 → main ed2bd567, независимое affected review и изолированная PostgreSQL проверка обновления/отката PASS. Режим меняет current planned занятия, для которых старое и новое начало строго будущие по закреплённому московскому cutoff и текущим часам БД; прошлые, начавшиеся, проведённые, отменённые и прежние поколения не меняются. Активные шаблоны обновляются лишь при matching неистёкшей creation fence; создаваемые занятия и история не перегенерируются. Для меняемых семестров root подтверждает отсутствие архивного запрета в pinned writableSemesterIds.

Реальный readonly InspectFuture на полной схеме текущего стенда PASS: расхождений нет, mutation не выполнялась. Ненулевое обновление и rollback проверены на изолированном SQL fixture. Эта операция запускается отдельно при смене серверной таблицы, с inventory/backup, остановленными писателями и короткой границей времени; самостоятельно при старте сервиса не запускается. Поздний rollback после истечения cutoff или начала пары не допускается. Автоматическая production migration не входит в это разрешение.
