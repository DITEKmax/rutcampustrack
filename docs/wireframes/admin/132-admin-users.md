### Сверка со сканом

- **ЗЕЛЁНОЕ:** «Создать пользователя», поле поиска, панель фильтров.
- **ЖЁЛТОЕ:** таблица пользователей; три блока «Если создают админа / препода / студента».
- **КРАСНОГО на экране нет вовсе** — единственный экран роли без фиксированных зон.
- **НЕОКРАШЕНО:** `MainNav`.
- **Не нарисовано, добавлено при разборе:** `<h1>`, `Pagination`, `ExportButton` (решение владельца), все non-happy состояния.

**Как прочитал (двоякие места):**

1. **Таблица жёлтая, хотя это основное содержимое.** Читаю так: условен не сам блок, а **набор строк** — он определяется поиском и фильтрами, поэтому нарисована только шапка. Таблица присутствует на странице по умолчанию; при входе без фильтров показывается первая страница всех пользователей. Отвергнутое прочтение — «до ввода поиска данные не запрашиваются» (`no-context`, как на 122): оно давало бы пустой экран при входе, что противоречит цели «видеть всех пользователей».
2. **Прим. 2, «Так же можно удалить».** Читаю как **удаление роли** — симметрично «добавить роль» в том же предложении. Удаление самого пользователя — это архивирование (JS-ADMIN-04, soft delete), отдельный пункт меню. Перевод в другую группу — **третий самостоятельный пункт**, а не следствие удаления.
3. **Три жёлтых блока «Если создают …» — это одна форма в трёх состояниях**, а не три формы на странице одновременно. Выбор роли — первый шаг, он определяет состав полей.

**Красный ≠ без взаимодействия** — на 132 неприменимо, красных зон нет.

## 4. Потребности в данных

### 4.1 Список пользователей

**Нужно.** Сущность «учётная запись». Поля: логин, ФИО, **`roles[]` с собственным статусом у каждой роли**, группа для студенческой роли, начальный пароль с признаком происхождения, табельный номер для преподавательской роли, Telegram id. Фильтрация — **по колонкам** (роль, группа, статус, колонки-состояния), серверная, поверх пагинации. Поиск: полнотекстовый по логину, ФИО, табельному номеру, Telegram id — отдельным контролом. ⚠️ **Правка 02.08.2026 (Р-24):** эти поля **получают** свои колоночные фильтры наравне с остальными; поиск и фильтр колонки складываются через И. **Пагинация серверная.** Сортировка: набор колонок приходит с бэкенда (§0 чат 4).

**Требования к описанию колонок** (`table-filters.md` §5):

- `[предложение по бэкенду]` — **многозначные ячейки**: колонки «Роль» и «Статус» содержат несколько значений, строка подходит по **любому** из них (`matchAny`). Иначе фильтр «отчислен» не найдёт человека, у которого вторая роль активна.
- `[предложение по бэкенду]` — **парная зависимость**: фильтр «Статус» осмыслен только вместе с фильтром «Роль» → `enabledWhen: { column: 'role' }` в дескрипторе колонки, с текстовой причиной недоступности.
- `[предложение по бэкенду]` — **справочник групп** отдаётся отдельным источником (`optionsSource`) с поиском по подстроке и собственной постраничностью: значений сотни, в описание колонки они не помещаются и **из загруженной страницы не собираются** (§3.2 — иначе часть групп молча пропадёт из фильтра).

**Сейчас.** `GET /academic/users` — существует; описание не раскрывает ни фильтров, ни поиска, ни пагинации.

- `[уточнение по контракту]` — есть ли фильтры по роли / группе / статусу, полнотекстовый поиск и постраничная разбивка. **Симптом тревожный:** соседний `GET /academic/users/teachers` прямо помечен «без постраничной разбивки» — значит по умолчанию отдаётся весь набор.
- `[предложение по бэкенду] — блокирующее` — **роль должна быть массивом, и у каждой роли свой статус** (вариант Б, владелец). Модель «студент + флаг `is_headman`» не расширяется ни на четыре роли, ни на пороли статусы. Без этого колонки «Роль» и «Статус» не собираются, а карточки 131 не сходятся с таблицей 132.
- `[предложение по бэкенду]` — **человекочитаемое название группы приходит в самом ответе списка**, а не догоняется по id. Иначе N+1 на каждую страницу (довод тот же, что для рейтинга на 103, §0 чат 2). Id остаётся ключом связи, в интерфейс не выводится (правило владельца, чат 7).
- `[предложение по бэкенду] + аудит безопасности` — **начальные пароли всего вуза в одном ответе списка.** Решение чата 5 («пароль виден, пока не сменён») принималось для 25 студентов одной группы. ~~Предлагаю: в списке — только признак «пароль не сменён», значение — по явному действию строки.~~ ✏️ **Отменено 10.08:** решение владельца — значение показывается до смены, отдельного действия «Показать» нет. Вопрос объёма выдачи остаётся к бэкенду, но на интерфейс не влияет. Прим. 1 скана 121 («не сразу давать данные») указывает туда же.

### 4.2 Создание пользователя

**Нужно.** Роль → набор полей: админ (ФИО, права, Tr id) · преподаватель (ФИО, табельный номер, Tr id опционально) · студент (ФИО, группа, Tr id). **Логин и пароль генерирует система**, в форме их нет. Группа выбирается по человекочитаемому названию из существующих, передаётся id.

**Сейчас.** `POST /academic/users` — существует.

- `[предложение по бэкенду] — блокирующее` — **новый алгоритм генерации логина** (решение владельца, чат 7): уникальный логин из данных человека, направление — фамилия и имя латиницей + последние 4 цифры Telegram id или табельного номера. **Фронт логин не составляет и не проверяет** — только показывает результат. Открытые части алгоритма, которые обязан закрыть бэкенд:
  - **источник цифр по ролям.** У преподавателя Tr id опционален → источник табельный номер; у студента табельного номера нет → источник Telegram id, значит **Tr id при создании студента обязателен** (на скане у студента он без пометки «опционально» — совпадает). У аккаунта только с ролью админа источник — Tr id;
  - **правило разрешения коллизий** (однофамильцы с одинаковым хвостом);
  - **правило транслитерации** и что делать с не-латинизируемыми именами;
  - **неизменность логина** при последующем добавлении ролей и смене табельного номера или Telegram id.
- `[уточнение по контракту]` — возвращает ли операция сгенерированные логин и пароль и в каком виде они попадают к администратору.
- `[предложение по бэкенду]` — **каталог прав администратора** («как для помошников старосты») в API отсутствует: `assistants/{id}/permissions` описывает права помощника. Нужен собственный перечень, приходящий как данные. Состав решается в выделенной сессии по правам помощника — одним заходом с ней.
- `[уточнение по контракту]` — Telegram id вводится администратором вручную или подтверждается ботом? От этого зависит, валидируемое это поле или доверенное; а поскольку из него берутся цифры логина — ещё и момент, когда логин вообще может быть сгенерирован.

### 4.3 Правка, добавление и снятие роли

| Ситуация | Путь | Итог |
|---|---|---|
| Правка ФИО, табельного номера, Tr id | `PATCH /academic/users/{id}` изменёнными полями | точечное изменение |
| Добавление роли существующему человеку | **отдельная операция** | заполняются только недостающие поля (прим. 2): у студента, ставшего преподавателем, ФИО уже есть — нужен табельный номер |
| Полная перезапись карточки | `PUT /academic/users/{id}` | **опасен**: затрёт поля ролей, которых нет в открытой ветке формы |

- **Ответ на вопрос «PUT против PATCH»:** `PATCH` — точечные правки; `PUT` **фронтом не используется**; роли меняются собственной операцией.
- `[предложение по бэкенду]` — явные операции **«добавить роль» и «снять роль»**. `PUT` для этого не годится по построению: он требует полного объекта, а форма видит одну ролевую ветку.
- `[вопрос к бэкенду]` — что происходит с данными снятой роли. Особый случай: снятие роли старосты у действующего старосты — по JS-ADMIN-07 помощники предыдущего автоматически деактивируются.

### 4.4 Перевод студента в другую группу

**Нужно.** Целевая группа (выбор по названию, передача id), **обязательная причина**, фиксация даты в истории группы (JS-ADMIN-03).
**Сейчас.** `POST /academic/users/{id}/transfer` — существует. `[уточнение по контракту]`: принимает ли причину и пишет ли историю.

| Что переносится | Что остаётся | Что показать до подтверждения |
|---|---|---|
| членство; будущие пары нового расписания | посещаемость за период членства в старой группе | сколько отметок остаётся в старой группе и с какой даты действует новая |
| — | тикеты, поданные в старой группе (их разбирал прежний староста) | количество открытых тикетов и что с ними станет |
| — | **роль старосты не переезжает** | если студент — староста старой группы: предупреждение, что группа останется без старосты, помощники деактивируются |

`[предложение по бэкенду]` — предпросмотр последствий перевода с количествами (правило §6.2: объём последствий числами до подтверждения).

### 4.5 Статусы — по одному на роль (вариант Б, подтверждено владельцем)

**Нужно.** Перечень статусов приходит **как данные с сервера**, с указанием, каким ролям какое значение применимо. Со скана и историй: `active` · `expelled` (отчислен) · `graduated` (выпустился) · `suspended` (академ) · `dismissed` (уволен) · `archived`. Прим. 1: пользователь **остаётся в системе** при любом терминальном статусе.

**Следствия варианта Б:**

- колонка «Статус» **многозначна** и выровнена по колонке «Роль»: «студент — отчислен», «преподаватель — активен»;
- фильтр по статусу осмыслен **только в паре с фильтром по роли**: «отчисленные» без указания роли — двусмысленный запрос. Носитель этого правила — **дескриптор колонки «Статус»** (`enabledWhen: { column: 'role' }`), а не снятая панель фильтров; недоступность показывается `disabled` с текстовой причиной, не скрытием;
- терминальный статус одной роли **не лишает доступа целиком** — человек продолжает входить и работать под оставшейся активной ролью;
- `RoleSwitcher` показывает **только роли в активном статусе**;
- счётчики на 131 считают роли в активном статусе (правило подсчёта должно совпасть с фильтром 132, иначе два экрана разойдутся).

`[предложение по бэкенду]` — статус переносится с аккаунта на роль. `[вопрос к бэкенду]` — **прекращается ли доступ, когда терминальны все роли**, и появляется ли у аккаунта производный признак «неактивен». Записано как следствие, требует подтверждения.

### ⚠️ Фактура к решению о транспорте

| | |
|---|---|
| Вход на экран | **3 запроса**: список + справочник фильтров + справочник ролей и статусов |
| Смена страницы / поиск / фильтр | 1 запрос |

### Ячейки

- `InitialPasswordCell`: `initial` · `admin_reset` · **`changed`** («сменён пользователем» текстом, не пустое поле).
- `TelegramIdCell`: значение либо `not-linked` с пояснением и действием «привязать» (для преподавателя).
- `UserRoleStatusList`: одна роль · несколько ролей · **смешанные статусы** (одна роль терминальна, другая активна). **Без показа смешанного случая экран врёт:** строка «отчислен» у человека, продолжающего преподавать, — прямая дезинформация.

### Общие и вырожденные

- `forbidden` — роль admin отсутствует: список **не запрашивается вовсе**, граница проводится сервером (§6.2). Формулировка — тема аудита безопасности.
- `role-inactive` — роль admin есть, активна другая: пояснение и кнопка переключения. Не `forbidden`.
- `no-active-semester` — **на 132 не влияет**: учётные записи от семестра не зависят. Это стоит сказать явно на экране при пустой системе, иначе он кажется сломанным.
- **Частичный успех массовой операции — неприменим:** массового создания нет (решение владельца, чат 7).
- **Долгая операция:** генерация выгрузки по всему вузу может считаться минуты — `ExportButton` показывает состояние подготовки файла, а не молчит.

### По ролям

Экран одноролевой. **Пользователь, совмещающий роли:** под активной ролью admin он видит и правит всех, **включая собственную учётную запись**. Отдельно требуется защита от самоблокировки: снятие себе роли admin, архивирование себя, перевод себя в терминальный статус — `ConfirmDialog` с прямым предупреждением «вы потеряете доступ к этому разделу». `[вопрос к бэкенду]` — запрещать это на сервере или только предупреждать; при единственном администраторе в системе запрет обязателен.

### A11y (структурно)

- `<h1>` «Пользователи»; **поиск** — в `<search>`-регионе перед таблицей; фильтры — в заголовках колонок самой таблицы.
- В `<th>` фильтруемой колонки **два контрола с разными доступными именами**: подпись-кнопка сортирует, кнопка рядом открывает фильтр. Поповер — ловушка фокуса, Esc, возврат фокуса на кнопку-триггер. Мультивыбор — `fieldset` с чекбоксами, не выпадающий список с галочками.
- Многозначные колонки «Роль» и «Статус» фильтруются **по любому из значений ячейки** — это проговаривается в описании фильтра, иначе результат выглядит непредсказуемым.
- Настоящая `<table>` с `<th scope="col">`. Колонки «Роль» и «Статус» многозначны: **каждый статус называет свою роль в доступном имени** («преподаватель: активен; студент: отчислен»), иначе выравнивание читается только глазами.
- ⋮ — `RowActionsMenu`: `aria-haspopup="menu"`, стрелки внутри, Esc, возврат фокуса на триггер; недоступные пункты — `disabled` с текстовой причиной, не скрыты.
- Изменение результата поиска и фильтрации объявляется `role="status"`; `Pagination` объявляет загруженную порцию.
- При раскрытии формы фокус переводится внутрь, при сворачивании возвращается на кнопку. **При исчезновении строки (архивирование) фокус переводится на следующую строку**, а не теряется в конце документа (§6.2).
- Логин, пароль и Telegram id — строки, которые скринридер читает слитно: доступное имя ячейки поясняет, что это за значение.
- Статусы и роли — **словами**, цвет вторичен. Тач-таргеты ⋮ ≥ 44×44.

## 7. Заметки на будущее

### Адаптив

Девять колонок при 1920 помещаются. Уже на 1440 «Табельный номер» и «Tr id» — первые кандидаты на перенос в раскрываемую строку. **Что нельзя терять:** колонки «Роль» и «Статус» — без них строка перестаёт отвечать на главный вопрос экрана, а при варианте Б они ещё и связаны попарно, значит прячутся только вместе. Панели фильтров нет — её место заняли заголовки колонок, поэтому фильтры уезжают вместе со своими колонками. **`SearchField` не должен отрываться от таблицы:** это единственный фильтрующий контрол вне неё, и в оторванном виде он читается как поиск по всему экрану. В мобильной версии таблица станет списком карточек — отдельный цикл, здесь не закладывается.

### Открытые вопросы и риски

1. **Алгоритм генерации логина не финализирован** — коллизии, транслитерация, источник цифр по ролям, неизменность. Блокирует создание пользователей и бота.
2. **Статус на роли (вариант Б)** — перестройка модели: затрагивает 131 (счёт по ролям), `RoleSwitcher`, вход в систему. Производный признак «аккаунт неактивен» требует подтверждения.
3. **Пароли и персональные данные:** весь вуз в одном ответе списка и в выгрузке — **аудит безопасности**.
4. **Операционная дыра закрыта** (решение владельца, чат 7): если группа осталась без старосты, администратор **переназначает старосту** — этого достаточно, админских экранов ведения группы не появляется. Механизм живёт на 133.
5. **Риск расхождения с 131:** счётчики главной и `total` таблицы должны считаться одним агрегатом с явным параметром (роль, статус), иначе два экрана покажут разные «количества студентов» — нарушение «одна метрика считается в одном месте» (§6.2).
6. **Права администратора** («как для помощников старосты») — состав неизвестен, уходит в выделенную сессию по правам помощника.
7. **Самоблокировка администратора:** запрет или предупреждение — решается вместе с JS-ADMIN-14 (восстановление админа вне продукта). Если единственный админ заархивирует себя, система останется без администратора, а внутрипродуктового пути возврата нет **по решению**.

## Решения задачи 4 — внесено 01.08.2026

Источник — `02-backend/backend-conflicts.md`. Правила ниже имеют приоритет над более ранними формулировками этой спеки.

**Пароль (Р-1, Р-19).** ✏️ **Уточнено 10.08:** прежняя формулировка «значение скрыто у всех, раскрытия нет» противоречила реестру и отменена — прав реестр. Сгенерированный пароль **показывается** в `InitialPasswordCell` до самостоятельной смены пользователем; после смены вместо значения стоит текст «сменён пользователем». Отдельного состояния `hidden` и действия «Показать» нет. Доступно также **копирование**, факт копирования пишется в аудит. В выгрузку значение не попадает **ни в одном формате**. Перечень состояний — ровно четыре: `initial` · `headman_reset` · `admin_reset` · `changed`. `headman_reset` и `admin_reset` **сосуществуют**: сбрасывать могут обе роли, староста — только своей группе. `changed` означает, что копирование недоступно.

**Логин (Р-12).** Предполагаемый логин в форме создания **не показывается**: значение появляется только в ответе на сохранение.

**Роль (Р-6).** Роль — массив, у каждой роли свой статус. Активная роль живёт на сервере. Роли в терминальных статусах (`expelled`, `graduated`, `archived`) остаются переключаемыми и доступны **только для чтения**.

**Отбор (Р-21, Р-24, Р-17, Р-23).** Совпадение по **любому** значению многозначной ячейки — человек с ролями student и teacher попадает в выборку по каждой. Фильтр по статусу **недоступен, пока не выбрана роль**: показывается неактивным с текстовой причиной, не скрывается. Поиск идёт по всем столбцам, включая подстроки, и складывается с фильтрами колонок **через И** — прежнее правило «поле, покрытое поиском, фильтра не получает» **отменено**. Отбор серверный, фильтры уходят в адрес и в выгрузку.
