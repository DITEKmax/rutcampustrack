<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Gateway → academic-service | `X-Is-Headman` header is injected by JwtAuthenticationFilter (gateway-controlled). Academic-service must trust this header only if it arrives from the gateway (internal network). Direct calls to academic-service from outside the gateway would allow header spoofing. |
| RoleCheckAspect bypass | The headman bypass widens the surface for `@RequireRole({STUDENT})` methods. The second security layer (`AssistantService.requireHeadman()`, `SubjectService.requireHeadman()`) must remain intact to prevent plain students from writing. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-54-01 | Elevation of Privilege | `RoleCheckAspect.checkRole()` | mitigate | Bypass only applies when `Arrays.asList(required).contains(UserRole.STUDENT)` — admin/teacher-only methods are NOT bypassable by headmen. Verified by RoleCheckAspectTest case: headman blocked for required=[ADMIN]. |
| T-54-02 | Spoofing | `X-Is-Headman` header | accept | Academic-service runs on internal Docker network; direct external access is blocked by nginx/gateway. Accepted for internal microservice communication; production routing enforces gateway-only entry. |
| T-54-03 | Information Disclosure | `GET /academic/users/teachers` | mitigate | Returns only teacher users (role='teacher'), never admin or student data. UserResponse contains `id`, `fullName`, `login`, `role` — no password, no sensitive fields. Annotated `@RequireRole({STUDENT})` so only authenticated users can call it. |
| T-54-04 | Elevation of Privilege | `AssistantService.requireHeadman()` | accept | Second layer remains — plain students cannot write via AssistantController even after aspect fix. Verified existing behavior, no change to service layer guards. |
</threat_model>
