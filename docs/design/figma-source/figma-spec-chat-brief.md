# figma-spec.md — готовый промпт

## Куда

**Тот же чат, где собирался брендбук и палитра.** Там уже лежат `brandbook-v2.md`, `tokens-v2.json`, `palette-v2.html`, все SVG-референсы чужой дизайн-системы и два PNG — календарь в разборе и состояния пагинации.

**Что докинуть, если чата хватает:** `COMPONENT_REGISTRY.md`. Без него спека соберётся не из твоего набора компонентов, а из чужого.

Если чат заполнился — новый, и прикладывать: реестр, брендбук, токены, палитру, PNG с календарём и пагинацией. SVG-референсы по одному-двум, для образца глубины.

Разговор длинный и делится на проходы. Не пытайся закрыть все компоненты одним сообщением.

## Промпт

```
Собираем figma-spec.md — спецификацию компонентов для сборки
библиотеки в Figma. Брендбук и токены готовы и приложены,
значения оттуда и берутся: в этом файле не появляется ни одного
нового цвета, размера или радиуса. Если чего-то не хватает —
скажи, что не хватает, и не изобретай.

ЧТО ЭТОТ ФАЙЛ ОТВЕЧАЕТ, А ЧТО НЕТ
Реестр отвечает, что компонент делает. Брендбук — какими
значениями он выражен. Этот файл отвечает, из чего он собран
и какого он размера. Третьего слоя сейчас нет нигде, поэтому
он и делается.

СОСТАВ БЕРЁТСЯ ИЗ РЕЕСТРА
Список компонентов — COMPONENT_REGISTRY.md, целиком и без правок.
Новых компонентов не заводим, существующие не сливаем.
Приложенные SVG чужой дизайн-системы — образец глубины проработки
и структуры документа, НЕ источник состава компонентов, цвета
и стиля. Если приём из референса хорош — назови приём, а не
копируй компонент.

ПО КАЖДОМУ КОМПОНЕНТУ
1. Анатомия: из каких частей собран, какая обязательна, какая
   опциональна. Как в приложенном PNG с календарём: сначала атом
   (число в пяти состояниях), потом ячейка, потом собранный
   компонент.
2. Размерные варианты. Сколько их и зачем каждый — не «sm/md/lg
   по привычке». Если компоненту хватает одного размера, так
   и скажи: лишний вариант в библиотеке дороже, чем кажется.
3. По каждому размеру: высота, внутренние отступы, кегль, радиус,
   толщина границы, размер иконки, минимальная и максимальная
   ширина — токенами, не числами. Число только там, где токена нет,
   и тогда с пометкой, что нужен новый токен.
4. По каждому размеру — ВСЕ состояния из брендбука §8.2:
   default, hover, pressed, focused, disabled, и где есть —
   selected, current, busy, error. Покрытие полное: не бывает
   размера, у которого состояния «подразумеваются».
   Помни §8.1: hover положен не всем. Где его нет — так и пиши,
   а не оставляй пустую клетку.
5. Поведение при переполнении: длинный русский текст, длинное имя
   группы, число в четыре знака, пустое значение. Что обрезается,
   что переносится, что растягивает компонент.
6. Слоты и вложенность: какой компонент может лежать внутри
   какого. Это будущие Figma-инстансы, ошибки здесь дорогие.

СБОРКА — ЭТО ЧАСТЬ СПЕКИ, НЕ ОТДЕЛЬНАЯ ЗАДАЧА
Иерархия такая, и её надо описать явно:
атом → компонент → блок → блок из блоков → экран → адаптив.
- Блок — самостоятельный кусок экрана, собранный из компонентов
  (карточка метрики, шапка с переключателем роли, панель фильтров,
  журнал целиком).
- Блоки могут вкладываться в блоки, столько уровней, сколько
  реально нужно — но каждый уровень надо оправдать.
- У блока свои размерные варианты под ширины 1920 / 1440 / 1280.
  Адаптив собирается ПЕРЕКЛЮЧЕНИЕМ ВАРИАНТА БЛОКА, а не
  растягиванием экрана и не отдельной вёрсткой под каждую ширину.
- Для каждого блока: что меняется между ширинами — число колонок,
  порядок, что сворачивается, что уходит под кнопку. Что НЕ
  меняется никогда.
Экраны в этом файле не рисуются. Описывается, из каких блоков
каждый экран собирается, — по спекам из 01-wireframes.

ПРАВИЛА FIGMA, КОТОРЫЕ НАДО ЗАЛОЖИТЬ СРАЗУ
Библиотеку будет заводить агент через Figma MCP, поэтому:
- имена компонентов и вариантов — по одной схеме, совместимой
  с той, что уже принята для токенов;
- какие оси вариантов у компонента (size, state, тип) и в каком
  порядке;
- где Auto Layout и с каким направлением, где фиксированная
  ширина, где hug, где fill;
- какие свойства выносятся в property (текст, иконка, булево);
- что делается вариантом, а что — отдельным компонентом.

ЧЕГО НЕ ДЕЛАТЬ
- Не рисовать экраны и не придумывать новые.
- Не менять состав компонентов реестра.
- Не заводить новые токены молча: только списком «нужен токен X,
  потому что Y», в конце файла.
- Не переоткрывать решения из BRAND_DIRECTION.md и брендбука.

ПОРЯДОК РАБОТЫ
Файл большой, за один проход не собрать. Предложи разбивку
на проходы по группам компонентов и начни с первой группы.
После каждой группы останавливайся и жди подтверждения.

ПЕРЕД ПЕРВЫМ ПРОХОДОМ
Задай мне вопросы, которые нужно закрыть до начала: размерные
варианты, ширины блоков, что считать блоком, спорные места
реестра. Одним списком.

ВЫДАЙ ФАЙЛОМ figma-spec.md, по группам, по мере готовности
```
