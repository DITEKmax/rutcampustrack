| Экран | Зона ответственности |

**Дублирование 122 и 123 признано и ограничено.** Четыре метрики в хвосте строки журнала (122) и строки сводки (123) — **одни и те же числа**; их считает **один серверный агрегат**. Разрез «по моим группам» (123) не дублирует ничего: аналога у student и headman нет, они привязаны к одной группе по определению.

**Контекст роли живёт в URL, а не в сессии.** Все переходы несут `groupId` / `subjectId` / тип занятия / `lessonId` **по идентификаторам** (правило чата 5): ссылку можно переслать, F5 не сбрасывает разрез. Между сессиями контекст **не сохраняется** — «липкий» контекст опаснее лишнего клика: преподаватель откроет вчерашний журнал, не заметив.

| Экран | Зона ответственности |

| 132 Пользователи | **учётные записи всего вуза**: создание, роли и их статусы, перевод между группами, восстановление доступа, архивирование |

| 134 Семестры | **учебные периоды**: создание, активация (0 или 1), архивация, удаление. Единственное место, где лечится `no-active-semester` |
| 135 Карта | **ведение схем**: какие корпуса и этажи заведены, что загружено, чего не хватает, замена и удаление |

**Порядок запуска системы: 134 → 133 → 132.** Без семестра нет учебного контекста, без группы нельзя создать студента (прим. 2 скана 132), без старосты группа остаётся черновиком. Именно этот порядок показывается в состоянии `empty-system` на каждом из трёх экранов.

**Границу проводит активная роль** (§0 чат 7). Экраны 101–108 и 111–119 роли admin не выдаются, даже когда API формально помечен `HEADMAN/ADMIN`. Операционная дыра «группа без старосты» закрывается **переназначением старосты** на 133, а не подменой старосты администратором.

**Контекст живёт в URL** на всех пяти экранах: разрез, фильтры, поиск, номер страницы, период. Ссылку можно переслать, F5 не сбрасывает. Между сессиями контекст **не сохраняется** — то же правило, что у роли teacher (чат 6).

### 8.7. Разграничение 135 (ведение) и 105 = 115 = карта преподавателя (просмотр) — чат 7

| Экран | Роли | Зона ответственности |
|---|---|---|
| **ПК-135 Карта — ведение** | admin | **какие схемы существуют**: реестр «корпус × этаж», загрузка пары файлов (svg + png), статусы загрузки, замена, удаление, спрос на этаж |
| **ПК-105 = 115 = карта преподавателя — просмотр** | student, headman, teacher | **что на схеме**: выбор корпуса и этажа, просмотр с зумом, скачивание png, легенда |

**Это разные экраны, а не варианты одного.** Совпадает только предметная область; данные, действия и состояния не пересекаются. Пересечение ровно одно: **135 порождает данные, которыми живёт 105** — замена схемы на 135 меняет то, что видят три роли на 105. Обратного влияния нет.

Следствия, зафиксированные в чате 7:
- **отдельной страницы просмотра у администратора не заводим** — если ему нужно посмотреть схему, он открывает 105;
- `FloorPlanViewer` на 135 не используется: достаточно превью внутри `FileUploadField`;
- состояние `partial` (загружен один файл из двух) на 135 обязано объяснять **последствие на 105**, а не показывать голый статус;
- при замене схемы 105 получает **текущую ссылку при каждом запросе**; кэширование идёт по хешу, а не по адресу этажа.
