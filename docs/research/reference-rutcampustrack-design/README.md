# RutCampusTrack — дизайн нового фронтенда

Полное переписывание фронтенда на **Vue**, архитектура **микрофронтендов**, новый визуал с нуля.
Репозиторий продукта: https://github.com/DITEKmax/rutcampustrack

Личный проект. С вузом не связан, согласований нет, язык интерфейса только русский, обращение на «ты».

**Состояние на 06.08.2026:** этапы 1, 1.5, 2 и 3 закрыты. Брендбук v2 выдан, гарнитура выбрана, `figma-spec.md` собран, накладка под shadcn-vue написана. Stitch снят с критического пути. Следующий шаг — сборка токенов и компонентов в коде по заданиям из `rutcampustrack-kit/tasks/`.

## 1. Как организована работа

| Тип чата | Где | Зачем | Что видит |
|---|---|---|---|
| **Рабочий** | внутри Claude Project | разбор экранов, правки спек, сводки | инструкции проекта + база знаний |
| **Стратегический** | обычный чат, вне проекта | планирование, ревью структуры, решения, подготовка промптов | прикладываемые файлы + handoff |
| **Сборочный** | Claude Code в корне Vue-проекта | токены, компоненты, блоки, экраны | `AGENTS.md`, скилл проекта, `design/`, `specs/` |

**Рабочие чаты не видят друг друга.** Общая у них только база знаний, поэтому `COMPONENT_REGISTRY.md` — единственный мост между ними. После каждого чата, изменившего реестр, его надо **перезалить в базу знаний проекта**, иначе следующий чат будет работать по отменённым правилам.

Содержимое `knowledge/` — это ровно то, что залито в базу знаний. Папка держится в этом состоянии специально: сверять по ней, ничего не добавляя «на всякий случай».

### Именование чатов в проекте

```
[0] Калибровка — 001,101,102
[1] Студент: учёба — 103,104
[2] Студент: сервисы — 105,107,108
[3] Староста
[4] Преподаватель
[5] Админ
[6] Сводка и figma-spec
[7] Backend requests
[8] Брендбук v2
```

Числовой префикс держит порядок в списке чатов.

### Переход в новый стратегический чат

1. Открыть **новый обычный чат**, не в проекте: инструкции проекта ограничивают его разбором экранов.
2. Отправить свежий файл из `_work/handoffs/` — там всегда лежит последний.
3. Приложить `README.md` и то, о чём пойдёт разговор.

`COMPONENT_REGISTRY.md` прикладывать только если разговор про компоненты — он большой (279 КБ). Планы в базу знаний проекта не грузятся: `_work/plans/` — для стратегических чатов, не для рабочих.

## 2. Две папки — и почему их две

| Папка | Роль | Живёт |
|---|---|---|
| **`rutcampustrack-design`** (эта) | архив проектирования и **единственный источник истины** по всем файлам | у владельца, рядом с исходниками |
| **`rutcampustrack-kit`** | обвязка агента: `SKILL.md`, `AGENTS.md`, `.mcp.json`, `SETUP.md`, задания по этапам и **копии** нужных файлов дизайна и спек | переезжает в корень Vue-проекта по `SETUP.md` |

Правило, которое держит их в согласии: **правка вносится в `design`, потом копируется в `kit`. Обратного направления не существует.** В `kit` руками ничего не редактируется, кроме его собственных файлов (`SKILL.md`, `AGENTS.md`, `tasks/`, `SETUP.md`, `.mcp.json`).

Что копируется в `kit`:

| Из `design` | В `kit` |
|---|---|
| `knowledge/BRAND_DIRECTION.md` | `design/` |
| `knowledge/COMPONENT_REGISTRY.md` | `design/` |
| `knowledge/A11Y_REQUIREMENTS.md` | `design/` |
| `03-brand/brandbook-v2.md` · `tokens-v2.json` · `palette-v2.html` | `design/` |
| `04-figma/figma-spec.md` · `figma-spec-shadcn-overlay.md` | `design/` |
| `01-wireframes/**` | `specs/wireframes/**` |

Остальное — `00-scans`, `02-backend`, `_work`, `job-stories.md` — агенту на этапах вёрстки не нужно и в `kit` не едет.

**Ключевая связка:** реестр компонентов → брендбук v2 → токены → компоненты Vue. Ничего не рисуется «из головы».

Порядок внутри сборки важен: **компоненты создаются до экранов**, экраны собираются из компонентов. Иначе shared-библиотека соберётся из разрозненных кусков. Компонент, собранный на литералах, дешевле перерисовать, чем связать с переменной задним числом.

Figma остаётся возможной поверхностью для макетов, но не обязательной: правка файла вне черновиков требует Full seat, REST API для переменных — Enterprise, переменные заводятся через Plugin API.

**Источник экранов — `.pptx`.** PNG это экспорт. Правки вносить в pptx и переэкспортировать.

`04-figma/figma-spec-delta/` — черновики пятнадцати проходов, из которых собран `figma-spec.md`. Они **не** являются его нарезкой и местами расходятся с ним; действующий файл один — `figma-spec.md`.

### Правила именования

- Спека экрана: `<код>-<роль>-<название>.md`, например `113-headman-stats.md`. Роль в имени намеренно продублирована — ссылки по всему проекту используют полное имя.
- Файлы базы знаний — `UPPER_SNAKE_CASE`, всё остальное — `kebab-case`. По регистру имени видно, лежит ли файл в базе знаний.
- `_work/archive/<этап>/` — материалы закрытого этапа. Ничего оттуда не читается в работе; лежит ради восстановимости обоснований.

## 6. Правила синхронизации после рабочего чата

1. Скачать выданные файлы.
2. Спеки → `01-wireframes/<роль>/` под полным именем.
3. Обновлённый реестр → `knowledge/COMPONENT_REGISTRY.md`.
4. В базе знаний проекта: удалить старый `COMPONENT_REGISTRY.md`, залить новый.
5. Если менялось то, что скопировано в `kit` (реестр, брендбук, токены, `BRAND_DIRECTION`, спеки, `figma-spec` и накладка) — **обновить копию в `kit`**.

Шаги 4 и 5 пропускать нельзя: пропущенный четвёртый заставит следующий чат изобретать синонимы компонентов, пропущенный пятый — заставит агента собрать компонент по отменённому правилу.

Снапшоты реестра не копятся: файл считается единственной действующей версией, история — в git репозитория.
