# Root-Cause-Only Debugging Contract (Java / Spring)

> Вставляй этот текст в задачу отладки, ИЛИ добавь как раздел в правила. Он запрещает агенту «прятать» баг слоями логов/гвардов/фолбэков вместо реального фикса. Адаптировано под Spring Boot микросервисы RutCampusTrack.

## Запрещённое поведение: Confirmation-Layering

Не решай дефект добавлением слоёв, которые лишь подтверждают/логируют/охраняют/описывают/компенсируют его.
Confirmation layer = любой новый код/лог/валидация/фолбэк/монитор/обёртка/precheck, чей главный эффект — заявить, что баг существует, вместо изменения пути кода, который баг создаёт.

## Обязательный порядок расследования

Когда данные некорректны/поле отсутствует/состояние невалидно — проверяй по порядку:

1. **Источник данных:** содержит ли upstream (REST-запрос, gRPC-вызов, RabbitMQ-событие) нужное значение, или его надо вывести локально?
2. **Парсер/маппер:** переименовано, пропущено, неверно скастовано, потеряно в DTO-маппинге (контроллер `implements` контракт — маппинг там)?
3. **DTO / контракт:** поле есть в `record`/response-классе, в валидации (`@Valid`), в сериализации?
4. **JPA-слой:** entity-маппинг, `LowercaseEnumConverter`, `@Column`, отношения, порядок вставки (parent до child)?
5. **Транзакции:** `@Transactional` границы; child-вставка после откаченного parent'а; propagation/isolation?
6. **Конкурентность:** TOCTOU (`findById` + условный `save` вне транзакции); две параллельные операции; идемпотентность consumer'а события?
7. **Flyway/схема:** допускает ли схема невалидный null/состояние, которое должно быть отвергнуто? Нужна ли `V{N+1}` миграция?
8. **Кэш:** Redis/Caffeine отдаёт устаревшее? Инвалидация есть?
9. **Историческая починка:** нужен ли backfill уже испорченных записей после фикса кода?

Не добавляй фолбэк/гвард/абстракцию, пока этот путь не пройден.

## Классификация патча

Каждое изменение классифицируй:
```
ROOT_FIX | DATA_REPAIR | TEST | OBSERVABILITY | GUARD | DOCUMENTATION | REFACTOR
```
Решают дефект только `ROOT_FIX`, `DATA_REPAIR`, `TEST`. `OBSERVABILITY`/`GUARD`/`DOCUMENTATION`/`REFACTOR` — не фикс, если не приложены к root-fix и не доказывают/защищают исправленное поведение.

## Требуемая структура ответа

```
1. Нарушенный инвариант
2. Подозреваемый путь-производитель (file:class:method)
3. Доказательство из кода
4. Корневая причина
5. Патч
6. Data repair (если записи уже испорчены)
7. Регрессионный тест (JUnit/Testcontainers), падающий ДО и зелёный ПОСЛЕ
8. Команда проверки (какой ./gradlew таск доказывает инвариант)
```
Не начинай с архитектуры/обёрток/доп-сервисов/мониторинга/фолбэков.

## Тест на отклонение

Перед финализацией спроси: «Если убрать новый слой валидации/лога/фолбэка — исходный путь данных реально починен?» Нет → это не фикс.

## Production-Wiring Self-Check

1. Какой production-entrypoint триггерит этот код? (REST-контроллер, gRPC-хендлер, `@RabbitListener`, `@Scheduled`, `@EventListener`).
2. Точная цепочка вызовов от entrypoint до пропатченной логики (file:class:method, не описание).
3. Какой старый/фолбэк-путь теперь удалён/обойдён/заменён?
4. Какая реальная таблица/gRPC-вызов/очередь/кэш/side-effect меняется при срабатывании entrypoint?
5. Какой тест исполняет реальный production-entrypoint (`@SpringBootTest` / `*IT` с Testcontainers), а не напрямую новый хелпер?

Если ответить нельзя — это `UNWIRED_CODE`, не фикс. Тест `NewService.handle()` доказывает, что NewService работает, но НЕ что приложение его использует. Требуемый тест стартует от реальной границы: HTTP-запрос / gRPC / событие / scheduled.

## Стандарт «починено»

Дефект починен только когда: (1) причина-производитель найдена; (2) производящий путь изменён; (3) испорченные данные починены или явно изолированы; (4) регрессионный тест падает до и проходит после; (5) команда/запрос доказывает инвариант.
