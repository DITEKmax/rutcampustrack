# ПК-001 — Вход (+ 001a, 001b — восстановление пароля)

> Этап 1, чат 1. Веб-десктоп 1920. Структура и логика, без визуала.
> Цветовые группы указаны по скану: ЗЕЛЁНЫЙ — управляющие элементы, ЖЁЛТЫЙ — условное/наложенное содержимое, КРАСНЫЙ — фиксированное отображение.

---

## 1. Идентификация

| | |
|---|---|
| **Название** | Вход (`AuthPage`) |
| **Роли** | все 4 — `student`, `headman`, `teacher`, `admin`. Экран единый |
| **Поверхность** | веб-десктоп 1920 |
| **Точка входа** | прямой заход на корень; редирект с любого защищённого маршрута при отсутствии или истечении сессии |
| **Цель** | получить сессию одним из трёх способов и уйти на главную |

**Со скана 001-1:** после входа система **всегда** переходит на главную страницу.

**Дизайн-заготовка (заметка 1 скана):** визуальное решение не выбрано — либо форма по центру, либо разделение экрана с иллюстрацией/лого. На этапе 1 фиксируем только наличие brand-зоны как региона, её структуру решаем на этапе 2.

## 2. Layout-регионы

```
AuthLayout
├─ [brand-зона]                    — пустая заглушка, структура решается на этапе 2
└─ <main> auth-панель
   ├─ h1 «Вход»
   ├─ Tabs  «Логин и пароль» · «OTP» · «QR»    [три равных сегмента]
   ├─ method-panel — одна из трёх              [ЖЁЛТЫЙ]
   │  ├─ LoginPasswordForm   (логин, пароль, запомнить, восстановление, submit)
   │  ├─ OtpForm             (код)
   │  └─ QrLoginPanel        (QR + статус)
   └─ feedback-зона: общая ошибка входа        ← добавлено, на бумаге нет
```

**Сверка со сканом.** Зелёная — только полоса вкладок «Логин и пароль / OTP / QR». Жёлтые — четыре блока полей (Логин, Пароль, ОТП код, QR код), то есть содержимое, появляющееся после выбора вкладки. Красных блоков на экране нет.

**Допущение:** три жёлтых блока нарисованы рядом как перечень вариантов; реально видна одна панель — та, что выбрана вкладкой. Наличие зелёной полосы вкладок это подтверждает.

**Решение владельца 17.08.2026:** ссылка «Забыли пароль» входит в
`LoginPasswordForm` и стоит справа под полем пароля, в одной строке с
`Checkbox` «Запомнить меня». В демонстрационном default checkbox отмечен;
значение остаётся данными `rememberMe`. Поля логина и пароля — капсулы
`radius/full`, submit полноширинный с `radius/2xl` и замыкает форму снизу.

**Решение владельца 17.08.2026 по темам:** `AuthLayout` использует соседние
растровые фоны dark / light с одинаковой композицией и режимом `FILL`.
Кнопка перехода в противоположную тему стоит в правом верхнем углу кадра,
вне формы. Это `AppButton`, не трёхзначный `ThemeSwitcher` из настроек.

## 4. Потребности в данных

Формат: **что нужно экрану** → **что доступно сейчас** → **пробел**.

### 4.1. Сессия по логину и паролю

- **Нужно:** `{login, password}` → `Session {accessToken, refreshToken, expiresIn}` **и сразу** `CurrentUser {id, ФИО, avatar, roles[], is_headman, groupId, activeSemesterId}`. Без профиля и ролей нельзя ни выбрать целевую главную, ни отрисовать шапку.
- **Сейчас:** `POST /auth/login`; отдельно `GET /academic/users/me`; вероятно `GET /auth/public-key` (если пароль шифруется на клиенте); активный семестр — из `GET /academic/semesters`.
- **Пробел:** `[предложение по бэкенду]` — единый bootstrap сессии: токены + профиль + роли + активный семестр одним ответом.

### 4.2. Вход по OTP

- **Нужно:** запрос кода по идентификатору → подтверждение `{code}` → та же `Session`. Фронту нужны **TTL кода** и **остаток попыток** (JS-SYSTEM-03: 120 с, 3 попытки за 5 минут) — как данные, а не как константы во фронте.
- **Сейчас:** `POST /auth/otp/request`, `POST /auth/otp/verify-by-code`.
- **Пробел:** `[уточнение по контракту]` — выдаёт ли `verify-by-code` полноценную сессию (в дайджесте OTP описан в контексте сброса пароля).
- **Пробел:** `[предложение по бэкенду]` — отдавать `ttl` и `attemptsLeft` в ответе, при блокировке — `retryAfter`.

> На скане в OTP-вкладке **одно поле** — значит код самодостаточен для идентификации пользователя. Наличие `verify-by-code` (без telegram id) это подтверждает.

### 4.3. Вход по QR

- **Нужно:** создать сессию входа → `{sessionId, qrPayload, expiresAt}`; канал статуса `pending | confirmed | expired | rejected`; при `confirmed` — `Session`. Подтверждение приходит из Telegram Mini App или PWA.
- **Сейчас:** `[нет API]`. `POST /auth/tma` — про другое (вход внутри Mini App). `POST /auth/ws-ticket` требует уже авторизованного пользователя и для неавторизованного QR-канала не подходит.
- **Пробел:** `[предложение по бэкенду]` — флоу целиком.

### 4.4. Восстановление пароля

- **Сейчас на вебе:** `[нет API]` — по JS-SYSTEM-03 сброс живёт только в боте.
- **Решение владельца:** через Telegram. На сайте — инструкция, как получить в боте **код**; сам код вводится на 001a. Ссылку на установку нового пароля генерирует **администратор** — это второй, независимый вход на 001b.
- Подробности — в разделах 001a и 001b ниже.

### ⚠️ Фактура к решению о транспорте

Самый простой экран продукта требует **3–4 запроса** до первого полезного кадра.

## 5. Состояния

На бумаге состояний нет ни одного — **всё добавлено при разборе**.

| Состояние | Где | Поведение |
|---|---|---|
| `loading` | панель | первичная проверка существующей сессии / получение public-key / генерация QR — скелетон, форма недоступна |
| `idle` | формы | поля пусты, submit недоступен до заполнения обязательных |
| `submitting` | формы | `aria-busy`, кнопка в busy, поля не блокируем |
| `error: credentials` | формы | `FormError` с `title`/`detail` из RFC 9457, `role="alert"`, фокус на сообщение |
| `error: validation` | поля | текстом, не только цветом; связь через `aria-describedby` |
| `error: rate-limited` | OTP | «повторить через N с», запрос кода недоступен до истечения |
| `otp-expired` | OTP | код истёк → предложение запросить новый, таймер обнулён |
| `qr-pending` / `qr-confirmed` / `qr-expired` | QR | ожидание · редирект · «обновить код» |
| `offline` | экран | вход невозможен, `OfflineState`, авто-повтор при восстановлении |
| `blocked-account` | после ответа сервера | статусы `expelled` / `suspended` / `archived` (JS-ADMIN-02, -04) — понятный текст без утечки деталей |
| `already-authenticated` | вход на экран | редирект на главную, форма не показывается |

**По ролям:** экран идентичен для всех четырёх ролей. Различается только целевая страница после входа.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| Вкладка метода (`Tabs`) | Переключает панель без перезагрузки. Стрелки двигают вкладку, Tab уводит внутрь панели. Данные других методов сбрасываются, QR-сессия при уходе с вкладки гасится. **Память активной вкладки принадлежит странице**, не компоненту (правило `Tabs`) |
| Submit (логин/пароль, OTP) | Успех → **всегда главная** (скан 001-1), с учётом `returnUrl`, если пришли редиректом с защищённого маршрута |
| QR подтверждён | Тот же переход, без действия пользователя на десктопе |
| «Забыли пароль» | → 001a |

- **Деструктивных действий нет**, подтверждения не требуются.
- **Нехватка прав:** неавторизованный запрос любого маршрута → редирект сюда с сохранением `returnUrl`.

### A11y (структурно)

- Один `h1`; панель внутри `<main>`; настоящая `<form>` с submit по Enter.
- У каждого поля явный `<label>`: подписи внутри блоков на скане — плейсхолдеры, лейблы обязательны.
- `autocomplete`: `username` / `current-password` / `one-time-code`.
- Вкладки по ARIA tabs-паттерну: стрелки, `aria-selected`, перевод фокуса в панель.
- **QR обязан иметь текстовую альтернативу** — код строкой для тех, кто не может отсканировать.
- Таймер — `role="status"`; «код истёк» дублируется текстом, а не только исчезновением отсчёта.

# ПК-001a — Восстановление: инструкция

**Новый экран, на сканах отсутствует.** Введён по решению владельца.

## Идентификация

| | |
|---|---|
| **Роли** | все 4 |
| **Точка входа** | ссылка «Забыли пароль» на 001 |
| **Цель** | принять код из Telegram-бота и дать точку входа для тех, у кого нет доступа к боту |

**Решение владельца:** 001a — это **ввод кода из Telegram** плюс указание обратиться к **старосте группы или администратору**, если бот недоступен.

**Почему отдельный маршрут, а не модалка:** ссылка, сгенерированная администратором, открывается в новой вкладке и должна вести сразу на шаг установки пароля — модалка поверх формы входа так не открывается. Плюс возврат на вход после успеха читается как навигация, а не как закрытие окна.

## Layout-регионы

```
AuthLayout
└─ <main>
   ├─ AppLink «← Назад»      — верх панели
   ├─ h1 «Введи код»
   ├─ RecoveryInstructions   — кратко: код отправлен в Telegram
   ├─ RecoveryCodeForm       — шесть ячеек кода + полноширинный submit
   ├─ fallback-блок          — «нет доступа к Telegram»: обратитесь к старосте
   │                            группы или к администратору (текст зависит от роли)
   └─ feedback-зона
```

## Компоненты

| Компонент | Назначение | Владение |
|---|---|---|
| `RecoveryInstructions` | Статичный текст-инструкция по боту + ролевой fallback | `local` (auth) |
| `RecoveryCodeForm` | Ввод шестизначного кода из бота; сценарий сброса, не входа | `local` (auth) |
| `CodeInput` | Шесть видимых ячеек, одна строка ввода, вставка полного кода | `shared` |
| `FormField`, `AppButton`, `FormError`, `CountdownTimer` | Переиспользуются со входа | `shared` |

> **`RecoveryCodeForm` ≠ `OtpForm`.** Внешне похожи, но разный контракт и разный результат: `OtpForm` выдаёт сессию, `RecoveryCodeForm` — право сменить пароль. Не сливать в один компонент, иначе сброс пароля окажется завязан на логику входа.

## Fallback по ролям (решение владельца)

Общая формулировка на экране — «обратитесь к старосте группы или к администратору»; конкретный адресат зависит от роли:

| Роль | Куда обращаться, если бот недоступен |
|---|---|
| `student` | к старосте группы — староста сбрасывает пароль и передаёт сгенерированный |
| `headman` | к администратору |
| `teacher` | к администратору (у преподавателя нет Telegram-бота, JS-TEACHER-05) |
| `admin` | **вне продукта** — эксплуатационная процедура: прямая работа с базой или перезапуск приложения. Внутрипродуктового пути нет, и текст инструкции ничего не обещает |

## Потребности в данных

- **Проверка кода/токена сброса.** Нужно: `{code}` или `{token}` → `{valid, ttl, purpose: 'password_reset'}` + одноразовый ticket для шага 2. Нужны `ttl` и `attemptsLeft`.
  Сейчас: `POST /auth/otp/verify-by-code` существует, но выдаёт ли он право на сброс без старого пароля — неизвестно.
  Пробел: `[уточнение по контракту]` + `[предложение по бэкенду]` — явное `purpose` у OTP (`login` / `password_reset`), чтобы код одного сценария не работал в другом.
- **Текст инструкции.** `[предложение по бэкенду]` (низкий приоритет) — отдавать команду бота и его @username как конфиг: при переименовании бота инструкция протухнет молча.
- **Сброс через старосту.** Со стороны студента — только текст, данных не нужно. Со стороны старосты — новая операция, уходит в чат headman.

## Состояния

Все добавлены при разборе: `idle` · `submitting` · `error: invalid-code` (с остатком попыток) · `error: rate-limited` (обратный отсчёт, submit недоступен) · `error: expired` → «запросите новый код в боте» · `offline`.

# ПК-001b — Восстановление: новый пароль

**Новый экран, на сканах отсутствует.**

## Идентификация

| | |
|---|---|
| **Роли** | все 4 |
| **Точки входа** | **два, равноправных:** (1) переход после верного кода, введённого на 001a; (2) ссылка с токеном в URL, **сгенерированная администратором** |
| **Цель** | установить новый пароль (двойной ввод) и вернуться ко входу |

## Layout-регионы

```
AuthLayout
└─ <main>
   ├─ h1 «Новый пароль»
   ├─ NewPasswordForm       — новый пароль + подтверждение (двойной ввод)
   ├─ PasswordPolicyHint    — требования к паролю
   └─ feedback-зона
```

## Компоненты

| Компонент | Назначение | Владение |
|---|---|---|
| `NewPasswordForm` | Новый пароль + подтверждение — **двойной ввод обязателен**, совпадение проверяется до отправки | `local` (auth) |
| `PasswordPolicyHint` | Требования к паролю со статусом выполнения; связан с полем через `aria-describedby` | `shared` |
| `PasswordField` | Переиспользуется | `shared` |

> **Старый пароль здесь не спрашивается** — это сброс, а не смена. Смена с вводом старого (JS-SYSTEM-04) живёт в профиле.

## Потребности в данных

- **Установка нового пароля по ticket.** Нужно: `{ticket|token, newPassword}` → успех; ошибки: токен истёк, уже использован, пароль не соответствует политике.
  Сейчас: `[нет API]`. `POST /auth/change-password` требует старый пароль и для сброса не подходит.
  Пробел: `[предложение по бэкенду]` — отдельная операция сброса по одноразовому ticket, **с инвалидацией всех активных сессий пользователя** после смены.
- **Политика пароля.** Нужно: правила (минимальная длина, обязательные классы символов) как данные, а не как константа во фронте — иначе три клиента разойдутся с бэкендом.
  Сейчас: `[нет API]`. Пробел: `[предложение по бэкенду]`.

## Состояния

Все добавлены при разборе: `loading` (проверка токена из ссылки) · `invalid-token` / `expired-token` / `used-token` → возврат на 001a с пояснением · `idle` · `validation-error` (по каждому правилу отдельно, текстом) · `submitting` · `success`.

**Success:** сообщение «пароль изменён» → возврат на вход. **Автологин не делаем:** пользователь должен убедиться, что новый пароль работает, и это дешевле по бэкенду.

## Навигация

```
001 Вход ──«Забыли пароль»──▶ 001a Инструкция + ввод кода
                                 │  код верный
Ссылка от администратора ────────┼──▶ 001b Новый пароль
                                 │        │ success
                                 ◀────────┴──▶ 001 Вход
001a ──«Вернуться ко входу»──▶ 001
```

- Деструктивных действий нет, подтверждений не требуется.
- Прямой заход на 001b без токена и без перехода с 001a → редирект на 001a с пояснением.
- Заход на 001a/001b **при активной сессии не редиректим на главную** (в отличие от 001): пользователь мог открыть ссылку сброса с уже залогиненного устройства.

### A11y

На каждом шаге свой `h1`; настоящая `<form>`; успех и ошибки — `role="alert"` с переводом фокуса; требования к паролю доступны **до** ввода, а не только как ошибка после; таймер повтора — `role="status"`; `autocomplete="new-password"` на обоих полях.
