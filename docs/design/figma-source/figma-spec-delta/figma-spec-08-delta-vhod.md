## 2. ПК-001 — Вход

### 2.1. `block/LoginMethods`

| Часть | Компонент | Обязательность |
|---|---|---|
| заголовок | h1 «Вход» | обязательна |
| выбор метода | `Tabs` — «Логин и пароль» · «OTP» · «QR» | обязательна |
| панель метода | одна из трёх, instance swap | обязательна |
| восстановление | `AppLink` «Забыли пароль» → 001a | обязательна |
| ошибка входа | `FormError` | видима при ошибке |

Панели метода:

| Вкладка | Компонент | Что выдаёт |
|---|---|---|
| Логин и пароль | `LoginPasswordForm` | сессию |
| OTP | `OtpForm` + `CountdownTimer` | **сессию** |
| QR | `QrLoginPanel` → `QrCodeDisplay` | сессию после подтверждения с мобильного |

**Видна ровно одна панель** — та, что выбрана вкладкой. Три жёлтых блока
на скане нарисованы рядом как перечень вариантов, а не как одновременное
содержимое.

`Tabs` здесь — настоящий `tablist`, не радиогруппа (решение владельца
по хвостам этапа 1.5).

### 2.2. Состояния блока

```
state = idle | submitting | error | offline
```

`QrLoginPanel` несёт собственные `waiting` · `confirmed` · `expired` · `error`;
`expired` заменяется действием «Обновить», а не пустой областью.

## 3. ПК-001a — Восстановление: инструкция и код

### 3.1. `block/RecoveryStart`

| Часть | Компонент | Обязательность |
|---|---|---|
| заголовок | h1 «Восстановление пароля» | обязательна |
| инструкция | `RecoveryInstructions` — команда боту → бот присылает код | обязательна |
| основной путь | `RecoveryCodeForm` + `CountdownTimer` | обязательна |
| запасной путь | `fallback` — «нет доступа к Telegram» | обязательна |
| возврат | `AppLink` «Вернуться ко входу» | обязательна |
| ошибка | `FormError` | видима при ошибке |

### 3.2. Ролевой fallback

Общая формулировка на экране — «обратитесь к старосте группы или
к администратору»; конкретный адресат зависит от роли.

```
fallback-role = student | headman | teacher | admin
```

| Значение | Текст ведёт |
|---|---|
| `student` | к старосте группы |
| `headman` | к администратору |
| `teacher` | к администратору — у преподавателя Telegram-бота нет |
| `admin` | **никуда**: эксплуатационная процедура вне продукта |

⚠️ **Вариант `admin` ничего не обещает.** Внутрипродуктового пути возврата
нет по решению, и текст инструкции не должен намекать, что он существует.
Это единственное место продукта, где блок сознательно не предлагает действия.

### 3.3. Состояния

```
state = idle | submitting | invalid-code | rate-limited | expired | offline
```

| Состояние | Что показывает |
|---|---|
| `invalid-code` | ошибка **с остатком попыток** |
| `rate-limited` | обратный отсчёт, submit недоступен |
| `expired` | «запросите новый код в боте» |

`RecoveryCodeForm` ≠ `OtpForm`: внешне похожи, но разный контракт и разный
результат — тот выдаёт сессию, этот право сменить пароль. В библиотеке
это два компонента (проход 05b §2.3).

## 4. ПК-001b — Восстановление: новый пароль

### 4.1. `block/NewPassword`

| Часть | Компонент | Обязательность |
|---|---|---|
| заголовок | h1 «Новый пароль» | обязательна |
| форма | `NewPasswordForm` `variant=reset` — **двойной ввод** | обязательна |
| требования | `PasswordPolicyHint` | обязательна, видима **до** ввода |
| ошибка | `FormError` | видима при ошибке |

**Старый пароль здесь не спрашивается** — это сброс, а не смена. Смена
с вводом старого живёт в профиле (108).

Совпадение паролей проверяется **до отправки**.

### 4.2. Две равноправные точки входа

1. переход после верного кода на 001a;
2. **ссылка с токеном в URL**, сгенерированная администратором.

Отсюда следствие для блока: экран **начинается с `loading`** — проверки
токена, а не с формы.

### 4.3. Состояния

```
state = loading | idle | validation-error | submitting | success
      | invalid-token | expired-token | used-token | offline
```

Три состояния токена различаются обязательно и ведут **на 001a с пояснением**,
а не показывают пустую форму.

`validation-error` — по каждому правилу отдельно, текстом: `PasswordPolicyHint`
показывает, какое именно правило не выполнено.

`success` — сообщение «пароль изменён» → возврат на вход. **Автологина нет:**
пользователь должен убедиться, что новый пароль работает.

## 6. Маршрутизация — влияет на состояния, не на раскладку

```
001 ──«Забыли пароль»──▶ 001a ──верный код──▶ 001b ──success──▶ 001
                                    ▲                  │
ссылка администратора ──────────────┴──────────────────┘
```

Два правила, задающие состояния блоков:

- **прямой заход на 001b без токена** → редирект на 001a с пояснением;
- **заход на 001a и 001b при активной сессии не редиректится на главную**
  (в отличие от 001): пользователь мог открыть ссылку сброса с уже
  залогиненного устройства.

## 7. Что закрыто и что осталось

**Закрыто:** пункт 1 §9 файла 08 — блоки входа больше не выведены из реестра,
они собраны по спеке.

**Осталось открытым по спеке:**

1. **QR-вход на мобильных поверхностях теряет смысл** — сканировать нечем.
   На этапе PWA метод скрывается или заменяется на «войти через Telegram».
   Решение отложено; на десктопные блоки не влияет.
2. **Аудит безопасности цепочки восстановления** отложен владельцем.
3. **Политика пароля как данные, а не константа фронта** — иначе три клиента
   разойдутся с бэкендом. Влияет на `PasswordPolicyHint`: состав правил
   приходит снаружи, компонент их не зашивает.
