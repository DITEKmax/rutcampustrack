# NP01 — пакет для назначения отдельных авторов

Goal: связанный пользователь впервые открывает личный чат бота и получает собственный сохранённый логин и разрешённый начальный пароль; после смены/сброса пользовательского пароля старые credential-данные убираются из прежних карточек. Both `/start` and `/credentials` (включая кнопку CREDENTIALS_LABEL) выполняют private/type/from_user/positive/chat equality guard до profile/credential fetch и до любого credential send/edit. Нет Telegram-from_user, group/supergroup/channel, sender/chat mismatch — безопасная общая подсказка, ноль credential RPC, ноль initial в ответе. Ни cached profile, ни arbitrary request UID, ни shared x-grpc-secret самостоятельно не дают новой capability. Academic доверяет аттестации своего защищённого bot-adapter; поля запроса не являются Telegram-signed end-user proof. Новая InternalJWT из Telegram ID не выпускается.

## Согласовать common contract перед parallel writers

Рекомендуемый additive proto fragment находится в proto-proposal.txt. Два точных RPC: `GetOwnBotInitialCredentials` для uncached own initial; `ManageOwnBotCredentialMessages` с closed oneof register/list-invalidated/complete-render/complete-cleanup для metadata-only durable tracker. Это технический minimum, достаточный для восстановления точных credential message IDs; generic GetUserByTelegramId и его initial_password=10 остаются blank. Existing proto methods/tags/reserved names не менять. Новый response содержит только own login, allowed initial, own UID и технические generation flags; никаких password_hash/changed password или несвязанных профилей. UNKNOWN enum=0 не трактовать как разрешение.

Exact method strings: `rutcampustrack.academic.AcademicGrpcService/GetOwnBotInitialCredentials` и `rutcampustrack.academic.AcademicGrpcService/ManageOwnBotCredentialMessages`. Receiver maps только их к `new ServicePrincipal("notification-bot")`, target ACADEMIC_SERVICE, отдельный BOT_TO_ACADEMIC directed canonical32-byte base64url token. Existing ServicePrincipal и ServiceIdentityServerInterceptor достаточны; новый Academic local wrapper/config, без широкого изменения shared core. Require SSL_SESSION и single canonical x-service-token; domain additionally requires verified bot principal in context so missing registration fails closed. Shared GrpcAuthInterceptor может продолжать требовать x-grpc-secret как дополнительный существующий factor; fallback через этот factor запрещён. Missing/malformed dedicated token/config/plaintext не включает capability.

Python client: только ssl_channel_credentials(CA)+secure_channel; explicit dedicated metadata_call_credentials(AuthMetadataPlugin) per-call, без token в global metadata/composite credentials. Plugin emits x-service-token только при exact service_url `https://{configuredAcademicAuthority}/rutcampustrack.academic.AcademicGrpcService` и method_name из этих двух методов; другой authority/scheme/service/method callback получает error без token. Нет tls flags/CA/dedicated token — protected call fails closed; ordinary RPC compatibility сохраняется. Python public metadata context не предоставляет Java SecurityLevel; secure gRPC transport и exact callback authority/method вместе с server TLS admission — проверяемая модель, не claim mTLS. Нельзя reuse bot-to-Notification token.

## Почему нужны generation metadata и durable message IDs

Исследованы users entity, migrations V1/V24/V51, proto, событие и current writers. credentials_version/password_version/telegram_binding_version отсутствуют. roles_version меняется от grants/admin profile; session_version относится к отдельной session/role selection; updated_at не даёт монотонной credential/binding identity. Не использовать их как поддельные версии credentials.

Common Flyway writer резервирует **следующий свободный** номер после текущего/pending V56 export (не занимать V56). Одна узкая Academic-only migration добавляет users.credentials_version BIGINT positive default1 и users.telegram_binding_version BIGINT positive default1. BEFORE UPDATE row trigger сохраняет версию при неизменной credential tuple `(password_hash, initial_password, password_changed)` и иначе advances+1; Telegram ID NULL↔value/value↔value advances binding version. Version не берётся из timestamp или plaintext/hash fingerprint. Trigger обеспечивает все текущие JDBC/JPA writes без перекрёстного редактирования UserService/credential SQL. Overflow не должен wrap/reuse generation; необработанный новый пути ошибки не допускать. Auth Flyway остаётся disabled.

Та же migration создаёт metadata-only `bot_credential_messages`: record_id, original user_id, original private chat_id, message_id, telegram_binding_version, credentials_version, state/revision, invalidated_by_credentials_version, safe operational timestamps. UNIQUE(chat_id,message_id), index(user_id,state,credentials_version). Никакого login/password/hash/Telegram update body. Не добавлять FK RESTRICT, который блокировал бы принятую final-delete; historical exact-card references не следует cascade удалять вместе с account до provider cleanup. UID остаётся исходным неизменным owner identity и никогда не переатрибутируется новой привязке.

При credential tuple change trigger атомарно помечает существующие карточки этого user_id с меньшей credentials_version invalidated by new version. Пользовательская смена уже держит user row lock; регистрация карточки проверяет свежую identity/versions/grants под тем же user-first lock и коммитится быстро. Никаких provider/network calls внутри DB transaction. Password change/reset/outbox rollback откатывает generation и tracker invalidation вместе. Роль/Binding change не становится password.changed и не устанавливает новую lifetime policy. При необходимости удаления initial при прямом credential-write без существующего caller/outbox новое доменное producer route согласовать с его текущим владельцем; unused Auth UserRepository.updatePassword сейчас не имеет callers.

Redis нельзя брать единственным durable tracker: prod Redis allkeys-lru (compose.prod122), RequestMessageTracker имеет7dayTTL, OTP tracker TTL равен OTP. Existing patterns useful for exact UID/card identity и post-provider receipts, но ни eviction, ни TTL не должны забывать initial-card ID до accepted cleanup. Поэтому scoped table в уже имеющейся Academic PostgreSQL; no new DB/stack/global Redis policy. Незавершённые metadata rows держать до confirmed cleanup; это technical receipt lifetime, не срок жизни credentials.

## Provider sequence и гонки

1. Validate private Telegram update; generic redacted lookup obtains expected UID. Fresh dedicated read проверяет owner/grants/provenance и возвращает current versions.
2. Send **nonsecret placeholder** в тот же private chat. Если Telegram send ответ потерян, неизвестная карточка не содержит credentials. По полученному message_id зарегистрировать exact UID/chat/message/versions через metadata RPC. DB/store failure ⇒ никаких plaintext edits.
3. Register is idempotent by exact card tuple; UID/binding/credential mismatch or password already changed ⇒ reject registration. Stored original versions never updated to new binding/account/initial generation. Fresh dedicated read immediately before edit checks expected versions and active authority again; does not reuse held credential response.
4. Edit only the recorded placeholder to own login+initial card. HTML escape dynamic data. Plaintext held transiently, never saved to tracker/log/exception/request artifact. Provider edit response loss is safe for future cleanup because exact ID is already durable. Post-edit lifecycle recheck removes the known card if credential/grant/binding state changed. Preserve state to allow restart/reconciliation of in-flight edit.
5. Password event handling gets only records marked invalidated for exact UID/generation; requests must not select arbitrary untracked message IDs. Edit each exact old bot card to harmless generic text without login/initial (delete is also allowed when provider accepts). Do not rely solely on deleteMessage age window: edit clears the actual credentials from retained bot message. Own existing cleanup schema/state supports repeated attempts; provider unavailable retains metadata and pending event, never labels cleaned.
6. Credential rendering and invalidation coordinate using durable state/revision, with bounded provider deadlines and event ordering; event-before-registration is fenced by fresh DB generation checks. Event consumer does not acknowledge completed cleanup while an invalidated registered card still has unresolved provider rendering/cleanup. A race cannot discard the record merely because the card was a placeholder when first inspected. Serialize normal in-process same-card actions and use server CAS for restarts/multiple instances; never hold DB locks across provider calls.

Required crash proof: restart after placeholder registration but before edit; edit succeeds but response lost; password event arrives before registration, during edit, and after edit; bot dies during cleanup; store/provider outages recover with known-ID cleanup. Telegram has no send idempotency key: existing queued send success alone cannot prove card cleanup. No blanket exactly-once/provider claims; late uncertain in-flight edit after cleanup remains a concrete risk until bounded concurrency tests/review show recovery. Safe source rule is never forget a known invalidated card or mark complete while its side effect is unresolved.

## Password event and rebinding contract

PasswordChangedEvent currently v1 payload `{telegram_id}` only, schema additionalProperties=false, event_version const1. Change/reset durable SQL already clears initial and calls PasswordChangedOutbox in same user-lock transaction. Upgrade explicit @EventVersion(2), **not silent v1 mutation**. v2 payload required user_id, credentials_version (POST-change invalidating generation), telegram_binding_version; optional positive telegram_id snapshot when currently bound. Existing event_id/source/occurred_at/trace_id retained. Common event schema accepts explicit v1/v2 variants; older consumer contract is recorded separately. `occurred_at` is observability, never generation ordering; event_id dedup prevents replay, credential version fences out-of-order changes.

Append still captures metadata under existing credential transaction. If current Telegram is absent but invalidated credential message records exist, must emit v2 cleanup event; current early return on null Telegram would orphan old cards after unlink. Avoid fresh notification to an arbitrary current Telegram from stale event. v1 lacks original UID/generation: never bind its Telegram ID to whoever owns it now for credential cleanup; classify legacy/unresolved, no fabricated cleanup guarantee.

Cleanup query selects only original UID, records truly invalidated by <= event generation; already cleaned/missing exact card is idempotent. New initial generation, later rebind card, same Telegram ID bound to another UID and other user's card remain untouched. Old tracked credential card can be sanitized at its ORIGINAL recorded chat/message even if binding/grants were later revoked: this removes a disclosed secret and does not authorize a new delivery. Sending a separate safe change notice requires fresh active own authority and current UID/Telegram/binding version matching event snapshot; mismatch suppresses notice, never redirects it. Cleanup must not be denied merely because the account is now archived; read the narrowly authenticated metadata records, not SQLRestriction generic profile. Removed account remains eligible only for sanitation of exact persisted original cards, not profile/credential delivery.
