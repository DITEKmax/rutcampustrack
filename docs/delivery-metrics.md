# Эффективность доставки — решение 2026-09-21

Цель: сокращать время от задания до работающего действия в общей сборке и повторную работу. Предел параллельности определяется текущими RULES и фактическими slots; это не целевая загрузка. Актуальный STOP/GO указан в CURRENT; этот документ сам не меняет состояние продукта. Метрики не заменяют приёмку и не уменьшают требования безопасности.

## Один источник данных

Root ведёт `.agent/orchestration-v2/metrics/packages.csv`: одна строка на связанный пакет, обновление при start, ready, integrated, accepted или STOP из существующих сообщений, команд и логов. Автор передаёт показатели в обычном summary. Отдельных агентов/сервисов/таймеров/тестов для этого не создавать. Не более нескольких минут учёта на пакет; если подробный учёт мешает работе, оставить timestamps, результаты и причины потерь. Старые пакеты задним числом не хронометрировать.

Поля:
- `package_id`, `kind` (product/process), `scope`, `owner`, `revision`, `state` — стабильный пакет и результат. Не дробить пакет ради роста throughput.
- `started_at`, `ready_at`, `integrated_at`, `accepted_at`, `updated_at` — ISO8601 UTC, неизвестное пусто. `owner_pause_min` — известная пауза владельца, исключается из elapsed.
- `implementation_min`, `product_fix_min`, `harness_fix_min`, `verification_min`, `review_min`, `coordination_min` — наблюдавшиеся agent-minutes, включая root coordination; отдельные непересекающиеся категории внутри одного исполнителя. Параллельные agent-minutes НЕ равны wall-clock времени. Не оценивать расход токенов по минутам.
- `dependency_wait_min`, `heavy_wait_min`, `integration_wait_min` — ожидание пакета; перекрывающиеся интервалы не суммировать как общий elapsed.
- `check_runs`, `repeat_pass_runs`, `repeat_pass_reasons`, `harness_failures`, `product_failures`, `review_rounds`, `handoffs`, `ready_queue_size` — известные события; повторный PASS требует конкретного нового изменения/риска. Генератор/сборка не отдельная принятая история.
- `accepted_ids`, `evidence`, `next_action`, `sample_complete` — связь с пользовательским результатом; complete означает полноту измерений, не готовность продукта. Отсутствие данных = unknown, не0.

## Расчёт и сравнение

В обычном итоговом сообщении: что принято в main; сколько пакетов готово, но ждёт; время start→integration и start→acceptance без owner pause, если все времена известны; основные ожидания; число повторных PASS и их причины; продуктовые исправления отдельно от обвязки.

Координационная доля = coordination / сумма известных activity agent-minutes, только при полном покрытии категорий. Аналогично доля verification+review и доля harness_fix; доля проверок сама по себе не признак избытка. Не делить agent-minutes на elapsed. Не выводить процент по неполным данным. Отдельно показывать sample size и риск/тип пакетов. Расход tokens/usage добавлять только при доступной атрибуции конкретному пакету; аккаунтный расход не приписывать одному агенту.

Исторический baseline: `.agent/orchestration-v2/metrics/baseline-20260921.md`. Он качественный: надёжной хронометрии прошлых итераций нет. Первые две продуктовые итерации — baseline нового режима; нельзя честно заявить ускорение x2 по сравнению с ненаблюдавшимся прошлым. Затем сравнивать похожие пакеты и median cycle time при хотя бы3 завершённых сопоставимых пакетах, показывая размер выборки. Не проводить искусственные повторы ради эксперимента.

## Сигналы и действия

- Два пакета ждут интеграции: ближайший свободный ресурс на разгрузку main, не на новую ветку.
- Повторный PASS без нового риска/изменения: остановить повтор; использовать уже полученное evidence.
- Вторая неудача по той же причине: сменить гипотезу, минимальная правка обвязки; третьего одинакового запуска нет.
- Coordination >20% двух полных сопоставимых наблюдений: убрать лишнюю передачу/пересказ, объединить ownership. Это начальный диагностический порог, не SLA и не повод скрывать учёт.
- Ожидание зависимости преобладает: закончить общий контракт или назначить действительно независимую работу, не увеличивать агентов вокруг одного файла.
- Очередь heavy при свободной памяти/CPU: рассмотреть второй изолированный lease; без данных о ёмкости сохранить один.
- Verification велика: посмотреть, какие риски она закрыла и были ли дубли; обязательные gates и существенные auth/history/transaction проверки не убирать ради цифры.
- После двух итераций рост незавершённого WIP/ожидания без прироста доставленных действий: уменьшить одновременно открытые пакеты. Выигрыш оценивается доставкой и исправлениями после интеграции, не занятостью всех доступных агентов.

Результат решения: в summary коротко «оставляем/меняем число параллельных пакетов, причина, evidence». Новая система мониторинга не нужна.

## Модельный эксперимент 2026-10-01
По решению владельца текущая итерация использует GPT-6.1 Sol high для всех новых исполнительских и review-задач; Luna временно исключена. Сравнивать время до интеграции/приёмки и существенные findings/corrections по уже существующему ledger, без дополнительных тестов или искусственных повторов. Первый пакет наследует незавершённый Luna WIP и известные findings: это смешанная работа, не чистое сравнение моделей; ускорение заранее не заявлять. Стоимость по агенту указывать только при доступных измерениях, не выводить из API-цены или общего аккаунтного лимита.
