## 3. Vue: страницы остаются компонентами, но не становятся монолитами

Твоё пожелание «не пихать всю страницу в Vue» трактуется как смысловая декомпозиция. `.vue` у страницы нормально; плохо, когда в ней одновременно вся разметка, API, бизнес-правила, состояние и стили приложения.

```text
frontends/packages/mobile-app/src/
  app/                         # bootstrap, router, providers
  pages/today/TodayPage.vue     # только композиция страницы
  features/schedule/
    index.ts                   # публичный API
    routes.ts
    ui/
      DaySchedule.vue
      DaySchedule.module.pcss
      LessonCard.vue
      LessonCard.module.pcss
    model/useSchedule.ts
    api/getDaySchedule.ts
    types/
    lib/
  shared/                      # только действительно общие механики
```

`App.vue` содержит корень приложения, outlet маршрутов и действительно глобальные host-элементы. `TodayPage.vue` компонует блоки. Feature владеет своей логикой; transport вынесен в API-слой; платформенный адаптер предоставляет возможности PWA/TMA. Не вводить искусственное правило «не более N строк» вместо проверки ответственности.

Общие правила из [frontend-исследования](C:/Users/maksd/Documents/Codex/2026-08-30/vue-vue-pcss-eslint-c-users/outputs/repository-research-contour/research/reports/frontend.md:27): typed props/emits, strict TypeScript, публичные границы feature, Pinia/composables, отдельный transport и слой токенов. Компонентные `.module.pcss` — выбранная адаптация исследованного подхода; глобально остаются reset, шрифты, токены и темы. Не копировать fixture-тексты из Figma в production-компоненты как данные.

**Владение состоянием определить заранее:** серверные данные имеют один cache/query owner; Pinia хранит принадлежащее приложению состояние, session context и нужные межэкранные черновики. Не поддерживать две независимые копии одного серверного ответа в query cache и store. Выбор конкретной query-библиотеки — отдельная запись в frontend ADR, а не следствие наличия React Query в старом коде.

PWA и Mini App используют общие мобильные сценарии, но разный bootstrap/auth и адаптеры навигации, viewport, файлов и хранения. Объект Telegram не должен попадать в доменный код. Веб позже переиспользует подходящие компоненты/контракты и получает собственную композицию. Роли приложения не превращаются в копии всего frontend.

## 4. BFF, сервисы и новая модель данных

Принятое [TRANSPORT.md](C:/Users/maksd/OneDrive/Desktop/rutcampustrack-design/knowledge/TRANSPORT.md:8) уже задаёт один отдельный BFF для поверхностей, REST снаружи и gRPC внутри. Gateway и BFF имеют разные обязанности. Бизнес-операции и агрегаты остаются у владельцев домена; BFF не становится общей базой данных и местом всех расчётов.

### 4.1 Контракт раньше параллельной реализации

Для каждой истории контракт задаёт запрос/ответ, права и серверные признаки доступности действий, ошибки, даты/часовой пояс, пагинацию, версии, поведение повторной команды и ожидаемую согласованность. Затем frontend получает моки, backend — ту же спецификацию.

Для нового публичного BFF рекомендую spec-first OpenAPI с генерацией клиента и проверкой реализации. Это **предложение**: старый проект использует Java API-contract модули и OpenAPI-снимки. Нельзя объявить ручной OpenAPI и ручные Java DTO двумя независимыми канонами. Альтернатива — сохранить Java-first с обязательным утверждаемым контрактным diff до работ фронта; выбрать ровно один процесс.

BFF не исправит одной сборкой DTO одиночную роль старой модели, новую семантику назначений, переходы статусов или конкурентные команды. По каждой истории backend-агент составляет необходимую дельту домена. Нужные изменения входят в ту же партию; unrelated refactoring оформляется отдельно.

### 4.2 Старые данные не сохраняем

Можно развернуть новую схему в чистом окружении и не строить совместимость со старыми frontend API. Не нужны dual-write и backfill только ради прежних клиентов. Старую реализацию сохранить в Git как историю до замены, не обязательно поддерживать её работающей.

Нужны воспроизводимое создание чистой БД, новые demo/test seeds и проверка ограничений. После первого нового выпуска последующие миграции снова становятся обычной частью жизненного цикла. Не следует бесконтрольно переписывать историю Flyway внутри уже использованной базы; новый baseline проверяется на новом наборе volumes/schema. Фактическое удаление конкретного окружения — отдельная операция последующего этапа, не действие этого отчёта.

### 4.3 События и связи

Для каждого изменённого сообщения фиксировать:

```text
event meaning → producer → schema/version → routing → consumers
              → transaction/outbox → deduplication → retry/DLQ
              → ordering/revision → observable failure → test evidence
```

В RabbitMQ различать exchange, routing key и queue/binding; слово «топик» не заменяет карту маршрутизации. Новые связи выводятся из сценария, а не из желания переименовать все старые события. Уже имеющиеся `proto`, `event-schemas`, outbox и idempotency — кандидаты на переиспользование после проверки.

Нужны тесты повторной и запоздалой доставки, не только тест happy path publisher. Отказ от старых данных не отменяет эти требования. Чтение и команды BFF должны иметь понятные тайм-ауты и обработку частичных отказов; backend не должен отдавать полные чужие данные с надеждой на фильтрацию в Vue.

## 5. Offline: ограниченный продуктовый сценарий

**Подтверждено владельцем:** offline студенту в PWA для расписания и ДЗ; TMA — online. Не утверждается техническая невозможность любых кешей в Telegram: это граница данного продукта.

**Предложение для первой реализации:** offline-чтение последнего сохранённого набора данных и shell приложения. Без отправки отметок, заявок, смены роли и редактирования из очереди после восстановления сети. Локальная отметка «ДЗ выполнено» тоже является записью и не включается автоматически.

| Ситуация | Предлагаемое поведение |
|---|---|
| Данные уже загружены, сеть пропала | можно открыть сохранённое расписание и текст ДЗ |
| Приложение закрыли и открыли offline | установленная PWA открывает shell и сохранённые данные |
| Нужного дня/ДЗ нет в сохранённом диапазоне | явно сообщить отсутствие сохранённых данных, не показывать пустоту как подтверждённое отсутствие занятий |
| После кеширования сервер изменил расписание | offline не обещать актуальность; после сети обновить снимок |
| Выход или смена пользователя/роли | не позволить следующей сессии увидеть чужой кеш |
| Запрошен файл ДЗ | доступен offline только если заранее сохранён и это включено в политику |
| TMA без сети | понятное недоступное состояние и повтор после подключения |

До реализации определить диапазон предварительной загрузки расписания/ДЗ, срок хранения, лимит объёма, вложения, очистку и поведение истёкшей сессии offline. Предлагаемый технический формат снимка содержит owner/scope/revision/fetchedAt и данные. Это не команда добавлять новый `freshness-mark` в Figma: тексты и отображение использовать из принятых состояний, визуальные пробелы выносить владельцу.

Проверять реальный PWA service worker. MSW-режим для разработки UI не является доказательством offline-работы production-сборки. Тесты SW проводить отдельно с настоящим SW и управляемым тестовым API.

## 6. Команда: один оркестратор, ограниченные исполнители, независимая приёмка

✏️ 05.09.2026 — прежняя таблица ролей ниже архивная. Действуют четыре логические
роли: orchestrator, explorer, developer, reviewer. Architect/security/ops/visual
назначаются по необходимости. Постоянных frontend/backend копий, observer
и judge не создаём; новый workflow и маршрутизация — §19 и комплект.

Предлагаются **роли**, не постоянно работающие процессы. Один агент может последовательно выполнять несколько ролей на разных партиях, но автор конкретного изменения не является его единственным принимающим reviewer.

| Роль | Ответственность | Результат | Запись |
|---|---|---|---|
| Оркестратор / планировщик / product manager | источники, stories, зависимости, объём, распределение, интеграция и закрытие | карточка партии, обновлённый board, решение по evidence | документы управления и интеграционные изменения |
| Frontend worker | Vue, PCSS, общие UI, platform adapters | код + собственные проверки + handoff | назначенные frontend paths |
| Backend worker | BFF, сервисы, БД, proto/events | код + contract/integration checks | назначенные backend paths |
| Acceptance reviewer | независимо сверяет историю, diff и проверки | PASS / FAIL / BLOCKED по критериям | production read-only |
| Domain/security reviewer | права, приватность, транзакции, повтор команд, события | конкретные воспроизводимые нарушения | production read-only |
| Browser QA | поведение приложения, визуальная сверка, accessibility, platform flows | шаги, screenshots/traces, observed vs expected | только тесты/артефакты в выделенной области |
| Observer | наблюдает уже запущенный build/test/CI, читает логи | completion/failure/зависание и ссылки | не редактирует код |

BFF-контракт проектирует backend-агент при участии frontend, принимает оркестратор с domain-review при необходимости. Постоянный отдельный «архитектор», который дублирует этот процесс, сначала не нужен. Release/DevOps-исполнитель подключается отдельным заданием для окружения и выпуска, а не работает в фоне без задач.

OpenAI документирует специализированных subagents и рекомендует осторожность с одновременной записью. Не заданные model/effort могут наследоваться; custom agent задаётся TOML-файлом с `name`, `description`, `developer_instructions`. Конкретная команда выше — проектная схема. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

### 6.1 Практическая параллельность

Для старта достаточно оркестратора и до трёх одновременно активных подзадач. Пока frontend и backend пишут код, третий слот используется для исследования контракта или проверок готовой независимой части. После стабилизации diff исполнителей сменяют acceptance reviewer, domain reviewer и browser QA. Не требуется одновременно держать все роли из таблицы.

Субагент запускается только на конкретную работу с ожидаемым артефактом. Оркестратор не запускает бесконечные «посмотри ещё раз». Если задачу можно завершить локально без полезной параллельной работы, отдельный агент необязателен. Это предложенный порядок проекта, не ограничение возможностей моделей.

### 6.2 Защита от конфликтующих правок

- На каждый путь и контракт в партии — один writer. Общие lockfile, конфигурация сборки, generated client и contract source не редактируются двумя агентами одновременно.
- Для независимых крупных изменений использовать отдельные worktrees/ветки; интегрирует один владелец. Для маленьких изменений общего checkout достаточно явного владения файлами.
- **Subagent сам по себе не гарантирует отдельный worktree.** В текущей среде субагенты разделяют рабочую директорию. Изоляцию нужно создавать и назначать явно, когда она нужна.
- Worktree отделяет файлы, но не порты, базы, очереди и Docker volumes. Тестовым окружениям назначать разные project names/порты; миграциями общей тестовой базы управляет один процесс.
- Reviewer получает стабильный commit/diff. Новое изменение после review инвалидирует затронутую часть вердикта.

Codex поддерживает работу с Git worktrees; выбор ветки/checkout и перенос результата — отдельные операции. [Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

## 7. Модели: официальные факты и рекомендуемые назначения

### 7.1 Что подтверждают официальные страницы

Ниже именно API model IDs и API reasoning levels; интерфейс Codex может предоставлять другой набор режимов.

| Модель | Официальное назначение | `reasoning.effort` в API | Источник |
|---|---|---|---|
| `gpt-6-astra` | самые сложные сквозные задачи, reasoning и coding | `low`, `medium`, `high`, `xhigh`, `max` | [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) |
| `gpt-5.6-sol` | флагман GPT-5.6 для сложной работы | `none`, `low`, `medium`, `high`, `xhigh`, `max`; default API — `medium` | [Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol) |
| `gpt-5.6-terra` | баланс возможностей и стоимости | тот же список, default API — `medium` | [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) |
| `gpt-5.6-luna` | экономичные массовые задачи | тот же список, default API — `medium` | [Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna) |

`gpt-5.6` — alias Sol. Для воспроизводимости назначения ролей в примерах используются явные имена. Названия `solm` и `tera` из сообщения трактуются как Sol и Terra. API-default не равен выбранному effort в Codex. [Руководство GPT-5.6](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6).

**Не смешивать три разных механизма:** уровень рассуждения модели; режим Ultra в конкретном продукте; количество запускаемых подзадач. В API-карточках перечисленных моделей `ultra` не указан как значение `reasoning.effort`. Документация subagents описывает Ultra в поддерживаемых поверхностях, а общий Config Reference перечисляет более узкий набор, чем model guide. Поэтому переносить `ultra` из UI в API JSON или TOML без проверки клиента нельзя. Для примеров ниже выбраны `low/medium/high`, по которым расхождения нет. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Config Reference](https://learn.chatgpt.com/docs/config-file/config-reference).

рутина Luna medium; Sol high — hard engineering и важное review.
Astra low — root, medium/high — архитектура, неоднозначность и критическое решение.

**Эта таблица — стартовая гипотеза проекта, не рекомендация OpenAI для твоего репозитория.**

| Роль | Начальная конфигурация | Когда усилить/сменить |
|---|---|---|
| Оркестратор | Astra `low`, сохраняя имеющуюся настройку | сравнить `medium/high` на конфликтных историях и архитектуре |
| Frontend worker | Sol `medium` | `high` для сложного состояния, offline и платформенной интеграции |

| Domain/security reviewer | Astra `high` | расширенный effort только по сложности и результатам |

Не считать Luna «непригодной к коду», а Terra «автоматически хорошим судьёй». Решение принимается по твоим задачам. Для первого сложного сценария приоритет качества; удешевлять подтверждённо повторяемые задачи после сравнения. Такой порядок — сначала требуемое качество, затем стоимость/скорость — соответствует [официальному руководству выбора модели](https://developers.openai.com/api/docs/guides/model-selection).

### 7.3 Что дать каждой модели

- **Astra-оркестратору:** карту приоритетов, принятые решения, release matrix, зависимости, owner boundaries, актуальный board и правила эскалации. Полные логи вместо этой структуры не нужны.
- **Sol-исполнителю:** одну историю, конкретный contract revision, назначенные файлы, образцы компонентов/стилей, исполнимые acceptance criteria и команды проверки.
- **Terra-проверяющему:** ограниченный diff, ожидаемое поведение, среду воспроизведения и форму evidence. Не поручать «проверь всё» без границ.
- **Luna-observer:** известную команду/идентификатор прогона, ожидаемый сигнал завершения, пути логов и компактный формат ответа. Запрет самостоятельных правок и повторных запусков.

Это различия в объёме задач и контексте, а не четыре несовместимых набора проектных правил. У всех один канон продукта.

### 7.4 Что подтверждено со скриншотов

Руководство Astra советует проверять skills/AGENTS.md на неоднозначные ограничения, явно задавать автономность и делегирование, не повторять достаточные проверки без новой причины. При миграции `none/minimal` заменяют стартовым `low`; в других случаях сохраняют текущий effective effort и сравнивают результат. Поэтому автоматически понижать или повышать твоё `low` оснований нет. Это не означает, что `low` оптимален для каждой роли. [Astra: prompting и migration](https://developers.openai.com/api/docs/guides/latest-model).

Для GPT-5.6 руководство рекомендует при переходе с GPT-5.5/5.4 сравнить прежний effort и уровень ниже на репрезентативных задачах. Это процедура сравнения, не правило «всегда меньше reasoning». [GPT-5.6 guide](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6).

## 8. Как настроить Codex: примеры для последующей установки

✏️ 05.09.2026 — примеры §8.3–8.5 оставлены для истории, **не устанавливать**.
Готовые файлы находятся в `_work/agent-bootstrap/project/.codex/`.
В файлах дочерних ролей model/effort не закреплены: оба параметра передаются
при spawn. По официальному precedence фиксированные значения файла роли
перекрывают spawn, поэтому прежний подход мешал динамической маршрутизации.
Фактические permissions наследуются от среды; текстовый read-only не является ACL.

### 8.1 Использовать локальный Codex, не строить свой agent framework заранее

Для первого этапа достаточно Codex в проекте, custom subagents, Git и файлов состояния. Собственный Responses/Agents SDK supervisor — отдельный проект и сейчас не требуется. Примеры ниже относятся к Codex configuration, не к настройкам моделей внутри Java/Vue приложения.

Пользовательская конфигурация находится в `~/.codex/config.toml`, проектная — в `.codex/config.toml`; проектные слои применяются для доверенного проекта. Явные CLI overrides имеют более высокий приоритет. Изменение файла не доказывает, что уже открытая задача использует новые параметры: проверить effective model/effort в новой задаче. [Config basics](https://learn.chatgpt.com/docs/config-file/config-basic).

### 8.2 Предлагаемый `.codex/config.toml`

```toml
model = "gpt-6-astra"
model_reasoning_effort = "low"

[agents]
enabled = true
max_concurrent_threads_per_session = 3
default_subagent_model = "gpt-5.6-terra"
default_subagent_reasoning_effort = "medium"
```

Лимит относится к spawned-agent threads **без основного агента**. Это предлагаемый предел одновременной работы, не обещание доступности дополнительных ресурсов. Legacy `max_threads` существует, но новый пример использует актуальное имя. Назначение конкретной роли важнее общего fallback. Проверить поддержку полей установленной версией клиента до начала реализации. [Config Reference](https://learn.chatgpt.com/docs/config-file/config-reference).

Не менять approval/sandbox ради ускорения и не включать full access по этому отчёту. Для исполнителей нужен доступ к workspace и разрешённым средствам проверки; для reviewers — минимальные права. Approval и sandbox — разные ограничения: запрет вопросов не расширяет разрешения. [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security).

✏️ 05.09.2026 — уточнение настройки. Если среда уже использует `default_permissions`, не добавлять к нему несовместимый `sandbox_mode` из примеров: выбрать поддерживаемый механизм и проверить effective policy. Файловый sandbox не является запретом записи через внешний MCP. `acceptance_reviewer` проверяет код; встроенный `approvals_reviewer` проверяет разрешение инструментального действия и не заменяет приёмку истории. Настройки automatic approval review этим отчётом не меняются. [Config Reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security).

### 8.3 Пример frontend-агента

Файл `.codex/agents/frontend_worker.toml`:

### 8.5 Пример принимающего reviewer

Файл `.codex/agents/acceptance_reviewer.toml`:

```toml
name = "acceptance_reviewer"
description = "Независимая приёмка стабильного изменения по истории и проверяемым критериям."
model = "gpt-6-astra"
model_reasoning_effort = "high"
sandbox_mode = "read-only"
developer_instructions = """
Сначала прочитай действующие требования и критерии, затем исследуй diff и evidence.

Разделяй подтверждённый дефект, вопрос и улучшение вне scope.
Не исправляй код и не меняй тесты. Figma не редактируй.
Верни PASS, FAIL либо BLOCKED с точными причинами и ограничениями проверки.
"""
```

Эти примеры используют документированный формат custom agents. Файл роли задаёт model и effort явно; не рассчитывать на неявное наследование сильной модели от оркестратора. Настройки дочерней роли не должны считаться обходом live permissions родителя. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Остальные роли оформить тем же форматом с обязанностями из §6 и моделями из §7. Browser QA может писать screenshots/traces и тесты в выделенную директорию, но не менять production-код. Observer — read-only; работа с уже запущенным процессом предпочтительнее запуска дубликата. Read-only reviewer не обязан запускать инструменты, которые пишут build/cache: прогон делает QA в отдельной разрешённой среде.

### 8.6 Проверка настройки до реальной партии

1. Открыть существующий `rutcampustrack` как проект, проверить обнаружение проектной конфигурации и инструкций.
2. Проверить доступность точных model IDs и effort в установленном клиенте/аккаунте. Наличие официальной API-карточки не гарантирует доступ через любой аккаунт Codex.
3. Выполнить короткую пробную делегацию на чтение: Luna составляет список файлов, Terra проверяет ссылки, Sol оценивает одну существующую feature. Не менять код.
4. Сверить реально выбранные модели/effort с заданными. Не принимать произвольное текстовое самоописание модели как единственное доказательство настройки.
5. Проверить, что роли видят нужные документы и команды, а Figma-write исключён из их рабочих заданий. Где клиент допускает фильтрацию инструментов, отключить write-инструменты Figma; текстовый запрет остаётся обязательным.
6. После успешной проверки запускать первую ограниченную реализацию. Если настройка не поддерживается, фиксировать версию/ошибку и корректировать конфигурацию, а не молча работать на другой модели.

## 9. Какие инструкции и skills нужны

### 9.1 Не объединять все правила в гигантский AGENTS.md

Корневой `AGENTS.md` должен содержать цель этапа, карту источников, запрет Figma-write, правила делегирования/владения и ссылки на workflow. `frontends/AGENTS.md` — Vue/PCSS, `services/AGENTS.md` — backend-инварианты, `tests/AGENTS.md` — правила evidence.

Codex собирает цепочку инструкций от корня к рабочей директории; ближайшие инструкции уточняют предыдущие. Документирован предел суммарного объёма по умолчанию 32 KiB. Поэтому вложенный AGENTS не стоит считать гарантированно загруженным при старте из корня: карточка подзадачи дополнительно называет инструкции её scope. Архивы не подключать как активные правила. [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

### 9.2 Предлагаемое ядро инструкций оркестратора

```text
Ты координируешь реализацию новой версии RutCampusTrack в одном репозитории.
Сначала установи действующее требование по source manifest и поздним решениям владельца.
Старый код показывает существующую реализацию, но не отменяет новые принятые требования.
Веди traceability: story → решение → контракт → реализация → проверки.

Разделяй независимую реализацию frontend и backend между субагентами после контракта.
На каждый путь и контракт назначай одного writer. Ограничивай число активных задач.
Для существенного изменения назначай независимого reviewer и проверку реального сценария.
Самоотчёт автора и большинство голосов не заменяют воспроизводимое доказательство.

Выполняй разрешённую работу до критерия готовности партии.
Рутинные технические решения принимай в пределах ADR и scope, фиксируя последствия.
Спрашивай при открытом продуктовом выборе, противоречии принятых требований,
изменении scope или необходимости отдельного разрешения среды/владельца.
Блокируй только зависимую часть; независимые задачи продолжай.

Figma не меняй без явного разрешения владельца на конкретную правку.
Не объявляй новый scope, permission или доменное правило принятым по собственной инициативе.
После обязательных проверок повторяй их только при изменении, отказе или открытом риске.
При остановке из-за инструкции назови файл, пункт и почему он применим.
Закрывай партию по evidence и выдай её статус; не начинай следующую незаказанную партию.
```

Это предлагаемый проектный текст. Он не отменяет системные разрешения, sandbox и текущий режим «только отчёт». Правило kit «одна партия — одна остановка» можно сохранить: внутри согласованной партии агенты работают автономно; между партиями владелец видит результат. Для непрерывного выполнения нескольких партий понадобится отдельное прямое разрешение на такой объём.

### 9.4 Что убрать или уточнить в старой обвязке

- Дублирующие остановки, когда работа уже разрешена; общий запрет любой технической догадки заменить различием routine choice и product decision.
- Обязательный «полный аудит всего проекта» перед маленьким изменением.
- Приоритет старого CLAUDE/кода над новым продуктом.
- Автоматическое чтение всего реестра, всех stories и всех логов каждой подзадачей.
- Двойные копии skills из kit/.claude и старых наборов.
- Неограниченные review loops и требование фиксированного числа замечаний.

Сохранять полезные инварианты. Правила зависимостей формулировать адресно: новый пакет или изменение выбранного стека — решение в рамках согласованного scope/ADR; восстановление по lockfile не должно требовать повторного продуктового согласования. Реальное разрешение сети/среды этим не отменяется.

## 10. Контекст, карточки задач и контроль job stories

Оркестратор не должен помнить весь проект только в переписке. `board.yaml` отражает текущие состояния, `traceability.yaml` — связи требований, `batches/` — задания, `evidence/` — подтверждения. Изменяет общее состояние один владелец; исполнители возвращают handoff, а не соревнуются за board.

Пример структуры карточки; идентификатор ниже иллюстративный, не существующая новая job story:

```yaml
id: BATCH-STUDENT-READ-01
status: ready
goal: Студент читает расписание и ДЗ в PWA и TMA; PWA показывает сохранённое offline.
story_refs: []                 # обязательные реальные ID до запуска
source_refs: []                # действующие документы и разделы
decisions: []                  # только принятые решения
contract_revision: pending    # заменить реальным commit/hash до реализации
owners:
  frontend: frontend_worker
  backend: backend_worker
  acceptance: acceptance_reviewer
write_paths: {}               # непересекающиеся наборы путей
acceptance:
  - id: AC-01
    rule: Ответ соответствует правам текущего студента.
  - id: AC-02
    rule: После online-загрузки расписание и текст ДЗ читаются в PWA без сети.
  - id: AC-03
    rule: TMA при потере сети показывает недоступность без ложного успеха.
evidence: []
open_questions: []
```

Перед запуском заполнить ссылки/области и уточнить offline-политику. Карточка с `pending` не является готовым контрактом. Полезные состояния: `proposed → ready → in_progress → mock_verified → integrated → reviewed → accepted`; `blocked` обязательно имеет причину и зависимость.

В handoff агент возвращает: baseline/commit, что изменил, какие criteria покрыты, команды и exit codes, ссылки на артефакты, что не запускалось, реальные blockers. Краткая сводка идёт оркестратору; полные логи лежат в evidence. После compaction/перезапуска оркестратор читает board и незакрытые карточки, а не начинает всё заново.

## 11. Судьи и аудиторы: принимать по доказательствам

### 11.1 Разделить вопросы проверки

**Acceptance reviewer:** реализовано ли принятое поведение истории, включая отрицательные сценарии? Не потеряна ли функция? Не появилась ли самовольная новая?

**Domain/security reviewer:** корректны ли серверные права, scoped DTO, смена роли, изоляция кеша, транзакции, повтор команд и доставка событий?

**Browser QA:** что реально происходит при кликах, Back, keyboard, перезапуске PWA и потере сети? Совпадает ли результат с готовым дизайном? Не объявлять отличие дефектом только потому, что reviewer предпочитает иной стиль.

**Observer:** завершился ли конкретный тест, какая первая полезная ошибка и где артефакт? Observer не выдаёт функциональную приёмку по зелёному логу.

### 11.2 Формат finding

```text
ID / severity / confidence
Criterion или инвариант:
Путь и строка / маршрут / operation:
Условия воспроизведения:
Фактический результат:
Ожидаемый результат:
Evidence:
Статус: confirmed defect / needs decision / out-of-scope suggestion
```

Не требовать от каждого судьи «минимум пять замечаний». Не штрафовать короткий правильный код. Не просить модель раскрывать скрытую цепочку рассуждений; достаточно проверяемого обоснования и evidence.

### 11.3 Протокол независимости и исправления

1. Дать reviewer требования и стабильный diff; сначала получить самостоятельную оценку.
2. Затем показать ответ автора и спорные evidence для разрешения разногласий.
3. Подтверждённый blocker исправляет назначенный writer, а не reviewer незаметно для остальных.
4. Повторно проверить изменённую область и затронутые инварианты. Если код не менялся и новых фактов нет, ещё один круг не нужен.
5. При разногласии выполнить воспроизведение или проверить источник. При продуктовом пробеле — решение владельца. Не голосовать о том, какие права должен иметь преподаватель.
6. Оркестратор закрывает все обязательные criteria и указывает residual risks. Он не может «перевесить» зелёными мнениями подтверждённый серьёзный дефект.

Для LLM-as-judge OpenAI рекомендует ясную rubric, pass/fail или сравнение вариантов, калибровку по человеческим оценкам и учёт position/verbosity bias. Это поддерживает подход к оценке, но не делает суждение модели доказательством корректности кода. [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

### 11.4 Когда какой объём review

| Изменение | Достаточная проверка |
|---|---|
| Текст/локальный стиль без поведения | lint/build по необходимости и визуальная сверка изменённого состояния |
| Новый сценарий UI | component/router tests, mock-browser checks, acceptance review |
| BFF endpoint/доменная команда | contract + integration + реальный E2E сценария |
| Auth/roles/privacy/schema/events/offline cache | дополнительно независимый domain/security review |
| Выпуск PWA/TMA | сборка production, целевые устройства, SW update/offline, smoke и эксплуатационная готовность |

## 12. Тестирование начинается с первой партии

Предлагаемые инструменты согласуются с уже имеющейся инфраструктурой; конкретная схема тестов — собственный стандарт проекта. Reference-исследование не обнаружило реализованной системы frontend-тестов, поэтому нельзя назвать её «перенесённой из эталонного репозитория».

| Слой | Проверки | Сервер |
|---|---|---|
| Unit/component | Vitest + Vue Test Utils: формы, состояния, composables, разрешённые действия | моки/локальные функции |
| Browser UI | Playwright: маршруты, длинные данные, ошибки, visual/a11y | MSW или управляемый mock API |
| Public contract | BFF implementation ↔ выбранный контракт; фикстуры ↔ schema | реальный BFF для conformance |
| Domain integration | JUnit/Testcontainers: БД, gRPC, права, atomicity, outbox/consumer | изолированный стек |
| E2E | реальные auth, чтение, отметка, заявка/решение и эффект | BFF + сервисы |
| PWA/TMA | SW, cold offline reopen, update, Telegram host, keyboard, files | production-like build и устройства |

Моки не располагаются внутри production-компонентов. Они моделируют API-границу по утверждённой версии контракта и включают error/empty/timeout/conflict. Неизвестный запрос в тесте должен обнаруживаться. Generated types сами по себе не проверяют рантайм-ответ сервера.

Старые Java tests и полезные сценарии сохранить после проверки актуальности. React UI tests переписать под Vue по поведению, а не построчно по старой реализации. Не снижать coverage threshold для прохождения миграции; не переносить старый threshold вслепую на другой объём кода. Тесты должны обнаруживать реальные нарушения, а не повторять ту же формулу, что в production.

Для новой обязательной suite отсутствие тестов — ошибка, а не зелёный `--passWithNoTests`. UI-прогоны на моках, реальные E2E и offline-SW прогоны должны иметь разные статусы. Visual baselines обновляются только после объяснения изменений, не автоматически ради зелёного CI.

## 13. Партии реализации и критерии выхода

| Партия | Работа | Параллельность | Что должно быть доказано |
|---|---|---|---|
| P0 — источники и scope | перенос документов, supersedes, release matrix, инструкции | исследование/сверка на чтение | одна актуальная ссылка на каждое требование, нет скрытых конфликтов |
| P1 — контракты и окружение | session/roles, первый read contract, clean DB, seeds, выбранный контрактный процесс | frontend foundation может идти после выбора стека | воспроизводимый bootstrap и согласованный API |
| P2 — первый реальный срез | вход → «Сегодня» → расписание/ДЗ PWA и TMA | Vue и BFF/domain | один сценарий прошёл с реальным backend в обеих оболочках |
| P3 — PWA offline | сохранённое расписание/ДЗ, cold reopen, очистка/обновление | UI/QA и cache implementation по областям | проходит настоящая production-SW проверка |
| P4 — действия и связанные роли | отметка → заявка → решение старосты; далее остальные истории по зависимости | feature + backend после каждого контракта | эффекты и права подтверждены end-to-end |
| P5 — остальные функции release scope | teacher/admin и остальные сценарии в принятом объёме | независимые истории с ограничением writers | вся release matrix имеет evidence либо явное решение об исключении |
| P6 — подготовка выпуска | сборки, deployment, config, мониторинг, devices, smoke | профильные проверки | выпуск воспроизводим, нет подтверждённых незакрытых blockers |
| P7 — веб | доработка desktop/web после мобильного запуска | по отдельному плану | общие части используются без копирования доменных правил |

Порядок — предложение, не календарная оценка. PWA и TMA нужно проверять с первого интегрированного среза: обещание «прикрутим Telegram в самом конце» откладывает риск авторизации и host behavior. Выпуск всей матрицы нельзя объявлять готовым после одного студенческого сценария.

До нового запуска отдельно решить судьбу Telegram bot/уведомлений и document-renderer: новые события могут затронуть их, даже если web-panel пока не переносится. Существование новых mobile-экранов не означает, что все сопутствующие consumers обновлены.

### 13.1 Определения готовности

- **Mock verified:** UI прошёл необходимые состояния по контракту; серверная корректность ещё не подтверждена.
- **Integrated:** тот же сценарий выполнен на реальном BFF/domain-стеке, подтверждены результаты команд.
- **Accepted:** независимая проверка criteria завершена, blockers закрыты.
- **Release ready:** приняты весь scope, целевые платформы и эксплуатационные проверки, а не только отдельные истории.

## 14. Калибровка агентов и управление стоимостью

Первую конфигурацию не объявлять оптимальной. Подготовить небольшой набор реальных задач: компонент со сложным состоянием, BFF projection, изменение ролей, повтор события, offline-сценарий и поиск намеренно внесённого дефекта в изолированном тестовом изменении.

Фиксировать по каждой: модель, effort, версия инструкций, baseline, пройденные criteria, пропущенные дефекты, ложные findings, количество исправлений, время и доступные данные расхода. Оценивать стоимость **принятой партии**, включая review/rework, а не одного ответа. Сначала проверить качество Astra/Sol, затем пробовать Terra/Luna на подходящих ограниченных ролях. Не делать вывод по единственному удачному примеру.

Ограничения процесса предлагаются такие: не более двух параллельных writers на старте; observer только для существующего долгого прогона; повторный review только после релевантного изменения/нового факта; при повторяющейся неудаче диагностика причины или усиление модели, а не бесконечное размножение судей. Это проектная политика эффективности.

Не переносить API-тарифы в расчёт подписочных лимитов Codex. Снимки pricing быстро устаревают; для выбора сначала достаточно качества и фактического расхода твоего аккаунта. При необходимости отдельного API supervisor бюджетируется весь граф вызовов, но он не входит в текущую рекомендацию.

## 15. Предлагаемый стартовый запрос оркестратору

Текст ниже предназначен для **будущего** запуска после принятия плана, не является командой выполнять его в текущем отчёте:

```text
Работаем в rutcampustrack. Выполни только подготовительную партию P0.
Объедини материалы проектирования, kit и frontend-исследования в один канон
с происхождением источников, историей и явными supersedes.
Новые принятые продуктовые требования выше старой реализации.
Старые данные и клиенты поддерживать не требуется; базы сейчас не удаляй.
Figma не изменяй. Используй отчёты kit и мои поздние решения.

Ты единственный оркестратор и владелец общего плана.
Используй ограниченные субзадачи для независимой сверки источников.
Подготовь release matrix по ролям и функциям, карту story→contract→service→test,
проект Vue/PCSS-правил и конфигурации ролей по утверждённой таблице моделей.
```
