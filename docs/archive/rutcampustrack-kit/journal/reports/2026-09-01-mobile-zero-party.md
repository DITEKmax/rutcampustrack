# Mobile zero party — PWA и Telegram Mini App

Дата: 01.09.2026. Файл Figma: `VgVjQYWILLG9AC7Eh12VMk`.

## Ответы на вопросы и разбор задания

- PWA и Telegram Mini App проектируются как мобильный продукт, а не как ещё
  один брейкпоинт desktop. ПК-экраны — источник работы пользователя и данных,
  но не раскладки.
- Для mobile принят отдельный визуальный диалект: градиенты, свечение,
  многослойные тени и несколько зон подсветки разрешены. Это явное исключение
  только для PWA/TMA; запреты desktop и auth не отменяются.
- Компоненты и иконки размещаются в том же файле, на логических страницах 21+.
  Отдельные дублирующие страницы или библиотеки PWA и TMA не создаются:
  один mobile-core, два адаптера оболочки.
- «Восемь адаптеров» трактуются как восемь зон контракта среды, а не восемь
  самостоятельных мастеров: host chrome, primary action, viewport, safe area,
  keyboard, theme, storage/offline, files/links.
- Параллельно выполнены три независимых разбора: управление библиотекой,
  матрица поверхностей и student-probe. Figma читалась только ведущим агентом;
  записей в неё не было.
- Для пограничных решений владелец разрешил повышать reasoning до xhigh/ultra.
  В этой партии governance и student-probe выполнены на xhigh, платформенная
  матрица — на high. Ultra оставлен для действительно неразрешимых дорогих
  развилок, а не как постоянный режим.

## Совет агентов и уровни

Совет остаётся функциональным, а не иерархией «сильный решает за слабого»:
каждый агент отвечает за отдельный вид ошибки, затем оркестратор сводит
аргументы и один сборщик последовательно пишет в Figma.

| Роль | Рабочий уровень | Когда повышать |
|---|---|---|
| Аналитик ПК | Terra high | Sol xhigh при конфликте спеки, реестра и live-мастера |
| Мобильный проектировщик | Sol xhigh | Ultra только у дорогой IA-развилки без победителя |
| Критик | Sol xhigh | Ultra для финального red-team перед общим мастер-решением |
| Платформенный | Terra high | Xhigh при расхождении PWA/TMA или рискованном offline contract |
| Визуальный системщик | Sol xhigh | Ultra перед новым material/token batch, если пробы равны |
| Сборщик | ведущий агент | Уровень не заменяет последовательность: один Figma writer |

В следующий совет варианты поступают обезличенно: критик не знает, какой
предложил оркестратор. Сначала каждый даёт независимое решение, затем получает
возражения другого агента и только после этого меняет позицию. Решение
принимается не голосованием, а по проверяемым критериям: касания, ошибки,
контракт платформы, доступность, стоимость нового владельца смысла и регрессия.

## Предложение по владению компонентами

Не являются новыми продукт-компонентами:

- `MobileShell` — шаблон сборки кадра;
- `SurfaceAdapter` — спецификация восьми runtime-зон;
- Telegram BackButton/MainButton — host fixtures для QA, а не имитация
  Telegram-кнопок внутри продукта.

Кандидаты mobile-foundation, требующие приёмки до внесения в закрытый реестр:

- `shared/MobileBottomNav`;
- `shared/MobileSyncStatus`;
- PWA-представление контекстного действия, только если существующий AppButton
  не покрывает sticky/safe-area контракт.

Переиспользуются существующие атомы и состояния: AppButton, AppLink, Checkbox
после repair-gate, Radio, Switch, SearchField, ConfirmDialog, EmptyState,
ErrorState, LoadingState, FileUploadField, AttendanceStatusBadge и
AttendanceStatusPicker.

Для student-probe сначала проверяются существующие `schedule/LessonCard`,
`block/CurrentLesson` и `block/TodaySchedule`. Новый `HeroCurrent` заранее не
заводится. Если mobile меняет не геометрию, а parts/focus contract, это будет
отдельно доказано до добавления нового смысла в реестр.

`COMPONENT_REGISTRY.md` в этой партии не менялся: список выше — proposal, а не
молчаливое дополнение закрытого реестра.

## Платформенная матрица

Шесть режимов поверхности:

1. PWA browser.
2. PWA standalone.
3. TMA overview compact.
4. TMA overview expanded.
5. TMA task compact.
6. TMA task expanded.

`compact/expanded` — состояние доступной высоты Telegram, не новая ширина.
Ширины 320 / 360 / 390 / 430 — CSS px viewport. Полное декартово произведение
не собирается. Минимальная pairwise-сетка — 36 сценариев: покрываются все
24 пары surface×width и пары со screen-state.

Обязательные риск-пробы до тиражирования:

- PWA browser 320: default → pressed → loading → result;
- PWA standalone 430: long/scrolled;
- TMA overview compact 360 и переход compact→expanded 390;
- TMA task compact 320 error;
- TMA task expanded 390 с клавиатурой;
- offline, sync, conflict, upload, длинный текст на 320;
- increased contrast, reduced motion, theme switch и external link.

Back и primary action принадлежат ровно одной оболочке. В TMA task это
нативные BackButton/MainButton; на overview и в PWA — продуктовая навигация.
Двойной Back и двойная нижняя панель запрещены.

## Student probe: функциональная карта и варианты

Цель: «Сегодня → текущая пара → отметка». Состояния: ready, checking, success
после server ack, geo denied, geo fail с серверной эскалацией, network fail с
retry, offline без очереди, geo-blocked, окно закрыто/опоздание,
cancelled/already marked.

### Вариант 1 — прямое действие на Today, рекомендован

Текущая пара — единственный главный фокус корня; `Отметиться` находится прямо
в карточке. Detail остаётся опциональным и открывается по самой карточке.
Касания: 1 с Today, 2 через detail, 1 из task deep link.

### Вариант 2 — обязательный detail

Сначала открывается текущая пара, затем действие. Касания: 2 с холодного
старта. Отклонён: добавляет шаг без подтверждённой ошибки пользователя,
которую этот шаг предотвращает.

### Вариант 3 — раскрытая строка дня, контрольный

Текущая пара раскрывается внутри списка расписания, без отдельной hero-карты.
Касания: 1. Это контроль против риска дублировать текущую пару hero-карточкой
и строкой списка.

Решение нулевой партии: вариант 1 — основной UX-probe, вариант 3 — контроль.
Вариант 2 не собирается. На одинаковых данных ready сравниваются три
визуальных направления: restrained, layered illumination и Telegram-native.
После выбора визуального направления проверяются success, geo-denied,
failed-escalated, offline и increased contrast.

## Визуальный слой и токены

Шестнадцать строк запроса из mobile-guide — это 16 проверяемых потребностей,
а не 16 автоматически новых токенов.

Покрыто или имеет существующий кандидат:

- accent-tinted surface — `color/accent/soft`;
- непрозрачная data-surface — `color/surface/base|raised` после контраст-пробы;
- mobile hero radius — `radius/2xl = 24`;
- press/morph durations — существующие 120 / 180 / 260 ms;
- базовое поднятие — `shadow/raised` и `shadow/overlay` как fallback.

Не покрыто и не создаётся до визуального probe:

- hero/current и selected-edge gradients;
- mobile glass base/strong — auth-glass запрещено переиспользовать;
- fluid/cut shape presets;
- campus pattern и его opacity;
- noise texture/effect;
- expressive easing в кодовой motion-spec;
- отдельный ambient glow, если его необходимость подтвердит победивший probe.

Градиент, свечение, тень и форма не обязаны быть одним глобальным токеном:
часть будет материалом/стилем, часть — asset/preset, motion — спецификацией Vue.
Анимация в Figma не создаётся; показываются статические before/after состояния.

## Что убрано и почему

- Desktop sidebar/header и таблицы — не соответствуют мобильной работе.
- Trend и SubjectStat с корня student-probe — не нужны для отметки сейчас.
- Обязательный detail перед отметкой — лишнее касание без доказанной пользы.
- Отдельные PWA/TMA копии компонентов — создают расхождение одного смысла.
- Восемь адаптеров как мастера — смешивают runtime contract и визуальный
  компонент.
- Новый `HeroCurrent` до аудита существующих LessonCard/CurrentLesson — риск
  второго мастера существующего смысла.
- Offline-очередь отметки — запрещена контрактом достоверности; доступен retry.
- Поясняющие абзацы внутри продукта — форма и состояние должны объяснять себя.

## Открытые ворота владельцу

1. Принять предложение mobile-foundation для дополнения реестра; до этого
   `COMPONENT_REGISTRY.md` не меняется.
2. Отдельно решить дубликат `shared/Checkbox` после покомпонентного readback;
   mobile не строится поверх неопределённого владельца.
3. Подтвердить, что массовая отметка остаётся запрещённой и для mobile;
   исключение attendance само по себе её не разрешает.
4. До token-batch принять визуального победителя на статическом probe; только
   после него согласовывать недостающие mobile materials пакетом.
5. Для реализации позже закрыть TMA launch points, политику MainButton,
   theme precedence, cache/privacy и файловые ссылки. Эти вопросы не блокируют
   статический foundation, но блокируют production contract.
