## 2. Layout-регионы

```
AppShell (тот же, что на 101 — заметка 1: шапка одинакова для всех страниц)
└─ <main>
   ├─ h1 «Посещаемость»
   ├─ Tabs                             [ЗЕЛЁНЫЙ]  «По неделям | По предметам»
   │
   ├─ ── режим «по неделям» ──────────────────────────────────
   │  ├─ DefinitionList variant="inline" [КРАСНЫЙ]  ФИО · Группа · Чётность недели · № недели от начала семестра
   │  ├─ DatePager (недели)            [КРАСНЫЙ, интерактивен]  ◀ 00.00 – 00.00 ▶
   │  ├─ StatRow: 5 × StatCard         [КРАСНЫЙ]  %«+» · %«н» · %«у» · %«+ и у» · прошедших пар за неделю
   │  └─ AttendanceWeekTable           [ЖЁЛТЫЙ]   пн–сб
   │     └─ AttendanceDayTable × 6
   │
   └─ ── режим «по предметам» ────────────────────────────────
      ├─ SubjectFilter                 [ЗЕЛЁНЫЙ]  предмет + типы занятий (мульти)
      ├─ DefinitionList variant="inline" [КРАСНЫЙ]  ФИО · Группа · Название предмета · Тип занятия
      ├─ StatRow: 5 × StatCard         [КРАСНЫЙ]  те же четыре доли + прошедших пар за семестр по фильтрам
      └─ AttendanceSubjectTable        [ЖЁЛТЫЙ]   колонки-даты
```

**Сверка со сканом.** Зелёные: полоса «По неделям / По предметам» и блок фильтров предмета с типами. Жёлтые: обе таблицы данных — показывается ровно одна (заметка 5: при нажатии одной кнопки данные другой пропадают). Красные: обе полосы-контексты, обе строки показателей, полоса `<- 00.00 – 00.00 ->`.

**Два отклонения от буквального чтения цвета:**
1. Полоса дат окрашена красным, но недели листаются — внутри неё живут интерактивные стрелки. Тот же `DatePager`, что на 101.
2. Заголовок «По неделям / По предметам» — одна зелёная полоса с текстом по краям; трактуется как **две вкладки одной группы**, а не два независимых тумблера. Заметка 5 подтверждает: режимы взаимоисключающие.

**Состав вкладок и память разреза.** Полоса разрезов — это `Tabs`. Перечень вкладок, активный разрез и **память каждого разреза** (выбранная неделя, выбранный предмет и типы занятий) принадлежат странице `StudentAttendancePage`, а не компоненту (K1). Отсюда же правило «фильтры другого режима не сбрасываются».

### Структура таблиц (уточнено владельцем)

На скане «Предмет» написано **вертикально** — это заголовки колонок, а «+ н у» под ними — **одна строка отметок**. Значит день это самостоятельная мини-таблица:

```
день (дата + пн)                                  ← caption / заголовок блока
├─ Предмет+тип │ Предмет+тип │ Предмет+тип        ← th scope="col", порядок расписания
└─ Отметка:  + │      н      │      у             ← единственная строка данных
```

- **Пробелов между парами нет** — колонки идут подряд по расписанию; номер слота отдельной строкой не выносится.
- **Отменённая пара занимает свою колонку** со статусом «отменена» и доступной причиной.
- Пустой день — колонка остаётся, внутри «Нет пар» (заметка 4).
- Над днём — дата (заметка 4).

Та же схема во втором режиме: `AttendanceSubjectTable` — колонки-даты (дата + день недели + тип занятия в заголовке), одна строка отметок.

## 4. Потребности в данных

### 4.1. Метаданные недели

- **Нужно:** для выбранной недели — границы дат, **чётность**, **порядковый номер от начала семестра**, границы семестра (чтобы ограничить листание).
- **Сейчас:** `GET /academic/semesters` — даты семестра. Чётность и номер недели пришлось бы вычислять на клиенте.
- **Пробел:** `[предложение по бэкенду]` — отдавать метаданные недели как данные. Бэкенд уже считает чётность при генерации расписания (JS-SYSTEM-05); если клиент повторит расчёт своей формулой, две реализации разойдутся на границе семестра или при переносах, и студент увидит «нечётная», сидя на паре чётной недели.

### 4.2. Недельная сетка

- **Нужно:** пары группы за неделю: предмет, **тип занятия**, время, аудитория, статус пары (включая `cancelled` + причину), **происхождение пары** (регулярная / разовая / перенесённая), мой статус отметки, для «у» — тип причины и комментарий.
- **Сейчас:** `GET /schedule/groups/{groupId}/lessons` + `GET /schedule/one-off-lessons` + `GET /attendance/reports/student/records` — два списка пар и сшивание с отметками на клиенте.
- **Пробел:** `[предложение по бэкенду]` — единый поток пар за период, разовые внутри него. Сейчас на каждую неделю это +1 запрос и слияние двух списков на клиенте.
- **Пробел:** `[предложение по бэкенду]` — причина отмены в представлении пары (заметка 3). Операция отмены есть (`PATCH /schedule/lessons/{id}/cancel`), но хранится ли причина и отдаётся ли — из дайджеста не видно.
- **Пробел:** `[предложение по бэкенду]` — признак происхождения пары. Студенту нужно понимать, почему пара появилась не по расписанию: «разовая» или «перенесена с 12.10».
- **Пробел:** `[нет API]` — операции **переноса** пары не существует, есть только отмена и создание разовой. Решается в чате headman.
- **Пробел:** `[уточнение по контракту]` — содержит ли `records` тип причины и комментарий, или за ними нужно идти в `GET /attendance/excuses/me` третьим запросом.

### 4.3. Агрегаты (одинаковы в обоих режимах)

- **Нужно:** за произвольный период **или** по фильтру «предмет + типы»: `%«+»`, `%«н»`, `%«у»`, `%«+ и у»`, число **прошедших** пар.
- **Правила знаменателя (подтверждены владельцем):**
  - отменённая пара **не входит ни в один знаменатель**, включая счётчик прошедших пар;
  - будущие пары не считаются — «нет данных», а не «0%»;
  - разовые и перенесённые пары участвуют **наравне с регулярными**.
- **Сейчас:** `GET /attendance/reports/student/stats`.
- **Пробел:** `[уточнение по контракту]` — принимает ли произвольный диапазон дат и фильтр «предмет + типы», возвращает ли все четыре доли сразу.
- **Пробел:** `[предложение по бэкенду]` — `%«+ и у»` должен считать сервер. Если считать долю на клиенте из двух других, цифра разойдётся с журналом старосты, где та же величина считается по-своему.

### 4.4. Мои предметы и доступные типы занятий

- **Нужно:** список предметов **моей группы в активном семестре** + для каждого — какие типы занятий реально существуют. Тип без пар недоступен для выбора.
- **Сейчас:** `GET /academic/subjects` — в дайджесте помечен «HEADMAN — только своя группа, ADMIN — все». Роль `student` не упомянута.
- **Решение владельца:** студент должен видеть предметы и их типы — **только на чтение**, без права редактирования.
- **Пробел:** `[предложение по бэкенду]` — доступ `student` на чтение предметов и типов своей группы. Без этого экран не работает вовсе.
- **Пробел:** `[предложение по бэкенду]` — «доступные типы занятий по предмету» приходят с сервера. Enum типов задан системой, но какие из них есть у конкретного предмета — данные; вычислять это на клиенте можно только выкачав все пары семестра.

### 4.5. Пары по предмету

- **Нужно:** все пары выбранного предмета с выбранными типами за семестр: дата, день недели, тип, статус пары, мой статус.
- **Сейчас:** `GET /schedule/groups/{groupId}/lessons` за весь семестр + фильтрация на клиенте + join с `records`.
- **Пробел:** `[предложение по бэкенду]` — фильтр по предмету и типам на стороне сервера. Иначе на каждое переключение предмета клиент тянет полное расписание семестра ради 15 строк.

### 4.6. Выгрузка (заметка 6)

- **Нужно:** экспорт **своей** посещаемости в том же табличном виде, с текущими фильтрами.
- **Сейчас:** `[нет API]` — есть `reports/headman-weekly/*` и `reports/journal`, но это отчёты старосты по группе, не выгрузка студента по себе.
- **Пробел:** `[предложение по бэкенду]`. На wireframe закладывается место под `ExportButton` с пометкой «идея, не подтверждено».

### 4.7. Кэширование (направление владельца)

- **Направление:** эндпоинты под форму экрана + кэшируемость, а не клиентская агрегация.
- **Пробел:** `[предложение по бэкенду]` — версия/ревизия расписания группы в ответе. Расписание мутирует: староста отменяет пары, добавляет разовые, меняет аудиторию. Без версии ключ кэша не инвалидируется, и студент увидит закэшированную неделю без только что добавленной пары.

### ⚠️ Фактура к решению о транспорте

- Режим «по неделям»: семестр → метаданные недели → пары → разовые пары → отметки → причины → агрегаты = **4–5 запросов**, два join'а на клиенте.
- Режим «по предметам»: предметы → доступные типы → пары семестра (over-fetch) → отметки → агрегаты = **4–5 запросов**, из них один заведомо избыточный по объёму.
- Каждое листание недели и каждая смена предмета повторяют цепочку.

## 5. Состояния

На бумаге есть одно — «Нет пар» для пустого дня (заметка 4). **Остальное добавлено при разборе.**

**Общие для экрана:** `loading` · `error` (RFC 9457 + повтор) · `offline` (показываем кэш с явной пометкой «данные могут быть устаревшими») · `forbidden` · `no-active-semester`.

### Режим «по неделям»

| Состояние | Условие |
|---|---|
| `day-empty` | в дне нет пар → «Нет пар», колонка остаётся видимой |
| `week-empty` | пар нет всю неделю (каникулы, праздничная неделя) |
| `week-out-of-semester` | листнули за границу семестра → стрелка недоступна с пояснением, а не пустая таблица |
| `week-future` | неделя не наступила: пары есть, отметок нет, проценты не считаются — **«нет данных», не «0%»** |
| `partial` | текущая неделя: часть пар прошла, часть впереди. Будущие видны, но в знаменатель не входят |

### Режим «по предметам»

| Состояние | Условие |
|---|---|
| `no-subject-selected` | стартовое: фильтр пуст, таблица и показатели не отрисованы, подсказка «выберите предмет» |
| `types-partially-available` | часть типов недоступна → `disabled` + пояснение почему, не молчаливая серость |
| `subject-empty` | предмет выбран, пар с такими типами нет |
| `subjects-empty` | у студента вообще нет предметов (семестр не наполнен) |

### Ячейка пары

`marked +` · `marked у` (доступна причина) · `marked н` · `cancelled` (доступна причина) · `no-data` (пара не началась или не закрыта) · `pending` (подана заявка late-checkin, решения нет — статус ещё «н», но не окончательный).

### По ролям

`student` и `headman` идентично. Свою группу староста смотрит на отдельном экране журнала — это чат headman.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| Вкладки разреза (`Tabs`) | Смена разреза. Данные другого режима скрываются, но **фильтры не сбрасываются** — вернувшись, студент видит прежний выбор. Правило принадлежит странице, а не `Tabs`. Режим и фильтры в URL |
| `DatePager` ◀ ▶ | Неделя ±1 в границах семестра; на границе стрелка недоступна с пояснением |
| `SubjectFilter` | Выбор предмета → подгрузка доступных типов → пересчёт показателей и таблицы |
| `LessonTypePicker` | Мульти-выбор (`multiple`, `context="filter"`); снятие всех типов = состояние «выберите хотя бы один», а не пустая таблица |
| наведение / фокус на «у» | `ExcuseReasonPopover` (заметка 3) |
| наведение / фокус на отменённой паре | `CancellationReasonPopover` (заметка 3) |
| `ExportButton` | Выгрузка текущего разреза — заглушка, API нет |

**Деструктивных действий нет** — экран целиком на чтение, подтверждения не требуются.
**Нехватка прав:** неавторизованный → 001 с `returnUrl`; `teacher` / `admin` по прямой ссылке → `ForbiddenState`.

### A11y (структурно)

- Обе сетки — настоящие `<table>` с `th scope="col"` и `scope="row"` (прямое требование A11Y_REQUIREMENTS: журналы и статистика в таблицах, не в grid из div'ов).
- `<caption>` с описанием периода или фильтра, чтобы таблица читалась вне контекста.
- Статусы `+ / н / у` — **текстом, не только цветом и не только символом**; символ разворачивается словом в `aria-label`.
- Подсказки по «у» и по отмене **обязаны открываться с клавиатуры**: на скане это hover, но hover-only исключает клавиатуру и тач.
- Смена недели объявляется через `role="status"` («неделя 7, 12.10–18.10»), иначе для скринридера таблица меняется молча.
- Недоступные типы занятий — `disabled` + `aria-describedby` с причиной.
- `DefinitionList variant="inline"` — не таблица, а список пар «термин → значение».
