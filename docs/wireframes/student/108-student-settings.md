# ПК-108 — Студент, Настройки

> Этап 1, чат 3. Веб-десктоп 1920. Структура и логика, без визуала.
> Сканы: `ПК — 108 — СТРАНИЦА СТУДЕНТ — НАСТРОЙКИ` (1, 2).

## 1. Идентификация

| | |
|---|---|
| Название | ПК-108 Студент — Настройки |
| Роли | **все четыре** — student, headman, teacher, admin. Единственное ролевое различие — блок делегированных прав |
| Поверхность | web-десктоп 1920 |
| Точка входа | `ProfileMenu` → «Настройки» (жёлтый поповер в шапке). В `MainNav` пункта нет |
| Цель | Посмотреть свои данные, сменить пароль, увидеть историю аккаунта и активные входы, привязать мобильный клиент по QR, выбрать тему |

**Решение владельца: ПК-108 — сквозной экран всех четырёх ролей.** Поля ведут себя **одинаково у всех ролей, включая администратора**: тот же состав, та же нередактируемость, те же действия. Это **явное исключение из правила «экраны 101–108 роли `admin` не выдаются»**: 108 выдаётся всем, включая `admin`; исключений по ролям внутри экрана нет, кроме блока делегированных прав, который рендерится только при их наличии.

## 2. Layout-регионы

```
AppShell
└─ main #main
   ├─ Колонка 1
   │  └─ DefinitionList variant="stack" [КРАСНЫЙ] Имя · Фамилия · Отчество · Группа
   ├─ Колонка 2
   │  ├─ Tg id                          [КРАСНЫЙ] в том же DefinitionList
   │  └─ DeviceLinkQr                   [КРАСНЫЙ] QR входа в PWA
   ├─ AccountHistoryList                [ЗЕЛЁНЫЙ] история событий аккаунта
   ├─ PermissionList                    [КРАСНЫЙ] делегированные права — только если они есть
   ├─ ActiveSessionsList                [КРАСНЫЙ] где сейчас выполнен вход
   ├─ NewPasswordForm variant="change"  [ЖЁЛТЫЙ] смена пароля
   ├─ ThemeSwitcher                     [добавлено] светлая · тёмная · как в системе
   └─ «Выйти на всех устройствах»       [ЗЕЛЁНЫЙ]
```

**Чтение скана:** «Доп права» и «закреплено где сейчас вход выполнен» нарисованы одним красным блоком, но это **разные сущности** — статичный набор прав и меняющийся список сессий. Развожу в два региона.
«История» окрашена зелёным → читаю как список с листанием и фильтром по типу события, а не как кнопку.

## 3. Компоненты

**Из реестра, без изменений:** `AppShell`, `AppHeader`, `MainNav`, `RoleSwitcher`, `ProfileMenu`, `FormField`, `PasswordField`, `PasswordPolicyHint`, `AppButton`, `AppLink`, `FormError`, `CountdownTimer`, `ConfirmDialog`, `QrCodeDisplay`, `Tooltip`, `LoadingState`, `EmptyState`, `ErrorState`, `OfflineState`.

**Из реестра, с изменением:**

| Компонент | Что меняется |
|---|---|
| `NewPasswordForm` | `local (auth)` → **`domain (auth)`** (второе применение). Появляются варианты: `reset` (001b, старый пароль не спрашивается) и `change` (108, **старый обязателен** + ссылка «Не помню пароль» → 001a). Ошибка «старый пароль неверен» ставится на поле, не общим `FormError` |
| `PasswordField` | Вставка и показ пароля **разрешены** (решение владельца отменяет прим. 1 скана). Специальных пропов не требуется |
| `DefinitionList` | вариант `stack` — вертикальная раскладка для профиля (на 102 тот же компонент в варианте `inline`). Новый компонент не заводим: это тот же «набор пар подпись → значение», семантически список определений |
| `QrLoginPanel` (001) | Рендер кода выносится в `QrCodeDisplay`, панель остаётся сценарной обёрткой |

**Новые:**

| Компонент | Назначение | Владение | Почему нет подходящего |
|---|---|---|---|
| `QrCodeDisplay` | Рендер QR + обязательная текстовая альтернатива кодом | `shared` | Второе применение (001 и 108) → по §2 уходит в общую библиотеку |
| `DeviceLinkQr` | QR привязки мобильного клиента из **авторизованной** сессии: код, TTL, обновление, статус «устройство привязано» | `local` (settings) | **Не синоним `QrLoginPanel`**: тот выпускает сессию неавторизованному гостю на ПК, этот передаёт доступ на второе устройство. Разные контракты — та же ошибка, что была бы `RecoveryCodeForm` = `OtpForm` |
| `AccountHistoryList` | Лог событий аккаунта: тип, дата, описание. Листание, фильтр по типу | `local` (settings), кандидат в `domain` — админу понадобится аудит | Списка событий в реестре нет |
| `ActiveSessionsList` | Текущие входы: устройство, место, время, пометка «это устройство» текстом | `local` (settings) | Отдельная сущность от истории: текущее состояние, а не прошедшие события |
| `PermissionList` | Набор делегированных прав. Варианты `readonly` (108) и `editable` (экран старосты) | `domain` (auth) | Староста будет теми же правами управлять (JS-HEADMAN-14, чат 4) — лучше один компонент с вариантами |
| `ThemeSwitcher` | Светлая · тёмная · **как в системе** (дефолт). Группа радиокнопок в `fieldset` — не тумблер, значений три | `shared` | Требование проекта «две темы»; на скане переключателя не было, добавлен решением владельца |

| 8 | Мои делегированные права | `GET /academic/assistants` — список помощников **группы**, ориентирован на старосту | `[предложение по бэкенду]`: права текущего пользователя приходят **вместе с сессией** (JS-SYSTEM-14) — от них зависит состав навигации |
| 9 | Уведомление в Telegram о смене пароля (прим. 1 скана) | в перечне JS-SYSTEM-10 нет | `[предложение по бэкенду]`: событие `password.changed` |
| 10 | Тема оформления | хранится локально на устройстве | `[предложение по бэкенду]`, низкий приоритет: если тема должна следовать за пользователем между устройствами — нужно поле в профиле |

**Редактируемых полей профиля нет.** ФИО, отчество, группа и id — только чтение (прим. 3 скана); менять их сможет староста на своём экране.
⚠️ Для чата 4: операции «староста меняет ФИО студента» в API тоже нет — `PUT /academic/users/{id}` помечен ADMIN.

**Аватар:** `PATCH /academic/users/me/avatar` существует, но на скане смены аватара нет. Решение владельца — «в будущем возможно загрузить фото». Не проектируем.

**Настройки уведомлений:** решение владельца — **в вебе их нет**. `/notifications/preferences`, `/push/subscribe`, `/push/vapid-public-key` фронтом десктопа не используются, с бэкенда не удаляются (понадобятся в PWA). В вебе уведомления существуют только как всплывающие сообщения по WebSocket.

**Фактура по транспорту:** вход на экран — **4–6 запросов, три из которых не существуют** (профиль, история, сессии, права, QR). Over-fetching нет, но экран собирается из пяти независимых источников — типичный кандидат на «один ответ под форму экрана».

## 5. Состояния

На бумаге состояний нет вовсе. Всё ниже добавлено.
Блоки грузятся и падают **независимо** (§6.2): упавшая история не мешает сменить пароль.

| Блок | Состояния |
|---|---|
| Профиль | `loading` / `error` + повтор. `empty` неприменим. Отдельно `not-linked` — Telegram не привязан: не пустое поле, а пояснение и что делать |
| QR привязки | `loading` выпуска · `success` (код + текстовая альтернатива + отсчёт) · **`expired`** — код истёк, действие «Обновить» · `error` выпуска · `linked` — устройство привязано, объявляется через `role="status"` |
| История | `loading` · `empty` («событий пока нет») · `error` · `out-of-range` при листании за границы |
| Активные входы | `loading` · `error`. `empty` **невозможен** — текущая сессия всегда есть; пустой список = ошибка, а не пустота |
| Делегированные права | у пользователя без прав блок **не рендерится вовсе** (решение владельца). Пустого состояния нет |
| Смена пароля | `idle` · `submitting` (`aria-busy`, кнопка `busy`) · `success` · ошибки: старый неверен (на поле) · не совпадают · не проходит политику · отклонён сервером (`FormError`, RFC 9457, фокус на сообщение). Введённое при ошибке сохраняется |
| Тема | значение всегда есть (дефолт — системная). Ошибок нет |
| Экран | `offline`: `OfflineState`, смена пароля и выход недоступны с пояснением. `forbidden` неприменим. `no-active-semester` неприменим — учебных данных на экране нет |

Ролевое различие ровно одно: блок прав. Всё остальное одинаково **для всех четырёх ролей**, включая `admin`.

## 6. Навигация и действия

| Элемент | Цвет на скане | Поведение |
|---|---|---|
| Имя, фамилия, отчество, группа, Tg id | красный | Только чтение. **Текстом, не `disabled`-инпутами** — заблокированное поле обещает редактирование, которого нет (§6.2) |
| QR | красный | Обновление по истечении TTL. Текстовая альтернатива обязательна — QR нечитаем скринридером |
| История | зелёный | Листание, фильтр по типу события. Строки не кликабельны — деталей событий не проектируем |
| Активные входы | красный | Только отображение. Завершения отдельной сессии на скане нет — не добавляю |
| Смена пароля | жёлтый | Поля: старый пароль → новый → повтор → `PasswordPolicyHint` → ссылка «Не помню пароль» → кнопка. Перед отправкой `ConfirmDialog` с явным предупреждением: **«Вы выйдете из системы на всех устройствах, включая это»** |
| «Не помню пароль» | добавлено | → 001a (сброс через Telegram), который тоже гасит все сессии |
| Тема | добавлено | Переключение немедленное, объявляется `role="status"` |
| «Выйти на всех устройствах» | зелёный | Деструктивно → `ConfirmDialog`. **Гасит и текущую сессию** → редирект на ПК-001 |
| `ProfileMenu` → «Выход» | зелёный / жёлтый | Выход только текущей сессии. Подтверждения не требует — действие обратимо повторным входом |

**Финал сценария смены пароля** (решение владельца): все сессии гасятся, включая текущую → редирект на ПК-001 с сообщением «Пароль изменён, войдите заново». Форма на экране не остаётся.

## 7. Адаптив (заметки)

- 1920: две колонки сверху (данные профиля / Telegram + QR), ниже блоки в одну колонку на всю ширину.
- При сужении: одна колонка, QR уходит под данные профиля. ✏️ **13.08:** ~~«поля пароля из строки в столбик»~~ отменено — поля пароля **вертикальны на всех ширинах**: три поля в ряд читаются хуже и ломают порядок ввода. Оси ширины у `NewPasswordForm` нет и не заводится.
- Порядок табуляции при перестроении обязан совпасть с визуальным — на этом экране колонки легко разъезжаются.
- PWA — отдельная поверхность; там настройки уведомлений появятся, в отличие от веба.

## Решено в этом чате

- Смена пароля и «Выйти на всех устройствах» гасят **все** сессии, включая текущую.
- Старый пароль при смене **обязателен**; путь «не помню» — сброс через Telegram.
- Вставка и показ пароля **разрешены** (прим. 1 скана отменено).
- Блок делегированных прав у пользователя без прав **не рендерится**.
- Настроек уведомлений в вебе нет.
- Переключатель темы добавлен, три значения.
- ПК-108 — сквозной экран всех четырёх ролей; поля ведут себя одинаково у всех, включая администратора.

## Замечание в сторону: уведомления в вебе

Из решения владельца следует, что в вебе уведомления существуют как всплывающие сообщения по WebSocket (JS-SYSTEM-09), но **экрана уведомлений в навигации нет**, и JS-STUDENT-WEB-06 («лог прошедших событий») не попал ни на один разобранный экран.

Всплывающее сообщение — сквозной элемент уровня `AppShell`, а не 108: ему нужна live-область (`role="status"` для нейтральных, `role="alert"` для критичных), правила накопления, TTL и группировки. Занесён в реестр как кандидат `LiveNotificationRegion` со статусом «требует отдельного разбора», чтобы следующий чат не изобрёл своё имя.
