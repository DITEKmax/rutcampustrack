# backend-requests — ПК-111 (Староста, Главная)

> Этап 1, чат 3. Часть общего файла запросов к бэкенду — предназначена для слияния
> с аналогичными файлами других экранов.
> Транспортно-нейтрально: сначала ЧТО нужно, потом где это лежит сейчас.
> Бэкенд не заморожен — это вход для бэкенд-задач, а не обход существующего API.

## Сводка по экрану

| Тип | Кол-во | Критичность |
|---|---|---|
| Отсутствующая подсистема | 1 | блокирующая — блок нечем наполнить |
| Новый агрегат / эндпоинт | 5 | высокая |
| Новое поле в существующем ответе | 4 | высокая — **без них экран врёт** |

## attendance-service

### A-1. Журнал действий по паре — **отсутствующая подсистема**
`[предложение по бэкенду]` · источник: ПК-111 §4.4, заметка 4 историй

- **Нужно:** хронология событий по `lessonId` с подгрузкой и сортировкой по времени. Событие: время, актор, тип, изменение. Типы: попытка геоотметки (с вердиктом и **расстоянием от центра допустимого радиуса**), автопростановка `н` при закрытии пары, подача и решение тикета по паре, ручные действия старосты (отметка, блокировка, отмена, восстановление).
- **Сейчас:** нет. `GET /attendance/reports/lesson/{lessonId}` отдаёт текущее состояние, не историю.
- **Почему нельзя обойти на клиенте:** данных не существует ни в каком виде — это не агрегация имеющегося. Клиент не может восстановить историю из финального состояния.
- **Примечание владельца:** допускается отдельный сервис под бизнес-лог.

### A-2. Результат геопроверки должен сохраняться
`[предложение по бэкенду]` · источник: §4.4

- **Нужно:** по попытке отметки — расстояние до центра допустимого круга, радиус, вердикт, время.
- **Сейчас:** проверка выполняется (`POST /attendance/checkin`), исход в пригодном для показа виде не сохраняется.
- **Зависимость:** без этого A-1 теряет половину ценности — заметка 4 историй просит именно «во сколько и как отмечался».

### A-3. Агрегат отметок по паре считает сервер
`[предложение по бэкенду]` · источник: §4.2, заметка 2 историй

- **Нужно:** по `lessonId` — `presentCount`, `excusedCount`, `absentCount`, `noDataCount`, `totalMembers`.
- **Сейчас:** клиент тянет `GET /attendance/reports/lesson/{lessonId}` + `GET /academic/groups/my/members` и считает сам.
- **Почему плох клиентский путь:** полный список отметок вытягивается ради двух чисел; те же показатели выводятся ещё на 101/102/103 — при клиентском счёте цифры разойдутся. Прямое продолжение JS-SYSTEM-16 (проценты и количества считает сервер).

### A-4. Живое обновление агрегата по паре
`[предложение по бэкенду]` · источник: §4.2 · **решается совместно с бэкендом**

- **Нужно:** доставка обновлённого агрегата при изменении отметок на идущей паре.
- **Сейчас:** WS-канал существует (`POST /auth/ws-ticket`, JS-SYSTEM-09), но события уровня «агрегат по паре» в перечне JS-SYSTEM-10 нет.
- **Открытый выбор:** WS-событие против поллинга. **Без решения требование «в реальном времени» из заметки 2 не выполняется.**

### A-5. Счётчик открытых заявок по типам
`[предложение по бэкенду]` · источник: §4.8, заметка 7 историй

- **Нужно:** по группе — количество открытых excuse-тикетов и открытых late-checkin, одним ответом, с живым обновлением.
- **Сейчас:** `GET /attendance/late-checkin/pending` + `GET /attendance/excuses/group/{groupId}` — два полных списка ради двух чисел.

### A-6. Источник и время отметки в отчёте по паре
`[уточнение по контракту]` · источник: §4.3, заметка 3 макета · **без этого экран врёт**

- **Нужно:** в представлении отметки — `source` (`student_geo` / `headman` / `auto_scheduler` / `teacher_override` / `late_checkin`), время отметки, кто изменил.
- **Почему критично:** заметка 3 макета прямо требует отличать самостоятельную отметку студента от ручной, а закрытая пара автоматически заполняется `н` — без источника староста примет автопростановку за собственное решение.

### A-7. Снятие отметки в «нет данных»
`[предложение по бэкенду]` · источник: §4.3

- **Нужно:** операция возврата ячейки в состояние «отметки нет».
- **Сейчас:** `PUT /attendance/lessons/{lessonId}/students/{userId}` умеет только присвоить одно из трёх значений.
- **Контекст:** заметка 3 скана 112 описывает цикл, в котором выбор можно снять.

### A-8. Фильтр excuses по статусу
`[уточнение по контракту]` · источник: §4.8

- **Нужно:** отбор только открытых (нерешённых) тикетов группы.
- **Сейчас:** `GET /attendance/excuses/group/{groupId}` — неясно, фильтруется ли по статусу. Без фильтра клиент вытянет всю историю группы за семестр ради счётчика «актуальных».

### A-9. Доступность ручной отметки для не начавшейся пары
`[уточнение по контракту]` · источник: §4.3

- **Вопрос:** принимает ли `PUT /attendance/lessons/{id}/students/{userId}` отметку для пары в статусе `planned`. Заметка 3 скана 112 разрешает правку «в течение всего семестра» — про будущее правил нет.

## schedule-service

### S-1. Полнота представления пары
`[уточнение по контракту]` · источник: §4.1 · **без этого экран врёт**

- **Нужно:** в паре из `GET /schedule/groups/{groupId}/lessons` — статус (`planned` / `active` / `closed` / `cancelled`), **признак блокировки старостой**, **признак гео-блокировки**, происхождение (`regular` / `one-off` / перенос), порядковый номер пары в дне, аудитория.
- **Почему критично:** без статуса нельзя ни выбрать текущую пару для счётчиков, ни объяснить происхождение автоматических `н`; без признаков блокировки экран покажет неверное состояние переключателя.

### S-2. `blockage` против `geo-block` — два механизма с пересекающимся смыслом
`[уточнение по контракту]` · источник: §4.5 · **требует решения до Figma**

- **Сейчас:** `POST` / `DELETE /schedule/lessons/{id}/blockage` (HEADMAN, «запретить геоотметку, посещаемость ставит только староста») и `PATCH /schedule/lessons/{id}/geo-block` (HEADMAN/ADMIN, «включить/выключить гео-блокировку»).
- **Вопрос:** это одно и то же или разное? Если одно — один механизм вывести из обихода. Если разное — нужны раздельные термины в словаре и раздельные контролы.
- **Почему важно:** два независимых флага дают четыре комбинации, две из которых бессмысленны, и фронт не сможет отрисовать непротиворечивое состояние. До ответа проектируется один переключатель на базе `blockage`.

### S-3. Блокировка закрытой и отменённой пары
`[уточнение по контракту]` · источник: §4.5

- **Вопрос:** допустима ли блокировка для пары в статусе `closed` / `cancelled`, или операция должна отклоняться.

### S-4. Версия расписания группы
`[предложение по бэкенду]` · источник: §4.1, JS-SYSTEM-15

- **Нужно:** ревизия/версия расписания в ответе.
- **Почему:** расписание мутирует в течение дня (отмена, разовая пара, перенос, смена аудитории). Главная старосты — экран реального времени, показывать кэш без изменений недопустимо.

### S-5. Определение «текущей пары» на стороне сервера
`[уточнение по контракту]` · источник: §4.2

- **Нужно:** признак «идёт сейчас» приходит как данные.
- **Почему:** клиентское вычисление по времени разойдётся с серверным закрытием пары; на границах, в перерывах и при накладках счётчики привяжутся не к той паре.

### S-6. Ближайшая следующая пара по предмету и типу
`[предложение по бэкенду]` · источник: §4.7, заметка 6 историй

- **Нужно:** «следующая пара по (предмет, тип занятия) после даты X» — для предзаполнения дедлайна в форме быстрой выдачи дз.
- **Сейчас:** только вычислением по `GET /schedule/groups/{groupId}/lessons`.
- **Почему плох клиентский путь:** клиент не знает, насколько далеко вперёд искать — предмет может не встретиться две недели, и диапазон запроса приходится выбирать наугад.

## academic-service

### AC-1. Фильтр домашних заданий по диапазону дат
`[предложение по бэкенду]` · источник: §4.6 · **дубль требования из JS-STUDENT-20 (ПК-104)**

- **Нужно:** отбор заданий группы по диапазону дат.
- **Сейчас:** `GET /academic/homeworks` — за семестр целиком.
- **Почему:** главная старосты тянет весь семестр ради одного дня. Требование уже зафиксировано для студенческого экрана дз — это второй экран с той же потребностью.

### AC-2. Привязка задания к паре и порядок в дне
`[предложение по бэкенду]` · источник: §4.6 · **дубль требования из JS-STUDENT-21**

- **Нужно:** у задания — ссылка на пару либо порядковый номер предмета в дне.
- **Почему:** без этого «дз на сегодня» нельзя упорядочить по расписанию, не вытягивая расписание отдельно и не джойня на клиенте.

### AC-3. Эффективные права текущего пользователя
`[предложение по бэкенду]` · источник: §4.9, продолжение JS-SYSTEM-14 · **блокирует корректный рендер**

- **Нужно:** в профиле/сессии — эффективный набор прав: сам староста или помощник с подмножеством (`mark_attendance`, `manage_excuses`, `manage_homework`, `cancel_lessons`, `view_stats`).
- **Сейчас:** `GET /academic/assistants` отдаёт список помощников группы, а не «мои права».
- **Почему плох клиентский путь:** фронт вынужден вытягивать список помощников и искать себя — а помощник может не иметь права читать этот список. Без эффективных прав экран покажет либо лишнее, либо ничего.

## Кросс-сервисное

### X-1. Три разные пары в одном экране одним обращением
`[предложение по бэкенду]` · источник: ⚠️ фактура §4

- **Ситуация:** на 111 одновременно живут три независимые привязки к паре — счётчики (текущая идущая), панель ручной отметки (выбранная слева), журнал действий (выбранная справа). Форма запроса одинаковая, пары разные.
- **Нужно:** возможность запросить состояние набора пар одним обращением.
- **Контекст:** независимо от решения REST/GraphQL. Экран — самый тяжёлый из разобранных: 8–10 запросов на первую отрисовку, из них три с явным over-fetching и один невозможный (A-1).

## schedule-service

### S-1. Полнота представления пары
`[уточнение по контракту]` · источник: §4.1 · **без этого экран врёт**

- **Нужно:** в паре из `GET /schedule/groups/{groupId}/lessons` — статус (`planned` / `active` / `closed` / `cancelled`), **признак блокировки старостой**, **признак гео-блокировки**, происхождение (`regular` / `one-off` / перенос), порядковый номер пары в дне, аудитория.

- **Вопрос:** это одно и то же или разное? Если одно — один механизм вывести из обихода. Если разное — нужны раздельные термины в словаре и раздельные контролы.
- **Почему важно:** два независимых флага дают четыре комбинации, две из которых бессмысленны, и фронт не сможет отрисовать непротиворечивое состояние. До ответа проектируется один переключатель на базе `blockage`.

### S-3. Блокировка закрытой и отменённой пары
`[уточнение по контракту]` · источник: §4.5

- **Вопрос:** допустима ли блокировка для пары в статусе `closed` / `cancelled`, или операция должна отклоняться.

### S-4. Версия расписания группы
`[предложение по бэкенду]` · источник: §4.1, JS-SYSTEM-15

- **Нужно:** ревизия/версия расписания в ответе.
- **Почему:** расписание мутирует в течение дня (отмена, разовая пара, перенос, смена аудитории). Главная старосты — экран реального времени, показывать кэш без изменений недопустимо.

### S-5. Определение «текущей пары» на стороне сервера
`[уточнение по контракту]` · источник: §4.2

- **Нужно:** признак «идёт сейчас» приходит как данные.
- **Почему:** клиентское вычисление по времени разойдётся с серверным закрытием пары; на границах, в перерывах и при накладках счётчики привяжутся не к той паре.

### S-6. Ближайшая следующая пара по предмету и типу
`[предложение по бэкенду]` · источник: §4.7, заметка 6 историй

- **Нужно:** «следующая пара по (предмет, тип занятия) после даты X» — для предзаполнения дедлайна в форме быстрой выдачи дз.
- **Сейчас:** только вычислением по `GET /schedule/groups/{groupId}/lessons`.
- **Почему плох клиентский путь:** клиент не знает, насколько далеко вперёд искать — предмет может не встретиться две недели, и диапазон запроса приходится выбирать наугад.

## academic-service

### AC-1. Фильтр домашних заданий по диапазону дат
`[предложение по бэкенду]` · источник: §4.6 · **дубль требования из JS-STUDENT-20 (ПК-104)**

- **Нужно:** отбор заданий группы по диапазону дат.
- **Сейчас:** `GET /academic/homeworks` — за семестр целиком.
- **Почему:** главная старосты тянет весь семестр ради одного дня. Требование уже зафиксировано для студенческого экрана дз — это второй экран с той же потребностью.

### AC-2. Привязка задания к паре и порядок в дне
`[предложение по бэкенду]` · источник: §4.6 · **дубль требования из JS-STUDENT-21**

- **Нужно:** у задания — ссылка на пару либо порядковый номер предмета в дне.
- **Почему:** без этого «дз на сегодня» нельзя упорядочить по расписанию, не вытягивая расписание отдельно и не джойня на клиенте.

### AC-3. Эффективные права текущего пользователя
`[предложение по бэкенду]` · источник: §4.9, продолжение JS-SYSTEM-14 · **блокирует корректный рендер**

- **Нужно:** в профиле/сессии — эффективный набор прав: сам староста или помощник с подмножеством (`mark_attendance`, `manage_excuses`, `manage_homework`, `cancel_lessons`, `view_stats`).
- **Сейчас:** `GET /academic/assistants` отдаёт список помощников группы, а не «мои права».
- **Почему плох клиентский путь:** фронт вынужден вытягивать список помощников и искать себя — а помощник может не иметь права читать этот список. Без эффективных прав экран покажет либо лишнее, либо ничего.

## Кросс-сервисное

### X-1. Три разные пары в одном экране одним обращением
`[предложение по бэкенду]` · источник: ⚠️ фактура §4

- **Ситуация:** на 111 одновременно живут три независимые привязки к паре — счётчики (текущая идущая), панель ручной отметки (выбранная слева), журнал действий (выбранная справа). Форма запроса одинаковая, пары разные.
- **Нужно:** возможность запросить состояние набора пар одним обращением.
- **Контекст:** независимо от решения REST/GraphQL. Экран — самый тяжёлый из разобранных: 8–10 запросов на первую отрисовку, из них три с явным over-fetching и один невозможный (A-1).
