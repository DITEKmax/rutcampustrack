# backend-requests.md

> Все пометки `[нет API]`, `[предложение по бэкенду]` и `[уточнение по контракту]`, накопленные при разборе wireframe'ов.
> **Источник:** чат 1 (этап 1) — экраны ПК-001, 001a, 001b, 101, 102. Роль `student` + сквозной вход.
>
> Бэкенд не заморожен: экраны не подгонялись под текущие эндпоинты.
> Потребности описаны транспортно-нейтрально — сначала ЧТО нужно, потом ГДЕ лежит сейчас.
>
> **Типы пометок:**
> - `[нет API]` — операции или данных не существует вовсе.
> - `[предложение по бэкенду]` — данные есть, но форма доставки неудобна экрану.
> - `[уточнение по контракту]` — из дайджеста не видно, есть ли нужное поле; надо свериться с `*-api-contract`.

## auth-service

### `[нет API]` Вход по QR-коду

Флоу отсутствует целиком. Нужно:
- выпуск сессии входа → `{sessionId, qrPayload, expiresAt}`;
- канал статуса `pending | confirmed | expired | rejected` **для неавторизованного клиента** (`POST /auth/ws-ticket` требует уже авторизованного пользователя и не подходит);
- операция подтверждения со стороны мобильного клиента (PWA / Telegram Mini App);
- TTL и перевыпуск кода.

`POST /auth/tma` решает другую задачу — вход внутри Mini App.
**Экран:** 001.

### `[нет API]` Сброс пароля по одноразовому ticket

`{ticket|token, newPassword}` → успех. Ошибки: токен истёк, уже использован, пароль не соответствует политике.
`POST /auth/change-password` требует старый пароль и для сброса не подходит.
Требование: **инвалидация всех активных сессий пользователя** после смены.
**Экран:** 001b.

### `[нет API]` Политика пароля как данные

Правила (минимальная длина, обязательные классы символов) должны приходить с сервера, а не быть константой во фронте — иначе три клиента разойдутся с бэкендом.
**Экраны:** 001b, профиль.

### `[нет API]` Сброс пароля студенту старостой

Операция «сбросить пароль участнику своей группы» → сгенерированный пароль, показываемый старосте **один раз**.
Условия (решение владельца): показывается только сгенерированный пароль — initial или после сброса. Пароль, выбранный пользователем самостоятельно, не показывается никогда и никому. Факт сброса пишется в аудит.
**Экран:** старосты, чат headman. Порождён fallback-текстом на 001a.

### `[предложение по бэкенду]` Bootstrap сессии одним ответом

Нужно: токены + профиль + роли + `is_headman` + группа + **активный семестр** одним ответом.
Сейчас: `POST /auth/login` → `GET /academic/users/me` → `GET /academic/semesters`, плюс, возможно, `GET /auth/public-key`.
Без профиля и ролей нельзя ни выбрать целевую главную, ни отрисовать шапку.
**Экран:** 001. Соответствует JS-SYSTEM-14.

### `[предложение по бэкенду]` Явное назначение OTP

У кода должно быть `purpose`: `login` либо `password_reset`. Иначе код одного сценария сработает в другом.
**Экраны:** 001, 001a.

### `[предложение по бэкенду]` TTL и остаток попыток в ответе

Сейчас ограничения (120 секунд, 3 попытки за 5 минут) известны только из job story. Фронт не должен зашивать их в код: нужны `ttl`, `attemptsLeft`, при блокировке — `retryAfter`.
**Экраны:** 001, 001a.

### `[уточнение по контракту]` Что выдаёт `otp/verify-by-code`

Полноценную сессию или только подтверждение кода? В дайджесте OTP описан в контексте сброса пароля, а на скане 001 это самостоятельный метод входа.
**Экран:** 001.

### `[предложение по бэкенду]` Конфиг Telegram-бота как данные

@username бота и команда получения кода — в текст инструкции подставляются с сервера. При переименовании бота захардкоженная инструкция протухнет молча. Низкий приоритет.
**Экран:** 001a.

## academic-service

### `[предложение по бэкенду]` Доступ `student` на чтение предметов и типов занятий

Нужно: предметы **своей группы в активном семестре** + для каждого — какие типы занятий (`lecture` / `practice` / `lab`) у него реально есть.
Сейчас: `GET /academic/subjects` помечен «HEADMAN — только своя группа, ADMIN — все»; роль `student` не упомянута.
Решение владельца: студент видит предметы и типы — **только на чтение**, без права редактирования.
Отдельно: «какие типы есть у предмета» — это **данные**, а не enum. Вычислять на клиенте можно только выкачав все пары семестра.
**Экран:** 102, режим «по предметам». **Без этого экран не работает.**

### `[уточнение по контракту]` Фильтр домашних заданий по дате

`GET /academic/homeworks` принимает группу и семестр. Есть ли фильтр по дате или паре — не видно.
Если нет: фронт грузит **все задания семестра**, чтобы показать три штуки за день.
**Экран:** 101.

### `[уточнение по контракту]` Признак «выполнено текущим студентом» в списке заданий

Из описания списка не видно, приходит ли флаг выполнения. Без него чекбокс не с чего инициализировать, а запрашивать деталь на каждое задание — N+1.
**Экран:** 101.

### `[предложение по бэкенду]` Вывод `free_attendance` из обихода

Статус «свободное посещение» отменён решением владельца — и как статус отметки, и как тип уважительной причины. Статусов ровно три: `+` (present), `у` (excused), `н` (absent).
Нужно: новых отметок с этим значением не создавать; решить, что делать с уже существующими записями.
**Экраны:** все, где показывается статус.

### `[предложение по бэкенду]` Перечень типов уважительных причин как данные

Состав: по болезни · по приказу вуза или иному документу · повестка от военкомата · прочее (комментарий обязателен и отображается пользователю). Перечень будет пополняться.
Требование: список отдаётся клиенту **как данные**, а не зашивается в код — расширение не должно требовать релиза фронта.
**Экран:** 102 (`ExcuseReasonPopover`), экраны заявок.

### Заметка: `/academic/thresholds/*` не используется

Механика порогов и «красной зоны» снята с продукта. Четыре операции фронтом **не вызываются**. С бэкенда не удалять — механика может вернуться.
**Затронутые истории:** JS-STUDENT-WEB-01, JS-STUDENT-WEB-05, JS-HEADMAN-WEB-08, JS-ADMIN-12.

## schedule-service

### `[нет API]` Операция переноса пары

Есть отмена и создание разовой пары; переноса как единого действия нет. Нужно: перенос одним действием, чтобы студент увидел пару на новом месте **с пометкой о переносе**, а статистика посчиталась корректно.
**Экраны:** 102 (отображение), экран старосты (действие).

### `[уточнение по контракту]` Флаг гео-блокировки в представлении пары

Блокировка ставится через `POST /schedule/lessons/{id}/blockage`, но отдаётся ли признак в списке пар — не видно.
Без него кнопка «Отметиться» показывается активной там, где отметка запрещена: студент нажимает и получает отказ.
**Экран:** 101. **Блокирует корректность экрана.**

### `[предложение по бэкенду]` Причина отмены пары в представлении пары

Студент видит причину всплывающей подсказкой на отменённой паре (заметка 3 скана 102). Операция отмены есть, хранится ли причина — не видно.
**Экраны:** 101, 102.

### `[предложение по бэкенду]` Признак смены аудитории

Нужно: `roomChanged` + прежнее значение, чтобы студент увидел изменение выделенным и не пришёл в старую аудиторию. Владелец отметил это как новый функционал; со стороны старосты появится соответствующее действие.
**Экраны:** 101, 102.

### `[предложение по бэкенду]` Признак происхождения пары

Нужно: `regular` / `one-off` / «перенесена с 12.10». Студенту нужно понимать, почему пара появилась не по расписанию.
**Экран:** 102.

### `[предложение по бэкенду]` Единый поток пар за период

Сейчас: `GET /schedule/groups/{groupId}/lessons` + `GET /schedule/one-off-lessons` — два списка, слияние на клиенте, +1 запрос на каждую неделю.
Разовые пары обязаны попадать в сетку и в агрегаты наравне с регулярными.
**Экраны:** 101, 102.

### `[предложение по бэкенду]` Метаданные недели

Нужно: чётность недели, порядковый номер от начала семестра, границы дат, границы семестра.
Сейчас клиенту пришлось бы вычислять это самому. Сервер уже считает чётность при генерации расписания (JS-SYSTEM-05) — две реализации разойдутся на границе семестра и при переносах, и студент увидит «нечётная», сидя на паре чётной недели.
**Экран:** 102.

### `[предложение по бэкенду]` Фильтр пар по предмету и типам занятий

Сейчас: расписание семестра целиком + фильтрация на клиенте. На каждое переключение предмета клиент тянет полный семестр ради 15 строк.
**Экран:** 102, режим «по предметам».

### `[предложение по бэкенду]` Версия / ревизия расписания группы

Расписание мутирует: отмена, восстановление, разовая пара, перенос, смена аудитории. Без версии в ответе ключ кэша не инвалидируется, и студент увидит закэшированную неделю без только что добавленной пары.
Прямо следует из направления владельца «кэшируемость вместо клиентской агрегации».
**Экраны:** 101, 102.

### `[предложение по бэкенду]` «Моя ближайшая релевантная пара»

Отдельная потребность экрана, а не выборка из недельного списка на клиенте.
**Экран:** 101.

## attendance-service

### `[предложение по бэкенду]` Авто-эскалация одной операцией + идемпотентность

**Флоу, подтверждённый владельцем:** студент нажимает «Отметиться» → если гео прошло, ставится `+`; если не прошло, заявка старосте уходит **автоматически**, студент видит уведомление, кнопка становится неактивной.

Требования:
1. Неуспешный чекин и создание заявки — **одна серверная операция**. Если собирать на клиенте двумя вызовами, при обрыве между ними студент останется с «н» и без заявки, а повторить нечем: ручная кнопка на карточке текущей пары убрана.
2. **Идемпотентность по паре `(студент, пара)`.** Тогда «одна заявка на пару» гарантируется ключом, а не поведением фронта, и клиент может безопасно повторить запрос.
3. Лимит **общий** для авто- и ручной заявки: это одна сущность с разным происхождением, а не два счётчика.
4. Отклонение старостой **окончательно** — повторная заявка по той же паре невозможна.

Сейчас: `POST /attendance/checkin` и `POST /attendance/late-checkin/{lessonId}` — раздельно.
**Экран:** 101. Соответствует изменённым JS-STUDENT-02, JS-STUDENT-06, JS-HEADMAN-05.

### `[предложение по бэкенду]` Гарантия доставки заявки старосте

Сохранение + повторы на стороне сервера. Фронт различает «заявка создана» и «староста увидел» — студенту показывается первое; второе не зона ответственности клиента.
**Экран:** 101. Событие `late_checkin.requested` теперь порождается и автоматически, без действия студента.

### `[предложение по бэкенду]` Статус заявки late-checkin в составе строки пары

Иначе после перезагрузки страницы кнопка снова выглядит активной, хотя заявка уже подана.
Сейчас: `GET /attendance/late-checkin/pending` — отдельный запрос и join по `lessonId` на клиенте.
**Экран:** 101.

### `[предложение по бэкенду]` Проценты считает сервер

`%«+ и у»` и остальные доли должны приходить готовыми, вместе с количествами. Если клиент считает долю из двух других, цифра разойдётся с журналом старосты, где та же величина считается по-своему.

**Единые правила знаменателя (подтверждены владельцем):**
- отменённая пара **не входит ни в один знаменатель**, включая счётчик прошедших пар;
- будущие пары не считаются — «нет данных», а не «0%»;
- разовые и перенесённые пары участвуют наравне с регулярными.

**Экраны:** 101, 102.

### `[предложение по бэкенду]` Агрегат по паре «предмет + тип занятия»

На 101 показатель рядом с карточкой пары — это **не общая посещаемость**, а процент по предмету текущей пары с её типом занятия, только по «+».
**Экран:** 101.

### `[уточнение по контракту]` Что именно отдаёт `reports/student/dashboard`

По описанию: общий процент, разбивка, недельный timeseries, топ пропущенных предметов. Не видно:
- timeseries — это «по неделям» или «по дням внутри недели»? Экрану 101 нужно второе;
- принимает ли эндпоинт произвольную неделю (график листается влево-вправо) или всегда текущую.

Отдельно: эндпоинт помечен как «для домашнего экрана PWA / Mini App». На десктопе 1920 места кратно больше — структура может не покрывать экран.
**Экран:** 101.

### `[предложение по бэкенду]` Режим «весь период» как параметр агрегата

График переключается между «эта неделя» и «весь период» — это должен быть параметр того же агрегата, а не отдельный источник.
**Экран:** 101.

### `[уточнение по контракту]` Параметры `reports/student/stats`

Принимает ли произвольный диапазон дат и фильтр «предмет + типы занятий», возвращает ли все четыре доли (`%«+»`, `%«н»`, `%«у»`, `%«+ и у»`) и число прошедших пар сразу.
**Экран:** 102, оба режима.

### `[уточнение по контракту]` Тип и комментарий уважительной причины в `records`

Содержит ли `reports/student/records` тип причины и комментарий, или за ними нужно идти в `GET /attendance/excuses/me` третьим запросом.
**Экран:** 102 (`ExcuseReasonPopover`).

### `[нет API]` Выгрузка студентом собственной посещаемости

Нужно: экспорт своей посещаемости в том же табличном виде, с текущими фильтрами.
Сейчас: `reports/headman-weekly/*` и `reports/journal` — отчёты старосты по группе, не выгрузка студента по себе.
**Статус:** идея владельца (заметка 6 скана 102), **не подтверждена как обязательная**. На скане кнопки нет.
**Экран:** 102.

## notification-service

### `[предложение по бэкенду]` Гарантированная доставка `late_checkin.requested`

Событие теперь порождается **автоматически** при неуспешной геоотметке, без действия студента. Доставка старосте должна быть гарантирована на стороне сервера (сохранение + повторы), поскольку студент повторить заявку не может.
Связано с пунктом об авто-эскалации в attendance-service.

## Сквозные требования

### Направление владельца по API

> **Эндпоинты под форму экрана + кэшируемость, а не клиентская агрегация.**

Практические следствия:
1. Экрану отдаётся то, что он показывает, — а не набор сущностей для сборки на клиенте.
2. Ответы кэшируемы (условные запросы, ETag).
3. **Инвалидация обязательна:** расписание мутирует, поэтому ключ кэша должен зависеть от версии расписания группы. Иначе кэш отдаст неделю без только что добавленной разовой пары.

### Расчёты, которые не должен делать клиент

| Что | Почему |
|---|---|
| Чётность и порядковый номер недели | Сервер уже считает при генерации расписания; две реализации разойдутся на границах семестра и при переносах |
| Проценты и доли | Одни цифры на трёх поверхностях; клиентское округление разойдётся с журналом старосты |
| Слияние регулярных и разовых пар | Порядок и полнота должны быть одинаковы у всех клиентов |
| «Какие типы занятий есть у предмета» | Вычисляется только выкачиванием всех пар семестра |

## Экраны, где текущий REST неудобен

Фактура для решения «REST или GraphQL». Решение не принято; ниже только измерения.

| Экран | Запросов до первого полного кадра | Клиентские join'ы | Over-fetching |
|---|---|---|---|
| **001 Вход** | **3–4** — login → профиль → активный семестр (+ public-key, если пароль шифруется) | нет | нет |
