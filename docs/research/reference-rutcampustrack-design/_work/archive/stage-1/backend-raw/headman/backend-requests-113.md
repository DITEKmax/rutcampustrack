| Тип | Кол-во | Критичность |

**Особенность экрана.** В отличие от ПК-111 и ПК-112, где были работающие эндпоинты с over-fetching'ом, здесь **не существует ни одного из нужных агрегатов**. Аналога `student/stats` и `student/dashboard` для группы нет. Владелец подтвердил: экран под наследие не подгоняем. Практическое следствие — форму ответов можно задать сразу под экран.

**Отменено на этом экране:** управление порогами посещаемости (`PUT /academic/thresholds/group`, `PUT /academic/thresholds/subject`) — механика снята с продукта целиком (§0 реестра). Эндпоинты остаются неиспользуемыми, с бэкенда не удаляются.

## Сквозное правило (вне одного экрана)

### C-1. Две метрики посещаемости отдаются всегда и рядом
`[предложение по бэкенду]` · источник: ПК-113 §4.3, заметка 3 job · **подтверждено владельцем** · **область действия: весь продукт**

- **Нужно:** везде, где считается посещаемость, сервер отдаёт **две величины рядом**: `%+` (только присутствие) и `%(+ и у)` (присутствие вместе с уважительными).
- **Обоснование владельца:** разные преподаватели оценивают посещаемость по-разному — одна метрика не обслуживает обе трактовки.
- **Затрагивает:** ПК-101, 102, 103 студента и все экраны старосты, преподавателя, администратора со статистикой.
- **Продолжение JS-SYSTEM-16:** проценты считает сервер и отдаёт вместе с количествами, чтобы округления на разных экранах не разошлись.
- ⛔ **Отменяется:** метрика `%у + н` (доля непосещения), нарисованная на скане 113. Избыточна — равна `100% − %+`.

## attendance-service

### C-2. Агрегат отметок по группе за семестр
`[предложение по бэкенду]` · источник: §4.1, заметка 1 макета

- **Нужно:** по группе за активный семестр, по всем предметам — количества `+`, `н`, `у` и обе метрики из C-1.
- **Сейчас:** нет. `GET /academic/dashboard/stats` — ADMIN и по системе целиком, не по группе.

### C-3. Инкрементальный расчёт вместо пересчёта
`[предложение по бэкенду]` · источник: §4.1 · **прямая формулировка владельца**

- **Формулировка владельца (заметка 1 макета):** «надо сделать функционал такой, что есть значение и оно инкрементируется, а не считать каждый раз».
- **Нужно:** агрегаты хранятся и обновляются по событию изменения отметки, а не пересчитываются на каждый запрос.
- **Связано с:** B-10 из ПК-112 — там та же идея применительно к выгрузкам, которые роняют сервис. Это одна архитектурная задача, а не две.

### C-4. Агрегат уважительных причин по типам
`[предложение по бэкенду]` · источник: §4.2, заметка 2 макета

- **Нужно:** количество **поданных** причин в разрезе типов, **упорядоченное по убыванию частоты**.
- **Подтверждено владельцем:** считаются поданные — «какие чаще всего подают», независимо от решения старосты.
- **Сейчас:** `GET /attendance/excuses/group/{groupId}` — список тикетов, агрегата нет.
- **Форма ответа:** список пар «тип → количество», **не фиксированный набор полей** — перечень типов пополняется и приходит как данные (§0 реестра).
- **Почему нельзя на клиенте:** иначе вытягиваются все тикеты группы за семестр ради нескольких чисел.

### C-5. Агрегат по студентам группы за семестр
`[предложение по бэкенду]` · источник: §4.4, заметка 3 макета · **ядро экрана**

- **Нужно:** строка на студента: `userId`, ФИО; `%н`, `%+`, `%у`, `%(+ и у)` **и те же четыре в количествах**; тикеты на «н» (late-checkin) — подано / одобрено / отклонено; тикеты на «у» (excuse) — подано / одобрено / отклонено; разбивка способа получения «+» (C-7).
- **Сейчас:** нет ни одного эндпоинта.
- **Требуется:** серверные сортировка, фильтрация и пагинация. Дефолтная сортировка — по `%+`.
- **Вариант со срезом:** тот же агрегат с фильтром по предмету и набору типов занятий — это второй табличный блок экрана. Желательно один контракт с параметрами, а не два разных.

### C-6. Агрегат тикетов с решениями в составе строки студента
`[предложение по бэкенду]` · источник: §4.6

- **Нужно:** количества поданных / одобренных / отклонённых, отдельно для late-checkin и для excuse, **внутри строки студента** (C-5).
- **Сейчас:** `GET /attendance/excuses/group/{groupId}` и `GET /attendance/late-checkin/group/{groupId}` — списки без агрегации.
- **Почему в составе строки:** отдельный подсчёт на каждого студента по двум спискам — это N+1 по составу группы (25–30 человек).

### C-7. Происхождение заявки late-checkin
`[предложение по бэкенду]` · источник: §4.5 · **новое поле**

- **Нужно:** у заявки хранится происхождение: `manual` (студент нажал «был, но забыл») либо `auto_after_failed_geo` (ушла автоматически при неудачной геоотметке).
- **Зачем:** колонка «способ получения "+"» на 113 требует различать четыре пути — гео · ручная заявка · заявка после неудачного гео · поставил староста. Текущий `source` отметки различает только `student_geo` / `late_checkin` / `headman`.
- **Согласование с §0 реестра:** решение «одна заявка на пару независимо от происхождения» **не противоречит** этому. Лимит остаётся общим, признак происхождения просто сохраняется.
- **Зависимость:** требует наличия `source` в отметке — см. B-4 из ПК-112.

### C-8. Временной ряд посещаемости группы
`[предложение по бэкенду]` · источник: §4.7, заметка 5 макета

- **Нужно:** ряд точек в трёх разрезах: семестр с делением по неделям · выбранная неделя с делением по дням · срез по предмету с типами занятий. В каждой точке — **обе метрики** из C-1. Плюс детализация точки для подсказки при наведении.
- **Подтверждено владельцем:** **сервер отдаёт данные, график рисует фронт.** Картинку сервер не готовит.
- **Обязательное условие:** обе серии приходят **на одной сетке ключей**. Требование уже сформулировано для студенческого 103 (JS-STUDENT-19) — если сетки разойдутся, клиент будет сшивать точки по датам.
- **Сейчас:** нет.

### C-9. Выгрузка блоков статистики
`[предложение по бэкенду]` · источник: §4.10 · продолжение B-9 и B-11 из ПК-112

- **Нужно:** выгрузка трёх блоков — таблица по группе, таблица по предмету, график — **с учётом всех активных фильтров**, в форматах из перечня, приходящего как данные.
- **Открытый пункт:** выгрузка **графика**. Владелец подтвердил, что рисует фронт, но файлы формирует сервер (B-9). Значит `png` графика требует **серверной отрисовки того же ряда**. Решить: сервер рисует картинку сам либо для графика доступны только табличные форматы.

### C-10. Детализация по студенту
`[предложение по бэкенду]` · источник: §4.9, заметка 2 job

- **Нужно:** подробный срез по одному студенту за семестр — предположительно разбивка по предметам и типам занятий, история тикетов, динамика по периодам.
- **Ограничение на подачу:** отображается **встроенной областью страницы, а не модальным окном** (прямое требование заметки 2 job). На контракт это не влияет, но объём ответа должен быть таким, чтобы панель открывалась быстро.
- **Открытый пункт:** точный состав не определён — уточняется при проектировании контракта.

## academic-service

### AC-6. Конфигурируемый набор сортировок и фильтров
`[предложение по бэкенду]` · источник: §4.8, заметка 3 макета · **подтверждено владельцем**

- **Формулировка владельца:** «сортировка и фильтр стараемся делать там, где уместно; на бэкенде добавляется, а на фронте рисуется, так что может меняться».
- **Нужно:** описание колонок (какие сортируются, какие фильтруются, каким типом фильтра) приходит **как данные** вместе с агрегатом либо отдельным описанием.
- **Почему:** фронт не должен зашивать перечень. Добавление фильтра на бэкенде не должно требовать релиза фронта — то же правило, что для типов уважительных причин и форматов выгрузки.
- **Требование:** сортировка и фильтрация выполняются **на сервере** вместе с пагинацией. Клиентская сортировка по неполной странице даёт неверный порядок.

### AC-7. Право помощника на статистику
`[уточнение по контракту]` · источник: §4.7 · **владелец: решаем после фронта**

- **Вопрос:** покрывает ли `view_stats` весь экран целиком или отдельные блоки (счётчики, таблицы, график, детальная панель).
- **Связано с:** AC-3 из ПК-111 (эффективные права в сессии), AC-5 из ПК-112 (право на выгрузку).
