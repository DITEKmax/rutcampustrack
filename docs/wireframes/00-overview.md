## 2. Карта навигации

### 2.0. Сквозные правила

- **Неавторизованный запрос любого защищённого маршрута** → ПК-001 с сохранением `returnUrl`. После входа — возврат на запрошенный адрес.
- **Успешный вход** → **всегда главная** активной роли (скан 001-1). Активная роль после входа — **базовая**: student вперёд headman, teacher вперёд admin (§0 реестра).
- **Нет роли** → `ForbiddenState`, данные не запрашиваются. **Роль есть, но активна другая** → `role-inactive` + кнопка переключения. Это разные состояния, не путать.
- **Контекст живёт в URL, не в сессии** — на всех экранах teacher и admin и на большинстве экранов student/headman: разрез, фильтры, поиск, страница, период, `groupId` / `subjectId` / `lessonId` **по идентификаторам**. F5 не сбрасывает, ссылку можно переслать. **Между сессиями контекст не сохраняется.**

### 2.1. Вход и восстановление

```
ПК-001 ──«Забыли пароль»──▶ ПК-001a ──[переход не описан → NI-2]──▶ ПК-001b
  ▲                            ▲
  │                            └── ПК-108 «Не помню пароль»
  │
  ├── редирект с любого защищённого маршрута (нет сессии / истекла)
  ├── ПК-108 «Выйти на всех устройствах» (гасит и текущую сессию)
  ├── ПК-108 успешная смена пароля (гасит все сессии)
  └── ProfileMenu → «Выход» с любого авторизованного экрана
```

Успех входа (логин/пароль · OTP · QR) → главная активной роли: ПК-101 / ПК-111 / ПК-121 / ПК-131.

Всё остальное на роли admin — раскрытие форм и панелей **на странице**, `RowActionsMenu`, `ConfirmDialog`: переходами не являются.

### 2.6. Межролевые переходы и переключение активной роли

**Единственный механизм — `RoleSwitcher`.** Других межролевых переходов в системе нет.

| Правило | Источник |
|---|---|
| Рендерится только при `roles.length > 1`; один аккаунт может нести все четыре роли при одном логине | §1 спеки 131, реестр §4 |
| Стартовое значение после входа — **базовая роль**: student вперёд headman, teacher вперёд admin | §0 реестра |
| Смена роли → **редирект на главную выбранной роли** и перезагрузка `MainNav`; данные страницы инвалидируются | 101, 111, 131 |
| **Подтверждения нет** — несохранённых данных на этих экранах не бывает; смена объявляется `role="status"` | 111, 131 |
| Состояние покинутого экрана **не сохраняется** | 111 |
| **Границу проводит активная роль, а не набор прав.** Под ролью admin недоступны действия других своих ролей | §0 чат 7 |
| Экраны 101–108 и 111–119 роли admin **не выдаются**, даже когда API помечен `HEADMAN/ADMIN`; прямой заход даёт `role-inactive` | §0 чат 7 → противоречие с 105, NI-11 |
| Староста отмечает **своё** дз и **свою** посещаемость, переключившись в роль student (ПК-101 / ПК-104) — это единственный путь, не урезанный вариант старостинского экрана | §0 чат 4, спека 111 |
| На ПК-115 (=105) переключение роли **визуально ничего не меняет** — это нормально | спека 115 |

Переходы между ролями всегда идут через главную: `RoleSwitcher` → ПК-101 / ПК-111 / ПК-121 / ПК-131. Прямых переходов «с экрана роли X на экран роли Y» не существует.

## 3. Экраны, общие для нескольких ролей

### 3.1. ПК-105 — один экран, три роли

**Экран один.** ПК-115 «Староста — Карта» и «Карта преподавателя» — **не самостоятельные экраны**, а тот же ПК-105 под другим пунктом навигации.

| Роль | Как попадает | Отличия |
|---|---|---|
| student | `MainNav` → «карта» | — |
| headman | `MainNav` набор A → «карта» (числится как ПК-115) | **ролевых различий нет** (JS-HEADMAN-WEB-01, заметка 1 скана 115) |
| teacher | `MainNav` → «карта» | отдельной страницы не заводим (прим. 2 скана 121) |
| admin | **пункта нет** | у админа — ПК-135, это другой экран → NI-11 |

Страница — `CampusMapPage`, один и тот же компонент. Отдельного кода карты преподавателя не существует.
При этом файлов спеки два (`student/105-student-map.md` и `headman/115 headman map.md`) → NI-6.

### 3.2. Экраны student, которые headman видит без изменений

ПК-101, ПК-102, ПК-103, ПК-104, ПК-107 — **тот же экран, тот же код, различий по роли нет** (JS-HEADMAN-WEB-01). У старосты для тех же задач есть **свои** экраны 111–114 и 119 с другой зоной ответственности; это не варианты одного экрана, а разные экраны.

Единственное исключение по 104: создания, редактирования и удаления заданий там нет **ни в каком состоянии**, даже у пользователя с ролью headman.

### 3.3. ПК-108 — Настройки

Заявлен в спеке для `student` и `headman` (единственное ролевое различие — блок делегированных прав), но `ProfileMenu` ведёт туда **со всех четырёх ролей**: явно у 121 (teacher) и 131 (admin). Реестр §8 числит экран как «все 4 (разобран для student)». Спека под teacher и admin не разбиралась → NI-7.

| `AppShell` | каркас **всех авторизованных** экранов: `<header>` + `<main>` + skip-link на `#main` | все авторизованные |
| `AppHeader` | внутри `AppShell`; контейнер для `RoleSwitcher`, `MainNav`, `ProfileMenu` | все авторизованные |
| `MainNav` | `AppHeader`. **Набор пунктов меняется вместе с активной ролью.** У headman — два независимых набора (два `<nav>` с разными `aria-label`), у остальных ролей один | все авторизованные |
| `RoleSwitcher` | `AppHeader`. Рендерится только при `roles.length > 1` | носители нескольких ролей |
| `ProfileMenu` | `AppHeader`. **Единственный** носитель «Настройки» и «Выход» — в `MainNav` их нет ни у одной роли | все авторизованные |
| `AuthLayout` | каркас **неавторизованных** экранов (001, 001a, 001b): brand-зона + панель. Brand-зона на этапе 1 — пустая заглушка, структура решается на этапе 2 | неавторизованные |
| `LiveNotificationRegion` | заявлен на уровне `AppShell`, сквозной для всех экранов. **Не разобран:** правила накопления, TTL и группировки не определены → отдельная сессия (§12.6) | все авторизованные |
| Skip-link «Пропустить навигацию» | `AppShell`, на `#main` — на каждом авторизованном экране | все |
| Состояния каркаса: `LoadingState` · `EmptyState` · `ErrorState` · `ForbiddenState` · `OfflineState` | доступны на всех экранах; обязаны быть **озвучиваемыми**, а не только визуальными | все |
| `role-inactive` | состояние маршрута при прямом заходе на экран неактивной роли | носители нескольких ролей |
| `returnUrl` | механизм редиректа на 001 и обратно; работает на всех защищённых маршрутах | все |

**Сквозные правила уровня каркаса, не привязанные к компоненту:**

- **Контекст в URL по идентификаторам**, не по названиям (правило чата 5). Между сессиями не сохраняется — «липкий» контекст опаснее лишнего клика.
- **Один `<h1>` на экран**, секции — `<h2>`, уровни без пропусков.
- **Правило крупных сеток** (§6.2, введено на 112): одна остановка Tab на таблицу, перемещение стрелками внутри (roving tabindex). Применяется на 112, 117, 118, при необходимости на 122.
- **Раскрытие панелей — сдвиг в DOM**, не наложение (§6.2).
- **При исчезновении строки фокус переводится на следующую**, а не теряется в конце документа (§6.2).
- **Символ не носитель смысла**: `+` · `у` · `н`, статусы, роли, направление дельты разворачиваются словами; цвет вторичен.
- **Перечни приходят с сервера как данные**: форматы выгрузки, колонки с сортировкой и фильтром, типы уважительных причин. Фронт их не зашивает.
