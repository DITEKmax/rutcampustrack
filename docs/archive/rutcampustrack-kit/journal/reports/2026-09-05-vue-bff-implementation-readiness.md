# ✏️ 05.09.2026 — готовность к Vue и переходу на BFF

## Ответы на вопросы

**Начинать перенос во Vue уже можно. Полностью откладывать бэкенд до окончания фронтенда не стоит.** Оптимальный порядок: согласованный контракт сценария → фронтенд на моках и реализация BFF/сервисов параллельно → интеграция → следующий сценарий.

- **Готова ли Figma?** Принимаем её готовой по уточнению владельца. Оставшиеся ручные правки не превращаем в новый аудит макетов.
- **Готов ли старый бэкенд?** Он обслуживал старый фронтенд. Это исходная реализация, но не подтверждение соответствия новым требованиям.
- **Когда менять бэкенд?** С начала реализации: сначала общие контракты и необходимые доменные изменения, затем доработка по сценариям вместе с Vue.
- **Нужны ли моки?** Да, по согласованным контрактам BFF. Они позволяют разрабатывать и проверять UI до готовности серверной реализации.
- **Когда тестировать?** В каждой партии. Финальный этап — проверка выпуска, а не первое тестирование приложения.
- **Переписывать ли все старые тесты?** Нет. Сохранять действующие бизнес-инварианты и инфраструктурные проверки; менять тесты изменившихся требований и реализацию UI-тестов под Vue.

## Что установлено

Изучены итоговый playbook и frontend-отчёт исследования, evidence audit, транспортные решения и план backend-track из папки проектирования, актуальные журналы kit, структура проекта, старые frontend package/config/source, отдельные Java-контракты, auth controller, gRPC/event/outbox-инфраструктура и CI/E2E-конфигурация. Это оценка готовности и последовательности, не полный аудит всех endpoint.

В проекте PWA и Mini App написаны на React. Уже существуют OpenAPI-снимки и генерация TypeScript-типов, Vitest, Playwright, Java unit/integration-разделение, Testcontainers, схемы событий и outbox. Их наличие подтверждено файлами; актуальная работоспособность тестовым прогоном не проверялась.

В `UserResponse.java` старая модель содержит одиночный `UserRole role`, `AccountStatus status` и признак `headman`. Новые решения требуют ролей со своими состояниями и серверного контекста активной роли. Это пример изменения домена, которое нельзя решить только преобразованием DTO в BFF.

Принятое `knowledge/TRANSPORT.md` уже задаёт REST/OpenAPI → отдельный BFF → внутренний gRPC, RabbitMQ для событий и один BFF для поверхностей. Gateway остаётся владельцем маршрутизации и своих инфраструктурных правил. Агрегаты посещаемости принадлежат attendance. Выбор REST против GraphQL повторно не открывается.

Уточнение владельца отменяет применение прежнего маршрута desktop-first к следующему этапу кода: сначала PWA и Telegram Mini App, затем доработка и подключение веб-версии. Повторный аудит Figma прекращён по просьбе владельца.

## Что взять из исследования

Применить Vue + TypeScript strict, разделение `app/pages/features/shared`, публичные `index.ts` модулей, typed props/emits, Pinia/composables для принадлежащего им состояния, отдельный API-слой, компонентный PCSS и общий слой токенов, воспроизводимую сборку и lint без автоматических исправлений в CI.

Исследование прямо допускает самостоятельное приложение без Module Federation. Микрофронтенды и точную инфраструктуру чужого репозитория нельзя считать обязательными правилами переноса. Во frontend-исследовании не найдено реализованной системы тестов: конкретные инструменты, фикстуры и пороги — стандарт нашего проекта.

Предложение для нового кода: общий доменный и UI-код мобильного продукта плюс оболочки PWA и TMA. Платформенные адаптеры отвечают за авторизацию, Back/commit, viewport/safe areas, клавиатуру, файлы, внешние ссылки и storage/offline. Позже веб использует подходящие общие части и собственную композицию экранов. Не копировать всю бизнес-логику между приложениями.

До первой партии контролов согласовать PCSS-подход исследования с существующей shadcn-vue-накладкой kit: она предполагает Tailwind-стилизацию базовых контролов. Нужна явная граница владения стилями либо решение об адаптации накладки; молча менять эту договорённость нельзя.

## Предлагаемый порядок

1. **Подготовить исполнимые правила переноса.** Зафиксировать состав первого выпуска, структуру Vue, источник токенов и assets, политику стилей, платформенные адаптеры, критерии готовности. Составить таблицу `сценарий → данные/команды → контракт BFF → сервис-владелец → изменения схемы/событий → тесты`. Статусы различать: существует и подходит / требует изменения / отсутствует / требует решения.
2. **Согласовать первый сквозной контракт.** Начать с входа, серверной сессии/ролей и «Сегодня». Для каждого ответа определить поля, доступность действий, ошибки, пустоту, даты/часовой пояс и правила актуальности. Моки и реализация используют одну версию публичного контракта. Не нужно проектировать все endpoint приложения до первого компонента, но общий session/error/pagination vocabulary нужен заранее.
3. **Поднять Vue-основу и первый BFF-срез.** Токены → базовые компоненты → мобильная оболочка → первый экран. Одновременно BFF и нужные сервисы реализуют утверждённые ответы. Фронтенд не должен временно брать на себя отсутствующие доменные расчёты и объединение больших серверных выборок.
4. **Рано проверить реальную интеграцию.** Вход → контекст пользователя → расписание → отметка/результат сервера. Затем связанный сценарий заявки студента и решения старосты. TMA-авторизацию и поведение оболочки проверить уже здесь, даже если PWA собирается первой.
5. **Повторять по функциональным партиям.** Для каждой — контракт, Vue, BFF/домен, нужные события/миграции, тесты и реальная проверка. Общий рефакторинг проводить отдельными небольшими изменениями, когда он нужен для понятности или надёжности; не смешивать его без необходимости с изменением бизнес-поведения.
6. **Подготовить выпуск PWA/TMA.** Проверить целевые устройства, обновление установленной PWA, старый service worker/cache, маршруты и deep links, окружение, миграции, smoke и возможность восстановления. После запуска развивать веб и продолжать изменения дизайна через те же контракты и регрессионные проверки.

## Как менять сервер

BFF собирает публичные ответы, применяет разрешённые проекции, отображает ошибки и обращается к владельцам данных. Он не заменяет доменную модель, транзакции и расчёты в сервисах. Сервисы также должны обеспечивать доступ к своим данным — UI guards не являются защитой.

Для каждого изменения событий описывать producer/consumer, payload/version, routing key, queue/binding, повторную доставку, дедупликацию, retry/DLQ и правила порядка. Новый BFF сам по себе не требует новых топиков: они возникают из новых событий и потребителей. Существующие схемы, outbox и idempotency использовать там, где они соответствуют новому поведению.

Схему БД менять там, где новые требования не выражаются старой моделью: роли, назначения, проекции или жизненный цикл операций. При необходимости сохранять данные — новые структуры → перенос данных → проверка → переключение чтения/записи → удаление старого отдельным шагом. Если это только одноразовая тестовая база, возможен более простой путь, но право сбросить её не предполагается.

## Как тестировать

| Уровень | Что проверяем | Нужен реальный backend |
|---|---|---|
| Unit/component: Vitest + Vue Test Utils | состояние компонентов, формы, сценарии ошибок, доступность действий, stores/composables | Нет |
| UI в браузере: Playwright + моки | переходы, роли, loading/empty/error, длинные данные, визуальная регрессия на принятых состояниях | Нет |
| Контракт BFF | ответы/ошибки и совместимость OpenAPI, соответствие фикстур схеме | Для проверки реализации — да |
| Java integration | доменная логика, права, БД, gRPC, outbox/consumer, повтор событий, миграции | Да, изолированное окружение |
| Сквозные E2E | настоящие вход, отметка, заявка, решение, смена роли и наблюдаемый результат | Да |
| Устройства и host | установка/обновление PWA, Telegram Back/viewport, keyboard, геолокация, файлы, сеть | Да для итоговой приёмки |

MSW предлагается как сетевой слой моков: приложение выполняет обычные запросы к BFF, тестовая среда возвращает подготовленные ответы. Фикстуры должны задавать ошибки, задержки, конфликты, пустые ответы и смену прав; неизвестные запросы в тестах должны выявляться. Моки не подменяют контрактную проверку реального сервера.

Разделить mock-режим UI и проверку production service worker: проверки PWA cache/update/offline выполнять с настоящим SW и тестовым API. Успешный моковый сценарий не доказывает корректность cookie, авторизации, очередей или транзакций. Эмуляция мобильного браузера не заменяет запуск внутри Telegram на целевых устройствах.

Старые React-компонентные тесты потребуют адаптации под Vue. API/E2E-сценарии и Java-инварианты оценивать по новым требованиям: например, прежний сценарий массовой отметки нельзя механически переносить, если в актуальных решениях оставлены одиночные действия. Тесты новой функциональности не должны получать зелёный статус только из-за `--passWithNoTests`.

**Готово на моках:** UI и его состояния проверены против согласованного контракта. **Интегрировано:** тот же сценарий прошёл с BFF и сервисами. **Готово к выпуску:** проверены целевые платформы, миграция/обновление и эксплуатационные условия.
