```

│  ├─ MainNav (admin, ОДИН набор)         [не окрашен] главная · пользователи · группы · семестры · карта

└─ <main> AdminHomePage
   ├─ <h1> «Главная — администратор»                    [не нарисован, добавлен при разборе]
   ├─ <section> «Масштаб системы»                       [КРАСНЫЙ]
   │  ├─ StatCard  «Количество студентов в системе»     + MetricDelta (всегда)
   │  ├─ StatCard  «Количество преподавателей в системе» + MetricDelta (всегда)
   │  └─ StatCard  «Количество групп в системе»          + MetricDelta (всегда)
   └─ <section> SystemActivityPanel                     [КРАСНЫЙ]
      ├─ Tabs  «сегодня» · «Всё время»                  [ЗЕЛЁНЫЙ, внутри красного блока]
      └─ DefinitionList variant="stack" (5 строк)       [КРАСНЫЙ]
         ├─ количество отметок «+»                       + MetricDelta только при period=today
         ├─ доля успешных гео-отметок от общего числа    + MetricDelta только при period=today
         ├─ количество просмотров карты                  + MetricDelta только при period=today
         ├─ количество заявок и тикетов                  + MetricDelta только при period=today
         └─ количество дз                                + MetricDelta только при period=today
```

### Сверка со сканом

- **ЗЕЛЁНОЕ:** пилюли ролей в шапке, кружок профиля, две кнопки «сегодня» и «Всё время».
- **ЖЁЛТОЕ:** поповер «Настройки / Выход» под кружком профиля.
- **КРАСНОЕ:** три карточки верхнего ряда, весь блок из пяти метрик.
- **НЕОКРАШЕНО:** строка `MainNav` («главная пользователи группы Семестры карта»).
- **Не нарисовано, следует из разбора:** `<h1>` страницы, заголовки двух секций, все non-happy состояния, подпись о правиле подсчёта на карточках.

**Как прочитал (сверено с владельцем):**

1. Две зелёные кнопки — **взаимоисключающий переключатель периода для всего блока из пяти метрик**, а не два независимых действия и не переключатель одной первой строки.
2. Три верхние карточки **периоду не подчиняются**: «сколько сейчас студентов» — состояние системы, а не событие за период. Прирост по дням у них показывается **всегда**, независимо от положения переключателя.
3. Прирост у пяти метрик показывается **только в режиме «сегодня»**. В режиме «Всё время» суточной дельты нет — она не «неизвестна», её не существует как величины.
4. Пять красных строк — **один блок с одним состоянием загрузки**, а не пять независимых плиток (в отличие от верхнего ряда).
5. `RoleSwitcher` с четырьмя пилюлями — **не шаблон скана, а реальный предельный случай**: один аккаунт может нести все четыре роли при одном логине. Состав пилюль = роли, которые у аккаунта реально есть; при одной роли компонент не рендерится (§4 реестра).

### Красный ≠ без взаимодействия

- **Блок метрик (КРАСНЫЙ) содержит `Tabs` (ЗЕЛЁНЫЙ).** Точечное управляющее действие внутри фиксированной зоны — прим. на скане нет, следует из цвета самих кнопок.
- **Карточки и строки метрик не кликабельны.** Переходов «с числа в раздел» на скане не нарисовано — фиксирую как наблюдение, не как пробел рисунка.

## 4. Потребности в данных

### 4.1 Масштаб системы — три карточки

**Нужно.** Агрегат «система», единственный объект, без фильтров и пагинации:

- `studentsCount`, `teachersCount`, `groupsCount`;
- те же три значения **на конец предыдущих суток** либо готовые дельты;
- правило подсчёта: **счёт по ролям, а не по головам.** Один аккаунт с ролями student и teacher попадает в обе карточки (скан 131-2, расширено владельцем до четырёх ролей на одном логине). Следствие: **сумма карточек ≠ количеству учётных записей**, и это надо сказать пользователю подписью, иначе он сложит числа;
- правило по статусам: входят ли `expelled`, `suspended`, `archived` (JS-ADMIN-11 говорит про «активных преподавателей»);
- для групп — входят ли архивные (на 133 архив групп есть, см. прим. 1 скана 133).

**Набор конечен, пагинации не требуется** — это единственный экран роли, где данные не растут со временем в объёме отдаваемого ответа.

**Сейчас.** `GET /academic/dashboard/stats` (ADMIN) — **эндпоинт существует.** Редкий случай для проекта.

**Пробел** `[уточнение по контракту]` — состав полей ответа неизвестен. Требуется подтвердить: три числа; правило подсчёта многоролевого аккаунта; фильтр по статусу пользователя; фильтр по статусу группы. **Без правила подсчёта экран врёт**: вопросы «сколько у нас студентов» и «сколько у нас людей» дают разные числа, и по экрану нельзя понять, какое из них перед тобой.

**Пробел** `[предложение по бэкенду]` — **суточная дельта требует снимков на конец дня или журнала изменений.** Клиент вычислить не может: вчерашнего значения у него нет. Кэшировать прошлый ответ в браузере нельзя — это будет «прирост с моего прошлого визита», а не «прирост за сутки», и у двух администраторов получатся разные числа. Предпочтительно отдавать **готовую дельту**, а не два значения: иначе фронт повторяет расчёт метрики, что запрещено правилом «одна метрика считается в одном месте» (§6.2).

### 4.2 Активность системы — блок из пяти метрик

**Нужно.** Кросс-сервисный агрегат «активность» с параметром `period ∈ {today, all_time}`:

| Метрика на скане | Что это на самом деле | Дельта |
|---|---|---|
| Количество отметок «+» | count отметок со статусом `present` за период | только `today` |
| Количество успешных отметок в процентах от общего («это когда по гео отметились сами») | доля отметок с **источником `student_geo`** (§7 «источник отметки») от всех «+». **Обязательны числитель и знаменатель**: процент без абсолютных чисел не показываем (§6.2) | только `today` |
| Количество просмотров карты | продуктовое событие «пользователь открыл схему этажа» | только `today` |
| Количество заявок и тикетов | тикеты на «у» + тикеты на «н» + late-checkin, **одним числом** | только `today` |
| Количество дз | count опубликованных домашних заданий | только `today` |

**Сейчас.** Не покрыто ничем. `GET /academic/dashboard/stats` живёт в `academic`, а четыре метрики из пяти считаются по данным `attendance`, пятая — по несуществующей телеметрии.

**Пробел** `[предложение по бэкенду]` — нужен **один кросс-сервисный агрегат активности с параметром периода**. Обходной путь на клиенте: 4–5 запросов в три сервиса, из которых ни один не умеет режим «за всё время» без вычитывания всей истории; плюс клиентское деление для процента — прямое нарушение §6.2.

**Пробел** `[нет API]` — **просмотры карты требуют подсистемы продуктовых событий, которой в системе нет как класса.** Это единственная метрика во всём продукте, считаемая по действиям пользователей, а не по учебным данным. Клиентского обходного пути не существует вовсе. Решение выходит за рамки экрана: заводим ли мы аналитику событий и что ещё в неё попадёт.

**Пробел** `[уточнение по контракту]` — «заявки и тикеты» одним числом объединяют **три сущности с разными жизненными циклами** (тикет на «у», тикет на «н», late-checkin). Считаем поданные за период или открытые на момент запроса? Для режима «Всё время» это принципиально разные числа: «подано 12 400» и «сейчас открыто 37».

### 4.3 Прирост и период — матрица поведения

| Ситуация | Путь | Итог |
|---|---|---|
| Карточка масштаба, любой период | значение + дельта к концу вчерашних суток | «4192 · прирост 12 за сутки» |
| Карточка масштаба, снимка за вчера нет (первый день инстанса) | дельта в состоянии `unknown` | «4192 · нет данных за вчера». **Не «+0»** |
| Метрика активности, период «сегодня» | значение за сегодня + дельта к вчерашнему дню целиком | «312 отметок · прирост 28 к вчерашнему дню» |
| Метрика активности, период «Всё время» | значение за всё время, **дельта не рендерится** | «412 900 отметок». Суточной дельты у величины «за всё время» не существует — не показываем ни нуля, ни прочерка |
| Переключение периода | перезапрашивается **только блок активности** | карточки не мигают и не перезапрашиваются |

**Пробел** `[уточнение по контракту]` — база сравнения для дельты в режиме «сегодня»: сравниваем сегодняшний неполный день со вчерашним полным (утром прирост всегда отрицательный) или с тем же временем суток вчера. **Без явного правила метрика вводит в заблуждение каждое утро.** Правило приходит с сервера вместе со значением, фронт его не назначает.

### 4.4 Идентичность пользователя и его роли

**Нужно.** Профиль текущего пользователя с **массивом ролей** и признаком активной роли — для `RoleSwitcher` и для решения о доступности маршрута. Предельный случай: четыре роли на одном аккаунте, один логин.

**Сейчас.** `GET /academic/users/me` — существует.

**Пробел** `[уточнение по контракту]` — отдаёт ли профиль **массив** ролей или одну роль. Модель «студент + флаг `is_headman`» (JS-ADMIN-06) плохо расширяется на «этот же человек ещё и преподаватель, и админ». **Если ролей в ответе одна, `RoleSwitcher` собрать не из чего.** Ключевой вопрос: базовая роль после входа определена парами (student вперёд headman, teacher вперёд admin), но **порядок между парами для аккаунта со всеми четырьмя ролями не задан** — открытый вопрос.

### ⚠️ Фактура к решению о транспорте

| | |
|---|---|
| При обогащённых контрактах | **2 запроса** (масштаб + активность). Из них существует **один**, и, вероятно, не в нужной форме |
| При наивной клиентской сборке | **5–7 запросов в 3 сервиса**, один невозможен физически (телеметрия), один требует клиентского деления |
| Смена периода | **1 запрос**, перезапрашивается только нижний блок |
| Over-fetching | **нет** — экран целиком состоит из агрегатов, лишних полей не приходит |
| N+1 | **нет** — списков на экране нет |

Экран нетипичен для роли: **все данные — числа, ни одного списка, ни одной пагинации.** Тяжесть не в количестве запросов, а в том, что нужных агрегатов не существует. По профилю нагрузки ближе всего к 123 (2–3 запроса, из которых существует ноль), но с одним существующим эндпоинтом вместо нуля.

## 5. Состояния

На бумаге нарисовано **только `success`**: три заполненные карточки и пять строк с числами. Всё нижеследующее добавлено при разборе.

### Автомат `SystemActivityPanel`

| Состояние | Условие | Что показываем |
|---|---|---|
| `loading` | запрос блока идёт | скелетон блока, `aria-busy`; переключатель периода остаётся доступен; карточки сверху не затронуты |
| `success` | данные пришли | пять метрик; дельта у каждой — только при `period=today` |
| `zero-activity` | период «сегодня», активности не было (ночь, выходной, каникулы) | **нули, а не `empty`.** Ноль отметок за день — валидные данные и корректный ответ на вопрос администратора. Подпись «за сегодня активности не было» |
| `partial-metrics` | часть метрик пришла, часть нет (агрегат кросс-сервисный; телеметрия просмотров может отсутствовать физически) | упавшая метрика заменяется пояснением, **остальные рисуются** (§6.2, частичная ошибка не убирает блок) |
| `error` | блок целиком не ответил | `ErrorState` + повтор. Три карточки сверху продолжают жить |
| `no-active-semester` | активного семестра нет | метрики, привязанные к учебному контексту (отметки, дз, заявки), **не определены** → пояснение вместо нулей. Метрика просмотров карты от семестра не зависит и остаётся |
| `delta-not-applicable` | `period=all_time` | дельта **не рендерится вовсе**: не прочерк, не ноль, не «нет данных» |
| `computing` | агрегат «за всё время» считается долго | `loading` с текстом «считаем за всё время», а не молчаливый скелетон неограниченной длительности |

**Критично: `zero-activity` против `error` против `delta-not-applicable`.** Три разные причины показать на месте числа что-то отличное от значения, и администратор смотрит на экран ровно затем, чтобы их различать (прим. 2: «реальная картина по системе»). **Единый ноль на все три случая — экран врёт**, причём именно той роли, которая по нему принимает решения.

### Автомат карточек масштаба

| Состояние | Условие | Что показываем |
|---|---|---|
| `loading` | запрос идёт | три скелетона |
| `success` | данные есть | число + подпись + дельта |
| `delta-unknown` | снимка за вчера нет | число есть, вместо дельты — «нет данных за вчера». **Не «+0»**: «не изменилось» и «не с чем сравнить» — разные утверждения |
| `error` | агрегат не ответил | один `ErrorState` на весь ряд: три числа приходят одним ответом и падают вместе — допустимо, состояние одно и объяснённое (§6.2, правило чата 6) |

### Остальные блоки

Ряд карточек и блок активности — **два независимых запроса, падают порознь**. Внутри каждого — единый ответ и единое состояние. Дробить ради формальной независимости не нужно.

### Общие и вырожденные

- **`empty-system` — новый инстанс: ни семестров, ни групп, ни пользователей.** Формально карточки покажут `0 / 0 / 0`, и это правда, но бесполезная. Показываем вырожденное состояние уровня `no-subjects` (117): пояснение «система пуста» и путь запуска — **семестр → группы → пользователи** (порядок обязателен: группу без семестра и студента без заведённой группы создать нельзя, см. прим. 2 скана 132 и прим. 4 скана 133). **Без этого первый вход администратора в новый инстанс неотличим от поломки.**
- `offline` — предупреждение, что числа могли устареть; переключатель периода остаётся, перезапрос откладывается до восстановления сети.
- `forbidden` — роль admin отсутствует: пояснение **без единого числа** (граница данных проводится сервером, §6.2). ⚠️ Конкретная формулировка и то, что вообще узнаёт посторонний о существовании раздела, — **тема аудита безопасности** (владелец), наравне с показом пароля на 116 и вложениями на 122.
- **`role-inactive` — новое сквозное состояние роли.** Аккаунт имеет роль admin, но активна другая роль, и пользователь пришёл по прямой ссылке на админский маршрут. Это **не `forbidden`**: прав достаточно, роль не активирована. Показываем пояснение и одну кнопку «Переключиться на администратора», которая переключает роль и открывает запрошенный адрес. Понадобится на всех пяти экранах роли.

### По ролям

Экран одноролевой, ролевых вариантов содержимого нет.

**Пользователь, совмещающий роли** (предельный случай — все четыре при одном логине):

- после входа активна **базовая** роль, не admin; он приземляется на главную базовой роли (101 или 121), а не на 131;
- в `MainNav` админских пунктов при этом **нет вовсе** — набор навигации меняется вместе с активной ролью;
- прямая ссылка на `/admin/...` при неактивной роли admin → `role-inactive`, см. выше;
- данные ролей не смешиваются: на 131 нет ничего, ограниченного назначениями преподавателя или группой старосты, поэтому пересечения ролей на этом экране безопасны;
- ⚠️ **порядок базовой роли для аккаунта, совмещающего пары** (например, student и teacher одновременно), решением не покрыт — открытый вопрос, см. §7.

### A11y (структурно)

- `<h1>` «Главная — администратор» присутствует, хотя на скане не нарисован; секции — `<h2>` («Масштаб системы», «Активность»). Skip-link на `#main` из `AppShell`.
- Три карточки — `<ul>`; блок метрик — `<dl>`. **Ни то, ни другое не таблица**: у чисел нет второй оси.
- `MainNav` — один `<nav>` с `aria-label`, активный пункт `aria-current="page"`. У admin **один** набор, второго `<nav>` нет (в отличие от headman).
- `Tabs` — `tablist` с навигацией стрелками; **смена периода объявляется через `role="status"`** («данные за сегодня»), иначе незрячий пользователь не узнает, что числа под ним изменились.
- `MetricDelta`: направление **словом** («прирост 12 за сутки»), не стрелкой и не цветом. Состояния `unknown` и `not-applicable` тоже текстовые.
- Проценты разворачиваются в доступном имени: «доля самостоятельных геоотметок 63 процента, 1240 из 1970» — символ «%» вслух не читается (§6.2), и процент без абсолютных чисел не показывается.
- **Подпись о правиле подсчёта** («один аккаунт может учитываться в нескольких карточках») — часть доступного имени карточки, а не только `Tooltip`.
- Порядок фокуса: skip-link → `RoleSwitcher` → `MainNav` → `ProfileMenu` → карточки (не фокусируемы, читаются как список) → `Tabs` → метрики.
- Тач-таргеты кнопок периода ≥ 44×44. `prefers-reduced-motion` — если появится анимация набегающих чисел, отключать; число обязано быть читаемым сразу.
- Крупных сеток и длинных списков на экране нет — паттерн roving tabindex не требуется.

## 7. Заметки на будущее

### Адаптив

- Три карточки в ряд переживают 1440 и, вероятно, 1280. Подписи длинные («Количество преподавателей в системе») — при сужении усечение с `Tooltip`, полный текст остаётся в доступном имени.
- Блок метрик — вертикальный список, схлопывается без потерь.
- **Что критично не потерять:** кнопки периода обязаны остаться визуально внутри блока, которым управляют (§6.2 — блок несёт подпись, к каким данным относится). Если при сужении переключатель уедет от строк метрик, экран начнёт врать так же, как врал бы 111 без подписей о паре.
- В мобильной версии экран, вероятно, останется одним и станет вертикальной лентой; дробление на два экрана не требуется. Проектируется отдельным циклом, здесь решения не закладываются.

### Открытые вопросы и риски

1. **У роли admin нет экрана статистики.** JS-ADMIN-12 (средняя посещаемость по группам за семестр) и JS-ADMIN-13 (выгрузка pdf / xlsx с фильтрами по группе, предмету, периоду) не ложатся ни на один экран из 131–135. На 131 нет ни таблицы по группам, ни `ExportButton`. Дыра уровня роли — проверить на 133, но по скану там управление группами, а не отчёт.
2. **Телеметрия продуктовых событий** — новая подсистема ради одной метрики («просмотры карты»). Требует продуктового решения, а не только эндпоинта.
3. **Риск расхождения чисел между 131 и 132.** На 132 будет серверная пагинация со своим `total` по пользователям. Если правило подсчёта на 131 (по ролям) и на 132 (по учётным записям) разойдётся, два экрана покажут разные «количества студентов» — прямое нарушение «одна метрика считается в одном месте» (§6.2). Число на карточке и `total` таблицы должны считаться **одним агрегатом с явным параметром**.
4. **База сравнения суточной дельты** в режиме «сегодня»: полный вчерашний день или то же время суток вчера. Без явного правила метрика вводит в заблуждение каждое утро.
5. **Модель ролей.** Один аккаунт — до четырёх ролей при одном логине. Порядок выбора базовой роли задан только внутри пар (student → headman, teacher → admin); **для аккаунта, совмещающего пары, порядок не определён**. Задевает не только 131: это условие входа во всю систему.
6. **Следствие для 132:** если один человек — и студент, и преподаватель, схема логинов `studentXXXXX` / `teacherXXXXX` (JS-ADMIN-01) ломается: логин один, а префиксов два. Это ровно то, о чём прим. 1 скана 121 просило «поменять механизм генерации логина». Разбирается на 132.
7. **`forbidden` и что видит посторонний** — тема аудита безопасности (владелец), вместе с показом пароля на 116 и вложениями к тикетам на 122.
8. **`role-inactive`** — новое состояние, понадобится на всех экранах роли; вносится в §6.1 реестра.
