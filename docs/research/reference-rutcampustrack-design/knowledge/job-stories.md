## Соглашения

- **Роли**: ADMIN, TEACHER, STUDENT (с флагом `is_headman` для старост)
- **Помощник старосты**: студент с делегированными правами из набора: `mark_attendance`, `manage_excuses`, `manage_homework`, `cancel_lessons`, `view_stats`
- **Статусы посещаемости**: ✏️ **ИЗМЕНЕНО** — `present` (`+`), `absent` (`н`), `excused` (`у`).
  ⛔ `free_attendance` **отменён**. Новых отметок с этим значением не создавать. Что делать с уже существующими — решение бэкенда.
- **Источники отметки**: `student_geo`, `headman`, `auto_scheduler`, `teacher_override`, `late_checkin`
- **Уважительные причины (excuse.type)**: ✏️ **ИЗМЕНЕНО (чат 2, состав зафиксирован).** Это **типы причин внутри статуса «у»**, а не статусы отметки — статусов по-прежнему три. Перечень:
  - по болезни;
  - по приказу вуза или иному документу;
  - повестка от военкомата;
  - прочее — **с обязательным комментарием, отображаемым пользователю**.

  ⛔ Прежние значения (`illness`, `summons`, `university_order`, `exemption`, `other`) выводятся из обихода в пользу этого перечня. ⛔ `free_attendance` исключён.
  Перечень **будет пополняться**. Правило в силе: перечень отдаётся клиенту как данные, а не зашивается в код — расширение списка не должно требовать релиза фронта.
  ❓ **ТРЕБУЕТ РЕШЕНИЯ:** владелец назвал типы «тремя», но перечислил четыре — вероятно, «прочее» не считается полноценным типом. Уточнить, влияет ли это на контракт.
- **Типы занятий**: `lecture`, `practice`, `lab`. Термин — «тип занятия»; «вид занятия» не использовать.
- 🆕 **Отменённая пара**: показывается в расписании и таблицах, но **не входит ни в один знаменатель** статистики и не считается пропуском.
- 🆕 **Разовые и перенесённые пары** старосты полноценно участвуют в расписании и статистике наравне с регулярными.
- 🆕 **Будущие пары** не считаются: по ним показывается «нет данных», а не «0%».
- 🆕 **Две метрики посещаемости (чат 4):** везде, где показывается посещаемость, **рядом идут две величины** — `%+` (только присутствие) и `%(+ и у)` (присутствие вместе с уважительными). Обе считает сервер.
  Причина: преподаватели оценивают посещаемость по-разному, одна метрика не обслуживает обе трактовки.
  ⛔ Метрика `%у + н` **не используется** — избыточна, равна `100% − %+`.
- 🆕 **Массовая отметка отменена (чат 4).** Отметка посещаемости только построчная, по одному студенту. Ручная отметка живёт в двух местах намеренно: ПК-111 (текущая пара, оперативно) и ПК-112 (любой период, журнал).
- 🆕 **Терминология сканов:** «тип предмета» в заметках ПК-114 читать как **«тип занятия»**.

## 3. Староста (STUDENT + is_headman = true)

### 3.1 Отметка посещаемости

**JS-HEADMAN-01**: ✏️ **ИЗМЕНЕНО (чат 4).** Когда пара идёт, я хочу отметить посещаемость студентов вручную через Telegram-бота или веб-панель, выбрав пару из расписания и проставив статусы **по одному студенту**.

> ⛔ **Массовая отметка отменена (решение владельца, чат 4):** ~~проставив статусы всем студентам разом~~. Кнопки «отметить всех» нет ни на одном экране. `POST /attendance/marks/batch` фронтом не используется.
> 🆕 **Механика отметки (чат 4, по сканам ПК-111 и ПК-112), единая для всех мест ручной простановки:**
> - пара **в будущем** — кружков выбора нет вовсе, показывается статус «пара ещё не прошла»;
> - **отметки нет** — три кружка `+` `н` `у` видны сразу, отметка ставится **в один клик**;
> - **отметка есть** — один символ + иконка редактирования; по нажатию раскрываются три кружка;
> - **повторное нажатие на выбранный кружок снимает** отметку;
> - подтверждений не требуется нигде.
>
> Требование «один клик» — ограничение конструкции, а не пожелание: массовая простановка неотметившихся это основной рабочий сценарий старосты, и путь «пусто → отмечено» не должен проходить через раскрытие.
> 🆕 **Ручная отметка живёт в двух местах намеренно:** ПК-111 (текущая пара, оперативно) и ПК-112 (любой период, журнал). Контрол при этом один.
> ❓ **[предложение по бэкенду]:** операции **снятия** отметки не существует — `PUT /attendance/lessons/{lessonId}/students/{userId}` умеет только присвоить одно из трёх значений.
> ❓ **[предложение по бэкенду]:** в представлении отметки нужен `source` — без него староста не отличит автопростановку `н` при закрытии пары от собственного решения.

**JS-HEADMAN-02**: Когда я хочу запретить студентам отмечаться по геолокации на конкретной паре (например, при подозрении на подмену), я хочу заблокировать пару для геоотметок, чтобы все отметки шли только через меня.

## 5. Системные / автоматические

### 5.1 Авторизация и учётные записи

**JS-SYSTEM-01**: Когда администратор создаёт пользователя, система генерирует логин по паттерну (`student00001`, `teacher00001`) и случайный пароль. При первом `/start` бота пользователю отправляются логин и пароль. Эти данные зафиксированы в диалоге бота. Если пароль сменён — старые данные удаляются, и в открытом виде пароль больше недоступен.

**JS-SYSTEM-02**: ✏️ **Уточнение.** Когда студент заходит в Telegram-бота, бот автоматически авторизует его по `telegram_id`, связанному с учётной записью (привязка при первом `/start`).

> 🆕 **Роль по умолчанию:** если к аккаунту привязано несколько ролей, активной после входа становится **базовая** — `student` вперёд `headman`, `teacher` вперёд `admin`. Расширенная роль включается вручную переключателем. Повышенные права не активны, пока не выбраны осознанно.

**JS-SYSTEM-03**: ✏️ **РАСШИРЕНО.** Когда пользователь забыл пароль, он запрашивает OTP-код сброса через Telegram-бота. OTP действует 120 секунд, одноразовый, максимум 3 попытки за 5 минут.

> 🆕 Веб-часть сценария: на странице входа есть «Забыли пароль» → экран с инструкцией, как получить код или ссылку в боте. Пользователь вводит код на сайте либо переходит по ссылке из бота и сразу задаёт новый пароль, после чего возвращается на страницу входа.
> Требования: TTL и остаток попыток приходят с сервера, а не зашиваются во фронт. У OTP должно быть явное назначение (`login` / `password_reset`), чтобы код одного сценария не работал в другом.
> Fallback по ролям: студент → староста, староста и преподаватель → администратор, администратор → эксплуатационная процедура вне продукта (JS-ADMIN-14).

**JS-SYSTEM-04**: ✏️ **Уточнено (чат 3).** Когда пользователь хочет сменить пароль (помнит старый), он вводит текущий и новый пароль через веб-панель. Старый пароль проверяется обязательно.

> Живёт в профиле (ПК-108). Не путать со сбросом (JS-SYSTEM-03): при сбросе старый пароль не спрашивается.
> 🆕 Если пользователь старый пароль не помнит — из формы есть переход на сброс через Telegram. Отдельного пути «сменить без старого» **не проектируем**: экран настроек доступен уже вошедшему, и такой путь позволил бы закрепиться в перехваченной сессии.
> 🆕 Успешная смена пароля **гасит все сессии, включая текущую** → пользователь возвращается на страницу входа. Об этом предупреждаем **до** отправки формы.
> 🆕 Факт смены пароля уведомляется в Telegram — требуется событие `password.changed`.

🆕 **JS-SYSTEM-13**: Когда пользователь входит в веб-панель, он может выбрать один из трёх методов: логин и пароль, одноразовый код из бота, либо QR-код, подтверждаемый в мобильном клиенте. Успешный вход любым методом ведёт на главную страницу активной роли.

> ❓ QR-вход: API отсутствует полностью. Нужны выпуск сессии входа, канал статуса для неавторизованного клиента, подтверждение со стороны мобильного клиента, TTL и перевыпуск.

🆕 **JS-SYSTEM-14**: Когда пользователь входит в систему, ему нужны токены, профиль, роли и текущий активный семестр — чтобы отрисовать интерфейс. Эти данные должны приходить вместе, а не собираться клиентом из нескольких запросов.

> 🆕 **Следствие (чат 2):** экраны статистики и дз не запрашивают активный семестр повторно — берут его из контекста сессии. Границы семестра нужны им для ограничения листания периода.

### 5.2 Автоматические процессы

**JS-SYSTEM-05**: Когда староста добавляет слот в расписание (предмет + день + номер пары + чётность), система автоматически генерирует все конкретные даты `lessons` на весь семестр на основе дат семестра и чётности недель.

> 🆕 **Следствие:** чётность и порядковый номер недели считает сервер и отдаёт как данные. Клиент их не вычисляет — две реализации разойдутся на границах семестра и при переносах.

**JS-SYSTEM-06**: Когда пара переходит в статус `active` (по времени начала), система публикует событие `lesson.started` → студенты группы получают push в Telegram: «Пара началась, отметьтесь».

**JS-SYSTEM-07**: Когда пара переходит в статус `closed` (по времени окончания), система автоматически проставляет `absent` всем студентам группы, у которых нет отметки за эту пару. Староста получает уведомление: «Сессия отметки завершена».
