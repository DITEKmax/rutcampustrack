**Расхождение с историями**

- **JS-TEACHER-03** обещает «столбцы — даты пар». Скан уточняет: столбец — **пара**, подпись столбца — дата, а **тип занятия появляется в подписи только когда выбрано несколько типов**. Это не даты, а пары: в один день у предмета может быть и ЛК, и ПЗ.
- **JS-TEACHER-04 подтверждён** (чат 6): ячейка — `AttendanceStatusBadge`, не `AttendanceStatusPicker`. Прим. 2 скана говорит то же самое.
- **JS-TEACHER-07 восстановлен решением владельца (чат 6).** Прежний вывод чата 4 «Excel снят» **отменён**: Excel закладывается в дизайн и в перечень форматов **везде**, где есть выгрузка. Итоговый перечень: **docx · pdf · png · html · xlsx**. Перечень по-прежнему приходит с сервера **как данные** — фронт его не зашивает, но макеты и шаблоны рассчитываем на пять форматов. Прим. 4 скана («шаблон надо будет сделать») относится ко всем пяти.
- **JS-TEACHER-01 подтверждён прим. 1:** сначала группа, предметы подтягиваются автоматически из выбранной группы, типы занятия — после предмета.
- **JS-TEACHER-02 подтверждён косвенно:** группа — обязательное первое звено цепочки, поэтому поток из нескольких групп физически не может слиться в одну таблицу.
- **Пометка реестра «`ExcuseTicketPanel` заведомо переиспользуется на экранах teacher» подтверждена сканом** (прим. 3 + жёлтая карточка внизу) — с изменённым составом, см. §4.4.
- **Прим. 1 второго скана** («список в алфавитном порядке, нет сортировки и фильтров») — прямое противопоставление таблицам старосты: `StatsByStudentTable` (113) сортируется и фильтруется серверно, `TableColumnFilter` здесь **не применяется вовсе**.

```
   │  ├─ SubjectFilter «Выбрать предмет»  [ЗЕЛЁНЫЙ]  зависит от группы
   │  └─ LessonTypePicker multiple ЛК·ПЗ·ЛЗ  [ЗЕЛЁНЫЙ]  зависит от предмета
   ├─ <section> AttendanceJournalGrid       [ЖЁЛТЫЙ — появляется после выбора]
   │     cellMode="read" rowMetrics
   │  ├─ шапка: Дата (+ Тип занятия, если типов выбрано >1)
   │  ├─ строки: ФИО + ячейки статусов (+ · у · н)
   │  └─ хвост строки: % «+» · % «у» · % «н» · % «+ и у»
   ├─ ExportButton «скачать»              [ЗЕЛЁНЫЙ]  docx · pdf · png · html · xlsx
   └─ <section> ExcuseTicketPanel         [ЖЁЛТЫЙ — по клику на ячейку «у»]
      ├─ ФИО · дата подачи · дата подтверждения старостой
      ├─ тип уважительной причины · комментарий
      ├─ пары тикета, относящиеся ТОЛЬКО к моему предмету
      └─ AttachmentList — «файлы можно посмотреть»
```

**Сверка со сканом.** ЗЕЛЁНЫЕ: «Группа», «Выбрать предмет», ЛК / ПЗ / ЛЗ, «скачать», переключатель ролей, круг профиля. ЖЁЛТЫЕ: вся область журнала, карточка уважительной причины, поповер профиля. **КРАСНОГО на скане нет вообще** — это первый экран роли без фиксированных блоков. НЕОКРАШЕНО: `MainNav`; подпись «Карточка aside уважительной причины» — заметка автора, не элемент.

**Структура таблицы — подтверждено владельцем: одна таблица.** Левая и правая половины жёлтого блока — **одна широкая таблица**, а не две. Повторяющиеся подписи «Дата / Тип занятия» на рисунке — заголовки разных столбцов-пар, а колонки процентов стоят в её правом конце как итог по строке. Следствия: один запрос, один горизонтальный скролл, один фиксированный столбец ФИО, метрики — часть той же строки студента, а не отдельный блок.

**Жёлтый ≠ модальное.** Журнал жёлтый потому, что появляется после выбора фильтров, а не потому, что это наложение. Карточка причины нарисована **на странице, под таблицей** — так и проектируем: `ExcuseTicketPanel` раскрывается в потоке страницы (§0 чат 3, единственная модалка продукта — `ConfirmDialog`). Слово «aside» в прим. 3 читаю как «врезкой сбоку», не как модальное окно.

## 4. Потребности в данных

### 4.1. Цепочка контекста: группы → предметы → типы занятий

**Нужно:** мои группы; для выбранной группы — **мои** предметы; для предмета — **реально заведённые у него** типы занятий, с признаком «этот тип у предмета есть / нет».

**Сейчас:** `GET /academic/assignments/my` — тот же источник, что на 121.

**Пробел `[предложение по бэкенду]` — блокирующее.** Снова измерение «тип занятия» в назначении (§9 реестра; 122 — четвёртый потребитель). Прим. 1 требует гасить недоступный тип, а отличить «типа у предмета нет» от «тип есть, но веду его не я» без третьего измерения невозможно. Оба случая ведут к `disabled`, но **с разным пояснением**, и подменять одно другим нельзя: преподаватель решит, что предмет заведён неверно.

### 4.2. Журнал: студенты × пары предмета

**Нужно:** сущность «журнал». Фильтры: `groupId` + `subjectId` + `lessonType[]` + период (семестр до текущей даты). Строки — студенты группы (`userId`, ФИО), **порядок алфавитный, серверный**. Колонки — пары (`lessonId`, дата, время, тип занятия, статус пары). Ячейка: статус (`+` / `у` / `н`), признак «пара не состоялась / отменена», признак `pending`, признак источника (`auto_scheduler` против ручного), **тип уважительной причины** (его показывает `ExcuseReasonPopover`; в прежней редакции контракт ячейки его не называл — K5, вопрос 2) **и ссылка на тикет (`excuseId`), если «у» получен по заявке**. Хвост строки — четыре агрегата: `%+`, `%у`, `%н`, `%(+ и у)`. Пагинации нет — группа целиком.

**Сейчас:** `GET /attendance/reports/journal` — «Journal grid (students x dates)».

**Пробел `[уточнение по контракту]` — критично.** По дайджесту неизвестно: (а) принимает ли фильтры по предмету и типу занятия; (б) есть ли в ячейке `excuseId`; (в) есть ли перстроковые агрегаты. Каждый пункт по отдельности ломает экран:

- без фильтра по предмету и типу вернётся вся сетка группы, а отобрать свои пары клиент **не может** (см. 4.1) — экран не строится вовсе;
- без `excuseId` карточку причины нечем открыть (см. 4.4);
- без агрегатов четыре колонки процентов придётся считать на клиенте, и они разойдутся с 123, где их считает сервер. **Две реализации одной метрики — гарантированное расхождение цифр в отчёте, уходящем на кафедру.**

**Пробел `[уточнение по контракту]`.** Проверяет ли `reports/journal` право преподавателя на группу и предмет: подмена `groupId` не должна отдавать чужую группу.

### 4.3. Режим одной пары (вход со строки дня на 121)

**Нужно:** по `lessonId` — контекст пары (дата, время, группа, предмет, тип, аудитория, статус) и список «студент → статус» в алфавитном порядке, с теми же признаками ячейки, что в 4.2.

**Сейчас:** `GET /attendance/reports/lesson/{lessonId}` — «Lesson attendance list». Ролевых пометок нет.

**Пробел `[уточнение по контракту]`.** Доступен ли эндпоинт роли teacher, проверяет ли принадлежность пары его назначению и содержит ли `excuseId` в строке: подсказка и карточка причины нужны и в этом режиме.

### 4.4. Заявка по ячейке «у» — представление для преподавателя (подтверждено владельцем, вариант «б»)

**Нужно:** по ссылке из ячейки — тикет в **урезанном представлении**:

| Показываем | Не показываем |
|---|---|
| ФИО автора | — |
| дату подачи и **дату подтверждения старостой** | кто именно из старост/помощников решил |
| тип уважительной причины и комментарий | — |
| **пары тикета, относящиеся только к моему предмету** | пары по чужим предметам — ни списком, ни количеством, ни «и ещё N пар» |
| вложения (имя, размер, просмотр) | — |

**Сейчас:** `GET /attendance/excuses/{id}` (детали) и `GET /attendance/excuses/group/{groupId}` (тикеты группы). Роль читателя в контракте **не указана**.

**Пробел `[предложение по бэкенду]` — высокий.** Нужно представление тикета, **отфильтрованное сервером по назначениям читателя**. Фильтровать на клиенте нельзя принципиально: тикет целиком приедет в браузер, и границей данных это не является — она проходит по сети, а не по разметке. Обходной путь через `excuses/group/{groupId}` хуже вдвойне: это выгрузка **всех** тикетов группы, включая тикеты на «н», к которым преподаватель отношения не имеет.

**Пробел `[предложение по бэкенду]`.** Дата подтверждения старостой — отдельное поле решения по тикету. В дайджесте есть только `PATCH /attendance/excuses/{id}/status`; хранится ли момент решения, неизвестно, а прим. 3 требует показать это преподавателю.

**Тикет остаётся неделимым (§0 чат 3).** Урезание — свойство **представления для читателя**, а не дробление сущности: решение по-прежнему одно на весь тикет и принимает его староста. Преподаватель тикет не одобряет и не отклоняет — у него нет ни кнопок, ни прав.

### 4.5. Выгрузка

**Нужно:** генерация отчёта по **текущему разрезу** (группа + предмет + типы + период) в **docx · pdf · png · html · xlsx**. Перечень форматов — данные, не константа фронта.

**Сейчас:** для старосты есть `headman-weekly/*`; **отчёта преподавателя нет**.

**Пробел `[предложение по бэкенду]`.** Нужен серверный шаблон отчёта преподавателя во всех пяти форматах — прим. 4 прямо говорит «шаблон надо будет сделать». Фронт отдаёт фильтры и получает файл. Клиентская генерация исключена: png, docx и xlsx на клиенте — три отдельных движка ради одной кнопки.

### ⚠️ Фактура к решению о транспорте

| Сценарий | Запросов |
|---|---|
| Вход через меню, до выбора | 1 (назначения) |
| Выбор группы → предмета → типов | 1 на построение журнала (если фильтры поддержаны) |
| Каждое переключение типа занятия | +1 полный журнал |
| Клик по «у» | +1 (тикет), +1 на каждое открытие вложения |
| Вход из 121 «Моих предметов» | 2 (назначения + журнал) |
| Вход из 121 по паре | 2 (пара + при необходимости тикет) |

**Итого 3–5 на сеанс, но тяжесть не в числе, а в форме ответа:** 25 студентов × ~30 пар предмета за семестр ≈ **750 ячеек**, каждая с четырьмя признаками, плюс четыре агрегата на строку. Сопоставимо с 112 (~600 и ~1000 ячеек). Отдельно: **если фильтр по предмету не поддержан, экран получает всю сетку группы по всем предметам — over-fetching чужих персональных данных, который к тому же не спасает, потому что отфильтровать своё клиент не может.**

## 5. Состояния

На бумаге нарисован **только `success`** — заполненный журнал и раскрытая карточка причины. Цепочка выбора описана словами (прим. 1), но её состояния не нарисованы. Всё остальное добавлено при разборе.

### `AttendanceJournalGrid` — автомат состояний

| Состояние | Условие | Что показываем |
|---|---|---|
| **`no-context`** | **вход через меню, группа не выбрана** | **приглашение выбрать группу. Данные не запрашивали — это `no-mode` по смыслу (114), а не `empty`. Пустая сетка с шапкой здесь врёт** |
| `no-subject` | группа выбрана, предмет нет | приглашение выбрать предмет; типы занятий `disabled` |

| `success` | есть пары и студенты | матрица + хвостовые метрики |
| `filtered-empty` | выбранные типы не дают ни одной пары | «по выбранным типам занятий пар нет» — **отличать от «данных нет»**, иначе преподаватель решит, что журнал сломан |
| `future` | предмет есть, пары семестра ещё не начались | «пар ещё не было» → **«нет данных», а не «0 %»** |
| `partial` | часть пар прошла, часть впереди | будущие пары показываются колонками **без отметок**, в знаменатель метрик не входят |
| `empty-group` | в группе нет студентов | «в группе нет студентов» — вырожденный, но реальный случай |
| `no-active-semester` | активного семестра нет | журнал не запрашиваем |
| `error` / `forbidden` / `offline` | — | `ErrorState` + повтор / `ForbiddenState` / `OfflineState` |

Признаки ячейки внутри `success`:

| Признак | Что показываем |
|---|---|
| `+` · `у` · `н` | символ + текстовая расшифровка в доступном имени |
| **`pending`** | **по паре есть активная заявка, решения нет — статус не окончательный.** Без этого преподаватель принимает «н» за факт, хотя тикет на рассмотрении |
| отменённая пара | колонка показывается, отметок нет, **в знаменатель не входит**; при отмене отметки стёрты (§0 чат 5) |
| `no-data` | пара не началась или не закрыта — **не «отсутствие»** |
| `auto-absent` | «н» проставлен автоматически при закрытии пары, а не человеком. **Различение обязательно**: преподаватель, увидев «н», делает вывод о студенте |

### `ExcuseTicketPanel` — автомат состояний

| Состояние | Условие | Что показываем |
|---|---|---|
| `closed` | ячейка не выбрана | панели нет |
| `loading` | тикет грузится | скелетон панели, фокус уже переведён |
| `success` | тикет найден | шапка + пары моего предмета + вложения |
| **`no-ticket`** | **статус «у» проставлен старостой вручную, заявки не существует** | **«причина указана старостой без заявки»: без пустых полей и без списка файлов. Критично: прим. 3 обещает документ, а документа может не быть в принципе — экран не должен обещать то, чего нет** |
| `no-attachments` | тикет есть, файлов нет | «файлов не приложено» — отличать от неудачной загрузки списка. **Состояние принадлежит `AttachmentList`** (K5), не панели |
| `attachment-error` | вложение не открылось | ошибка **внутри** панели, панель остаётся. **Состояние принадлежит `AttachmentList`** (K5) |
| `error` / `forbidden` | тикет не отдан / нет права читать | `ErrorState` / `ForbiddenState` **внутри панели**, таблица остаётся живой |

Из перечисленного самой панели принадлежит `no-ticket`; два состояния вложений живут в `AttachmentList` (K5).

### Режим одной пары

Добавляются: `lesson-cancelled` (пара отменена — отметок нет, показываем причину, а не пустой список), `lesson-not-started` (`no-data` на всю пару), `lesson-not-mine` (`forbidden` при подмене `lessonId`).

### Остальные блоки

Фильтры, журнал и панель причины — **три независимых блока**: падение панели не роняет журнал, падение журнала не гасит фильтры. `ExportButton` недоступна, пока журнал не построен, — **с пояснением, а не молча**; во время генерации файла — `busy`, файл собирает сервер.

### По ролям

Экран одноролевой. Совмещённый teacher + admin видит `RoleSwitcher`; при активной роли admin маршрут отдаёт `forbidden`. Отличий содержимого по ролям **нет**: расширенная роль не добавляет преподавателю ни колонок, ни прав на этом экране.

### Границы данных — явно

| Видит | Не видит |
|---|---|
| ФИО студентов выбранной группы | логин, пароль, `initial`-пароль, Telegram-id, делегированные права, блокировки |
| Отметки **только по своим парам** своего предмета и выбранных типов | пары других предметов и других преподавателей, журнал группы целиком |
| Четыре метрики по студенту **в пределах своего предмета** | общую посещаемость студента по всем предметам, рейтинг в группе, детализацию по чужим предметам |
| Тикеты на «у», привязанные к его парам, **в границах своего предмета** | пары того же тикета по чужим предметам (даже количеством), тикеты на «н», историю попыток захвата пары, счётчик лимита |

**Преподаватель ограничен своими назначениями, а не группой.** Это принципиально: группа целиком — зона старосты и админа.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| `GroupFilter` | выбор группы. **Сбрасывает предмет и типы** — они принадлежат группе. Сброс объявляется, а не происходит молча |
| `SubjectFilter` | выбор предмета. Сбрасывает типы, размораживает `LessonTypePicker` |
| ЛК / ПЗ / ЛЗ | мульти-выбор, перестроение журнала. Тип без пар у предмета — `disabled` **с пояснением** |
| Ячейка со статусом «у» | наведение или фокус → `ExcuseReasonPopover` с типом причины; нажатие → раскрывается `ExcuseTicketPanel` под таблицей, фокус переводится в панель и **не запирается**; повторное нажатие или Esc — закрыть, фокус возвращается на ячейку |
| Ячейка с любым другим статусом | **не интерактивна.** Отметку преподаватель не ставит (JS-TEACHER-04) |
| Строка (ФИО) | **не кликабельна.** Детализации по студенту у преподавателя нет ни на скане, ни по правам |
| Вложение в панели | открытие файла через `AppLink`; доступное имя содержит имя файла и формат |
| `ExportButton` «скачать» | генерация отчёта по текущему разрезу в одном из пяти форматов. Подтверждения нет — действие не деструктивно; `busy` на время генерации обязателен |
| Заголовки колонок | **ничего.** Сортировки и фильтров нет (прим. 1 второго скана) |
| Из режима одной пары | ссылка «открыть журнал по этому предмету за семестр» — **добавлено при разборе**: иначе вход со 121 оказывается тупиком |

Оптимистичного UI нет нигде: экран ничего не меняет на сервере.

**Контекст в URL.** `groupId`, `subjectId`, `lessonType[]` — либо `lessonId` для режима одной пары. Всё по идентификаторам (правило чата 5). Ссылка на журнал пересылается коллеге, F5 не сбрасывает разрез. Между сессиями не сохраняем.

**Нехватка прав**

| Ситуация | Итог |
|---|---|
| Неавторизованный | редирект на 001 с сохранением адреса возврата |
| Нет роли teacher | `ForbiddenState` |
| Нет назначений | `no-assignments`, как на 121 — фильтр группы пуст, и это объясняется |
| Прямая ссылка на чужую группу / чужой предмет / чужую пару / чужой тикет | серверный 403 → `ForbiddenState`. Клиентская проверка «нет в моём списке» — **UX, не защита** |

**A11y (структурно)**

- `<h1>` «Посещаемость»; `<h2>` у фильтров, журнала и панели причины. Панель — не `<aside>` в смысле «в стороне», а именованный регион, связанный с ячейкой-триггером.
- Журнал — настоящая `<table>`: `<th scope="row">` = ФИО, `<th scope="col">` = дата (+ тип занятия); **пары одного дня объединяются датой через `colspan` + `scope="colgroup"`** (решение чата 4). Хвостовые колонки метрик — `<th scope="col">`. ✏️ **Правка 09.08.2026:**
требование «полные подписи» относится к **доступному имени**, а не к видимому
тексту: четыре полных названия в шапке шириной 80px не помещаются, а расширять
колонки за счёт данных нельзя. Видимая подпись остаётся сокращённой —
`%+ · %(+ и у) · %у · %н`, полная уходит в `aria-label` и в `Tooltip`,
открывающийся и по наведению, и по фокусу. Тот же приём, что у длинного ФИО
в первом столбце. Утверждённые формулировки: «Процент присутствий», «Процент
присутствий и уважительных причин», «Процент уважительных причин», «Процент
отсутствий».
- **Интерактивна только часть ячеек** (статус «у»), поэтому массовый `radiogroup` здесь не нужен. Но если «у» в сетке десятки, **применяем правило крупных сеток**: одна остановка Tab на таблицу, перемещение стрелками, Enter открывает панель.
- Ячейка «у» — `<button>` **внутри** `<td>`, не кликабельный `<td>`. Доступное имя: «Уважительная причина, Иванов И. И., 12 марта, лекция — открыть заявку».
- `ExcuseReasonPopover` открывается **и по наведению, и по фокусу**; его содержимое **дублируется в доступном имени кнопки** — подсказка мышью для клавиатуры недостаточна. Требование повышено до сквозного правила продукта (K5).
- Первый столбец ФИО фиксирован визуально; **порядок чтения при этом не меняется**.
- Перестроение журнала после смены фильтра объявляется через `role="status"`: предмет, типы, число студентов и пар. Иначе таблица молча подменяется.
- Раскрытие панели — **сдвиг в DOM сразу после таблицы**, а не наложение (§6.2).
- Символы `+` · `у` · `н` разворачиваются словами в доступном имени; цвет носителем смысла не является.
- `ExportButton`: выбор формата — именованные варианты, доступное имя включает предмет и формат («Скачать журнал: Предмет 1, лекция, xlsx»).

## 7. Заметки на будущее

**Адаптив.** На 1920 журнал предмета за семестр уже не помещается по ширине — горизонтальный скролл при фиксированном столбце ФИО работает **уже сейчас**, а не с 1440. Критично не потерять при сужении: фиксированный первый столбец; **четыре** колонки метрик (их тянет схлопнуть в две, но владелец нарисовал четыре); подпись типа занятия в шапке при мульти-выборе; текстовые расшифровки статусов. В мобильной версии журнал почти наверняка станет «студент → его отметки» с выбором студента, то есть **другим экраном**, — но PWA отдельная поверхность и отдельный цикл.

**Разграничение с уже разобранным** (для §8 реестра):

| Экран | Зона ответственности |
|---|---|
| 112 Староста — Посещаемость | журнал **своей группы по всем предметам**, с правкой отметок и недельным разрезом |
| **122 Преподаватель — Посещаемость** | журнал **своего предмета по нескольким группам**, только чтение, с метриками по студенту и заявками на «у» |
| 122, режим одной пары | оперативная справка «кто был на этой паре» — вход со среза дня 121 |

**Открытые вопросы и риски**

1. **Метрики: сервер или клиент.** Если агрегаты не придут с журналом, цифры 122 и 123 разойдутся. Считать на клиенте недопустимо для отчёта, уходящего на кафедру.
2. **Тип занятия в назначении** — блокирующее, четвёртый потребитель.
3. **Шаблон отчёта преподавателя в пяти форматах** — новый серверный артефакт, включая **xlsx** (возвращён решением чата 6). Excel требует табличной модели отчёта, а не рендера картинки: png и docx можно собрать из одного макета, xlsx — нет.
4. **Excel записывается везде, где есть выгрузка** — значит, синхронизации требуют уже сданные файлы 112, 113, 116 и описание `ExportButton`. Внесено в §11 реестра.
5. **Отфильтрованное представление тикета** — новый контракт, следствие варианта «б». Фильтрация обязана быть серверной.
6. **Период журнала не выбирается.** На скане нет ни `DatePager`, ни `DateRangePicker` — читаю как «весь семестр до текущей даты», как на 112. Если понадобится диапазон, это `DateRangePicker`, а не листание.
7. **Решено (K5-1).** Слоя два, компонента два: `ExcuseReasonPopover` — краткая причина, `ExcuseTicketPanel` — заявка целиком. Отдельный `Tooltip` под причину не заводится.
8. **Персональные данные особой категории.** Вложения к тикетам на «у» — как правило, медицинские справки. Вариант «б» оставляет их доступными преподавателю: круг лиц, видящих сведения о здоровье студента, расширяется. Технически это одна ссылка, юридически — тема для аудита, наравне с показом пароля на 116.
