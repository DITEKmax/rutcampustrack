# M18 Decisions

Архитектурные и продуктовые решения по milestone.

Формат: `## Dx (YYYY-MM-DD) — короткое название`, затем контекст / решение / последствия.

---

## D1 (2026-05-02) — Доступ только старосте

**Контекст:** отчет отражает журнал группы и предназначен для старосты.

**Решение:** UI и API доступны только старосте своей группы. `groupId` не передается клиентом, а берется из `RequestContext`.

**Последствия:** меньше риск IDOR. Обычный студент, преподаватель и админ получают `403` при прямом запросе.

---

## D2 (2026-05-02) — Web entrypoint остается на weekly-journal

**Контекст:** староста уже работает с недельным журналом на `headman/weekly-journal`.

**Решение:** не создаем отдельную страницу. На текущей странице добавляем две кнопки: текущая неделя и несколько недель через модалку.

**Последствия:** меньше навигации, меньше новых экранов, сценарий остается рядом с данными журнала.

---

## D3 (2026-05-02) — PWA получает аналогичный блок в группе

**Контекст:** старосты могут работать с мобильного телефона.

**Решение:** в PWA на странице `Группа` добавляется отдельный блок с тем же выбором недель и форматов.

**Последствия:** функционал есть в обоих интерфейсах, но без отдельной страницы и без предпросмотра.

---

## D4 (2026-05-02) — Три формата экспорта

**Контекст:** пользователю нужны `docx`, `pdf`, `png`.

**Решение:** backend поддерживает все три формата сразу.

**Последствия:** DOCX является первичным артефактом. PDF и PNG генерируются из DOCX, чтобы визуальная форма совпадала с шаблоном.

---

## D5 (2026-05-02) — Multi-week export: один файл для DOCX/PDF, ZIP для PNG

**Контекст:** староста может выбрать несколько недель, включая недели не подряд.

**Решение:** для `docx` и `pdf` возвращается один многостраничный файл. Для `png` возвращается ZIP с отдельным PNG на каждую выбранную неделю.

**Последствия:** DOCX/PDF удобно печатать одним документом. PNG остается набором отдельных изображений, потому что многостраничного PNG не существует как практичного пользовательского формата.

---

## D6 (2026-05-02) — Непоследовательный выбор недель помечается в имени файла

**Контекст:** диапазон дат в имени файла может выглядеть как непрерывный, хотя пользователь выбрал недели с пропусками.

**Решение:** если выбранные недели не образуют непрерывную последовательность, добавляем `_С_ПРОПУСКАМИ` в имя файла.

**Последствия:** имя файла честно показывает, что внутри не весь диапазон.

---

## D7 (2026-05-02) — Лимиты шаблона дают 422

**Контекст:** текущий шаблон рассчитан на 35 студентов и 5 пар в день.

**Решение:** если данных больше лимита, не обрезаем и не пытаемся расширять шаблон. Возвращаем `422` с понятным сообщением.

**Последствия:** нет тихой потери данных. Расширенный шаблон можно сделать отдельной задачей, если такой кейс появится.

---

## D8 (2026-05-02) — PDF/PNG через отдельный gRPC renderer-service

**Контекст:** конвертация DOCX в PDF/PNG требует LibreOffice/headless или аналогичного системного рендера.

**Решение:** предпочтительный вариант — отдельный внутренний `document-renderer-service` как gRPC-only сервис. `attendance-service` генерирует DOCX и вызывает renderer только для PDF/PNG.

**Соответствие `CLAUDE.md`:** отдельный сервис не публикует собственный REST API, поэтому не нужен `*-api-contract`. Контракт живет в `proto/document_renderer.proto`, а межсервисный вызов идет через gRPC. Если когда-нибудь renderer получит REST API, понадобится `document-renderer-api-contract` + controller interfaces.

**Альтернатива:** встроить LibreOffice прямо в контейнер `attendance-service`.

**Почему не альтернатива:** системный рендер тяжелый, увеличивает образ основного сервиса и добавляет нестабильность в критичный attendance-service.

**Последствия:** появляется дополнительный внутренний сервис и сетевой вызов, зато конвертация изолирована и проще масштабируется/отлаживается.

## D9 (2026-05-02) — Нижние поля шаблона не заполняются

**Контекст:** поля старосты и подписи пользователь хочет заполнять вручную.

**Решение:** backend не подставляет ФИО старосты и не меняет подпись.

**Последствия:** academic-service не нужен для поиска ФИО старосты в M18.

---

## D10 (2026-05-02) — Нумерация учебных недель от недели старта семестра

**Контекст:** UI выбора нескольких недель должен показывать стабильный номер учебной недели и диапазон дат.

**Решение:** неделя 1 — это неделя `понедельник-воскресенье`, в которую попадает `date_from` активного семестра. Дальше недели считаются подряд по понедельникам до недели, в которую попадает `date_to` активного семестра включительно.

**Последствия:** список недель может начинаться до `date_from` и заканчиваться после `date_to`, если семестр начинается или заканчивается в середине недели. Экспорт валидирует `weekStart` только по этому списку и возвращает `422`, если неделя вне активного семестра.

---

## D11 (2026-05-02) — Текущий шаблон заполняет дни понедельник-суббота

**Контекст:** M17-шаблон `headman-weekly.docx` содержит placeholders для `mon..sat`, но не содержит колонку/секцию воскресенья.

**Решение:** модель отчета M18 хранит 6 шаблонных дней (`Mon-Sat`). Диапазон учебной недели и имя файла остаются `понедельник-воскресенье` по D10, но если schedule-service вернет непустые неотмененные занятия на воскресенье, backend возвращает `422`, чтобы не потерять данные молча.

**Последствия:** обычные пустые воскресенья не мешают экспорту. Для поддержки воскресных занятий нужен отдельный шаблон или расширение текущего DOCX.
