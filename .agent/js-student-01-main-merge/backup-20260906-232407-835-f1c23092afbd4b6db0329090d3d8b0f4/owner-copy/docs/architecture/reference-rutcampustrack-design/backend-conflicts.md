## 2. Решения — формулировки для §5

### Р-1. Видимость пароля

Пароль выдаётся при первой регистрации и при сбросе (старостой — своей группе,
администратором — любому). Значение **скрыто под звёздочками у всех, раскрытия
не существует**; единственный доступ — **копирование из ячейки**. Правило единое
для 116 и 132. Значение **не попадает в выгрузку ни в одном формате**.
После смены пароля студентом копирование снимается, остаётся только состояние.
**Факт копирования пишется в аудит** (кто, чей пароль, когда).

Цель правила — исключить фотографирование экрана. Она достигается полностью.
Знать при этом стоит: чтобы строку можно было скопировать, значение приходит
в браузер и доступно в инструментах разработчика. Если понадобится защита
и от намеренного извлечения, копирование выносится в отдельную серверную операцию —
аудит под неё уже заведён.

### Р-2. Прошения о замене «н» и лимит попыток

Разведены **два механизма**, которые в предыдущих файлах смешивались:

1. **Автоматический запрос старосте** — порождается системой в момент неудачной
   геоотметки во время пары. Отдельного действия студента нет. **Лимитом не ограничен.**
   Не истекает: староста может подтвердить присутствие и через несколько дней.
2. **Прошение о замене «н» на «+» по прошедшей паре** — ручное действие студента.
   **Ограничено пятью парами за семестр.** Попытка расходуется **в момент подачи**.
   Подаётся по одной паре.

**Отклонение прошения пару не закрывает** — подать по ней заново можно, но повторная
подача расходует ещё одну попытку. Механизм ограничивает себя сам: пять отказов —
и попытки кончились. Дальше только через старосту.

**Староста может увеличить лимит студенту на N** — в строке студента на 116;
операция пишется в аудит. Остаток попыток показывается студенту **до** подачи,
а не сообщением об отказе после.

**Тикеты на «у» лимитом не ограничены.** **Решение по тикету необратимо:**
«Изменить решение» не проектируется, староста перепроставляет отметки вручную.

### Р-3. Выгрузки

Перечень форматов: **excel · docx · pdf · png · html**. Таблицы выгружаются во все пять,
включая png — это большое изображение, собранное из html-макета. **График выгружается
только как png и html**; html-версия интерактивна (наведение показывает значения,
разрезы по неделям и другим осям).

Генерация вынесена в **отдельный сервис и выполняется асинхронно**: файл отдаётся
по готовности. Шаблоны предоставляются позже; вероятная схема — один html-макет
как источник остальных форматов. Точная привязка форматов к разрезам решается
на этапе рендера и шаблонов, не сейчас.

### Р-4. Число метрик

Сервер всегда отдаёт **четыре метрики и четыре количества**. Экран показывает нужное
подмножество; «две величины рядом» — правило отображения карточек и графиков,
а не состав контракта. Количества обязательны всегда. Отменена только сумма `%у+н`;
`%у` и `%н` по отдельности входят в обязательный состав.

### Р-5. Аудитории этажа

Справочника аудиторий нет и на этом этапе не будет; в будущем возможен.
Текстовой альтернативы к схеме не добавляем — оговаривать, что карта только
для просмотра, не нужно.

**Следствие принимается сознательно:** схема этажа на 105 остаётся изображением
без текстового содержания. Записывается в файл требований A11Y как известное
и датированное ограничение. MAP-07 остаётся отложенным.

### Р-6. Модель роли

Роль — массив, у каждой роли свой статус. Схема хранения может быть пересобрана
под эту модель.

- **Активная роль живёт на сервере**, в сессии, приходит в контексте сессии;
  переключение — серверная операция. Выбор переживает перезагрузку и одинаков
  во всех вкладках.
- **Роль по умолчанию — student**, если она есть; иначе teacher. Admin по умолчанию
  не выбирается никогда.
- **Роли в терминальных статусах** (`expelled`, `graduated`, `archived`) остаются
  переключаемыми и показывают данные **только для чтения**.
- `RoleSwitcher` рендерится всегда, включая случай одной роли.

### Р-7. Отменённая пара

Отмена возможна и задним числом. Отметки **помечаются недействительными, а не удаляются**;
колонка пары остаётся в журнале с отдельным состоянием «пара отменена» и причиной;
пара исключена из знаменателя всех метрик; привязанное дз уходит в архив;
восстановление возвращает **пустую** сетку.

### Р-8. Ссылка в задании

Одно поле под одну основную ссылку. Сервер значение **не нормализует и формат
не валидирует**. Правило фронта: значение показывается как введено и всегда
открывается как внешний адрес; строка без схемы не достраивается и относительной
ссылкой не считается.

### Р-9. Файлы заявки

Файлы хранятся на нашей стороне **год с момента загрузки**, независимо от судьбы
тикета и статуса студента. Вместе с тикетом файл не удаляется.
После истечения срока карточка тикета показывает состояние **«вложение удалено
по сроку хранения»**, а не битую ссылку и не пустоту.
JS-STUDENT-WEB-07 («через бота без хранения») снимается из `job-stories.md`.

### Р-10. QR

Один механизм выпуска кода с параметром назначения, как у OTP. Правила авторизации
для входа гостя и для привязки устройства раздельные. Окончательное слово —
за security-аудитом.

### Р-11. blockage / geo-block

Один механизм — **`blockage`**. `geo-block` выводится из обихода: операция остаётся
на бэкенде, фронтом не вызывается. Один признак в представлении пары, один переключатель.

Смысл механизма шире геоотметки: блокировка запрещает студенту **любое взаимодействие
с парой**. При заблокированной паре доступен **только тикет на «у»**; ни геоотметка,
ни прошение о замене «н» невозможны.

### Р-12. Логин

Предполагаемый логин в форме создания не показывается: значение появляется только
в ответе на сохранение.

### Р-13. Классификация пунктов

Формальность: два одинаковых требования были помечены в разных чатах разными типами,
что давало им разный приоритет при одинаковом содержании. Оба сведены
к `[предложение по бэкенду]` (AC-23, AC-24).

### Р-14. Согласующий в тикетах

Решение принимает только староста (и помощник с правом `manage_excuses`).
Преподаватель тикет **читает** в урезанном сервером представлении (AT-39).
Администратор в согласовании не участвует.

### Р-15. Границы данных и каталог дисциплин

Каждая роль видит только относящееся к ней: староста — свою группу и свои предметы,
преподаватель — предметы, к которым его привязали. Всё видит только администратор.
Связи везде по `id`/`uuid`; текстовое сопоставление не используется нигде.

**Общего каталога дисциплин не будет.** Староста заводит предметы своей группы
вручную и сам следит за их составом. Подсказка названий из общего пула (AC-06)
снимается: наполнить её нечем, не нарушая границ данных.

**Следствие для 123:** «Предмет 1» в разных группах — разные записи. Преподаватель
в разрезе «по моим группам» не может выбрать один предмет и увидеть его сразу
по всем группам; предмет выбирается внутри каждой группы отдельно. AC-05
(кросс-групповая идентичность предмета) снимается.

### Р-16. Фильтр и сортировка у колонки

Правило: **у каждой колонки есть фильтр и сортировка**. Структура описания — §3.1
`table-filters.md`; описание приходит с бэкенда, фронт колонки и перечни значений
не зашивает.

**Три исключения, подтверждённые явно:**

1. **Состав группы на 116** — ни фильтров, ни сортировки; порядок алфавитный.
2. **Список семестров на 134** — фильтр по статусу есть, сортировки по колонкам нет.
3. **Колонка «Почему черновик» на 133** — без фильтра: внутри разреза причина одна.

### Р-17. Отбор, порядок, сброс

- **Всё на сервере. Везде.** Фильтрация, сортировка и пагинация — серверные,
  включая наборы, приходящие целиком (123, 134). Клиентского режима в продукте нет.
  Списки отдаются с HATEOAS и постраничностью там, где она нужна.
- **Мультисортировка без предела:** ключей столько, сколько колонок включил
  пользователь; порядок применения — **в порядке включения**; **приоритет ключа
  показывается в заголовке колонки**.
- **Кнопка «Сбросить»** появляется, как только активен хотя бы один фильтр
  или хотя бы одна сортировка, и сбрасывает **всё сразу** — и фильтры, и сортировки.
- Инварианты списочной операции, следующие из «всё на сервере»: порядок применения
  **фильтр → сортировка → страница**; `total` и счётчик результата считаются
  **по отфильтрованному набору**; последним ключом сортировки всегда идёт
  **уникальный разрешитель**, иначе строки дублируются и пропадают между страницами.

### Р-18. Справочники

Фиксированные перечни (типы причин, типы занятий, права, форматы выгрузки, состояния)
выносятся в **одно место и переиспользуются**, а не описываются вручную в каждой
операции. Малые перечни приходят внутри описания колонки, большие — отдельной
операцией с поиском по подстроке и постраничностью. Перечень **никогда** не собирается
из загруженной страницы: при пагинации это молча скроет варианты.

### Р-19. Колонка «Пароль»

Единый перечень из четырёх значений:
`initial` · `headman_reset` · `admin_reset` · `changed`.
`headman_reset` и `admin_reset` сосуществуют: сбрасывать могут обе роли, староста —
только своей группе. Состояние `changed` означает, что копирование недоступно.
Состояние показывает, **по чьей инициативе** пароль последний раз менялся.

### Р-20. Фильтрация по вычисляемым значениям

Агрегаты хранятся **материализованно**: инкремент обновляет хранимую строку,
а не пересчитывает её при чтении. Фильтрация, сортировка и пагинация по этим полям —
серверные, по индексам хранимых значений. Согласуется с Р-17: клиентского отбора
по агрегатам нет нигде.

### Р-21. Многозначные ячейки

**Совпадение по любому значению:** строка попадает в результат, если совпало хотя бы
одно значение ячейки. Человек с ролями student и teacher попадает в выборку
по каждой из них. Других вариантов семантики нет.

**Фильтр по статусу недоступен, пока не выбрана роль** — статус принадлежит роли,
и отбор по нему без роли двусмыслен. Недоступный фильтр показывается неактивным
с текстовой причиной, а не скрывается.

### Р-22. Черновики групп

**Статус «черновик» сохраняется.** Порядок создания: сначала заводится группа,
затем в неё добавляются студенты, затем из них назначается староста.
До назначения группа лежит в черновиках.

Старосту **нельзя снять явно** — можно только заменить другим студентом группы.
В черновики группа возвращается, когда староста **выбыл сам**: отчислен, переведён,
выпущен. Перевод выполняется сервером, а не действием администратора.

Причин черновика **две**: «группа только создана» и «староста выбыл» с указанием
основания. Текст приходит с сервера, колонка фильтра не получает (Р-16).
AC-16 остаётся в силе целиком: `draft` — значение статуса, параметр разреза
и счётчик вкладки на 133.

### Р-23. Фильтры в выгрузке и в адресе

Выбранные в таблице фильтры **уходят в файл выгрузки**: выгружается то, что видно
на экране, с теми же фильтрами и в том же порядке.

Фильтры **пишутся в адрес страницы**, чтобы перезагрузка и кнопка «Назад»
не сбрасывали отбор. Структура значений одна и та же в запросе, в адресе
и в параметрах выгрузки. Невалидные значения в адресе сбрасываются к умолчанию
с пояснением.

**Правило доступа, действующее независимо от адреса:** по ссылке показывается только
то, что относится к текущему пользователю; чужие данные не открываются никогда —
сервер отвечает 404, а не отфильтрованным чужим набором. Передача ссылки другому
человеку смысла не имеет и сценарием не является.

### Р-24. Поиск и фильтры вместе

Полнотекстовый поиск идёт **по всем столбцам, включая подстроки**. Поиск и фильтры
колонок работают одновременно и **складываются через И**: поиск сужает набор,
фильтры колонок сужают найденное.

Прежнее правило `table-filters.md` (§1, п. 4) — «поле, покрытое поиском, фильтра
в своей колонке не получает» — **отменяется**. Разделение по назначению: поиск
находит запись, фильтр сужает набор.

### Р-25. Перенос пары — одна операция

🆕 **Решено 12.08.2026.** Закрывает SC-01, блокировавший 114, 117, 118
и отображение на 102 и 121.

**Было:** операции переноса в API нет. Обходной путь — отменить пару и создать
разовую — непригоден дважды: отмена **стирает отметки** и отправляет привязанное
дз в архив, а две операции без транзакции рвут расписание при обрыве связи.

**Стало:** одна операция `POST /schedule/lessons/{id}/transfer` с новыми датой,
временем и аудиторией. **Всё внутри одной транзакции:**

- старая пара получает статус «перенесена» и ссылку на новую (по идентификатору);
- новая пара создаётся с тем же назначением (Р-26), то есть тем же предметом,
  типом занятия, группой и преподавателем;
- привязанное дз **переезжает по идентификатору пары** и остаётся актуальным;
- в ответе возвращаются **обе пары**, чтобы фронт не ходил повторно.

**Переносить можно только будущую пару.** У будущей отметок нет — значит вопроса
«куда девать отметки» не существует; прошедшую переносить бессмысленно, она уже
состоялась. Это упрощение снимает половину сложности операции и записано
ограничением, а не умолчанием.

Обе пары остаются в истории: старая не удаляется, а помечается. Отчёты и агрегаты
считают по фактическому состоянию, отменённые и перенесённые учитываются
правилами знаменателя (AT-18).

### Р-26. Назначение как отдельная сущность

🆕 **Решено 12.08.2026.** Закрывает AC-07, блокировавший роль teacher целиком
и экраны 116.1, 117, 121, 122, 123.

**Было:** преподаватель привязан к предмету целиком — «Иванов ↔ Матанализ».
Тип занятия в связи не участвует. Следствие: «мои пары» отобрать не из чего,
строки «Матанализ · лекция» и «Матанализ · практика» неразличимы, «типа нет»
не отличается от «тип есть, но веду не я».

**Стало: назначение — самостоятельная сущность со своим идентификатором.**
Состав: группа × предмет × тип занятия × семестр × преподаватель.

```
ИТ-201 · Матанализ · лекция       · осень 2026 · Иванов
ИТ-201 · Матанализ · практика     · осень 2026 · Петрова
ИТ-201 · Матанализ · лабораторная · осень 2026 · Сидоров
ИТ-201 · Матанализ · лабораторная · осень 2026 · Кузнецов
```

**Преподавателей на один тип занятия может быть сколько угодно** — двое, трое
и больше; ограничения сверху нет. Отдельной механики для этого нет: каждый преподаватель — своя строка
назначения. Прежняя связь «предмет ↔ преподаватель» уходит: она становится
частным случаем назначения.

**Связь только по идентификаторам.** Пара расписания ссылается на назначение
по его идентификатору, а не на кортеж «предмет + тип + группа». Правило проекта
действует и здесь: **идентификатор — это uuid или инкрементный ключ, никогда
не текст и никогда не комбинация полей.** Названия предмета, группы и типа
занятия — отображаемые данные, не ключи.

**Смена преподавателя не переписывает прошлое.** Назначение не редактируется
на живую и не удаляется: у него есть период действия. При смене прежнее
закрывается датой окончания, новое заводится с датой начала. Пары ссылаются
на конкретное назначение по идентификатору, поэтому пара, проведённая при
прежнем преподавателе, **навсегда сохраняет, кто её вёл**. Журналы, статистика
и выгрузки прошлых периодов от смены не меняются.

**В расписании преподавателя группа пишется всегда** — это следует из состава
назначения и требования SC-03: поля разреза по преподавателю включают
идентификатор группы и её название.

**Обогащение `GET /academic/assignments/my`** (AC-21): возвращаются не голые
идентификаторы, а названия группы и предмета вместе с типом занятия,
отфильтрованные **по активному семестру на сервере**. Иначе экран покажет
прошлогодние назначения как текущие — переключателя семестра на макетах нет.

### Р-27. Расписание преподавателя за диапазон

🆕 **Решено 15.08.2026.** Найдено при сборке `block/TeacherDay` (экран 121).

**Было:** запроса «мои пары» у преподавателя нет. Обход — по одному
`GET /schedule/groups/{groupId}/lessons` на каждую свою группу. Р-26 сделал
такой обход технически возможным: пары ссылаются на назначение, а назначение
знает преподавателя. Но веер запросов он не убрал — восемь групп означают
восемь запросов, частичные ошибки и невозможность показать срез дня **одним
объяснённым состоянием**, как требует спека 121 §5.

**Стало: один запрос «мои пары за диапазон».** Границы диапазона — параметры;
отбор по назначениям активного преподавателя выполняет сервер. Не «за день»:
на 121 срез дневной, но листалка ходит по дням, а 122 работает семестром —
диапазон закрывает оба случая одним контрактом.

**Состав пары в ответе** следует из Р-26 и SC-03: идентификатор назначения,
группа (идентификатор и название), предмет, тип занятия, время, аудитория,
и признаки состояния пары — разовая, перенесена, отменена (Р-25). Признаки
отображаются текстом, не иконками.

**Активный семестр фильтрует на сервере**, тем же основанием, что обогащение
`assignments/my` в Р-26: переключателя семестра на макетах нет.

### Р-28. Метрики посещаемости — один серверный расчёт

🆕 **Решено 15.08.2026.** Найдено при сборке блоков 122 и 123.

**Было:** одни и те же четыре метрики берутся из разных мест. На 122 они
приходят вместе с журнальной сеткой; на 123 нужен собственный источник,
которого не существует. Разные наборы данных дают расхождение цифр —
и расходятся они именно в отчёте, уходящем на кафедру.

**Стало: считает сервер, одним расчётом.** 122 отдаёт метрики вместе с сеткой.
123 запрашивает агрегат в двух разрезах — по студентам внутри назначения
и по группам преподавателя. Клиентский расчёт исключён на обоих экранах;
это частный случай уже действующего правила «клиентский отбор отменён везде».

**«Учтено пар» приходит тем же ответом, что таблица разреза.** Отдельного
запроса ради одного числа не заводится: шапка отчёта принадлежит отчёту.

**Что этим не закрывается.** Кросс-групповая идентичность предмета: предмет
принадлежит группе (Р-15), сравнивать группы «по одному предмету» не по чему.
Отбор по предмету в разрезе по группам остаётся недоступным с текстовой
причиной — решение не переоткрывается.

### Р-29. Активность системы — один агрегат с периодом

🆕 **Решено 15.08.2026.** Найдено при сборке `block/SystemActivity` (экран 131).

**Было:** пять показателей блока активности — отметки «+», доля успешных
геоотметок, просмотры карты, заявки и тикеты, домашние задания — принадлежат
разным подсистемам, и запроса, который отдаёт их вместе, не существует.
Собирать их пятью запросами значит получить пять независимых отказов там,
где спека 131 требует **одного состояния на блок**.

**Стало: один агрегат с параметром `period = today | all_time`.** Сервер
собирает показатели из своих подсистем и отдаёт одним ответом с одним
состоянием.

**База сравнения суточной дельты — то же время вчера, а не полный вчерашний
день.** Иначе каждое утро метрика показывает падение, которого нет: половина
дня сравнивается с целыми сутками.

**При `period=all_time` дельты не существует как величины.** Сервер не отдаёт
ноль и не отдаёт прочерк — поля нет; фронт не рендерит компонент вовсе.

**Просмотры карты — продуктовая телеметрия**, а не производная от имеющихся
данных: под неё нужна подсистема событий. Это единственный показатель блока,
требующий нового сбора, и решение о нём продуктовое, а не только серверное.

### Р-30. Схемы корпусов — одна подсистема

🆕 **Решено 15.08.2026.** Найдено при сборке `FloorPlansRegistry`
и `FloorPlanUpload` (экран 135).

**Было:** у экрана схем нет ни одного описанного эндпоинта — ни реестра,
ни загрузки, ни метрики спроса. Экран существует в макетах, в контрактах его нет.

**Стало: одна подсистема, три операции.**

- **Реестр** — список схем: корпус, этаж, форматы, статусы загрузки каждого
  формата, спрос, дата обновления. Два формата (**PNG и SVG**) — независимые
  статусы у одной записи, а не два разных объекта: на 1280 они и показываются
  одной ячейкой с подписями форматов.
- **Загрузка и замена** — одна операция с двумя ветками. Замена не удаляет
  прошлую схему молча: у записи есть версия, прежняя остаётся доступной,
  иначе ссылки на аудитории в расписании укажут в пустоту.
- **Спрос считает сервер.** Это метрика обращений к схеме, а не поле записи;
  клиент её не выводит и не накапливает.

**Ограничение аудиторий признано ранее (Р-5)** и здесь не переоткрывается:
справочника аудиторий нет, схема — картинка с зонами, а не структура данных.

### Р-31. Одна метрика — один расчёт, с явным параметром

🆕 **Решено 15.08.2026.** Найдено при сборке 131 и 132.

**Было:** «сколько студентов в системе» считается на 131 карточкой масштаба,
а на 132 — как `total` серверной пагинации. Если 131 считает по ролям,
а 132 по учётным записям, два экрана роли admin покажут **разные числа
одного и того же**, и оба будут правы по-своему.

**Стало: количество считает один агрегат с явным параметром**, и оба экрана
берут его оттуда. Расхождение правил подсчёта — не деталь реализации,
а нарушение §6.2 реестра: одна метрика считается в одном месте.

**Практическое следствие для аккаунтов с несколькими ролями:** один человек
может быть и студентом, и преподавателем (Р-6 — роль это массив). Правило
подсчёта обязано сказать, попадает он в оба количества или в одно; молчание
здесь и есть тот самый источник расхождения.

## 3. Механика отметки посещаемости — сведено

Собрано из ответов по Р-2 и Р-11; в таком виде не записано ни в одном файле.
Это состав правил, а не предложение — переносится в спеки 101, 107, 111, 112 как есть.

**Окно отметки.** Геоотметка доступна с **5 минут до начала пары** до **5 минут
после её окончания**. Всё это время ячейки отметок **пусты по умолчанию** — пустота
означает «ещё не решено», а не «нет данных».

**Пути получения «+»:**

1. Студент нажимает «Отметиться», геопроверка успешна → **«+»**.
2. Геопроверка неуспешна → система **автоматически** отправляет старосте запрос
   на ручную отметку (сейчас — сообщение в Telegram с двумя кнопками: подтвердить
   присутствие / отклонить). Подтверждение → **«+»**. Запрос **не истекает**:
   староста может подтвердить и через несколько дней.
3. Староста поставил «н» вручную во время пары, а студент затем успешно отметился
   по гео → **«н» заменяется на «+»**. Если гео при этом не сработала — уходит
   тот же автоматический запрос; подтверждение старосты → **«+»**.
4. Прошение о замене «н» на «+» по **прошедшей** паре, одобренное старостой → **«+»**.
   Ограничено пятью парами за семестр (Р-2).

**Закрытие окна.** После окончания пары и пятиминутного хвоста оставшиеся пустые
ячейки становятся **«н»**; счётчики, агрегаты и журнал обновляются в этот момент.

**«у»** ставится **только по тикету** и никаким другим путём. Одобрение тикета
не заменяет уже проставленный «+» — такие пары исключаются из эффекта (AT-33).

**Приоритет источников.** Успешная геоотметка и подтверждение старосты **перекрывают
ручное «н»**. Тикет на «у» перекрывает любое состояние, кроме «+».
Сервер обязан разрешать эту перезапись — сейчас `PUT /attendance/lessons/{lessonId}/students/{userId}`
описан как присвоение значения без правил приоритета.

**При заблокированной паре** (Р-11) недоступны пути 1–4; остаётся только тикет на «у».

   о готовности. WS-канал (`POST /auth/ws-ticket`) и уведомления — кандидаты;
   события «выгрузка готова» нет ни в NT-01…NT-03, ни в X-01.
2. **Операция увеличения лимита попыток** старостой, с аудитом (AT-11).
3. **Правила приоритета источников отметки** — сейчас операция ручной отметки
   описана как присвоение значения, без указания, что чем перекрывается (§3).

   Затрагивает Р-1 (кому доступно копирование пароля), Р-2 (кто увеличивает лимит),
   Р-14 (кто решает по тикетам).
3. **Форма QR-механизма** (Р-10) — решение по контракту принято, окончательное
   слово за security-аудитом.
4. **Спеки и `COMPONENT_REGISTRY.md` к этой сессии не прикладывались.**
   Адреса правок в §5 и §6 выведены из `backend-requests.md` и `table-filters.md`
   и по самим файлам не сверены.
5. ✅ **Задача 5 закрыта 01.08.2026 — уточнение к формулировке.** Верно, что ни один пункт
   не требует конкретного транспорта: все 24 выразимы и эндпоинтом под экран, и схемой.
   Неверно, что они **равноценны по цене**. Четыре из шести проверенных склоняют к REST:
   Р-17 (динамические дескрипторы колонок выключают типизацию схемы), Р-23 (по HTTP-кэшу,

   в резолверы), Р-20 (снимает лучший аргумент за GraphQL). Р-18 почти нейтрален, Р-9
   опровергает саму рамку «или-или»: при GraphQL REST остаётся в любом случае.
   Ни один из 24 пунктов при этом не тронут. Сводка наклонов — `transport-decision.md` §2.
