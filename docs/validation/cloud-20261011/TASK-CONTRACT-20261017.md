## 4. Required behavior — конкретные доработки

### A01. Единый PasswordEncoder и явные зависимости

**Что устранить:** Academic UserService создаёт собственный BCrypt encoder; в SubjectController найден field injection. Это неоднородность зависимостей, а не доказанная ошибка входа.

- Используй управляемый PasswordEncoder с согласованными параметрами; в разных сервисах допустимы отдельные beans, реализующие тот же контракт. Не пытайся передавать Java bean через границу процессов.
- Адресно переведи найденные зависимости на конструктор. Сохрани существующие request-scope/proxy и ObjectProvider там, где они решают нужный lifecycle.
- Сохрани совместимость уже записанных хешей, создания, административного сброса и пользовательской смены пароля. Массовая перезапись паролей не нужна.

**Приёмка:** затронутая операция использует согласованный encoder; применимая проверка подтверждает создание/проверку хеша и соответствующий lifecycle. Тест существования bean ради покрытия не добавлять.

### A02. Enum в коде, устойчивые текстовые коды в БД

**Конкретный starting point:** `Assignment.lifecycleState` и строковые сравнения `ACTIVE/PREPARED/CLOSED`.

- Если поле ещё строковое, введи доменный enum и согласованно обнови JPA/JDBC, assembler, сравнения и затронутых consumers.
- В БД сохраняй **человекочитаемые устойчивые строки**, не числа и не ordinal. Существующие `ACTIVE`, `PREPARED`, `CLOSED`, `lecture`, `docx` не переименовывать из-за Java-стиля.
- Адресно найди аналогичные **закрытые** состояния/режимы/виды сортировки в затронутых контрактах и убери реально оставшиеся повторяемые строковые литералы. Свободные имена/описания не превращать в enum; опубликованные API-строки допустимы на границе с явным преобразованием.
- Сохрани существующие явные converters и исправленный Locale.ROOT. Числовые protobuf wire codes остаются прежними: это другой договор, не формат хранения БД.
- Для обязательного значения различай unknown/null/отсутствие. Неизвестный код не должен становиться ACTIVE, ролью или разрешением по умолчанию.
- Java String→enum с прежними SQL-строками сам по себе не требует миграции. При реальной несовместимости данных/кэша используй адресный совместимый переход, без переписывания старых SQL и очистки Redis целиком.

**Приёмка:** принятые значения читаются/пишутся с прежним смыслом; JSON/protobuf/PWA/TMA совместимы; значимая неизвестная константа получает предусмотренный отказ. Список действительно изменённых конечных наборов — в коротком handoff.

### A03. Безопасный auth-контракт, логи и CI artifacts

- Убери пароль из `LoginRequest.toString()`, если актуальный record всё ещё выводит его; используй существующий redaction pattern. Соседние DTO меняй только при таком же конкретном раскрытии.
- Сопоставь `JwtService.parseSignedToken` с принятым RS256-профилем Gateway/internal validator. Если фактический parser допускает лишние алгоритмы относительно этого контракта, явно ограничь допустимый профиль API используемой библиотеки. Сохрани issuer/audience/purpose/time/signature checks. Различие реализации не объявляй установленным exploit.
- Проверь **конкретные upload paths** CI: безопасный summary не очищает отдельно публикуемые raw XML/HTML unit reports. Адресно исключи ненужные чувствительные данные/публикацию либо обеспечь безопасный минимальный артефакт без потери полезной диагностики падения.
- Не помещай credentials в message, structured arguments, stack details, MDC, baggage, spans или URL. Одна маска formattedMessage не защищает остальные поля.
- В изменённых error paths возвращай безопасную понятную ошибку и нужный статус. Уже выполненные redaction и валидацию не реализовывать заново.

**Приёмка:** безопасные синтетические маркеры не попадают в затронутую диагностическую выдачу/публикуемый артефакт; разрешённый вход и правильные токены остаются рабочими; профиль отклоняет существенный неверный вход по нужной причине. Реальные пароли/токены/артефакты ради поиска утечки не читать.

### A04. Убрать подтверждённые запросы на каждую строку двух списков

В исходном разборе найдены два конкретных пути:

1. Страница ДЗ вызывает `isCompleted/existsByHomeworkIdAndStudentId` для каждого задания.
2. SubjectAssembler отдельно читает типы занятий/назначения для каждой строки предметов.

Если актуальный путь сохраняет это поведение, получай нужные данные пакетно по IDs текущей страницы. Для ДЗ обязательно сохраняй scope текущего студента; для предметов используй их собственный контракт загрузки.

Не включай EAGER/EntityGraph повсеместно. Если нужен согласованный снимок ответа, установи требуемую гарантию и подходящие границу/изоляцию; одна read-only транзакция с несколькими SELECT не объявляется автоматически единым snapshot.

**Приёмка:** состав, порядок, пагинация и вычисленные поля не меняются, чужие данные не появляются, число дополнительных обращений не растёт по одному на каждую строку. Достаточны адресные проверки ответа и количества обращений; общий benchmark не нужен. Если путь уже пакетный — пакет закрывается существующей реализацией.

### M01. Связанные IDs, сквозная трасса и чистый контекст

Результат: по ID ошибки открытого журнала можно найти работу Gateway → BFF → нужного сервиса, а при фоновом продолжении — связанную задачу/сообщение.

- На Gateway формируй канонический requestId или безопасно нормализуй вход по единому действующему контракту; верни его клиенту, включая ранний application-отказ.
- Стандартный trace context связывает цепочку; каждый этап имеет собственный spanId с правильным parent или link. Request ID, trace ID и бизнес/idempotency ID имеют разные назначения.
- HTTP/gRPC, reactive/servlet, используемые executors и event consumers должны переносить нужную корреляцию и очищать/восстанавливать контекст после success/error/cancel. Собственный ID worker не стирает исходную связь. Отложенная/redelivery работа может иметь отдельную трассу с link и message/operation correlation.
- Используй совместимые framework propagators/observations/configured client builders. Не пиши собственный tracing framework и не копируй весь MDC или Authentication.
- Закрой фактический source-gap BFF: проверь runtime зависимости/config bridge/exporter и service identity; при отсутствии добавь совместимое подключение. compileOnly не считать доказательством runtime tracing.
- Согласуй реальную схему service/environment/version/instance/traceId/spanId/requestId с логами и Grafana. Неверный диагностический header не даёт прав и не должен сам ломать полезное действие.

**Приёмка:** один текущий безопасный синхронный путь и одно реально используемое background/event-продолжение показывают правильные связи; два независимых обращения/повтор worker не смешивают контекст. TLS/parser ошибки до application имеют отдельный ingress/access источник.

### M02. Полный сбор метрик и правильный смысл результата

Составь один небольшой inventory **фактически развёрнутых** компонентов и требуемых сигналов; используй его для реализации и приёмки.

- Закрой актуальный пробел production scrape/exposure Gateway; включи нужный renderer и остальные реальные приложения/экземпляры. Prometheus должен читать защищённые нужные endpoints, а не весь actuator.
- Покрой host/container/JVM/GC/threads/pools/queues, ingress, PostgreSQL/MongoDB/Redis/RabbitMQ и действующие workers/bot/renderer. Переиспользуй exporters; добавь недостающий совместимый binder/exporter с минимальными правами.
- Различай host RAM/container limit/Java heap/native renderer; Hikari и server-side DB signals; Redis временные tickets/лимиты и PostgreSQL authority сессий.
- Business metrics должны отражать login/OTP и существенные принятые операции, возраст/готовность заданий/очередей, окончательный success/failure и last success там, где он нужен. Для пути отчётов/событий нужны фактические ready/unacked, DLQ depth/age, retry/redrive и terminal outcome; IDs сообщений/задач остаются в logs/traces.
- Уточни `outbox published` и другие затронутые counters: attempt, broker confirmation и commit — разные факты. Meter, обещающий committed outcome, не должен считать откатившуюся запись успешной.
- Labels имеют конечный смысловой набор. User/request/trace/job UUID, raw URL и произвольная exception message не становятся metric labels.
- Rate/count/ratio/histogram/units должны соответствовать названию. Выбери sampling и resource budgets для telemetry; доступность не считать по sampled traces.

**Приёмка:** каждый обязательный компонент виден с правильной identity; известная операция даёт ожидаемый существенный сигнал; отсутствующие targets/series различимы с нулём трафика; labels и расход ресурсов ограничены. Не добавляй прибор только ради галочки.

### M03. Правдивые панели Grafana и переходы logs ↔ traces

Сохрани существующие datasource UIDs и Git provisioning.

- Исправь актуальные конкретные ошибки: disk `min`, скрывающий самый полный диск; process CPU с подписью host CPU; Remaining memory с формулой занятой памяти; count/rate подписи; неположительный max и смешение перегруженных/свободных реплик.
- Каждая оставленная панель имеет работающую метрику, правильные selectors/units/title и понятную область environment/service/instance. No-data, stale и query error не показывать здоровым нулём.
- Верхний обзор показывает полезные функции, трафик/ошибки/скорость, затем ведёт к конкретному ресурсу/зависимости.
- Доведи оба перехода logs ↔ traces по реальным JSON traceId/service полям, включая недостающий Loki derived field, если он всё ещё отсутствует. Обеспечь поиск по requestId без новых неограниченных labels.
- Принятые изменения панелей/источников сохраняй в существующих versioned files; UI-save не считать записью в Git.

**Приёмка:** панели дают правдивый ответ на известных безопасных данных; по текущей ошибке/ID доступны связанные logs и trace в нужном окне. Ненужные demo panels не оставлять в качестве «полноты».

### M04. Доступность, DLQ, восстановление отчёта и оповещения

- Раздели живость процесса, готовность обслуживать свою функцию и успешную полезную операцию. Зависимости readiness выбирай по роли сервиса; общий downstream outage не должен вызывать бессмысленный каскад liveness restart.
- Обнаруживай пропавшие ожидаемые jobs/instances и потерю host независимым сигналом. Same-host blackbox не доказывает обнаружение гибели всей машины; HTML200 не доказывает работающий журнал.
- Сверь фактические producers/labels правил. Устрани актуальные мёртвые ссылки/runbooks и правило `health_status`, если реального источника нет; не выдумывай metric name.
- Согласуй панели/alerts/recording rules: абсолютные errors/sec и error ratio различаются; p95 агрегируется из buckets. Различай no traffic, missing target, query error и реальный отказ.
- Определи eligible/good/error/slow и окна для важных функций по принятым требованиям. Числовые SLO/нагрузку/пороги, которых нет, предложи владельцу как недостающее решение; не выдавай учебные500ms/99.5% за норматив.
- Проверь grouping/dedup/inhibition/quiet hours/labels, owner/impact/action/runbook и firing/resolved до контролируемого тестового receiver. Реального alert-бота владелец подключит локально позже; подготовь безопасные URL/auth/secret-reference настройки и короткий порядок подключения без реального token/chat. Не путай отложенный alert-бот с существующим бизнес-consumer notification-bot.
- Наблюдай сам pipeline: scrape/evaluation/ingest/drop/queues/freshness/storage/notification failures существующих Prometheus/Grafana/Loki/Tempo/агента.

#### Обязательный сценарий: WORD посещаемости за 18 недель

Владелец сообщил: запросил WORD-отчёт по посещаемости за 18 недель в конце семестра; после сбоя система восстановилась, ответ не пришёл; повторный запрос снова вызвал сбой. Не установлено, падал ли broker, consumer, renderer или другой слой.

- Установи точку входа и проследи реальную цепочку: данные → job/outbox/event → broker/consumer → renderer → готовность/получение результата. Не делай вывод «слишком большое RabbitMQ-сообщение» только по периоду отчёта.
- На реалистичных синтетических данных добейся корректного DOCX за 18 недель: файл открывается, данные/итоги начала и конца периода не теряются. Нормальный семестровый отчёт не запрещать и не сокращать ради PASS. Проверь также безопасное отклонение действительно недопустимого входа и работу следующей обычной задачи.
- Для **временных** сбоев реализуй/подтверди выбранное владельцем **автоматическое ограниченное восстановление обработки** с backoff, явными retry/redrive бюджетами и ограниченной конкуренцией. Исходная задача после восстановления должна получить реальный результат или предусмотренный явный terminal status, не остаться потерянным ожиданием. Успех новой задачи не доказывает восстановление старой.
- Для устойчиво неверного payload/неисправимого состояния — сохранённое изолированное сообщение, понятная причина и алёрт для разбора. Не делать hot requeue/бесконечный DLQ→main цикл; после исчерпания политики не удалять сообщение молча.
- Проверь на настоящем выделенном брокере DLX/bindings/permissions/queue policies, ack/nack и publisher confirm/return, временный отказ, попадание в DLQ и разрешённый автоматический redrive после устранения причины. Сохраняй message/business IDs и idempotency: повтор доставки не создаёт повторный бизнес-эффект.
- Ограничения HTTP/сообщения/пакета, prefetch, timeouts, memory/disk/backpressure разбирать по фактической причине. Поднятие max size или RAM без устранения причины не является результатом. Сообщение, отвергнутое до принятия брокером, не обязано попасть в DLQ: publisher/job/outbox должен обработать этот отказ корректно.
- Сверь реальную версию и типы очередей с официальной документацией; локально найден RabbitMQ3.13. Не обещай zero loss по одному наличию DLX и не удаляй живые очереди ради redeclare. Starting points: `docs/operations/runbooks/dlq-triage.md`, shared-events/shared-outbox и фактический report/consumer/renderer путь. [RabbitMQ3.13: DLX](https://www.rabbitmq.com/docs/3.13/dlx), [ack/confirms](https://www.rabbitmq.com/docs/3.13/confirms).

**Приёмка M04:** изменённые формулы проверены компактными fixtures; firing/resolved доходит до тестового receiver. Подтверждены нормальный 18-недельный отчёт, временный отказ с автоматическим возобновлением, изоляция устойчиво ошибочного сообщения и продолжение обычных задач после тяжёлого/недопустимого запроса. По возможности тем же сценарием подтвердить trace/log/metrics вместо отдельных повторных кампаний.

**DEFERRED_LOCAL:** подключение и реальная доставка алёртов будущему боту выполняются с владельцем локально; это не blocker Cloud DONE и не заявляется проверенным. Независимый probe/другие обязательные недоступные ресурсы сохраняют собственный статус blocker. Бизнес-обработка и DLQ/recovery не откладываются вместе с alert-ботом.

### M05. Безопасная и воспроизводимая эксплуатация мониторинга

- Защити Grafana и отдельно raw storage/query/receiver/exporter APIs. Разрешённый scrape не открывает admin mutations/подробности. Сохрани минимальные machine/operator права и доверенные ingress/proxy/origin границы.
- Исправь реальное `unknown-service` у BFF, если фактический override его не устраняет.
- Для существующего сборщика реши сохранность positions при recreate: persistent checkpoint либо явно принятая стратегия перечитывания. Сохранённый volume Loki сам по себе этот вопрос не решает.
- Установи действительные retention/rotation/disk/inodes/headroom, storage и resource limits; очереди/attributes/spans/series ограничены. Telemetry outage не блокирует сохранение пользовательских данных.
- Сохрани одну конфигурационную правду: panels/datasources/rules/volumes воспроизводимы; восстановление после разрешённого адресного restart/recreate проверяется на выделенном стенде, без потери чужих данных.
- Обнови **одну существующую** актуальную карту stores/owners/auth и необходимые runbook links: PG auth_sessions, shared users Auth/Academic, durable preferences, реальные service calls/credentials. Не создавай серию новых архитектурных отчётов.

**Приёмка:** доступ ограничен по назначению, состояние/настройки переживают предусмотренное обновление, сведения о service identity и данных соответствуют коду; capacity/freshness проблемы наблюдаемы. Actual production deploy и rotation keys не входят.

### C01–C03. Условные вопросы, не отдельная кампания исследования

Активируй строку только при конкретном оставшемся пробеле актуального кода/конфигурации или существенной гарантии изменяемой операции. Если достаточный механизм/доказательство уже есть — «существует, изменений не требуется» и двигайся дальше.

| ID | Ограниченная точка | Когда и что сделать |
| --- | --- | --- |
| C01 | GroupService cache eviction рядом с не transactionAware manager; важный ticket miss; реально затронутый cache payload | При установленном неверном commit/invalidation/rollback окне исправить адресно с существующим afterCommit-подходом. При небезопасном miss изменить конкретный fallback. DTO snapshot/сужение serializer types — только при конкретной проблеме. Глобальный transactionAware/перенос всех Entity/новая Redis архитектура не назначены. |
| C02 | Защита опубликованной истории Flyway | Если нужный invariant неизменности имён/SQL не обеспечен, добавь один узкий guard по доверенной опубликованной revision с принятой CRLF/LF политикой. Существующие fresh/upgrade tests сохраняются; старые SQL не переписывать и repair/удаление volume не использовать как исправление. |
| C03 | Shared users Auth/Academic и права runtime БД | Уточни владельцев общих полей/операций в существующей карте. Все девять пакетов и активированные C-строки исполняются один раз как связанные результаты. Новые соседние дефекты можно исправлять, если они мешают этому результату; новое существенное продуктовое решение требует вопроса, а не самостоятельного расширения проекта.

## 5. Constraints — сохранить принятый продукт

- **Vue остаётся интерфейсом.** Thymeleaf, отдельный чистый HTML-клиент, GraphQL, новая ORM/IdP архитектура и замена REST/gRPC не входят. Совместимые средства мониторинга можно дополнять; Collector/HA/K8s не обязательны по названию «production».
- Рабочие ownAuth, PostgreSQL session authority, live admission, grants/object policy сохраняются. PWA password/OTP persistence — 7 дней без нового RememberMe checkbox; native TMA вход не ломать.
- **Начальный и выданный после сброса администратором пароль видны в согласованном административном сценарии/карточке/credentials-выгрузке.** Сохрани права и lifecycle до пользовательской смены. Это не выдача изменённого пользователем пароля и не разрешение помещать секрет в общий профиль/отчёт/log/trace/CI artifact.
- Refresh в TokenResponse JSON имеет TMA compatibility. Не запрещай его механически и не удаляй все Set-Cookie. Issue/refresh/clear/flags/path/host должны оставаться согласованными.
- Same-site не равно same-origin. Сохрани принятый CSRF/CORS-контракт; пересматривать его следует для конкретного изменения условий/доказанного пробела, согласованно на server+client.
- Локальная Spring transaction не отменяет автоматически удалённый commit. Для затронутой записи учти proxy/propagation/checked exceptions/flush/afterCommit; межсервисное восстановление — идемпотентность/outbox/retry/compensation по реальному предметному контракту. Не обещай атомарность всей сети одной аннотацией.
- Перед исправлением открывай принятый RCT сценарий и релевантную официальную документацию **реально используемой версии**. Достаточны нужный раздел и краткое объяснение решения; новое исследование всех лекций не нужно.
- HATEOAS уже есть. В затронутых подходящих операциях PWA/TMA переиспользуй принятые rel/self/page/action links и правильный внешний Gateway origin. Ссылки не заменяют права; новый HAL framework/массовая переделка DTO не нужны.
- Deploy, production migration/grants, удаление данных/backup, firewall и rotation secrets требуют отдельного конкретного разрешения. Используй выделенный допустимый synthetic scope. Внешние сообщения/тестовые alert deliveries — только по разрешённому каналу.
- Результат веди в существующей ветке PR #2, без merge/main push. При действующем разрешении этого чата публикуй готовые коммиты в неё и обновляй существующий draft PR; второй PR автоматически не открывай. При отсутствии разрешения подготовь точный patch/commits и обновлённый текст PR, не подменяя этим недостающую functional verification.

## 6. Existing patterns — что переиспользовать

Constructor injection, управляемые BCrypt beans, records/DTO/assemblers; явные enum converters и frozen wire codes; существующие Spring/JDBC transactions, lock/CAS/outbox; адресный afterCommit; стандартные observations/propagators и framework builders; JSON stdout, Prometheus, Loki, Tempo, Grafana provisioning и Alertmanager; адресные unit/IT/Testcontainers/Playwright/promtool checks.

Выбор новой библиотеки должен закрывать конкретный пробел этих механизмов. Сначала сопоставь актуальное поведение с результатом пакета; работающий результат можно принять без переписывания.

## 7. Acceptance criteria — строгие условия завершения

**DONE означает готовность облачного задания.** Реальная доставка алёртов будущему боту имеет явно согласованный статус DEFERRED_LOCAL и проверяется локально; боевой канал до этого не считается принятым.

Завершение этого этапа не отменяет сохранившиеся manual/environment ограничения прежнего этапа и не превращает его WAITING_ENV в DONE. В итоговом handoff раздели результат новых пакетов и прежние остающиеся ограничения; B013 остаётся FROZEN.

**DONE допустим только одновременно при следующем:**

1. A01–A04 и M01–M05 имеют конечный результат: исправлено и подтверждено либо уже работает на актуальной базе с применимым доказательством. Старый статус «source-only» не становится PASS сам по себе.
2. Для C01–C03 есть короткое решение: конкретное изменение завершено или установлен достаточный существующий механизм/отсутствие основания. «Не посмотрел» не равно «не требуется», но новая общая исследовательская кампания не нужна.
3. Enum хранит прежние текстовые DB-коды; затронутые API/wire/client mappings совместимы. Credential lifecycle и разрешённые административные функции сохранены.
4. Обязательный inventory мониторинга покрыт: реальные приложения/зависимости, нужные metrics/logs/traces, правдивые panels, resource/capacity/freshness, meaningful alerts и самодиагностика.
5. Продемонстрирован нужный сквозной путь с ID и background-связью; поиск/logs↔traces, значения meters, alert/recovery до тестового receiver относятся к принятой revision. WORD-отчёт за 18 недель и DLQ/ограниченное автоматическое восстановление временного отказа подтверждены реальным broker/worker путём. Подключение alert-бота явно передано как DEFERRED_LOCAL, остальные prerequisites не скрыты.
6. Применимые обязательные checks успешны; новые/изменённые существенные assertions обнаруживают нужный неверный результат. Skipped/NOT_RUN/UNKNOWN не выдаются за PASS. Старые достаточные PASS не повторяются без причины.
7. Независимый reviewer проверил финальные изменения безопасности/поведения/конфигурации и применимость evidence. Значимые findings закрыты с адресным recheck; reviewer не становится автором своих исправлений.
8. В связанном объёме нет открытого существенного дефекта, блокирующего правильную работу/безопасность или обязательный monitoring. Нет скрытого WIP, несогласованных generated/config changes и оставленного fault mode.
9. Другой агент может продолжить по короткому handoff: exact base/final executable SHA, изменения/причины, проверки, сохранённые решения и реальные остатки. Документационный head и проверенный исполняемый SHA не путать.

**Если обязательный результат заблокирован:** не объявляй DONE. Продолжай все независимые доступные пакеты. Когда полезной незаблокированной работы больше нет, выдай WAITING_OWNER или WAITING_ENV с конкретной причиной, доказательством, точным требуемым решением/доступом и командой/шагом продолжения. Частично законченный monitoring не называть полной production-приёмкой. Владелец может отдельно принять исключение; сам себе исключения не назначай.

## 8. Verification и автономная работа

- В начале создай конечный backlog по пакетам, использовав уже имеющиеся results. Для каждого нового запуска назови изменённое поведение или конкретную недоказанную обязательную гарантию.
- Уровень проверки выбирай по изменению: mapping/DTO → адресные assertions; реальные SQL query count/изоляция → нужный IT; propagation → соответствующий runtime путь; meters → delta/labels/export; alerts → formula fixtures и нужный firing/resolved; Grafana → фактическая query/переход. Само число тестов не прогресс.
- Обязательные gates не снимать. Для нескольких изменённых Java-модулей сначала нужные compileJava/compileTestJava, затем адресные integrationTest в одном последовательном Gradle invocation по workflow. Normal CI evidence относится к фактической исполняемой revision; прежний green на старом SHA недостаточен для изменённого кода.
- В первом проходе прочитай задание/нужные источники и **задай в этом чате непонятные существенные вопросы**, по возможности в первый час. По ходу работы также спрашивай, если обнаружилось недостающее решение. Формат: контекст → конкретный вопрос → рекомендуемый вариант/последствия → какая часть зависит от ответа. Уже отвеченное не спрашивать повторно; реальные token/chat для отложенного alert-бота сейчас не запрашивать.
- Ответ может прийти не сразу: запиши вопрос в CURRENT и продолжай независимую работу без паузы всего задания. Технические решения в действующем контракте принимай сам; зависимую от существенного продуктового решения часть не подменяй догадкой. Запоздалый ответ внеси в состояние и используй без повторного запуска уже достаточных проверок.
- Используй один сохранённый task contract, один компактный CURRENT и итоговый HANDOFF, например `docs/validation/production-readiness-20261017/`. В CURRENT держи base/SHA, конечный backlog, принятые ответы, blockers, owners и следующий шаг. Evidence — по действующему workflow, сырые логи не публикуй в Git.
- После compaction прочитай этот contract и CURRENT, восстанови scope и следующий шаг. Не начинай исследования заново и не повторяй завершённые проверки. Перед рискованным переключением/сжатием запиши полезное новое состояние.
- Работай небольшими законченными пакетами, интегрируй и проверяй изменения по мере готовности. Не жди окончания всех scouts, если известная независимая правка уже может выполняться.
- После закрытия каждого пакета A01–A04/M01–M05 напиши в этом Cloud-чате короткий отчёт: ID → что изменено/результат → достаточная проверка/evidence и executable SHA → сколько пакетов закрыто из9 → следующий шаг/blocker. Для крупного пакета допускается отчёт после значимого проверенного подшага, но такой подшаг не считается ещё одним закрытым пакетом. Отчёт не требует ожидания подтверждения; продолжай работу.
- В одном существующем CURRENT веди компактные девять строк пакетов со статусом NOT_STARTED/IN_PROGRESS/READY_FOR_REVIEW/DONE_CHANGED/ALREADY_SATISFIED/BLOCKED, доказательством и SHA. DONE_CHANGED означает внесённую и принятую доработку, ALREADY_SATISFIED — применимое достаточное существующее доказательство; оба закрывают пакет, но показываются раздельно. Публикуй актуальный CURRENT вместе с нормальными checkpoint готовых изменений, без отдельного коммита ради каждой строки. C01–C03 учитываются отдельно по фактической активации. Число закрытых пакетов не является процентом готовности всего продукта.
- Существенный blocker или вопрос сообщай сразу; при долгой работе без закрытого пакета достаточно короткой сводки о реальном продвижении/следующем шаге. Не создавать отчёты об отчётах, новую telemetry ради оценки эффективности агента или бесконечное наблюдение неизменного CI.
- Итог: reviewable изменения текущей ветки и обновлённый draft PR #2 либо подготовленное обновление PR по действующим разрешениям. Отдельно покажи diff нового этапа относительно сохранённого starting SHA, чтобы его можно было проверить без повторного разбора всего старого PR. В handoff достаточно таблицы пакетов, списка файлов/изменений с причинами, применимых checks/SHA и вопросов владельцу. Полный реестр лекционных пунктов к результату не копировать.

## 9. Do not — исключённый объём

- Не реализовывать повторно готовые DTO/MVC/DI базового wiring, cookie issuance/refresh/revoke, guards, outbox, Flyway fresh/upgrade и форматирование всего репозитория. Форматировать реально изменённые файлы по существующим правилам.
- Не делать полный повтор прежней функциональной матрицы, всех браузеров/форм, security/load/mutation/fault кампании ради покрытия. Смежный реальный дефект исправляется адресно в текущем результате.
- Не разделять физически БД, не вводить богатый ORM-граф/EAGER/cascades/Version повсюду, не мигрировать enum в числа и не перенумеровывать protobuf.
- Не вводить Thymeleaf/GraphQL/учебный OAuth/Keycloak, новый web, новый BFF на страницу или весь backend на Reactor.
- Не добавлять Collector/exemplars/service graph/management port/HA только ради совпадения с лекцией; обязательный monitoring обязан работать независимо от наличия этих конкретных вариантов.
- Не перечитывать все лекции/архивы/историю старого чата перед началом известной правки. Не открывать другие чаты и не отправлять им сообщения без отдельного поручения.
- **B013 остаётся platform-rejected/FROZEN/WAITING_ENV.** Не повторять и не обходить эквивалентную mutation через код, CI, другую модель или поверхность. Разрешение владельца на обычную разработку этот платформенный блок не снимает. Известный B013 сохранить отдельным ограничением; его обход не является условием этого задания.
- Не расширять разрешения, не удалять чужие данные/volumes/backup, не читать/печатать реальные secrets и не выполнять production операции ради зелёного отчёта.
