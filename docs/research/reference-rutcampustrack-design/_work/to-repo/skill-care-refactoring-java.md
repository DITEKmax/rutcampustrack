# Care Refactoring (Java / Spring)

Прагматичный maintenance-рефакторинг одного сервиса RutCampusTrack. Оптимизируй под будущую работу людей и агентов, не под эстетику. Валидный результат: `No code changes needed`.

## Operating Rules

- Сначала — правила репозитория: `CLAUDE.md` (contract-first, enum-as-string, Flyway, изоляция доменов) и `AGENTS.md`.
- Сохраняй несвязанные изменения пользователя. Проверь `git status --short --branch` перед правкой.
- **Сохраняй без изменений (если пользователь явно не просит иначе):** публичные REST/gRPC контракты (`*-api-contract`, `proto/`), формат ошибок (RFC 9457), схему БД, права/security-поведение, бизнес-правила, форматы событий.
- Одно маленькое ценное улучшение лучше широкого переписывания.
- Не навязывай новую архитектуру, если текущая явно не проваливается.
- Не меняй код, пока challenge-чекпоинт не закончился `PROCEED_WITH_SCOPE` или `NARROW_SCOPE`.
- Перед изменением production-кода зафиксируй важное поведение characterization-тестом (JUnit/Testcontainers), если оно ещё не покрыто и тестовый слой пропорционален.

## Discovery

1. Прочитай контекст: `CLAUDE.md`, `docs/` сервиса, `build.gradle.kts`, релевантные тесты (`*Test`/`*IT`).
2. Определи слой/модуль, стек сервиса (PG/Mongo/Redis), конвенции пакетов `ru.rutcampustrack.{service}.{module}`.
3. Смотри текущие diff'ы, не трогай несвязанные изменённые файлы.
4. Найди владеющий слой для поведения под ревью.

Если нужен широкий поиск и доступны саб-агенты — делегируй поиск, проси компактную карту: `path:line`, символ/эндпоинт, сниппет, почему важно. Критичные находки проверь сам перед правкой.

## Refactor Candidates (что искать)

- Бизнес-логика, зашитая в контроллеры/gRPC-хендлеры/`@EventListener`/JPA-репозитории/сериализаторы вместо application/domain слоя.
- God-классы/сервисы, смешивающие оркестрацию, persistence, форматирование, права, внешние вызовы.
- Дублированные бизнес-правила между эндпоинтами/сервисами.
- Скрытые зависимости от времени (`LocalDateTime.now()` вместо инжектируемого `Clock`), рандома, env, синглтонов.
- `shared`/`common`/`util` пакеты, превращающиеся в свалку.
- Нарушения изоляции доменов (`report/` тянет из `checkin/` напрямую, минуя `shared/port/`).
- Код, из-за которого следующая фича скопирует плохой паттерн.

## Responsibility Boundaries (Spring)

- **Controller (transport):** принять запрос, вызвать application-слой, смаппить результат/ошибку. Ничего доменного.
- **Application/Service:** пользовательский сценарий, права, `@Transactional`, оркестрация.
- **Domain:** чистые правила, инварианты, расчёты, доменные исключения.
- **Infrastructure:** репозитории, gRPC-клиенты, RabbitMQ, Redis, внешние API.
- Эвристика: «что должно произойти?» → application/domain; «как говорим с внешней системой?» → infrastructure; «как принимаем вход/отдаём выход?» → controller.

## Scope Proposal

Перед правкой предложи максимум 1–3 маленьких ценных скоупа. Для каждого:
- конкретный smell;
- сохраняемое поведение и публичные контракты;
- минимальное полезное изменение;
- главный риск;
- сигнал валидации (какой `./gradlew` таск);
- нужен ли characterization-тест до рефактора (или уже есть / был бы избыточен).

## Challenge Checkpoint

Если доступны саб-агенты — свежий challenge-агент (сильная модель, high reasoning, НЕ пишет код) валидирует скоуп:
- Стоит ли вообще делать этот рефактор?
- Достаточно ли мал скоуп?
- Какой контракт/поведение можно случайно сломать?
- Есть ли более простое улучшение?
- Это оверинжиниринг?
- Какой characterization-тест должен защитить поведение до рефактора?
- Proceed / narrow / do nothing / отдельная продуктовая задача?

Максимум 2 коротких раунда несогласия. Итог — ровно одно решение:
`PROCEED_WITH_SCOPE` | `NARROW_SCOPE` | `NO_CHANGES_NEEDED` | `SEPARATE_PRODUCT_TASK`.
Не меняй код кроме как при `PROCEED_WITH_SCOPE`/`NARROW_SCOPE`.

## Characterization Tests

Для поведение-сохраняющих рефакторов — зелёный characterization-тест до правки production-кода:
- используй самый ценный существующий тест-слой пропорционально скоупу (unit / `*IT` с Testcontainers);
- тестируй наблюдаемое поведение/контракты/инварианты, не детали реализации;
- достаточно узкий, чтобы упасть при случайном изменении поведения;
- прогони до правки, подтверди зелёный на текущем поведении;
- нет подходящего слоя или тест был бы несоразмерен — скажи явно, используй быстрейший надёжный сигнал.

Не выдумывай тяжёлый тест-harness ради галочки. Не кодируй известный баг как желаемое поведение (если пользователь явно не просит сохранить баг).

## Implementation Loop (на каждый принятый скоуп)

1. Осмотри окружающий код и тесты.
2. Зафиксируй smell, сохраняемое поведение, контракты, риски, минимальное изменение.
3. Добавь/найди characterization-тест, прогони до правки.
4. Сделай минимальный связный diff.
5. Перенеси решения на владеющий слой; не патчь симптомы в детях/лист-хелперах, когда неверное решение принято выше.
6. Обнови точечные тесты только там, где защищают переносимое поведение.
7. Прогони релевантные проверки: `./gradlew :services:<svc>:<module>:test` → `check`.

TDD для нетривиального поведения/контрактов/auth/persistence/query/валидации/переходов состояний, если тест-слой пропорционален.

## Avoid

- Переписывание с нуля.
- Новые фреймворки/зависимости без явной необходимости.
- Interface/port/repository/factory/mediator/event bus/CQRS без текущей ценности.
- Дробление простого кода на кучу файлов ради «чистоты».
- Посторонний cleanup / doc churn.
- TODO вместо завершения рефактора.
- Архитектура, делающая код труднее для чтения.
- Перенос бизнес-сценариев в infrastructure/query/gRPC-код.
- Утечка infrastructure/фреймворк-деталей в чистую доменную логику.
- Нарушение contract-first (логика в контроллере), Lombok в контрактных модулях, `EnumType.ORDINAL`.

## Pre-Final Review (как свежий ревьюер)

- Поведение сохранено; скоуп остался маленьким; публичные контракты не изменены.
- Characterization-покрытие добавлено/было/осознанно пропущено с причиной.
- Тесты/`check` проходят, или ясно объяснено, что не удалось запустить.
- Доки правятся только при изменении устойчивой архитектуры/операций/контрактов.

Если рефактор больше не выглядит стоящим — откати только свои изменения, отчитайся `No useful maintenance refactor found`.

## Final Report

- Итог: без изменений / изменения сделаны / частично провалидировано.
- Осмотренные скоупы; решение challenge-чекпоинта; изменённые скоупы.
- Что улучшилось и почему важно; сохранённые контракты.
- Characterization-покрытие: добавлено/переиспользовано/пропущено.
- `Primary signal status`; `Secondary signal status` (какие `./gradlew` таски).
- Docs status; оставшиеся риски; предложенное сообщение коммита (Conventional Commits).
