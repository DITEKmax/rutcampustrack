## Продукт

**RutCampusTrack** — университетская система трекинга посещаемости и расписания для студентов РУТ (МИИТ).

- **Основная аудитория:** студенты 18–25.
- **Вторичная:** преподаватели и администраторы 30–60.
- **Прод:** `ruttrack.site`
- **Репозиторий:** https://github.com/DITEKmax/rutcampustrack

## Роли пользователей

| Роль | Описание |
|---|---|
| `student` | Студент — базовая роль |
| `headman` | Староста (`STUDENT` + `is_headman = true`) — расширяет student |
| `teacher` | Преподаватель |
| `admin` | Администратор |

## Фронтенд: полный переписывание с нуля

**Всё переписывается на Vue в архитектуре микрофронтендов. От старого фронтенда уходим полностью.**

- Новый визуальный дизайн всей системы — создаётся заново.
- Старая дизайн-система «Transit Grid» (концепция, палитра, шрифты Clash Display / General Sans / DM Sans / JetBrains Mono, токены) — **отменена**. Не использовать ни в каком виде. Принятое направление «Табло» ассоциативно соседствует с транспортной темой по механике времени — это совпадение приёма, а не преемственность: ничего из «Transit Grid» не возвращается.
- Старые приложения (`frontends/landing` React, `frontends/web-panel` Angular 19, `frontends/mini-app` React, `frontends/pwa` React) — **legacy, подлежат замене**. Их код, компоненты и стили не являются образцом.
- Миграции нет — greenfield. Совместимость со старыми токенами не требуется.

**Архитектура микрофронтендов** — пример эталонного проекта будет добавлен позже. До этого момента считать открытым вопросом: границы микрофронтендов, состав shared-библиотеки, механизм композиции.

## Поверхности

Продукт в итоге живёт на трёх поверхностях, но **они проектируются последовательно, а не одновременно**:

| Поверхность | Статус | Роли |
|---|---|---|
| **Веб-десктоп** | ✅ **в работе сейчас**, базовое разрешение **1920** | все 4 роли: admin, teacher, headman, student |
| PWA (мобильный) | позже, отдельным этапом | преимущественно student/headman |
| Telegram Mini App | позже, отдельным этапом | преимущественно student |

**Важно:** PWA и Telegram Mini App — это **отдельные продуктовые поверхности со своими экранами и сценариями**, а не «сжатая десктопная версия». Их нельзя получить простым адаптивом от 1920. Проектируются отдельно, после десктопа.

На текущем этапе учитывать только веб-десктоп. Ограничения Telegram WebApp API — отложены до соответствующего этапа.

Как поверхности распределятся по микрофронтендам — часть решения об архитектуре.

## Технические требования (в силе)

- **Две темы** — dark и light. Только CSS-переменные для цветов/теней/бордеров, без хардкода. Обе темы проверяются.
- **Accessibility** — минимум AA-контраст (4.5:1 для текста), focus-visible, semantic HTML. Детали — `a11y-checklist.md`.
- **Performance** — lazy-load изображений, code-split роутов, `font-display: swap`.
- Тема Telegram не должна перетирать брендовые цвета.
- **Бренд-направление — «Табло».** Правила характера, отклика и поведения в состояниях — `BRAND_DIRECTION.md`. Оно обязательно для всех чатов по визуалу.

## Бэкенд (остаётся, но не заморожен)

Java 21 + Spring Boot 3.4, микросервисы: `auth-service`, `academic-service`, `schedule-service`, `attendance-service`, `notification-service`, `api-gateway`.

- Contract-first: публичные контракты в `services/*/*-api-contract`.
- REST через API Gateway (`/api/{service}/...`), ошибки RFC 9457 Problem Details, HATEOAS.
- Между сервисами gRPC, события через RabbitMQ.
- Хранилища: PostgreSQL (auth/academic/schedule), MongoDB (attendance/notification), Redis.
- Доступные эндпоинты — в `api-digest.md` (112 штук, роли указаны в описаниях).

**Бэкенд можно менять под нужды фронта.** Если экрану нужны данные, которых нет — описывай потребность и помечай `[предложение по бэкенду]`.

**Транспорт: решено (01.08.2026) — REST.** GraphQL отклонён. Перед существующими сервисами появляется тонкий слой композиции (BFF): вниз gRPC, вверх ресурсы формы экрана; отдельная единица выпуска, один общий на все три поверхности. Подробности и правила — `TRANSPORT.md`.

**Потребности в данных по-прежнему описываются транспортно-нейтрально.** Спеки и `COMPONENT_REGISTRY.md` решением не затрагиваются: доменные сервисы не знают о формах экранов, формы живут только в слое композиции.
