## Phase Boundary

Фаза объединяет две тесно связанные задачи, которые всплыли одновременно при
разборе багов старосты:

1. **#4-Full — Починка модели «предмет группы + его преподаватели»** (сейчас
   модель неконсистентна: фронт шлёт `teacherId` при создании предмета, но
   бэкенд его игнорирует; `Subject.type` не задаётся из UI; нет привязки
   subject→group; `TeacherSubjectGroup` не создаётся).
2. **#5 — UI управления расписанием для старосты** (его сейчас вообще нет)
   с поддержкой единоразовых правок (отмена конкретной пары + вставка разовой
   пары на конкретную дату).

Обе задачи завязаны на одну и ту же модель (Subject → TeacherSubjectGroup →
ScheduleItem), поэтому объединены в одну фазу.

### Что делаем в этой фазе

**Backend (academic-service):**
- Починить DTO/сервис `CreateSubjectRequest` и `SubjectService.createSubject`,
  чтобы корректно принимать `groupId`, `type` (LECTURE/PRACTICE/LAB) и
  список `teacherIds`, и атомарно создавать:
  - запись в `subjects`;
  - N записей в `teacher_subject_groups` (текущий семестр).
- UI/endpoints для управления преподавателями существующего предмета
  (добавить/убрать препода у `(subject, group, semester)`).
- Добавить `groupId` в `Subject` entity + миграция Flyway (предмет группы,
  не глобальный).

**Backend (schedule-service):**
- Новые endpoints для старосты:
  - CRUD шаблона расписания (`ScheduleItem`) — только для своей группы.
  - Разовые правки: **отмена конкретной даты** (уже есть — проверить) и
    **вставка одноразовой пары** на конкретную дату.
- Модель одноразовой пары: новая сущность `ScheduleException` (или аналог) —
  привязка к date + slot (lessonNumber), со ссылкой на существующий
  `Subject` группы. **Не** модифицирует шаблон `ScheduleItem`.
- Посещаемость по одноразовой паре **учитывается как обычная пара** в
  статистике по этому предмету.

**Frontend (web-panel, роль HEADMAN):**
- Новая страница `/headman/schedule` — матрица (дни × слоты) с отображением
  шаблона текущего семестра для группы.
- Режимы редактирования шаблона: добавить/изменить/удалить слот
  (предмет, преподаватель из списка привязанных, кабинет, WeekType).
- Режим «разовая правка на дату X»:
  - на ячейке шаблона — «отменить эту пару на дату X» (уже реализовано? —
    сверить);
  - кнопка «Добавить разовую пару» — форма выбора даты + слота + предмета
    + кабинета (препод берётся из привязки subject→teacher).

### Out of scope

- Перенос как единая операция (в этой фазе староста выполняет «отменить» +
  «вставить» двумя действиями — см. D-04).
- Права помощника старосты на управление расписанием (обсудить отдельно
  позже — см. D-07).
- UX-улучшения: drag-and-drop, автоподсказки по конфликтам, календарный
  view. В этой фазе — базовая матрица + диалоги. DnD можно добавить
  следующей итерацией.

## Implementation Decisions (зафиксированы пользователем)

### Модель предмета и преподавателей

- **D-00 (контекст существующей модели):**
  - `Subject` = `{id, name, type, createdAt}` — глобальный, **без группы**,
    **без преподавателя**.
  - `TeacherSubjectGroup` = связка `(teacher, subject, group, semester)` с
    уникальным constraint по этим четырём полям — **уже поддерживает N
    преподавателей на один предмет+группу**.
  - `ScheduleItem` (schedule-service) имеет `teacherId` на слот — поле,
    которое по финальной модели **удаляется** (см. D-16).

- **D-01 (Q-01, решено):** Предмет привязан к **группе** (не глобальный).
  Добавить `group_id NOT NULL` в `subjects` через Flyway-миграцию.
  **Миграция данных:** удалить все существующие записи `subjects` (база
  пока только тестовая, в проде не используется). После миграции
  `group_id` сразу `NOT NULL`, без промежуточного nullable-этапа.

- **D-02:** При создании предмета староста указывает:
  - Название (`name`)
  - Тип (`type`: LECTURE/PRACTICE/LAB — уже enum есть)
  - **Список преподавателей** (N штук — все равноправные read-only
    наблюдатели; роли `is_primary` / primary vs observer **НЕ вводим** —
    см. D-15)
  - Группа берётся из контекста старосты (его группа), не с формы.

- **D-15 (модель преподавателей — финальная):** Все преподы в системе —
  **чистые read-only наблюдатели**. Они НЕ получают push/уведомлений,
  НЕ проставляют отметки, НЕ взаимодействуют с ботом. Единственное
  действие препода — открыть `/teacher/journal` и **смотреть** посещаемость
  тех групп/предметов, где он есть в `TeacherSubjectGroup`. Поэтому:
  - `TeacherSubjectGroup` **остаётся без изменений** — без `is_primary`,
    без ролей, все записи равноправны.
  - «Основного» препода в смысле «кто ведёт пару» в модели нет.
  - Отметки студентов делают сами студенты (геолокация) + автоматический
    `absent` при закрытии пары.
  - Напоминания о начале пары шлются **только студентам** группы.

- **D-16 (Q-02, решено):** `ScheduleItem.teacherId` **удаляется**. Слот
  хранит только `{subject_id, day, lesson_number, classroom, week_type}`.
  Препод к журналу предмета получает доступ через JOIN:
  ```
  lessons (видимые преподу) =
     ScheduleItem JOIN TeacherSubjectGroup
     WHERE TSG.teacher_id = :currentTeacher
  ```
  Если у предмета N преподов в TSG — все N видят одинаковый журнал.
  Аналогично для `schedule_one_off_lessons` — без `teacher_id`.

### Разовая пара (single-lesson insert)

- **D-03 (предмет):** Разовая пара **обязательно** ссылается на
  существующий предмет группы (dropdown из каталога её предметов). Нельзя
  создавать «одноразовый предмет» — иначе статистика сломается
  (новый subject = 1 пара = 100%/0%).

- **D-04 (Q-03, решено — модель в БД):** Новая таблица
  `schedule_one_off_lessons` в schedule-service:
  ```
  {id, group_id, subject_id, date, lesson_number, classroom,
   created_by, created_at}
  ```
  **Без `teacher_id`** (см. D-16). На read-путях сливается с шаблоном
  `ScheduleItem` по `(group_id, date, lesson_number)` — для downstream
  (журнал препода, журнал старосты, расписание студента, статистика
  по предмету, геофенс, напоминания, auto-absent) разовая пара
  **неотличима** от обычной. Единственное различие — визуальная
  пометка «Разовая пара» в UI студента.

- **D-05 (время):** Только существующие слоты (1-я, 2-я, ... пара).
  Свободных time range нет.

- **D-06 (операция переноса):** Реализовать как **два независимых
  действия** — «отменить пару на дату X» (уже есть у старосты? — сверить)
  и «вставить разовую пару на дату Y». Не делать единой операции
  «Перенести».

- **D-07 (видимость):** Студенты группы видят разовую пару в расписании
  на дату Y с пометкой «Разовая пара». Поведение отметки (геоотметка,
  attendance) — идентично обычной паре. Посещаемость учитывается в
  общую статистику по предмету.

- **D-08 (ограничения по дате):** Можно вставлять разовую пару на
  **любую дату** — прошлую, сегодня, будущую (староста исправляет
  задним числом). Единственное обязательное поле — явно указанная
  дата целевой пары.

- **D-09 (слот занят, решено):** **Вариант (a)** — запретить. Если в
  шаблоне на `(date, lesson_number)` стоит пара и она не отменена на эту
  дату — API возвращает 409 Conflict. Староста сначала выполняет
  «отменить пару на дату X», потом «вставить разовую на дату X».

- **D-10 (проверка конфликтов преподов):** Не делаем. Староста
  правит только свою группу; пересечения по преподам на уровне вуза
  не наша забота в этой фазе.

### Права

- **D-11 (староста):** Староста редактирует расписание **только своей
  группы**. Проверка — через `RequestContext` (аналогично subject
  management, где уже работает `requireHeadman()`).

- **D-12 (помощник старосты):** В этой фазе **не даём** прав на
  управление расписанием. Позже можно добавить новое разрешение в
  `assistant_permissions` (сейчас: excuse_approve, late_checkin_approve,
  subject_manage, attendance_mark; добавить `schedule_manage`?).

### UI

- **D-13:** Страница `/headman/schedule` — матрица дни×слоты,
  отображение шаблона на активный семестр. Редактирование — через
  диалоги (консистентно с существующим `subject-dialog.component.ts`).

- **D-14:** Drag-and-drop в этой фазе **НЕ делаем**. Только клик по
  ячейке → диалог. DnD можно добавить в отдельной итерации, если
  UX потребует.

## Events & Push (решено)

- **D-17 (Q-05, решено):** Используем **типизированные события**
  (Вариант A — в стиле проекта `{domain}.{action}`):
  - `lesson.cancelled` — **УЖЕ СУЩЕСТВУЕТ**. Файлы подтверждены в сессии
    2026-04-14:
    - `event-schemas/lesson.cancelled.json`
    - `services/schedule-service/.../event/LessonCancelledEvent.java`
    - `services/notification-bot/bot/notifications/lesson_cancelled.py`
    - attendance-service `EventConsumer` уже обрабатывает.
    Переиспользуем **без изменений**.
  - `lesson.one_off.created` — новый event type, при создании разовой
    пары старостой. Добавить JSON Schema + publisher + consumers.
  - `lesson.one_off.cancelled` — новый event type, при удалении разовой
    пары старостой (касается в т.ч. удаления с каскадом past-даты,
    см. D-22).
  JSON-схемы добавить в `event-schemas/`. Подписчики:
  - **notification-bot** — push студентам группы (понятный текст с
    указанием предмета/слота/кабинета/даты).
  - **notification-web** — WebSocket в открытые вкладки PWA/web-panel.
  - **attendance-service** — обновление read-модели для генерации
    `lessons` на дату.

- **D-18 (получатели push):** При создании/отмене разовой пары push
  получают **все студенты группы, включая самого старосту**. Староста
  не исключается из рассылки — оставляем единый канал для всей группы.

## Backend cancel-lesson — текущее состояние (Q-04, решено)

- **D-20 (Q-04, решено):** Backend отмены конкретного урока **уже
  реализован** (подтверждено чтением кода 2026-04-14):
  - DTO: `CancelLessonRequest {reason: String}` (contract), `MassCancelRequest`.
  - Endpoints в `LessonApi`: `POST /api/schedule/lessons/{id}/cancel`,
    `POST /api/schedule/lessons/restore`, mass-cancel — все помечены
    в Swagger как «HEADMAN/ADMIN».
  - Role-guard: `@RequireRole({ADMIN, STUDENT})` (HEADMAN в v9 = STUDENT
    с `is_headman=true` — корректно).
  - Event `lesson.cancelled` публикуется, notification-bot/web и
    attendance-service уже обрабатывают.

  **В фазе 60 backend отмены НЕ трогаем.** Работаем только на фронте:
  - Кнопка «Отменить пару на дату X» в ячейке `/headman/schedule`
    (вызывает существующий API).
  - Проверка «редактирует только свою группу» уже должна делаться через
    `RequestContext` — **проверить при планировании**, что guard реально
    сверяет `groupId` урока с группой старосты (если нет — это baby fix
    в той же фазе, не отдельный плановый блок).

## One-off lesson — constraints и lifecycle (решено)

- **D-21 (Q-06, решено):** Таблица `schedule_one_off_lessons` имеет
  UNIQUE constraint на `(group_id, date, lesson_number)`. Двойной клик
  «Добавить разовую пару» возвращает 409 Conflict вместо создания
  дубля. Констрейнт описать в Flyway-миграции.

- **D-22 (Q-07, решено):** Удаление разовой пары **разрешено на любую
  дату** (включая прошедшие), **с каскадным удалением attendance-записей**.
  Механика:
  - При `DELETE /api/schedule/one-off-lessons/{id}` schedule-service
    удаляет запись one-off и публикует event `lesson.one_off.cancelled`
    с `{groupId, date, lessonNumber, subjectId}`.
  - attendance-service на этот event **удаляет** соответствующую
    `lesson` и все каскадные записи (attendance marks, excuses и т.п.)
    — как если бы пары не было.
  - Студенты группы получают push «Разовая пара на дату X отменена».

  Логика каскадного удаления в attendance-service — **важный
  integration point**, планировщик должен разложить это в отдельный
  подплан (реализация + тесты).

- **D-23 (Q-08, решено):** `schedule_one_off_lessons.semester_id NOT NULL`
  (консистентно со `ScheduleItem`). При создании one-off — semester
  определяется автоматически по `date` (lookup в academic-service, как
  это уже делается для lesson-generation). Фильтрация по семестру
  корректно работает в отчётах старого семестра.
