### Сверка со сканом

- **КРАСНОЕ:** четыре плитки верхнего ряда — количество «+», «н», «у» и разбивка по типам причин.
- **ЖЁЛТОЕ:** поповер профиля, обе таблицы, блок графика.
- **ЗЕЛЁНОЕ:** `RoleSwitcher`, кружок профиля, три группы docx/pdf/png, «Выбрать предмет», кнопки ЛК/ПЗ/ЛЗ.
- **НЕОКРАШЕНО:** оба набора навигации, серый фон.
- **НЕ НАРИСОВАНО, но следует из заметок:** фильтры на колонках (заметка 3 макета), переключатели разреза графика (заметка 5 макета), панель детальной статистики (заметка 2 job), триггер её вызова.

### Красный ≠ без взаимодействия

Четыре верхние плитки — фиксированное отображение, действий на них нет. Но у каждой есть `loading` / `error` и вырожденный случай «семестр только начался, значения нулевые» — **и это не ошибка, а валидный результат**, который нельзя показывать как пустоту или сбой.

### Замечание по разведению имён

## 4. Потребности в данных

**Общая рамка: на этом экране практически ничего нет в API.** Аналога `student/stats` и `student/dashboard` для группы не существует. Владелец подтвердил: экран под наследие не подгоняем — если понадобится, бэкенд переделывается.

### 4.1 Итоговые счётчики за семестр (заметка 1 макета)

- **Нужно:** по группе за активный семестр, по всем предметам — количество `+`, `н`, `у`.
- **Сейчас:** нет. Ближайшее — `GET /academic/dashboard/stats`, но это ADMIN и по системе целиком.
- **Пробел:** `[предложение по бэкенду]` — агрегат по группе за семестр.
- **Пробел:** `[предложение по бэкенду]` — **инкрементальное хранение вместо пересчёта.** Прямая формулировка владельца (заметка 1): «надо сделать функционал такой, что есть значение и оно инкрементируется, а не считать каждый раз». Смыкается с B-10 из ПК-112 — там та же идея для выгрузок.

### 4.2 Разбивка уважительных причин по типам (заметка 2 макета)

- **Нужно:** количество **поданных** причин в разрезе типов из перечня §0 реестра (болезнь · приказ вуза или иной документ · повестка от военкомата · прочее), **упорядоченное по убыванию частоты**.
- **Подтверждено владельцем:** считаются **поданные** — «какие чаще всего подают», независимо от решения старосты.
- **Сейчас:** `GET /attendance/excuses/group/{groupId}` — список тикетов, агрегата нет.
- **Пробел:** `[предложение по бэкенду]` — агрегат по типам причин. Клиентский подсчёт означает вытягивание всех тикетов группы за семестр ради нескольких чисел.
- **Пробел:** `[предложение по бэкенду]` — **перечень типов приходит как данные** (правило §0 реестра: перечень пополняется без релиза фронта). Значит и разбивка отдаётся списком пар «тип → количество», а не фиксированным набором полей.

### 4.3 Две метрики посещаемости — сквозное правило (заметка 3 job)

- **Нужно:** везде, где считается посещаемость, отдаются **две величины рядом**: `%+` и `%(+ и у)`.
- **Обоснование владельца:** преподаватели оценивают посещаемость по-разному — одна метрика не обслуживает обе трактовки.
- **Подтверждено владельцем:** «всегда такая статистика будет рядом».
- **Пробел:** `[предложение по бэкенду]` — обе метрики считает и отдаёт **сервер** (продолжение JS-SYSTEM-16: округления на разных экранах не должны расходиться).
- **Область действия:** решение **выходит за пределы 113** — применяется к 101, 102, 103 студента и ко всем будущим экранам. Идёт в реестр как общее правило.
- ⛔ **Отменено:** колонка `%у + н`, нарисованная на скане. Доля непосещения избыточна — она равна `100% − %+`. Благодаря этому **колонки таблиц совпадают с линиями графика один в один**.

### 4.4 Таблица по группе (заметка 3 макета)

- **Нужно:** строка на студента: ФИО; `%н`, `%+`, `%у`, `%(+ и у)` **и те же четыре в количествах**; тикеты на «н» (late-checkin) — подано / одобрено / отклонено; тикеты на «у» (excuse) — подано / одобрено / отклонено; разбивка способа получения «+» (см. 4.5).
- **Сейчас:** ни одного эндпоинта.
- **Пробел:** `[предложение по бэкенду]` — агрегат «по студентам группы за семестр» со всеми перечисленными разрезами, с серверными сортировкой, фильтрацией и пагинацией.
- **Дефолтная сортировка:** по `%+` (заметка 3 макета: «по умолчанию считается по % "+"»).

### 4.5 Способ получения отметки «+» — новое требование к данным

- **Нужно:** доля `+`, полученных: через геолокацию · через **ручную** заявку старосте · через заявку, ушедшую **автоматически при неудачном гео** · поставленных старостой вручную.
- **Сейчас:** `source` в отметке (если он вообще есть — см. B-4 из ПК-112) различает `student_geo` / `late_checkin` / `headman`, но **не различает происхождение заявки**.
- **Пробел:** `[предложение по бэкенду]` — у заявки late-checkin должно храниться происхождение (`manual` / `auto_after_failed_geo`).
- **Согласование с §0 реестра:** решение «одна заявка на пару независимо от происхождения» **не противоречит** этому требованию: лимит остаётся общим, а признак происхождения сохраняется и попадает в статистику.

### 4.6 Тикеты с решениями

- **Нужно:** по студенту — количество поданных, одобренных, отклонённых, отдельно для «н» (late-checkin) и «у» (excuse).
- **Сейчас:** `GET /attendance/excuses/group/{groupId}`, `GET /attendance/late-checkin/group/{groupId}` — списки без агрегации.
- **Пробел:** `[предложение по бэкенду]` — агрегат в составе строки студента (4.4). Иначе на каждого студента — отдельный подсчёт по двум спискам, то есть N+1 по составу группы.

### 4.7 График динамики (заметка 5 макета)

- **Нужно:** ряд точек в трёх разрезах — семестр с делением по неделям · выбранная неделя с делением по дням · срез по предмету (с типами занятий). В каждой точке — **обе метрики**. Плюс подробность за точку для подсказки при наведении.
- **Подтверждено владельцем:** **с сервера приходят данные, график рисует фронт.** Картинку сервер не отдаёт.
- **Сейчас:** нет.
- **Пробел:** `[предложение по бэкенду]` — временной ряд посещаемости группы с параметрами разреза.
- **Пробел:** `[предложение по бэкенду]` — **обе серии приходят на одной сетке ключей.** Требование уже сформулировано для студенческого 103 (JS-STUDENT-19): если сетки разойдутся, клиент будет сшивать точки по датам.
- **Фиксированная шкала 0–100** (заметка 5 макета) — требование к отрисовке, не к данным. Записывается, чтобы автоматический масштаб не исказил сравнение периодов.

### 4.8 Фильтры и сортировка на колонках (заметка 3 макета)

- **Нужно:** сортировка по любой колонке (дефолт — `%+`) и фильтрация **по всем полям** таблицы.
- **Подтверждено владельцем:** «сортировка и фильтр стараемся делать там, где уместно; на бэкенде добавляется, на фронте рисуется, так что может меняться».
- **Следствие для фронта:** фильтрация идёт по всем полям, но **набор всё равно приходит описанием** (§0 чат 4): таблица получает дескрипторы колонок снаружи и рисует контролы по ним. Добавление фильтра на бэкенде не требует правки фронта. Формат дескриптора — `table-filters.md` §3.1.
- ✏️ **Подтверждено задачей 4 (Р-17):** сортировка **и фильтрация серверные, вместе с пагинацией**; мультисортировка без предела ключей, приоритет виден в заголовке; «Сбросить» снимает фильтры и сортировки разом; фильтры уходят в адрес страницы и в выгрузку (Р-23). Прежняя пометка `[предложение по бэкенду]` снята. Клиентская сортировка по неполной странице даст неверный порядок; клиентский фильтр по ней же молча скроет часть набора.
- **Перечень значений enum-фильтра приходит с бэкенда** (`options` либо `optionsSource`) и никогда не собирается из загруженной страницы (`table-filters.md` §3.2).
- **Расхождение с ПК-103 студента:** там в реестре зафиксировано, что «Фильтр» описывал исключительно сортировку и мог быть избыточен. Здесь фильтр — полноценный отбор. Разница осмысленна: у студента одна своя строка, у старосты — вся группа.

### 4.9 Детальная статистика (заметка 2 job)

- **Нужно:** по выбору строки — подробный срез по студенту, отображаемый **во встроенной области страницы, а не модальным окном поверх контента** (прямое требование заметки 2 job).
- **Подтверждено владельцем:** триггер — **строка целиком** либо **стрелка в строке**, по тому, что лучше по UX. Решение §6.
- **Сейчас:** нет.
- **Пробел:** `[предложение по бэкенду]` — детализация по студенту за семестр. Состав — предположительно разбивка по предметам и типам занятий, история тикетов, помесячная или понедельная динамика.
- **Пробел:** `[уточнение по контракту]` — состав панели не определён до появления контракта; на скане области нет.

### 4.10 Выгрузка

Как на ПК-112: форматы и шаблоны на бэкенде, перечень приходит данными, выгрузка учитывает активные фильтры. Здесь **три независимые точки выгрузки** — две таблицы и график.

- **Пробел:** `[предложение по бэкенду]` — выгрузка **графика**. Владелец подтвердил, что с сервера приходят данные, а рисует фронт. При этом форматы файлов формирует сервер (B-9), а `png` графика требует **серверной отрисовки** того же ряда. Нужно решить: сервер рисует картинку сам, либо для графика доступны только табличные форматы.

### ⚠️ Фактура к решению о транспорте

| Блок | Запросов | Существует в API |
|---|---|---|
| профиль / права / семестр | 1 | частично |
| три счётчика | 1–3 | **нет** |
| разбивка причин | 1 | **нет** |
| таблица по группе | 1 | **нет** |
| таблица по предмету | 1 + список предметов | **нет** |
| график | 1 | **нет** |
| детальная панель | 1 на выбор строки | **нет** |

**6–8 запросов, из которых существует ноль.**

Это принципиально иная ситуация, чем на 111 и 112: там был over-fetching поверх работающих эндпоинтов, здесь экран проектируется **до появления данных**. Владелец подтвердил, что экран под наследие не подгоняется. Практический вывод: форму ответов можно задать сразу под экран — и это самый дешёвый момент, чтобы сделать её удобной, независимо от того, каким окажется решение по транспорту.

## 5. Состояния

На бумаге не нарисовано ни одного non-happy состояния. **Всё ниже добавлено при разборе.**

### `StatsByStudentTable` (оба экземпляра)

| Состояние | Условие | Что показываем |
|---|---|---|
| `loading` | грузится агрегат | скелетон, `aria-busy` |
| `no-active-semester` | активного семестра нет | пояснение, таблица не рендерится |
| `semester-not-started` | семестр активен, прошедших пар нет | **«нет данных», а не «0%»** — правило `future` из §6.1 реестра |
| `partial` | часть пар прошла, часть впереди | считаем по прошедшим, будущие в знаменатель не входят — **подписать явно**, иначе цифры выглядят заниженными |
| `no-members` | в группе нет студентов | `empty` — вырожденный, но реальный сразу после создания группы |
| `filtered-empty` | фильтры не оставили строк | «под выбранные фильтры ничего не подошло» + сброс. **Отличать от «данных нет»** — иначе староста решит, что статистика сломалась |
| `sorted` / `filtered` | применены сортировка или фильтр | `aria-sort` на колонке, видимый и **текстовый** признак активного фильтра. Признак активного фильтра живёт **в доступном имени кнопки-триггера колонки** — иначе с клавиатуры состояние фильтра не читается |
| `subject-not-selected` | во втором блоке предмет не выбран | таблица не строится, типы занятий disabled |
| `error` | агрегат не пришёл | `ErrorState` + повтор; **остальные блоки продолжают работать** |
| `forbidden` | нет права на статистику | блок не рендерится — конкретика после согласования прав |

### `AttendanceTrendChart`

| Состояние | Условие | Что показываем |
|---|---|---|
| `empty-series` | точек нет | «динамики пока нет» — **не пустые оси** |
| `partial-series` | одна серия не пришла | **вторая рисуется**, упавшая заменяется пояснением (§6.2 реестра) |

### Счётчики и разбивка причин

`loading` / `error` / **нулевые значения как валидный результат** в начале семестра — не пустота и не сбой.

### `StatsDetailPanel`

| Состояние | Условие | Что показываем |
|---|---|---|
| `idle` | строка не выбрана | панель не занимает место либо показывает подсказку «выберите студента» |
| `loading` | грузится детализация | скелетон в панели, таблица остаётся доступной |
| `success` | данные есть | детализация + видимая связь с выбранной строкой |
| `error` | не пришло | ошибка **внутри панели**, таблица не страдает |

**Ключевое:** панель **не модальная** (заметка 2 job). Значит основной контент остаётся доступен, фокус в панели **не запирается**, а закрытие не обязано быть единственным выходом.

### Общие

- `offline` — просмотр по кэшу с пометкой об устаревании, выгрузка блокируется.
- `forbidden` — `student` без `is_headman` при прямом заходе по адресу.
- Все четыре блока грузятся и падают **независимо** (§6.2 реестра).

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| Заголовок колонки — подпись-кнопка | сортировка; приоритеты накапливаются в порядке кликов (правило реестра), `aria-sort`. **Отдельный контрол**, фильтр не открывает |
| `TableColumnFilter` — кнопка рядом с подписью | открывает `Popover` с отбором по колонке; активный фильтр помечен видимо **и текстом**. **Второй контрол того же `<th>`** |
| Строка студента | открывает `StatsDetailPanel` для этого студента |
| `RowDetailTrigger` (стрелка) | то же действие, **явный видимый аффорданс** |
| `SubjectFilter` + типы | пересобирают вторую таблицу; недоступные типы disabled с пояснением, не скрыты |
| `Tabs` | смена разреза; в режиме «неделя по дням» появляется `DatePager`, в режиме «по предмету» — фильтр предмета |
| Точка на графике | подсказка с данными точки — **по наведению и по фокусу с клавиатуры** |
| `ExportButton` ×3 | выгрузка своего блока со всеми активными фильтрами |

### Про триггер детальной панели — рекомендация

Владелец оставил выбор за UX. Предлагаю **оба способа одновременно**, и это не компромисс, а требование доступности:

- **Кнопка-стрелка в конце строки** — основной механизм: у неё есть доступное имя («Подробнее о ‹ФИО›»), она попадает в порядок табуляции и работает с клавиатуры.
- **Клик по строке целиком** — дополнительный способ для мыши, увеличивает область попадания.

Почему не «только строка»: `<tr>` нельзя сделать кнопкой, не сломав семантику таблицы. Строка-кнопка либо выпадает из клавиатурной навигации, либо требует навешивания роли, которая конфликтует с `row`. Кнопка в ячейке решает это чисто. Обратное («только стрелка») тоже хуже: на широкой таблице попасть в маленькую стрелку сложнее, чем в строку.

### Нехватка прав

Неавторизованный → вход с возвратом. Без `is_headman` → `ForbiddenState` без утечки данных группы. Помощник — предположительно по `view_stats`; конкретика после согласования прав (владелец: разбираемся после фронта).

### A11y (структурно)

- `h1` «Статистика — ‹код группы›»; `h2` на каждую из четырёх секций; уровни без пропусков.
- Таблицы — настоящие `<table>`: `<th scope="col">` в шапке, ФИО — `<th scope="row">`. Шапка и первый столбец фиксируются при скролле (заметка 4 макета), **не выпадая из порядка табуляции**.
- Сортировка — `aria-sort`; перестроение объявляется через `role="status"`, иначе после клика таблица меняется молча.
- `TableColumnFilter` — `Popover` из реестра: ловушка фокуса, Esc, **возврат фокуса на кнопку-триггер фильтра**, а не на заголовок колонки.
- В `<th>` фильтруемой колонки **два контрола с разными доступными именами**: подпись-кнопка сортирует, кнопка рядом открывает фильтр. Слитый в один контрол заголовок делает одно из двух действий недостижимым.
- **График не может быть единственным носителем информации** — `ChartDataTable` обязателен (A11Y_REQUIREMENTS, реестр).
- Две линии различаются **подписями**, не только цветом; точки доступны с клавиатуры.
- Плавное перетекание графика (заметка 5) уважает `prefers-reduced-motion`.
- Числа в плитках сопровождаются текстовой подписью периода («за семестр»), иначе «42» без контекста.
- `StatsDetailPanel` — `role="region"` с `aria-label`; появление объявляется через `role="status"`; фокус переводится в панель, но **не запирается** — она не модальная.
- Разбивка причин — список определений («тип → количество»), не таблица из div'ов.

## 7. Заметки на будущее

### Адаптив

Три широкие таблицы плюс график. Заметка 4 макета требует **общий вертикальный скролл страницы** (таблицы не скроллятся внутри себя, в отличие от панелей на ПК-111), горизонтальный — только если не влезает, и тогда ФИО и шапка фиксированы.

- **Первый кандидат на схлопывание:** колонка «способ получения "+"» с четырьмя подзначениями — уходит в подсказку или в `StatsDetailPanel`.
- **Второй:** блоки тикетов с тремя подзначениями каждый.
- **Нельзя потерять:** пару метрик `%+` и `%(+ и у)` рядом — это смысловое ядро экрана; фиксацию ФИО и шапки; `ChartDataTable`.

### Мобильная поверхность (не сейчас, отдельный цикл)

Таблица «студенты × метрики» на телефон не переносится. Мобильный аналог — список студентов с одной метрикой и переходом в карточку; `StatsDetailPanel` там станет отдельным экраном.

### Конфликты с уже разобранным

- **Решение о двух метриках задевает 101, 102, 103 студента.** Там показатели описаны без пары `%+` / `%(+ и у)`. При финальной сборке файлы студенческих экранов нужно синхронизировать — это не переделка структуры, а добавление второй величины рядом с первой.
- **ПК-112** — способ получения «+» (4.5) требует того же поля `source`, что и журнал, плюс происхождение заявки. Требования усиливают друг друга, не конфликтуют.
