## Findings

**BR-T01 — P2, слабая проверка точной чужой карточки.** Python runner:336, related :300/:328/:384. Первый `/start` создаёт foreign card A в foreign chat. После rebind второй `/start` создаёт foreign card B в own chat с тем же unchanged initial marker. `provider.contains(foreign_marker)` ищет marker среди всех карточек. Ошибочное удаление требуемой новой B всё ещё удовлетворяет проверку, потому что A остаётся в другом chat. Требование T002 — сохранить новую чужую карточку в том же chat — так не доказано. Независимый безопасный dictionary counterexample реально выполнен: после удаления только новой tuple global contains=true, exact new key=false. Это доказательство слабого oracle, не установленное неверное удаление продуктом и не native runtime failure. Нужно сохранить точную новую `(chat_id, message_id)` и полный text, проверить ту же карточку/text после reset cleanup и recovery, различать старую карточку; контролируемое удаление новой foreign card должно падать на этом exact-card assertion.

**BR-G01 — P2, дочерние процессы наследуют полный parent environment.** Java IT:177 и :395, Python runner:219. `ProcessBuilder.environment()` сохраняет весь parent env; удаляются лишь два NP01 поля. Нужен минимальный явный OS/runtime environment и только собственные NP01 synthetic mappings для supervisor/worker; проверить также keytool process. Это статический source counterexample. Значения настоящего environment/credentials не читались; actual leak не заявляется.

**BR-G02 — P2, timeout cleanup убивает supervisor до reap worker.** Java IT:403–408. Код force-kills descendants, немедленно force-kills supervisor и лишь затем ждёт parent/descendant `onExit`. При 180s timeout supervisor может не успеть собрать killed worker; под unreaping PID1 возможен orphan zombie, а wait/onExit может не доказать отсутствие PID. Нормальный Python `stop_worker` содержит kill+wait и этого finding не вызывает. На failure path нужно завершить и дождаться descendants, пока жив supervisor, который их reap-ит, затем завершить и дождаться самого supervisor; неисправность cleanup остаётся явным bounded failure. Это статический failure-flow counterexample. Процессы и сигналы не запускались; observed orphan не заявляется.

**BR-R01 — P2, нет требуемого explicit loopback binding каждого mapped port.** Java IT:107–113. PG/Rabbit/Redis используют default Testcontainers exposed/mapped ports без HostIp=127.0.0.1 binding. `getHost()==localhost` задаёт адрес подключения, а не ограничивает host exposure. Стандартный empty Docker HostIp mapping может bind-ить все interfaces, включая unauthenticated Redis. План обещает ephemeral loopback для всех mapped ports. До launch нужны explicit ephemeral 127.0.0.1 bindings для каждого фактически exposed PG/Rabbit AMQP+management/Redis port либо доказанная эквивалентная confinement; actual inspect после отдельного grant.
