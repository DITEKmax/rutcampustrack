## Open questions (требуют ответа от пользователя)

### Высокий приоритет (блокируют разработку)

1. **Где именно вертикальное название предмета?** Подтвердить, что оно в
   заголовке подколонки сверху (под датой дня), а не внутри клетки

2. **Разовые пары (`one_off_lessons`)** — включаются в отчёт на тех же
   правах что обычные?

3. **Несколько пар по одному предмету в день** — каждая отдельной
   подколонкой (например, две колонки «Математика» в одну среду)?
   По умолчанию — да, каждая пара отдельно.

4. **>5 пар в день в реальности** — возможно ли это в принципе у вашей
   группы? Если да, что делать (предлагается: 422 с ошибкой). Если
   расписание ограничено 5 — снимаем риск.

5. **>35 студентов в группе** — возможно ли? То же решение (422).

6. **Имя файла** — предлагается
   `понедельный-{group_name}-{дата_начала_недели}.docx`
   (например `понедельный-УВПв-511-27.04.2026.docx`).

### Средний приоритет

7. **Слияние нескольких недель в один файл — формат:**
   - **(δ) ZIP** с N файлами — проще всего технически.
   - **(ε) Один многостраничный docx** — UX лучше, разработка сложнее
     (нужен docx-merger, не входит в docxtemplater из коробки).
   - **(ζ) Только одна неделя, без слияния** — уход от вопроса.
   Рекомендация — **δ (ZIP)** для первой версии, ε как улучшение позже.

8. **Курс группы** — это вычисляется из `group_name` (например
   `УВПв-511` → 5-й курс по первой цифре)? Или хранится отдельным полем?
   В академик-сервисе явного поля `course_number` нет, нужен парсер.

9. **Семестр в шапке** — число (`1` / `2`) или название
   («Весенний 2025/2026»)?

10. **Дата вверху всего документа** (если она вообще есть отдельная,
    не путать с датами колонок) — что туда ставится: дата генерации,
    дата начала недели, дата подписания?

### Низкий приоритет (можно решить в процессе)

11. **Библиотека для генерации `.docx` на JVM:**
    - **Apache POI XWPF** — стандарт, тяжёлый, шаблонизация ручная.
    - **docx4j** — мощнее POI, более удобный API для шаблонов.
    - **JOOXML / kotlinx-docx** — нишевые.
    - **Velocity/Freemarker + ZIP-замена** — самопис, не рекомендуется.

    Для шаблонизации лучше всего работает паттерн «открыть docx как ZIP,
    подменить XML внутри» — это и есть основа всех Java-библиотек.
    docxtemplater из node.js не подходит (мы на JVM). Эквивалент
    на JVM — **`docx-stamper`** (https://github.com/thombergs/docx-stamper) —
    тонкая обёртка над docx4j с MVEL-плейсхолдерами в стиле
    `${student.lastName}`. Хороший кандидат.

### Риски

- **Дата перевода студента** в БД явно не хранится. Проверка
  «зачёркивать ли фамилию» требует доступа к истории. Вариант обхода:
  смотреть на самый ранний `attendance_record` для пары в этой группе —
  если для студента нет ни одной отметки до даты X, значит его не было.
  Грубо, но работает для первой версии.

- **Шаблон со слиянием ячеек** в docx — болезненная штука.
  `colspan`/`rowspan` в Word устроен через `gridSpan`/`vMerge`, и любая
  ошибка в шаблоне → сломанный файл. Нужно тестировать на реальном
  Word, а не только на LibreOffice.

- **Локали в docx** — Word на Windows может по-разному рендерить
  кириллический шрифт по сравнению с LibreOffice. Тест на обоих.

- **Альбомная ориентация + таблица 6 столбцов × 5 подколонок** = 30
  колонок с очень узкими ячейками. Если шрифт по умолчанию — переполнение.
  Шаблон уже это решает (в эталоне 8pt примерно), просто помним.
