# Vue Frontend Build

Реализация нового Vue-фронта RutCampusTrack из Figma-макетов. Компонентная архитектура со строгим владением стилями, адаптив, типизированная интеграция с бэком.

> Контекст: бэкенд — Spring Boot микросервисы через API Gateway (`/api/{service}/...`), ошибки в формате RFC 9457 Problem Details, роли student/headman/teacher/admin, есть openapi-контракты. Существующие фронты: web-panel (Angular), pwa/mini-app (React) — новый фронт на **Vue**, стеки не смешивать.

## Core Principle — владение стилями

Каждый визуальный стиль живёт **внутри** компонента. Внешний код (страницы/роуты) НЕ передаёт косметические оверрайды (`style`, `class` для внешнего вида, CSS-объекты).

Снаружи допустимо только:
- **семантические пропы:** `variant`, `size`, `tone`, `state`, `disabled`, `fullWidth` — доменные режимы;
- **layout через wrapper-компоненты:** direction, gap, padding-как-ритм-раскладки, alignment, grid/flex, позиционирование.

Правило: если стиль описывает, **как компонент выглядит** — внутрь компонента. Если только **как он размещён** среди других — наружу, в layout-wrapper.

Почему: это ровно та боль, которую в чате называли главной («стили хардкодятся снаружи поверх внутренних → каша», «прототип → в коде вермишель»). Строгое владение стилями её убирает.

## Плохие практики (цели рефактора/чего не делать)

- Передача `style`/`class`/inline-CSS для изменения внешнего вида компонента.
- Разделение визуала между компонентом и местом вызова.
- Wrapper переопределяет padding/color/border/background/radius/typography ребёнка.
- Компонент как «недоделанная база», финальный вид которой собирают на месте вызова.
- Пропы-зеркала CSS (`padding`, `background`, `borderRadius`) вместо семантических вариантов.

## Целевая архитектура

- Компоненты с семантическим API (`variant`/`size`/`tone`/`state`), самодостаточные визуально (свои surface/padding/radius/typography/state-стили).
- Layout-wrapper'ы только для размещения (direction/gap/align/grid).
- Плоский `src/components/` для переиспользуемых компонентов. Страницы/роуты/views — слои композиции, собираемые из `components/`. Не держи локальные для страницы компоненты, если их можно переиспользовать.
- Единый дизайн-токен/тема (цвета/типографика/spacing-scale) — из Figma, в одном месте (CSS vars / Vue-плагин темы), не разбросанно.

## Vue-специфика

- Composition API (`<script setup>`), TypeScript.
- Стили компонента — `<style scoped>` внутри `.vue`, привязка к токенам темы, не к магическим значениям.
- Пропы типизированы; семантические варианты через union-типы, не через прокидывание классов.
- Состояния (loading/empty/error/success) — как явные ветки в компоненте, не «забытые».

## Интеграция с бэком (типобезопасно)

- Генерируй типы из openapi бэка (`openapi-typescript`) — как уже сделано для web-panel/pwa. Не пиши DTO руками.
- Запросы — через API Gateway (`/api/{service}/...`). Обрабатывай ошибки в формате **RFC 9457** (`application/problem+json`): показывай `title`/`detail`/`fieldErrors[]` пользователю осмысленно, а не «Error 500».
- Auth: HttpOnly cookie + refresh-lifecycle как на существующих фронтах. Не изобретай свой auth.
- Роли: экраны/действия зависят от роли (student/headman/teacher/admin) — enforce на UI, но помни, что настоящий authz на бэке (UI-скрытие ≠ безопасность).

## Адаптив

- Mobile-first. Реальные брейкпоинты из Figma.
- Отдельно проверь: тач-таргеты достаточного размера, читаемость, деструктивные действия («отменить пару», «удалить») требуют подтверждения, а не одного случайного тапа (у тебя есть студенты — user base с разной техграмотностью).
- PWA-контекст: offline/reconnect состояния, если экран завязан на live-данные (STOMP/WebSocket у notification).

## Workflow (по одному экрану/компоненту)

Работай последовательно: закончи и провалидируй один срез до следующего.

1. **Осмотри существующее.** Есть ли уже подходящий компонент в `components/`? Расширь его семантическим пропом вместо дубля. Прочитай Figma-спеку экрана и wireframe (из `screens-to-wireframe`).
2. **Открой целевой экран/компонент.** Раздели: внешний layout vs внутренний визуал.
3. **Визуал — внутрь компонентов.** Извлеки локальные для страницы компоненты в плоский `components/`. Каждый — самодостаточный визуальный юнит.
4. **Layout — наружу.** Wrapper'ы для direction/gap/padding/align. API wrapper'а — про раскладку, не косметику.
5. **Данные и состояния.** Подключи типизированный API, реализуй loading/empty/error/success, role-ветки.
6. **Сохрани поведение.** Не ломай бизнес-логику/права/роутинг. Доступность, состояния, адаптив — целы.
7. **Валидируй до перехода.** `npm run typecheck` / `vitest` / build / браузер-проверка затронутого. Упало — чини до следующего файла.

## Decision Rules

- В спорных случаях — более строгая граница компонента.
- Не оставляй временные механизмы оверрайда.
- Не держи локальный компонент страницы, если он используется даже раз, но переиспользуем.
- Не создавай новый компонент, если существующий можно чисто расширить.
- Не смешивай Vue с React/Angular-паттернами других фронтов.

## Per-file Report

После каждого файла/группы: что было не так; какой визуал ушёл внутрь компонентов; что осталось снаружи как layout; какие пропы добавлены/упрощены/удалены; какие локальные компоненты переехали в `components/`; почему чище; что провалидировано.

## Expected Result

Views/роуты — чистые слои композиции. Компоненты — предсказуемые, переиспользуемые, визуально самодостаточные. Никаких косметических style-pass-through, разбросанного хардкода стилей, сборки финального UI на месте вызова. Типы API — из openapi, ошибки — RFC 9457, роли — учтены.
