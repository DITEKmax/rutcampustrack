### Сверка со сканом

- **ЗЕЛЁНОЕ:** переключатель ролей «староста | студент», круг профиля, кнопка «скачать» под таблицей справа, а внутри красного блока — «Фильтр» и «Сбросить».
- **ЖЁЛТОЕ:** поповер профиля «Настройки / Выход» и **вся таблица состава группы**.
- **КРАСНОЕ:** блок раскрытия статистики по студенту — нарисован в поле заметок рядом с прим. 3, на самой странице появляется под строкой.
- **НЕ ОКРАШЕНО:** оба набора `MainNav`, иконки `˅` и `⋮` в конце строки.

Жёлтая таблица — **контент по умолчанию**, а не оверлей: жёлтым на этом скане помечены данные, приходящие после загрузки. То же прочтение применяется к 117–119.

**Не нарисовано, но следует из заметок:** `h1` и skip-link; содержимое меню `⋮` — пять пунктов (прим. 2); форма редактирования данных студента — по §0 чата 3 раскрывается **на странице**, не модалкой; подпись «пароль сгенерирован старостой» (прим. 2, job 3); сортировка списка — **всегда по алфавиту**, № — порядковый номер строки, а не идентификатор (прим. 2).

### Красный ≠ без взаимодействия

Блок раскрытия (**прим. 3**) отмечен красным, но:

- содержит два зелёных контрола — «Фильтр» и «Сбросить»;
- прим. 3 прямо ссылается на экран ПК-103, где у таблицы предметов есть сортировка по колонкам;
- сам блок появляется только по действию пользователя, то есть имеет собственные `loading` и `error`.

## 4. Потребности в данных

### 4.1 Состав группы

- **Нужно:** сущность «участник группы» с полями — идентификатор, ФИО, логин, telegram id либо признак «не привязан», признак старосты, признак помощника и перечень его прав, статус блокировки подачи тикетов на «н» и счётчик израсходованных попыток, признак наличия сгенерированного и ещё не сменённого пароля. Фильтров нет. Сортировка одна — **алфавит по ФИО**, задаётся сервером. Пагинации нет: группа 20–30 человек, отдаётся целиком.
- **Сейчас:** `GET /academic/groups/my/members` (STUDENT/HEADMAN) — базовый состав. `GET /academic/assistants` — помощники группы и их права.
- **Пробел** `[уточнение по контракту]`: входят ли в представление участника **логин** и **telegram id**. Без них две колонки из семи пустые, и экран нельзя сдать.
- **Пробел** `[предложение по бэкенду]`: признак помощника и его права должны приходить **в том же ответе**, что состав группы. Обходной путь — сшивать два списка по идентификатору на клиенте; при рассинхроне между запросами (помощника отозвали) таблица покажет права у человека, у которого их уже нет.

### 4.2 Пароль и восстановление доступа

- **Нужно:** операция «сбросить пароль студенту» с возвратом сгенерированного значения; операция «выдать ссылку сброса» с возвратом ссылки и срока жизни; в представлении участника — **происхождение текущего пароля** (`initial` — выдан при создании, `headman_reset` — сгенерирован старостой) и признак «сменён пользователем».
- **Сейчас:** ничего. `POST /auth/change-password` — про себя, не про третье лицо.
- **Пробел** `[нет API]`: обе операции отсутствуют (JS-HEADMAN-23). Обходного пути на клиенте не существует.
- **Пробел** `[предложение по бэкенду]`: **пароль отдаётся в списке участников и остаётся доступным, пока студент его не сменил** — подтверждено владельцем. Это осознанное расширение видимости, а не побочный эффект: подпись о происхождении обязательна (job 3), иначе староста передаст студенту пароль, о природе которого не знает. Факт сброса и факт показа пишутся в аудит.

### 4.3 Права помощника

- **Нужно:** каталог прав с **человекочитаемыми подписями** (job 4) + текущий набор по каждому помощнику; операции «назначить», «обновить набор», «отозвать».
- **Сейчас:** `GET/POST/DELETE /academic/assistants`, `PATCH /academic/assistants/{id}/permissions` — операции покрывают сценарий.
- **Пробел** `[предложение по бэкенду]`: **каталог прав приходит как данные**. Коды (`mark_attendance`, `manage_excuses`, `manage_homework`, `cancel_lessons`, `view_stats`) фронт не подписывает сам — то же правило, что для типов уважительных причин и форматов выгрузки. Иначе добавление права требует релиза фронта.
- **Пробел** `[вопрос к бэкенду]`: может ли **помощник** управлять помощниками. Конкретный набор прав не согласован и вынесен в отдельную сессию — не додумывается.

### 4.4 Блокировка подачи тикетов на «н»

- **Нужно:** по каждому студенту — израсходованные попытки захвата пары, лимит семестра, флаг блокировки; операция снятия блокировки.
- **Сейчас:** ничего.
- **Пробел** `[нет API]`: ни счётчика, ни флага, ни операции снятия (JS-HEADMAN-24, чат 3). **Без этого колонка пустая, и экран врёт:** староста не увидит, что студент заблокирован, и не поймёт, почему тот перестал подавать тикеты. Вычислить на клиенте невозможно — данные о захватах нигде не публикуются.

### 4.5 Детализация по студенту (раскрытие строки)

- **Нужно:** агрегаты **по конкретному студенту, запрошенные старостой**: `%+`, `%(+ и у)`, `%н`, `%у` и те же величины в количествах, позиция в рейтинге группы, разбивка по предметам (строки — предметы, колонки — те же метрики). Фильтр по предметам и сортировка — серверные, пагинации нет.
- **Сейчас:** `GET /attendance/reports/student/stats` и `GET /attendance/reports/student/records` работают по текущему пользователю (`X-User-Id`).
- **Пробел** `[предложение по бэкенду]`: тем же агрегатам нужен параметр «студент» с проверкой, что запрашивающий — староста или помощник **его** группы. Это **тот же агрегат**, что нужен `StatsDetailPanel` на ПК-113 — в `backend-requests.md` идёт одним пунктом с двумя потребителями.
- **Пробел** `[уточнение по контракту]`: возвращает ли агрегат позицию в рейтинге. Отдельный запрос ради одного числа на каждое раскрытие строки — прямой N+1.

### 4.6 Выгрузка состава группы

- **Нужно:** файл со списком группы в выбранном формате; перечень форматов и шаблоны — на сервере (job 1).
- **Сейчас:** отчёты существуют только по посещаемости: `GET /attendance/reports/headman-weekly/current`, `POST /attendance/reports/headman-weekly/export`, `GET /attendance/reports/journal`.
- **Пробел** `[предложение по бэкенду]`: выгрузка **состава группы** как отдельный отчёт. Клиент собрать не может — шаблоны живут на бэкенде. Это **четвёртая точка выгрузки** роли (JS-HEADMAN-19 знал о пяти на 112–113, перечень расширяется).

### 4.7 Редактирование данных студента

- **Нужно:** перечень полей, которые староста вправе менять, и операция обновления в этих границах.
- **Сейчас:** `PUT /academic/users/{id}` и `PATCH /academic/users/{id}` помечены **ADMIN**.
- **Пробел** `[вопрос к бэкенду]`: прим. 2 даёт старосте правку данных студента, API — нет (зафиксировано в §9 реестра ещё в чате 4). До решения пункт меню рисуется, но помечен как неподтверждённый. **Активная кнопка, на которую сервер отвечает отказом, — тот же дефект, что зафиксирован на дз в чате 4**; допускать его второй раз нельзя.

### ⚠️ Фактура к решению о транспорте

| Что | Оценка |
|---|---|
| Запросов на входе в экран | **2–3**: состав группы + помощники с правами + (возможно) каталог подписей прав. Все три обязаны быть одним ответом |
| N+1 | **по раскрытиям строк**: каждое раскрытие — отдельный запрос за агрегатом студента, плюс потенциально второй за позицией в рейтинге. Ленивая загрузка здесь оправдана (30 агрегатов вперёд грузить хуже), но при выгрузке «скачать» тот же набор считается сервером заново |
| Over-fetching | `GET /academic/assistants` отдаёт полные записи помощников, тогда как строке таблицы нужен один флаг и массив кодов |
| Не существует вовсе | **три блока из шести**: пароли, блокировка захватов, выгрузка состава. Ещё один существует, но не для этой роли (агрегат по студенту) |

## 5. Состояния

**На бумаге не нарисовано ни одного состояния** — на скане только `success` с заполненной таблицей. Всё, что ниже, добавлено при разборе.

### Автомат ячейки «Пароль» (`InitialPasswordCell`)

| Состояние | Условие | Что показываем |
|---|---|---|
| `initial` | пароль сгенерирован системой при создании учётной записи, не сменён | значение + подпись «выдан при создании» + копирование |
| `generated` | пароль сгенерирован **старостой** при сбросе, студент ещё не менял | значение + **обязательная подпись «сгенерирован старостой»** (job 3) + копирование |
| `changed` | студент сменил пароль сам | текст «пароль сменён студентом». **Не пустое `disabled`-поле:** заблокированный инпут обещает редактирование, которого нет (§6.2 реестра) |
| `pending` | выполняется сброс | `aria-busy`, пункты меню, меняющие пароль, заблокированы |
| `error` | сброс не прошёл | текст ошибки в строке; **предыдущее значение не затирается** |

**Различение `initial` и `generated` критично: без него староста передаёт студенту пароль, о происхождении которого не знает** — ровно то, что job 3 требует подписать явно.

### Остальные блоки

- **Таблица:** `loading` (скелетон строк), `empty` (в группе нет студентов — вырожденный, но реальный случай для только что созданной группы), `error` с повтором. `filtered-empty` **не применим** — фильтров у основной таблицы нет (подтверждено `table-filters.md` §4: перенос фильтров в колонки основной таблицы не касается).
- **Раскрытая строка грузится и падает независимо:** ошибка агрегата по одному студенту не роняет таблицу, вторая раскрытая строка продолжает работать.
- **`StatsBySubjectTable` внутри детализации** имеет собственные `empty` («у студента ещё не было пар») и `filtered-empty` («фильтр не оставил предметов»). Тексты обязаны различаться — правило §6.2.
- **`ExportButton`:** `busy` на время сборки файла, `error` отдельным сообщением, успех — доступная ссылка на готовый файл.

### Общие

- `offline` — таблица показывается с пометкой, что данные могут быть устаревшими; **все действия строки блокируются**. Сброс пароля вслепую недопустим: староста не увидит результат и продиктует студенту несуществующее значение.
- `no-active-semester` — таблица состава **рендерится** (состав группы не про семестр), а детализация и выгрузка показывают пояснение, а не нули.
- `forbidden` — экран целиком для роли без прав.

### По ролям

| Кто | Что видит и может |
|---|---|
| **Староста** | всё |
| **Помощник с соответствующим правом** | таблица и те действия, которые покрыты его правами |
| **Помощник без права на действие** | пункт меню **виден и заблокирован**, с пояснением, кто может выполнить (§0 чат 4) |
| **Помощник без права на блок данных** | колонки «Пароль» и блок детализации **не рендерятся вовсе** — это учётные и персональные данные, видимость чужих данных это утечка |
| **student / teacher / admin** | `forbidden` без утечки состава группы |

**Привязка конкретных прав к колонкам этого экрана — вопрос выделенной сессии, здесь не додумывается.** Фиксирую лишь наблюдение: «Пароль» и «Блокировка» — самые чувствительные колонки из всего, что разобрано в роли старосты; при согласовании прав начинать стоит с них.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| Строка целиком / `DetailTrigger` `˅` | Раскрывает `StatsDetailPanel variant="row"` под строкой. `aria-expanded` на стрелке, ленивая загрузка данных, повторное нажатие сворачивает. **Оптимистичного UI нет** — данных на клиенте ещё не существует |
| `⋮` → «Дать разрешения» | Раскрывает `PermissionList editable` в строке. Сохранение по кнопке формы, **без `ConfirmDialog`** — действие обратимо |
| `⋮` → «Забрать разрешения» | **`ConfirmDialog`.** Помощник немедленно теряет доступ к ведению группы — деструктивно |
| `⋮` → «Сбросить пароль» | **`ConfirmDialog`** с явным предупреждением: старый пароль перестаёт работать, активные сессии студента гасятся. **Оптимистичного UI нет** — значение приходит только с сервера. Результат попадает в колонку «Пароль» и **остаётся там до смены студентом** |
| `⋮` → «Сгенерировать ссылку сброса» | Раскрывает `RecoveryLinkPanel` со ссылкой, сроком жизни и копированием. Подтверждения не требует — доступ не отзывается |
| `⋮` → «Редактировать данные» | Раскрывает `StudentProfileEditForm` на странице. ⚠️ Доступность пункта зависит от решения по §4.7; до решения — помечен как неподтверждённый |
| «Сбросить» в колонке «Блокировка» | Снимает блокировку подачи тикетов на «н». **Без подтверждения:** действие в пользу студента и обратимо — повторный захват снова израсходует попытки. Оптимистичное обновление счётчика с откатом при ошибке |
| `ExportButton` «скачать» | Собирает файл в выбранном формате по текущему составу. `busy` на время сборки, результат — ссылка на готовый файл |
| Фильтры в заголовках колонок / «Сбросить» в детализации | Фильтрация таблицы предметов идёт **по заголовкам колонок**; «Сбросить» снимает фильтры **по всей таблице разом**. Выполняется **на сервере** вместе с сортировкой |
| `MainNav` | Переходы по разделам и управлению |
| `RoleSwitcher` → «студент» | Переключение на базовую роль; экран недоступен, уход на ПК-101 |

### Нехватка прав

- **Неавторизованный** — редирект на ПК-001 с сохранением адреса возврата.
- **Авторизован, роль не headman** — `ForbiddenState` с пояснением, **без утечки состава группы**.
- **Помощник** — по принципу §0 чата 4: действие без права видно и заблокировано с пояснением; блок данных без права не рендерится.

### A11y (структурно)

- Один `h1` «Группа». Skip-link на `#main`. Два `<nav>` с разными `aria-label` («разделы», «управление»).
- Таблица — настоящая `<table>`: `<th scope="col">` в шапке, ФИО — `<th scope="row">`. Grid из `div`-ов не допускается.
- **Раскрытие — отдельный `<tr>` с `colspan` сразу после строки студента**, а не абсолютно позиционированный блок: иначе порядок чтения разойдётся с визуальным.
- `<tr>` кнопкой не делаем — стрелка `DetailTrigger` обязательна как клавиатурный путь (правило чата 4); клик по строке остаётся дополнительным путём для мыши.
- Меню `⋮` — `<button aria-haspopup="menu">`, навигация стрелками внутри, Esc закрывает, фокус возвращается на триггер.
- Появление нового сгенерированного пароля объявляется через `role="status"`; ошибка сброса — `role="alert"` с переводом фокуса на сообщение.
- Роли в группе, права и статус блокировки передаются **текстом**, не цветом и не только иконкой.
- Тач-таргеты `˅` и `⋮` — не меньше 44×44 с достаточным зазором: они стоят вплотную друг к другу.
- Раскрытие и сворачивание строки уважают `prefers-reduced-motion`.
- Все состояния (`loading`, `empty`, `error`, `forbidden`, `offline`) озвучиваемы, а не только визуальны.
