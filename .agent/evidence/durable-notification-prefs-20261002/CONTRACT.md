# Durable notification preferences — frozen protocol proposal, S3

## Goal
Выключенная категория/mute переживают Redis eviction/restart. Неизвестные настройки откладывают уведомление; не превращаются в enabled или молчаливый drop. Canonical user prefs и Telegram-specific выбор сохраняют прежнюю область действия.

## Required behavior
**Authority/storage.** notification_db Mongo: `user_notification_preferences` `_id=userId` for canonical categories/mute; `telegram_notification_preferences` `_id="userId:telegramId"` with exact immutable positive IDs, globalEnabled/categories/mute; `notification_preference_legacy_bindings` `_id=telegramId` pins first adopted legacy Telegram source to userId. Original facet never reassigned/copied. New binding gets a new facet only after live binding validation and successful legacy lookup; marker owned by another user prevents reimport of that Telegram source and creates new-binding defaults. Canonical user prefs remain with user. Missing durable record requires successful reads of Redis `notif:prefs:user:{userId}` or exact Telegram legacy keys; Redis outage is unavailable, never missing. Existing durable document is authority and does not consult/replace from Redis. Lost/evicted legacy data cannot be reconstructed. Lazy bootstrap insert-if-absent (`$setOnInsert`) only; atomic field updates/toggles preserve unmentioned categories. Malformed legacy mute/known-field values are not silently adopted as an enabled default.

**Identity/transport.** Private GET and POST only `/internal/bot/notification-preferences/{userId}/{telegramId}`, both positive IDs. Bot resolves current Academic mapping before call; Notification revalidates both directions through existing GetUserByTelegramId and GetUserById, requires exact requested UID/TG pair for every read/update/delivery/replay. Stale/unbound mismatch cannot mutate another account or authorize delivery. No authority source fallback. Header `X-Bot-Preferences-Token`: dedicated BOT_TO_NOTIFICATION_SERVICE_TOKEN, same value only trusted Bot/Notification, canonical32byte unpadded base64url, constant-time comparison; missing/invalid token401. Exact-route user-filter exclusion is paired with mandatory controller service authentication; no Gateway guest route. Binding conflict409; authority/required legacy unavailable503; malformed command400.

GET optional `category` from six existing categories; without category returns settings snapshot (not an unclassified delivery permit). Response local canonical Java DTO `BotNotificationPreferencesDto`: userId, telegramId, globalEnabled, categories (Telegram facet), mutedUntil (facet), canonicalCategories, canonicalMutedUntil, eligible (for explicitly requested category; null for snapshot). Eligibility is facet-global AND canonical-category AND facet-category AND neither mute active. All maps contain six validated boolean fields; malformed response treated unavailable by typed Bot adapter. Unknown category is400, not bypass.

POST local canonical DTO `UpdateBotNotificationPreferencesRequest`: requestKey (1..128 ASCII alphanumeric/_/-/:), operation enum TOGGLE_GLOBAL, TOGGLE_CATEGORY, SET_GLOBAL, SET_CATEGORY, SET_MUTE, CLEAR_MUTE; category/ enabled/ mutedUntil only when applicable. One bounded field command, not whole-document replace. Bot callback.id supplies stable requestKey; HTTP retry repeats identical body. Mongo mutation receipt scoped to exact UID/TG/requestKey with SHA256 normalized command fingerprint, in same Mongo transaction as atomic facet mutation; repeat does not toggle again, different body conflicts409; replay rechecks binding. Receipt stores original result snapshot. No retention/session cleanup policy invented. Canonical public self-user GET/PUT transport unchanged; existing null-mutedUntil clears mute, category map updates only supplied known fields, one atomic DB update.

**Delivery/claims.** WebPush resolves applicable canonical preference eligibility in event transaction before WS/enqueue/claim commit; group/headman and user-scoped recipients keep existing authority/audience rules. Async receives admitted eligible user snapshot; it does not perform a new authority read after claim commit. Unknown throws transient error, rolls back claim and uses existing listener retry/durable DLQ (same event ID, no unknown-as-disabled filter). Bot dispatcher stages actual SendTasks in existing queue context; resolves all applicable preferences before flushing any staged task/consumer completion. Unavailable => discard staging only, release claim, delayed NACK/requeue retaining original event. Worker rechecks applicable preferences before actual send; unavailable retains/retries that task, never crashes/drop/task_done. Known disabled/muted suppresses by user choice. No new queue/framework/provider retry redesign.

System exception is explicit trusted classification/flag set ONLY by alert_fired producer; default SendTask requires preferences, generic(categoryNone,userIdNone) is NOT an exemption. OTP/password direct security paths retain existing behavior. Unclassified delivery task fails closed instead of silently sending. Six user categories require exact live binding. In-memory queued-task crash boundary and provider exactly-once remain unproven; existing broker/DLQ retention is unchanged, not declared infinite recovery.

## Constraints
No actual .env/secrets, Redis flush, production migration/deploy/rotation/push, provider calls, or dependency install. No heavy until root lease. Collections have no TTL for preferences; `_id` uniqueness and collection initialization outside first transaction follow existing Mongo startup pattern. Config examples have placeholders/synthetic dev defaults only, no generated secret. Token format reuses directed credential canonical32byte invariant. Do not mutate other component auth/report/schedule/recovery.

Existing system alert producer documents preference exemption; new explicit flag closes generic bypass ambiguity.

## Acceptance criteria
Real Mongo prefs persist after owned Redis synthetic clear/restart; known old choices imported once and never overwrite DB; needed Redis outage refuses defaults. Canonical/Telegram scope, stale/crossbinding rejection, marker rebind prevention, atomic distinct-field updates, concurrent toggles and requestKey replay/conflict. Mongo authority failure before event commit leaves claim retryable/no task flushed; retry admits once; worker outage retains task and resumes once. No bot fail-open/direct Redis canonical authority remains; explicit system alert exemption only. Current new-user defaults/category/mute semantics retained after confirmed missing legacy lookup.
