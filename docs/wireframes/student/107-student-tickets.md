# ПК-107 — Студент, Заявки и тикеты

> Этап 1, чат 3. Веб-десктоп 1920. Структура и логика, без визуала.
> Сканы: `ПК — 107 — СТРАНИЦА СТУДЕНТ — ЗАЯВКИ И ТИКЕТЫ` (1, 2) + отдельный скрин карточек.

## 1. Идентификация

| | |
|---|---|
| Название | ПК-107 Студент — Заявки и тикеты |
| Роли | student, headman (ролевых различий нет) |
| Поверхность | web-десктоп 1920 |
| Точка входа | `MainNav` → «заявки и тикеты». ⚠️ Сквозные входы с 101 и 102 по паре со статусом «н» — **не подтверждены**: решение отложено владельцем, переходы не вводим до подтверждения. Строка сохранена как заявка со стороны принимающего экрана |
| Цель | Подать тикет по набору пар, отслеживать рассмотрение, видеть решение старосты |

### Модель экрана

Два **типа тикета** и два **представления списка** — это разные оси:

| Ось | Значения |
|---|---|
| Тип тикета | тикет на «у» (уважительная причина + файлы) · тикет на «н» (оспаривание проставленного «н») |
| Представление | На рассмотрении (со счётчиком) · Архив (оба типа вперемешку, прим. 4) |

Тикет на «н» — это **пакетный late-checkin из прошедших пар**. Форма у него подмножество формы «у» (прим. 2: «часть тикета на "у"»).

**Решение владельца:** тикет — **неделимая единица**, одобряется или отклоняется целиком. Статусов по отдельным парам внутри тикета нет.

**Разграничение с 101** (§8.2 реестра): на 101 `LateCheckInButton` — быстрый одиночный путь по сегодняшней паре в одно нажатие; здесь — выбор нескольких прошедших пар. Лимит общий: по паре может существовать только одна **активная** заявка.

**Решение владельца:** форма **раскрывается на самой странице**, ничего поверх. `role="dialog"` и ловушка фокуса не нужны; нужны `aria-expanded` на кнопке подачи, перевод фокуса в первое поле при раскрытии и возврат на кнопку при сворачивании.

**Состав вкладок и память разреза.** Вкладки «На рассмотрении (N) / Архив» — это `Tabs`. Перечень вкладок, счётчик в подписи и память разреза (какой список открыт, его страница, фильтры и позиция) принадлежат **странице**, а не компоненту (K1). Счётчик — часть доступного имени вкладки, отдельного бейджа нет.

**Уточнено владельцем:** чекбоксы рядом с парами внутри карточек «на рассмотрении» и «архив» — остаток шаблона формы. В карточке пары показываются **простым списком**, чекбоксов там нет.

## 4. Потребности в данных

### 4.1 Форма подачи

**Нужно:**

1. **Типы причин** — перечень с сервера: `code`, `label`, `commentRequired`.
   Сейчас: решение §0 есть, эндпоинта в дайджесте нет → `[предложение по бэкенду]`.

2. **Пары выбранного диапазона с признаком доступности.** `Lesson` + поля: предмет, тип занятия, дата, время, статус пары, моя текущая отметка, **`canDispute`** (можно ли включить в тикет этого типа) и **`reason`** при отказе: уже есть активная заявка · пара отменена · пара ещё не прошла · уже стоит «у» · **«н» проставлен вручную старостой**.
   Фильтр — диапазон дат; сортировка — по дате и порядку пар в дне.
   Сейчас: `GET /schedule/groups/{groupId}/lessons` + `GET /attendance/reports/student/records`; данных о существующих тикетах нет. Клиент джойнит три источника **на каждое изменение диапазона**.
   → `[предложение по бэкенду]`: один ответ «пары диапазона, пригодные для тикета типа X» с готовым флагом и причиной. Иначе правило «одна активная заявка на пару» проверяется только на сервере, и студент узнаёт о запрете после отправки.

3. **Отправка тикета.**
   Сейчас: `POST /attendance/excuses` и `POST /attendance/excuses/with-file` — из дайджеста не видно, принимают ли они **список пар**. Тикет на скане — одна причина + один комментарий + один набор файлов на **набор** пар.
   Для типа «н»: `POST /attendance/late-checkin/{lessonId}` — строго по одной паре, атомарный тикет им **невыразим в принципе**.
   → `[предложение по бэкенду]`: тикет как агрегат «тип + причина + вложения + набор пар», одна операция, один результат.

4. **Антиспам** (прим. 4, уточнено владельцем): попытка захватить пару, где «н» проставлен вручную старостой, тратит одну из **3 попыток на семестр**; после исчерпания подача тикетов на «н» блокируется. Снимает блокировку староста отдельной кнопкой в управлении студентами группы (чат 4).
   → `[предложение по бэкенду]`: на пользователе — `attemptsUsed` / `attemptsLimit` и признак блокировки. Фронту это нужно **как данные**, а не как реакция на ошибку, иначе кнопка недоступна молча.

   Правило вывода права **не должно жить на клиенте**: источник отметки (`headman` / `teacher_override` → нельзя, `auto_scheduler` → можно) может пополниться, и две реализации разойдутся.

### 4.2 Списки тикетов

**Нужно:** `Ticket`: `number` (человекочитаемый), `createdAt`, `type` (`excused` / `absent`), `reason` + `comment` (только «у»), `attachments[]`, `dateFrom` / `dateTo`, `lessons[]` (предмет, тип занятия, дата), `status`, `decidedAt`, `decidedBy`, **`decisionComment` — причина отклонения**. Пагинация обязательна для архива, сортировка — новые сверху.

**Сейчас:** `GET /attendance/excuses/me`, `GET /attendance/excuses/{id}`. Личных заявок late-checkin нет вообще — есть только `GET /attendance/late-checkin/pending` и `.../group/{groupId}`, оба для старосты → `[нет API]`.

`[предложение по бэкенду]`:

- Единый список «мои тикеты» с фильтром `scope: pending | archive`, объединяющий обе сущности — прим. 4 требует именно объединённый архив, иначе фронт склеивает два списка с разной пагинацией.
- Отмена тикета студентом — операции нет (`PATCH /{id}/status` — сторона согласующего) → `[нет API]`.
- Причина отклонения в ответе — иначе студенту нечего показать, кроме слова «отклонено».
- Лёгкий счётчик тикетов на рассмотрении, по образцу `GET /notifications/unread-count` — нужен в подписи вкладки до загрузки списка.
- Человекочитаемый номер тикета: если это UUID, показывать его бессмысленно.
- Лимиты вложений (размер, форматы, количество) — с сервера, не зашиваются во фронт.

### 4.3 Фактура по транспорту

Худший из разобранных экранов:
- смена диапазона дат — **3 запроса** (расписание + отметки + существующие тикеты, последнего нет) + явный N+1 при склейке;
- подача «н» на 5 пар — **5 запросов** при текущем контракте;
- вход на экран — **2–3** (список + счётчик + справочник причин).

## 5. Состояния

На бумаге: только success формы и success двух списков. Остальное добавлено.

### Форма (`TicketForm`)

| Состояние | Что показываем |
|---|---|
| `idle` | форма свёрнута, видны только кнопки подачи |
| `loading` справочника причин | селект `disabled`, `aria-busy` |
| `empty` диапазона | «В выбранные даты пар нет» |
| все пары недоступны | пояснение + причина по каждой паре, отправка `disabled`. Текст **отличается** от «пар нет» (§6.2) |
| `future` | пара ещё не прошла: для «н» недоступна (оспаривать нечего), для «у» **доступна** (JS-STUDENT-05 разрешает заранее) |
| `error` подгрузки пар | `ErrorState` внутри блока + повтор, остальная форма живёт (§6.2) |
| валидация | не выбрано ни одной пары · «прочее» без комментария · диапазон вне границ семестра · файл не прошёл. Ошибки текстом через `aria-describedby`, не цветом |
| `submitting` | `aria-busy`, кнопка `busy`, повторная отправка заблокирована |
| `submit-error` | `FormError` с `title` / `detail` из RFC 9457, фокус на сообщение. **Введённое не теряется** |
| `blocked` | лимит попыток семестра исчерпан: кнопка «Подать тикет на "н"» недоступна **с пояснением**, а не молча |

### Файл (`FileUploadField`)

`empty` (не выбрано) → `selected` (имя, размер, превью для изображений, «Удалить вложение» с доступным именем, содержащим имя файла) → `uploading` (детерминированный прогресс + «Отменить загрузку», завершение через `role="status"`) → `success`.

Ошибки, различимые **текстом**: превышен размер (с указанием лимита) · формат не поддерживается (со списком допустимых) · сбой сети (с повтором) · сервер отклонил.

Ограничения показываются **до** выбора, по образцу `PasswordPolicyHint`.

Решение владельца: файлы **хранятся на нашей стороне**, закладывается просмотр вложения (`AttachmentList`). JS-STUDENT-WEB-07 («через бота без хранения у нас») устарел.

### Статусы, которые видит студент

на рассмотрении · одобрен · отклонён (+ причина отклонения, если пришла) · отменён мной.
Для тикета «н» причины пропуска нет по определению — поле не рендерится.

**Отклонение НЕ окончательно** (решение владельца, чат 3): после отклонения или отмены пара снова доступна для подачи. Это должно быть понятно из карточки, иначе студент не будет искать повторный путь.

### Сквозное состояние `pending`

Прим. 3: «во всей системе у студента отображается, что на эти пары что-то подано». В реестре это `pending` (§6.1) — на 101 и 102 такие пары показываются неактивными с подсказкой. Источник признака — тикет, и он должен приходить **в представлении пары**, а не догоняться отдельным запросом.

## Решения задачи 4 — внесено 01.08.2026

Источник — `02-backend/backend-conflicts.md`. Правила ниже имеют приоритет над более ранними формулировками этой спеки.

**Два механизма разведены (Р-2)** — раньше они смешивались:

1. **Автоматический запрос старосте** — порождается системой в момент неудачной геоотметки во время пары. Отдельного действия студента нет, **лимитом не ограничен, не истекает**.
2. **Прошение о замене «н» на «+» по прошедшей паре** — ручное действие студента, **ограничено пятью парами за семестр**, подаётся по одной паре, попытка расходуется **в момент подачи**.

- **Отклонение прошения пару не закрывает:** подать по ней заново можно, но повторная подача расходует ещё одну попытку. Механизм ограничивает себя сам — пять отказов, и попытки кончились.
- **Остаток попыток показывается до подачи**, а не сообщением об отказе после.
- **Староста может увеличить лимит студенту** (операция на 116, пишется в аудит).
- **Тикеты на «у» лимитом не ограничены.**
- **Решение по тикету необратимо:** «Изменить решение» не проектируется, староста перепроставляет отметки вручную.
