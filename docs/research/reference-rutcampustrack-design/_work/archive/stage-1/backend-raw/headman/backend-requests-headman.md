# backend-requests — роль headman (ПК-111 … ПК-115)

> Этап 1, чат 4. Сводка всех пометок `[нет API]`, `[предложение по бэкенду]`,
> `[уточнение по контракту]` и `[вопрос к бэкенду]` по пяти экранам роли старосты.
> Дубли между экранами сведены в один пункт с перечнем потребителей.
>
> Транспортно-нейтрально: сначала ЧТО нужно, потом где это лежит сейчас.
> Бэкенд не заморожен — это вход для бэкенд-задач, а не обход существующего API.

## Как читать приоритет

| Уровень | Что означает |
|---|---|
| 🔴 **блокирующее** | экран нельзя реализовать или он будет показывать неправду |
| 🟠 **высокое** | экран реализуем, но с потерей смысла или тяжёлым обходом |
| 🟡 **среднее** | уточнение контракта: возможно, поле уже есть |
| ⚪ **информационно** | фиксация того, что фронтом не используется |

**Три архитектурные темы, проходящие через несколько экранов:**

1. **Аудит-подсистема** — журнал по паре (111) и история дз (114) — один механизм на двух сущностях.
2. **Инкрементальный расчёт агрегатов** — счётчики (113) и падение выгрузок (112) — одна задача.
3. **Эффективные права пользователя** — нужны всем пяти экранам.

## 🔴 Блокирующее

### 1. Сетка журнала должна быть по **парам**, а не по датам
`[предложение по бэкенду]` · **112** · подтверждено владельцем

- **Нужно:** «студенты × пары» с двухуровневой группировкой колонок: дата → пары внутри даты.
- **Сейчас:** `GET /attendance/reports/journal` — «Journal grid (students × dates)».
- **Почему блокирующее:** в дне у группы 2–4 пары со **разными** статусами. Одноуровневая сетка по датам физически не может их нести.
- **Колонка:** дата, день недели, номер пары в дне, предмет, тип занятия, статус пары, происхождение, аудитория.
- **Ячейка:** статус отметки, `source`, время отметки, ссылка на тикет для «у».

### 2. Право править дз — по праву публикации, а не по авторству
`[предложение по бэкенду]` · **114** · подтверждено владельцем

- **Сейчас:** `PUT` и `DELETE /academic/homeworks/{id}` — «HEADMAN, **только автор**».
- **Нужно:** доступ определяется правом публиковать дз в группе (`manage_homework` либо роль старосты).
- **Почему блокирующее:** у группы несколько авторов (староста + помощники). При текущем правиле помощник видит активные кнопки и получает отказ сервера.
- **Уточнить:** распространяется ли снятие на `DELETE` — применено по аналогии.

### 3. Источник отметки (`source`)
`[уточнение по контракту]` · **111, 112, 113** · три потребителя

- **Нужно:** `source` (`student_geo` / `headman` / `auto_scheduler` / `teacher_override` / `late_checkin`), время отметки, кто изменил.
- **Почему блокирующее:** после закрытия пары журнал автоматически заполняется `н` (JS-SYSTEM-07). Без источника **староста не отличит автопростановку от собственного решения** — экран врёт. Заметка 2 скана 112 формулирует это прямо.

### 4. Полнота представления пары
`[уточнение по контракту]` · **111, 112** · подтверждено владельцем («да, я бы добавлял»)

- **Нужно:** статус (`planned` / `active` / `closed` / `cancelled`), **признак блокировки старостой**, **признак гео-блокировки**, происхождение (`regular` / `one-off` / **перенос**), номер пары в дне, аудитория — в том числе **внутри ответа журнала**, а не только в расписании.
- **Почему блокирующее:** без статуса нельзя выбрать текущую пару для счётчиков, объяснить автоматические `н`, отличить будущую пару от неотмеченной (в будущей ячейке кружков быть не должно) и выделить отменённые и перенесённые.

### 5. Эффективные права текущего пользователя
`[предложение по бэкенду]` · **все пять экранов** · продолжение JS-SYSTEM-14

- **Нужно:** в профиле/сессии — эффективный набор прав: сам староста или помощник с подмножеством (`mark_attendance`, `manage_excuses`, `manage_homework`, `cancel_lessons`, `view_stats`).
- **Сейчас:** `GET /academic/assistants` отдаёт список помощников группы, а не «мои права».
- **Почему блокирующее:** фронт вынужден тянуть список помощников и искать себя — **а помощник может не иметь права его читать**. Без эффективных прав экран покажет либо лишнее, либо ничего.

### 6. `blockage` против `geo-block` — два механизма с пересекающимся смыслом
`[уточнение по контракту]` · **111** · требует решения **до Figma**

- **Сейчас:** `POST` / `DELETE /schedule/lessons/{id}/blockage` (HEADMAN) и `PATCH /schedule/lessons/{id}/geo-block` (HEADMAN/ADMIN).
- **Вопрос:** одно и то же или разное? Если одно — вывести один из обихода; если разное — нужны раздельные термины и контролы.
- **Почему важно:** два независимых флага дают четыре комбинации, две из которых бессмысленны. До ответа проектируется один переключатель на базе `blockage`.

## 🟠 Высокое — attendance-service

### 7. Журнал действий по паре — **отсутствующая подсистема**
`[нет API]` · **111**

- **Нужно:** хронология событий по `lessonId` с подгрузкой и сортировкой по времени: попытки геоотметки (вердикт + **расстояние от центра допустимого радиуса**), автопростановка `н`, подача и решение тикетов, ручные действия старосты.

- **Почему нельзя обойти:** данных не существует — это не агрегация имеющегося. Историю нельзя восстановить из финального состояния.
- **Примечание владельца:** допускается отдельный сервис под бизнес-лог.

### 8. Результат геопроверки должен сохраняться

- **Сейчас:** проверка выполняется (`POST /attendance/checkin`), исход в пригодном для показа виде не сохраняется.

### 9. Агрегат отметок по паре
`[предложение по бэкенду]` · **111**

### 10. Живое обновление
`[предложение по бэкенду]` · **111** · **решается совместно с бэкендом**

- **Нужно:** доставка обновлённых агрегатов по паре и счётчиков заявок при изменении.

- **Открытый выбор:** WS-событие против поллинга. Без решения требование «в реальном времени» (заметка 2 историй 111) не выполняется.

### 11. Снятие отметки
`[предложение по бэкенду]` · **111, 112** · подтверждено владельцем

- **Нужно:** операция возврата ячейки в «нет данных».
- **Сейчас:** `PUT /attendance/lessons/{lessonId}/students/{userId}` умеет только присвоить одно из трёх значений.
- **Механика:** повторное нажатие на выбранный кружок снимает статус. Без операции снятия «пусто» из отмеченного состояния недостижимо.

### 12. Счётчик открытых тикетов по типам
`[предложение по бэкенду]` · **111**

- **Нужно:** по группе — количество открытых тикетов на «у» и на «н», одним ответом, с живым обновлением.
- **Сейчас:** `GET /attendance/late-checkin/pending` + `GET /attendance/excuses/group/{groupId}` — два полных списка ради двух чисел.
- **Смежно:** `[уточнение по контракту]` — фильтруются ли excuses по статусу. Без фильтра клиент вытянет всю историю группы.

### 13. Журнал с фильтром по предмету и типам занятий
`[предложение по бэкенду]` · **112** · подтверждено владельцем

- **Нужно:** та же сетка «студенты × пары», отфильтрованная по предмету и набору типов, за период **от начала семестра до текущей недели включительно**. Будущие пары не отдаются, отменённые отдаются.
- **Объём:** 25–30 студентов × 30–40 пар ≈ 1000 ячеек. Решить: отдавать целиком или пагинировать по колонкам.

### 14. Причина «у» и `excuseId` в самой ячейке журнала
`[предложение по бэкенду]` · **112** · владелец: решаем на бэкенде

- **Нужно:** тип причины, комментарий и `excuseId` приходят вместе с ячейкой.
- **Почему:** иначе каждое наведение на «у» — отдельный запрос: **N+1 по числу «у»**, а их в неделе десятки.

### 15. Доступ к файлу заявки из веба
`[предложение по бэкенду]` · **112** · подтверждает решение чата 3

- **Нужно:** получение вложения и его метаданных (имя, размер, тип).

### 16. Метаданные недели: номер и чётность
`[предложение по бэкенду]` · **112** · следствие JS-SYSTEM-05

- **Нужно:** границы недели, **порядковый номер от начала семестра**, чётность; границы семестра для ограничения листания.
- **Почему нельзя на клиенте:** JS-SYSTEM-05 уже постановил, что считает сервер — две реализации разойдутся на границах семестра и при переносах.

### 17. Признак «пустой день»
`[предложение по бэкенду]` · **112**

- **Нужно:** день без пар приходит явно, а не как отсутствие колонок: заметка 1 скана требует показывать его **неактивным в сетке**, он занимает место.

### 18. Агрегаты статистики группы — **не существует ни одного**
`[нет API]` · **113**

Аналога `student/stats` и `student/dashboard` для группы нет. Нужны:

| # | Агрегат | Состав |
|---|---|---|
| 18.1 | по группе за семестр | количества `+`, `н`, `у` + обе метрики (п. 22) |
| 18.2 | причины по типам | **поданные**, по убыванию частоты; список пар «тип → количество», не фиксированный набор полей — перечень типов пополняется |
| 18.3 | по студентам группы | ФИО; `%н`, `%+`, `%у`, `%(+ и у)` и те же в количествах; тикеты на «н» и «у» — подано/одобрено/отклонено; способ получения «+» (п. 19). Серверные сортировка, фильтрация, пагинация; дефолт — по `%+` |
| 18.4 | временной ряд | три разреза: семестр по неделям · неделя по дням · по предмету с типами. В каждой точке — **обе метрики**, **на одной сетке ключей** |
| 18.5 | детализация по студенту | состав не определён; вероятно разбивка по предметам и типам, история тикетов, динамика |

**Тикеты с решениями (18.3)** обязаны считаться внутри строки студента: отдельный подсчёт на каждого — N+1 по составу группы.

### 19. Происхождение заявки late-checkin
`[предложение по бэкенду]` · **113**

- **Нужно:** у заявки хранится `manual` либо `auto_after_failed_geo`.
- **Зачем:** колонка «способ получения "+"» различает четыре пути; текущий `source` различает только три.
- **Согласование с §0 реестра:** «одна активная заявка на пару независимо от происхождения» **не противоречит** — лимит общий, признак сохраняется.

### 20. Инкрементальный расчёт вместо пересчёта
`[предложение по бэкенду]` · **112, 113** · прямая формулировка владельца

- **Формулировка (заметка 1 скана 113):** «есть значение, и оно инкрементируется, а не считать каждый раз».
- **Нужно:** агрегаты хранятся и обновляются по событию изменения отметки.
- **Вторая половина той же задачи:** **пакетная выгрузка роняет сервис** (заметка 4 job 112). Направление владельца — хранить состояние отчёта либо считать инкрементально, а не собирать заново на каждый запрос.
- **Следствие для фронта:** пока решения нет, нужен режим долгой операции (прогресс либо «пришлём, когда готово»).

### 21. Выгрузка
`[предложение по бэкенду]` · **112, 113** · подтверждено владельцем

- **Перечень форматов приходит как данные** — сейчас docx, pdf, png; в планах html; Excel не нужен. Расширение не должно требовать релиза фронта.
- **Шаблоны с placeholder'ами** — задача бэкенда.
- **Выгрузка учитывает активные фильтры**, разрезов пять: две таблицы на 112, две таблицы и график на 113.
- **Открытый пункт — график:** данные для отрисовки отдаёт сервер, рисует фронт; но файлы формирует сервер. Значит `png` графика требует **серверной отрисовки**. Решить: сервер рисует сам либо для графика только табличные форматы.

### 22. Две метрики посещаемости — сквозное правило
`[предложение по бэкенду]` · **весь продукт** · подтверждено владельцем

- **Нужно:** везде, где считается посещаемость, сервер отдаёт **две величины рядом**: `%+` и `%(+ и у)`.
- **Обоснование:** преподаватели оценивают посещаемость по-разному — одна метрика не обслуживает обе трактовки.
- **Затрагивает:** 101, 102, 103 студента и все экраны старосты, преподавателя, администратора.
- ⛔ **Отменяется** метрика `%у + н` со скана 113 — избыточна, равна `100% − %+`.

### 31. Признак актуальности задания приходит с сервера
`[предложение по бэкенду]` · **114** · критерий подтверждён владельцем

- **Правило:** задание уходит в архив, когда **прошла пара, на которую оно создано**. Задание отменённой пары — тоже в архив. Возврата из архива нет.
- **Без привязки к паре:** критерий — выбранная дата (следствие, требует сверки).
- **Почему нельзя на клиенте:** правило опирается на время окончания пары и её статус отмены, а не на одну дату в задании.

## ⚪ Информационно — фронтом не используется

| Что | Причина |
|---|---|
| `GET /academic/thresholds`, `PUT .../global`, `.../group`, `.../subject`, `GET .../resolve` | механика порогов и красной зоны снята с продукта целиком (§0 реестра). Экранов управления порогами не проектируется ни для одной роли. С бэкенда **не удаляется** — может вернуться |
| `POST /attendance/marks/batch` | массовая отметка **отменена целиком** решением владельца (чат 4) |
| Сопоставление аудитории расписания со справочником карты | карта автономна: переходов «с пары на карту» не проектируется, аудитория в паре остаётся строкой |
