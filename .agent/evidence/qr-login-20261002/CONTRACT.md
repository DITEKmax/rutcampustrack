Internal /auth, Gateway /api/auth. POST /qr/challenges {purpose:LOGIN,issuerId?,issuerSecret?}: initial random server issuer identity+secret; reissue authenticates existing issuer, invalidates its previous challenge atomically. Returns issuerId/issuerSecret only to browser, challengeId, expiresAt, ttl, pollAfterSeconds, qrPayload (version1/purposeLOGIN/challengeId/approvalToken; NEVER issuerSecret). Separate independent256-bit browser/approval secrets, SHA256-only QR storage, redacted DTOs/logs, no URLquery secrets/tokens. POST /qr/status and /qr/exchange {purpose,issuerId,issuerSecret,challengeId}: status only pending/confirmed/rejected/expired+expiry, no account data/tokens; exchange returns ordinary TokenResponse + existing HttpOnly refresh cookie; GET /auth/session remains canonical role/profile/password-change context. Protected POST /qr/preview {purpose,challengeId,approvalToken} returns server-observed browser label/issued time + login warning, no mutation. Protected POST /qr/decision {...,decision:CONFIRM|REJECT} requires selected live access principal, explicit action, authenticates approval capability; cannot select user/role. LOGIN only accepted; foreign purpose/unknown capability uniformly denied. No GET scan authorization.

## Existing patterns / transaction strategy
Durable qr_login_issuers(id,secret_hash,current_challenge_id) and qr_login_challenges(id,issuer_id,purpose,approval_hash,state,expires_at,confirmed_user_id,confirmed_source_sid,confirmed_source_sv/rv,issued_target_sid,issued_at,replay_until,target_sv/rv,initial_refresh_jti_hash); no raw browser/approval/JWT. Lock issuer -> challenge -> canonical user -> source session -> target session; existing revoke/grant/password operations user->session, never QR locks. Confirm checks canonical live source under user/session locks; first decision wins, terminal conflict. Exchange in one outer REQUIRED tx rechecks challenge TTL/purpose/browser proof + source revocation/user/grants, calls canonical SessionLifecycleService through AuthService fixed trusted issuance identity seam, atomically stores session-ref receipt and audit. No second auth system; existing authority transaction joins outer tx. AuthService narrow create-only trusted seam delegates existing canonical lifecycle and returns accepted snapshot inside the outer tx; existing normal issueSession retains same seam. Signing uses accepted snapshot after durable commit through narrow canonical signing seam. Crash precommit rolls back both challenge/session; postcommit retry resolves receipt and re-signs same original SID/JTI/time, never creates/rotates another session. Replay rechecks source and target live/current version/grants and hash of existing current refresh JTI; any rotation/revoke/role drift rejects, no stored bearer. Reissue shares issuer lock so cannot race a pending exchange into two winners. Password change/logout-all serialize on user lock and invalidate source/target as appropriate.

## Acceptance criteria
Real guest issue -> authorized preview/confirm -> original browser exchange -> ordinary session/default role/password flag. Wrong browser/approval-only exchange, anonymous confirm, wrong purpose, expired/rejected/unknown and cross-issuer fail without session mutation. Concurrent confirm/exchange single winner; exact lost-response retry same SID/token pair/no duplicated LOGIN event. Source/account revoke between confirmation/exchange and before replay fails. Reissue invalidates old challenge, preview/scan never authenticates.
