# QR-вход: серверная часть в текущем этапе

Решение владельца 2026-10-02: реализовать серверную часть QR-входа сейчас, чтобы сократить остаток backend для будущей веб-панели.

Scope: JS-SYSTEM-13 / AU-01 — выпуск QR-запроса гостевым браузером, получение статуса, явное подтверждение или отклонение из авторизованного PWA/TMA и получение обычной сессии исходным браузером. Срок действия, одноразовость, изоляция назначений и актуальные ограничения аккаунта обязательны.

Это снимает прежний вопрос «включать API сейчас или вместе с веб-панелью». Интерфейс веб-панели, сканирование и подтверждение в мобильном UI остаются отдельным клиентским этапом. Реализация серверных операций не означает приёмку пользовательского пути на настоящем Telegram.

Основания: `docs/product/specs/wireframes/shared/001-login.md`, раздел 4.3; `docs/architecture/reference-rutcampustrack-design/backend-conflicts.md`, Р-10. Один механизм выпуска с параметром назначения; авторизация гостевого входа и привязки устройства различается. Текущий пакет реализует вход, не расширяет автоматически операции привязки устройства.

Исполнитель: `v_homework_lifecycle_1002`, отдельный существующий worktree; Auth и необходимые ограничения Gateway. Параллельный пакет разовых занятий остаётся у `v_homework_bff_1002` в Schedule. Обоим назначен GPT-6.1 Sol high; фактические возможности runtime не подменяются настройкой defaults.
