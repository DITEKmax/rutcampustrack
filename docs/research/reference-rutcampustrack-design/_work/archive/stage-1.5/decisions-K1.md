## 2. Разбор по группам

### 2.1. Шесть обёрток над `Tabs` → одна `Tabs`

Что каждая обёртка реально добавляла:

| Обёртка | Заявленное отличие | Куда девается |
|---|---|---|
| `PeriodTabs` (101, 103, 131) | подписи приходят пропом; на 131 управляет не графиком, а блоком метрик | `items` — и уже было пропом |
| `ViewModeTabs` (102) | режимы взаимоисключающие, фильтры другого режима не сбрасываются | взаимоисключение — свойство `Tabs`; память фильтров — панель |
| `HomeworkScopeTabs` (104) | каждый режим помнит свою дату | память даты — панель / URL |
| `ChartScopeTabs` (113) | разрез графика | `items` |
| `StatsScopeTabs` (123) | каждый разрез помнит фильтры и сортировку | память — панель |
| `GroupScopeTabs` (133) | каждый разрез помнит фильтры и страницу; счётчик черновиков в доступном имени | память — панель; счётчик — поле элемента `items` |

Ни одна не несёт собственной структуры, поведения или набора действий. Остаётся `Tabs`.

**Финальные пропы `Tabs`:**

- `items: TabItem[]`, где `TabItem = { id, label, count?, disabled?, disabledReason? }`.
  `count` входит в **доступное имя** вкладки («Активные, 3»), отдельного бейджа нет — так уже описаны `TicketScopeTabs` и `GroupScopeTabs`.
- `modelValue: TabItem['id']`, эмит `update:modelValue`.
- `ariaLabel: string` — обязателен: экземпляров на экране может быть несколько.

**Чего `Tabs` не владеет** (записать явно, иначе при удалении обёрток потеряется требование):
память разреза — выбранная дата, фильтры, сортировка, страница — и синхронизация значения с URL принадлежат **панели-потребителю**. Образцы владения уже есть в реестре: `WeekJournalPanel`, `TeacherDayPanel`, `SystemActivityPanel`.

**Не ввожу сейчас:** визуальный `variant`. На 133 разрезы нарисованы рядом кнопок, на 119 — вкладками; это различие подачи, а не структуры → Figma (см. §4).

### 2.2. Пять фильтр-панелей → одна `FilterBar`

Состав полей: 114 — предмет · тип занятия · диапазон дат; 119 — тип тикета · ФИО · дата · сортировка;
132 — роль · группа · статус; 133 — курс · код (мультивыбор); 134 — статус.

Структура у всех одна: **набор контролов, построенный по описанию, которое приходит снаружи**.
Правило §0 (чат 4) прямо запрещает зашивать перечень на фронте — значит, различие между панелями лежит в данных, и пять компонентов описывают одни и те же данные пятью способами.

Особые случаи и то, как они укладываются в один компонент:

- **Зависимость полей** (132: «статус осмыслен только в паре с ролью») — поле описания `enabledWhen`, приходит с бэкендом. На клиенте правило не зашивается.
- **Мультивыбор чекбоксами** (133, прим. 2) — следствие `multiple: true`: множественный выбор рендерится `fieldset` с чекбоксами, а не выпадающим списком с галочками. Это a11y-решение уровня компонента, одинаковое для всех экранов.
- **Два «бара» на 133** (по курсу и по коду) — один экземпляр `FilterBar` с двумя полями. Разнос по разным местам страницы — вопрос дизайна.
- **Одно поле на 134** — `FilterBar` с одним полем, а не `SelectField`: поведение то же (значение в URL, сброс страницы, объявление результата). Отдельного имени `SemesterStatusFilter` это не оправдывает.
- **Сортировка на 119** — поле описания типа `sort`. Нужна там, где список **не табличный** (карточки); в таблицах сортировка живёт в `TableColumnFilter`.
- **Доменные поля** (`SubjectFilter`, `LessonTypeToggleGroup`, `GroupFilter`) — подставляются картой `controls`, поэтому `FilterBar` домена не знает и остаётся `shared`.

**Финальные пропы `FilterBar`:**

- `fields: FilterFieldDescriptor[]` — с бэкенда. Дескриптор: `{ id, label, type, multiple?, options?, enabledWhen?, defaultValue?, hint? }`; `type ∈ 'enum' | 'text' | 'date' | 'dateRange' | 'sort' | 'custom'`.
- `modelValue: Record<fieldId, value>`, эмит `update:modelValue`.
- `controls?: Record<type | fieldId, Component>` — карта доменных контролов.
- `ariaLabel`, `resultCount?` (объявление через `role="status"`), `busy?`.
- ⚠️ `reset` (сброс всех фильтров) — **моё предложение, в спеках его нет**; см. §4.

**Владение `shared`:** домена не знает, потребителей ≥ 2 микрофронтендов (homework, attendance, admin/academic). Если при контракте окажется, что дескриптор несёт доменную семантику, владение падает до `domain (academic)` — но по приложенным спекам оснований к этому нет.

### 2.3. `DatePager` / `LessonPager` / `ReturnToCurrentWeekButton`

**`LessonPager` — не шестое значение `unit`.** Различия структурные, а не оформительские:

| | `DatePager` | `LessonPager` |
|---|---|---|
| тип значения | дата | id пары |
| происхождение оси | вычисляется по календарю | приходит данными (пары выбранного дня) |
| границы | `min` / `max` — даты (границы семестра) | первая и последняя пара дня |
| «текущее» | сегодня / текущая неделя | **идущая пара** (§0 чат 4) |
| подписи | относительные («вчера / завтра»), дальше даты | предмет и время пары |

Один компонент с `unit: … | 'lesson'` означал бы, что `modelValue`, `min` и `max` меняют тип вместе с `unit` — это два компонента, а не один проп.

**Но общее ядро реальное** и сейчас дублируется: стрелки, недоступность на границе **с пояснением**, обязательный `ariaLabel` при нескольких экземплярах на экране, объявление смены через `role="status"`, возврат к текущему значению.

**Примитив `StepPager`** (`shared`) — шаговое листание по одной единице оси, оси не знает.
Пропы: `label`, `hasPrev`, `hasNext`, `boundaryReason`, `showCurrentReset`, `currentResetLabel`, `isAtCurrent`, `ariaLabel`; эмиты `prev`, `next`, `reset`.
Имя намеренно **не `Pager`** — рядом живёт `Pagination`, пара «Pager / Pagination» нечитаема.

**Обёрток ровно две**, обе уже существуют по именам:
`DatePager` (`shared`, `unit: 'day' | 'week' | 'month'`) и `LessonPager` (`domain` (schedule), `items` + id пары).

**`ReturnToCurrentWeekButton` удаляется.** Его описание («всплывающая „вернуться к текущей“, видна только вне текущей недели») совпадает с действием «Сегодня» у пейджера на 104 слово в слово по смыслу. Единое поведение: контрол показывается **только когда значение не текущее**, подпись зависит от `unit`. Проп переименовывается `showTodayReset` → **`showCurrentReset`**: «today» неверно для недели, месяца и пары.
Размещение (внутри пейджера или всплывающим над таблицей) — вопрос дизайна; если понадобится рендерить вне пейджера, это слот того же компонента, а не новое имя.

### 2.4. Контекст: `SubjectFilter` и `TableColumnFilter` не поглощены

- `SubjectFilter` — **поле**, `FilterBar` — **панель полей**. При появлении внутри панели подставляется через `controls`; собственного дубля не возникает, `context: 'filter' | 'form'` сохраняется без изменений.
- `TableColumnFilter` — другой механизм и другое место в разметке. Спека 132 прямо запрещает смешивать его с панелью фильтров на одном экране; фиксирую как сквозное правило: **либо `FilterBar` над списком, либо `TableColumnFilter` в заголовках, но не оба.** Пересечений по экранам сейчас нет (113, 116, 123 против 114, 119, 132, 133, 134).
- Ни одна строка `SubjectFilter` / `TableColumnFilter` не меняется по существу.
