## 1. Соглашения об именовании

- Компоненты — `PascalCase`, семантические, без указания на визуал: `LessonCard`, не `BlueBox`.
- Layout-обёртки — суффикс `Layout` или `Shell`: `AppShell`, `AuthLayout`.
- Состояния — отдельными компонентами: `EmptyState`, `ErrorState`.
- Не использовать в именах: цвета, размеры в пикселях, позиционирование.
- **Ось строк живёт в имени, срез данных — в пропе** (K2). Двухосные сетки носят суффикс `Grid` (`ScheduleBuilderGrid`, `LessonManagementGrid`, `AttendanceJournalGrid`, `TimetableGrid`), одноосные — `Table`, и имя называет строку, а не таблицу целиком. Проп, меняющий ось строк, не заводится.
- **Обёрток над `Tabs` не существует** (K1, K5). Состав вкладок — всегда данные, счётчик — поле элемента и часть доступного имени. Память разреза принадлежит панели-потребителю.
- **Носитель смысла статуса и роли — текст** (K4). Цвет, фон и иконка только дублируют его; пояснение к значению входит в доступное имя.
- **Содержательная подсказка дублируется в доступном имени триггера** (K5). Там, где триггер уже несёт действие, отдельный фокусируемый элемент под подсказку не заводится.
- **Варианты вместо синонимов.** Если компонент показывает ту же сущность в другой компоновке — это `variant`, а не новый компонент. Действующие примеры: `LessonCard` (`featured` / `row` / `cell`), `HomeworkItem` (`compact` / `full`), `TicketForm` (`excused` / `absent`), `TicketCard` (`pending` / `archived`), `NewPasswordForm` (`reset` / `change`), `PermissionList` (`readonly` / `editable`), `DefinitionList` (`inline` / `stack`), `AttendanceJournalGrid` (`lessonScope`: `subject` / `week`, `cellMode`: `edit` / `read`), `LessonAttendanceRoster` (`cellMode`: `edit` / `read`), `StatsByStudentTable` (`scope`: `all` / `subject`), `AttendanceStatusPicker` (`row` / `cell`), `HeadmanHomeworkItem` (`editable` / `readonly`), `GroupStatsTable` (`scope: all / subject`), 🆕 `TicketCard` (`pending` / `archived` / `incoming`), 🆕 `StatsDetailPanel` (`region` / `row`), 🆕 `ScheduleSlotCell` (`full` / `split`), 🆕 `SubjectFilter` и `LessonTypeToggleGroup` (`context: filter / form`), 🆕 `UserCreateForm` (`create` / `add-role`), 🆕 `FloorPlanUploadForm` (`create` / `replace`), 🆕 `SemesterForm` и `GroupCreateForm` (`create` / `edit`).
- Компоненты-формы — суффикс `Form`, всплывающее содержимое — `Popover`, наборы вкладок — `Tabs`, списки сущностей — `List`, поля формы — `Field`.

## 2. Владение компонентом (важно для микрофронтендов)

| Уровень | Что это | Признак |
|---|---|---|
| `shared` | Общая UI-библиотека, используется в ≥2 микрофронтендах | Не знает о домене, только UI |
| `domain` | Общий для роли/домена, но не для всех | Знает о сущностях домена |
| `local` | Живёт внутри одного микрофронтенда | Используется в одном месте |

Правило: компонент попадает в `shared` только когда реально понадобился во втором месте. Не помещай туда «на будущее».

**Исключение — каркас приложения.** `AppShell`, `AppHeader`, `MainNav`, `RoleSwitcher`, `ProfileMenu` знают о ролях, но по определению общие для всех микрофронтендов. Владение `shared`, состав пунктов и ролей приходит снаружи пропами, внутрь не зашивается.

### 6.2. Правила независимости

- Блоки страницы грузятся и падают **независимо**: ошибка одного блока не роняет экран.
- `loading` / `empty` / `error` / `forbidden` / `offline` обязаны быть **озвучиваемы**, а не только визуальны.
- «Нет взаимодействия» ≠ «нет состояний»: блок только на чтение всё равно имеет loading / empty / error.
- Формулировка `empty` различает **будущее** («ещё не задано», «пары не прошли») и **прошедшее** («не было задано», «данных нет»). Один текст на оба случая — дефект.
- Частичная ошибка внутри блока не убирает блок: если упала одна серия графика, вторая рисуется, упавшая заменяется пояснением.
- Перестановка элемента списка по действию пользователя **не уводит фокус**: фокус остаётся на элементе, факт перемещения объявляется через `role="status"`.
- 🆕 **Данные только на чтение показываются текстом, а не `disabled`-полем формы.** Заблокированный инпут обещает редактирование, которого нет (ФИО, группа, id на 108).
- **Изображение не может быть единственным носителем информации.** Для схем корпусов: осмысленный `alt` + текстовая легенда иконок (`PlanLegend`). ⚠️ **Правка 02.08.2026 по Р-5:** справочника аудиторий не будет ни на этом этапе, ни в ближайшем; текстовый перечень аудиторий этажа **не добавляется**. Снятие ограничения, записанное в чате 4, отменено. Схема этажа остаётся изображением без текстового содержания — известное и датированное ограничение, `A11Y_REQUIREMENTS.md`, MAP-07 отложен.
- 🆕 **Наложения поверх страницы — только `ConfirmDialog`.** Формы и панели раскрываются на самой странице (решение владельца, чат 3).
- 🆕 **Блок обязан нести подпись, к каким данным он относится, если на экране их несколько.** На 111 три независимые привязки к паре (счётчики — текущая, две панели — выбранные): без подписи экран врёт при любом листании.
- 🆕 **Массовые сетки: три контрола в ячейке — один `radiogroup`, а не три кнопки.** В журнале ~600 ячеек; при наивной разметке это 1800 Tab-остановок. В `radiogroup` в порядок табуляции попадает один элемент, внутри — стрелки.
- 🆕 **Визуальный ритм не превращается в семантику.** Деление каждые 5 студентов — оформление; `<tbody>`-группы объявят скринридеру структуру, которой нет.
- 🆕 **Частота действия определяет конструкцию контрола.** Основной сценарий выполняется **в один клик**: раскрытие допустимо только для правки уже существующего значения (§0, механика ячейки).

- 🆕 **Сетки с десятками интерактивных ячеек — одна остановка Tab и навигация стрелками внутри** (roving tabindex). Правило чата 4 про журнал распространяется на конструктор расписания (до 96 элементов) и управление парами (до 48).
- 🆕 **`rowspan` допустим там, где структура действительно двухуровневая.** На 116.1 предмет объединяет свои типы занятий — это факт данных, а не оформление. Не противоречит правилу «визуальный ритм не превращается в семантику»: там семантика приписывалась там, где её нет.
- 🆕 **Раскрытие «под строкой» — сдвиг в DOM, а не визуальное наложение.** Панель рендерится отдельным `<tr colspan>` сразу после своей строки, иначе порядок чтения расходится с картинкой.
- 🆕 **Режимы выбора цели обязаны быть клавиатурными.** Перенос пары не может опираться на drag&drop как единственный путь: включение режима объявляется, цели именуются, Esc отменяет и возвращает фокус.
- 🆕 **Действие, уничтожающее данные, называет объём последствий до подтверждения.** «Удалится всё» — не предупреждение: нужны количества (сколько пар, отметок, заданий). Без этого пользователь подтверждает вслепую.
- 🆕 **При исчезновении элемента из очереди фокус переводится на следующий элемент**, а не теряется в конец документа. Разбор очереди заявок с клавиатуры — основной сценарий 119.

- 🆕 **Границу данных проводит сервер, а не разметка.** Если пользователю нельзя видеть часть сущности, урезанное представление приходит с сервера. Фильтрация на клиенте границей не является: данные уже пересекли сеть. Введено на 122 (тикет на «у» урезается по назначениям преподавателя).
- 🆕 **Процент без абсолютных чисел не показываем.** «50 %» при двух парах и при тридцати — разные утверждения; рядом с метрикой обязательны числитель и знаменатель, а при сравнении субъектов — колонка «сколько пар учтено».
- 🆕 **Символы и аббревиатуры разворачиваются словами в доступном имени.** `+` · `у` · `н`, ЛК · ПЗ · ЛЗ, «% +» вслух не читаются: подпись колонки и доступное имя ячейки содержат полную формулировку.
- 🆕 **Два блока из одного ответа падают вместе — и это допустимо**, если состояние **одно и объяснённое**. Дробить один ответ на два запроса ради формальной независимости хуже, чем один понятный `error` (121: «Мои группы» и «Мои предметы»).
- 🆕 **Одна метрика считается в одном месте.** Если одно и то же число показывают два экрана, его считает один серверный агрегат. Две реализации расходятся, и расходятся в документе, уходящем наружу (122 и 123).

- 🆕 **Активная роль — граница действий, а не подсказка.** Пользователь совершает только действия выбранной роли; маршруты других своих ролей дают `role-inactive`, а не `forbidden` и не молчаливый редирект (§0 чат 7).
- 🆕 **Ссылки на файлы приходят от бэкенда, фронт их не конструирует.** Ни из хеша, ни из id, ни из имени. Относится к схемам этажей, вложениям, выгрузкам, аватарам (решение владельца, чат 7).
- 🆕 **Id — ключ связи, человекочитаемое название — интерфейс.** Дополняет правило «все связи по идентификаторам» (чат 5): id в интерфейс не выводится, название собирает сервер.
- 🆕 **Обратимое и необратимое действия показываются рядом, а не вместо друг друга.** «Архивировать» и «Удалить» соседствуют; выбор делает пользователь, а не конструкция экрана (§0 чат 7). Развитие правила «обе кнопки формы слота видны постоянно».
- 🆕 **Ноль и «нет данных» — разные утверждения, и различать их обязательно.** «0 отметок за день», «метрика не считается», «сравнивать не с чем» выглядят одинаково пустыми, а означают разное. Особенно критично на экранах, где пользователь принимает решения по числам (131, 135).
- 🆕 **Массовая операция обязана иметь предпросмотр и состояние частичного успеха.** Dry-run с количествами до подтверждения, поимённый разбор после. Операция над сотнями сущностей не атомарна по умолчанию.
- 🆕 **Недоступность действия объясняется до нажатия, а не после.** Если удаление невозможно (есть данные, сущность в архиве), пункт `disabled` с причиной; ошибка сервера в ответ на нажатие — дефект интерфейса, а не защита.
- 🆕 **Многозначная ячейка называет, к чему относится каждое значение.** Колонки «Роль» и «Статус» на 132 выровнены попарно: доступное имя статуса содержит роль, иначе связь видна только глазами.
