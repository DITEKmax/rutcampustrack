## Причинная цепь в source

1. `GroupsPage.vue:293` подписан на `useWebLiveRefresh`; callback сначала делает реальный `requirePermission('GROUPS_VIEW')`. В `use-admin.ts:39–54` ошибочный authority read очищает локальную authority; toolbar/table защищены `admin.can('GROUPS_VIEW')` (`GroupsPage.vue:343,362`). Значит missing DOM withdrawal совместим с **непришедшим invalidation**, а не обязательно с неисправным permission gate.
2. `app/live.ts:43–70` получает invalidation от реального Notification STOMP, успешного connect/reconnect, browser online/focus. Периодического authority poll нет. Student assistant boundary эту ADMIN страницу не защищает. `notifications-realtime.ts` запрашивает настоящий `/api/auth/ws-ticket`, соединяется через `/api/ws`; `onConnect` вызывает invalidation. Retry отсутствующего канала и `onWebSocketClose` сами REST authority не обновляют.
3. Публичный isolated compose содержит Auth/Academic/Gateway/edge/Postgres/Redis/Rabbit и **не содержит notification-web/Mongo**. Gateway `application.yml:400` направляет `/api/ws/**` в `NOTIFICATION_WEB_URL`, по умолчанию `notification-web:9094`. Поэтому штатный realtime/reconnect путь в этом realm не обеспечен. Main Notification другого realm нельзя подставлять: JWT, ticket, issuer и данные должны принадлежать isolated realm.
4. Harness `revokedOpenPage` делает denied read через Playwright `page.request`, который обходит app transport/owner и не обязан менять Vue state. `bringToFront()` без фактически наблюдённого browser focus не доказывает вызов focus handler в headless Chromium. В receipt нет post-revoke app authority read; trigger этого oracle не квалифицирован.
5. Есть самостоятельный source риск для требования **самопроизвольного idle withdrawal**: `AuthIdentityOperationStore.java:362–370` добавляет `admin.access.changed` только при `desired.assigned=true`; revoke outbox fact этого вида не создаётся. `AdminAccessChangedOutbox` также отвергает unassigned. Academic revoke лишь выполняет identity operation. Notification публикует history hint на `/topic/user/{id}` после обработки события, но для revoke этого события нет. WS admission проверяется при SUBSCRIBE и protected outgoing MESSAGE; heartbeat не вызывает admission. Поэтому здоровый, молчащий socket не обязан закрыться из-за revoke, а source client не имеет периодической fallback проверки. Missing Notification объясняет отсутствие доступного канала, но не доказывает, что его добавление само обеспечит idle revoke signal.

## Минимальный следующий шаг

Для предусмотренного **реального reconnect** criterion нужен полноценный isolated Notification путь, не fake STOMP и не main fallback. Минимальная stand extension: один существующий Notification JAR + собственная Mongo notification DB с replica-set transactions; использовать существующие isolated Rabbit/Redis/Auth/Academic/Gateway и собственные issuer/ticket/directed-service credentials/TLS trust. Gateway должен резолвить isolated notification-web. Bot/Schedule/Attendance и новый framework для этого не требуются без конкретного startup blocker. Mongo image/resource admission отдельно проверяет runtime owner; скрытый pull недопустим.

Notification/shared source diff60346b26→Root7ff пуст. Это подтверждает локальный кандидат/provenance, не здоровье запущенного сервиса. Его успешный genuine private-channel connect/reconnect должен стать наблюдаемым precondition, прежде чем новый withdrawal oracle будет интерпретирован как application результат.

Следующий finite case — **только withdrawal/reconnect**, два новых bounded native intents: combined LIMITED USERS_VIEW+GROUPS_VIEW grant и revoke от свежего canonical CAS. Старые Users-only/denied/granted checks закрыты и не повторяются как новая кампания. Сохранить открытую Groups DOM; после revoke получить реальный поддерживаемый browser/realtime reconnect без manual reload/navigation и зафиксировать app-origin `/admin-access/me`/session reconciliation. Если настоящий invalidation пришёл, app authority read произошёл, но DOM остался — это конкретный APPLICATION reproduction в live-refresh/authority/retirement boundary.

Если требование означает idle withdrawal **без любого focus/reconnect/другого события**, сначала адресно закрыть source design gap: автор должен определить реальный revoke/security signal либо ограниченную fail-closed authority reconciliation.
