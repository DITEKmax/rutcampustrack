## attendance

### Тикеты (107) — самый крупный блок

| # | Потребность | Тип | Приоритет |
|---|---|---|---|
| A-1 | **Тикет как агрегат:** `{type, reason, comment, attachments[], lessons[]}` — одна операция, один результат. Тикет **неделим** (решение владельца), одобряется/отклоняется целиком. Сейчас `POST /attendance/excuses` — из контракта не видно, принимает ли список пар; `POST /attendance/late-checkin/{lessonId}` строго по одной паре и атомарный тикет **невыразим в принципе** | `[предложение по бэкенду]` | высокий |
| A-2 | **Пары диапазона с готовым признаком доступности:** `Lesson` + `canDispute` + `reason` отказа (есть активная заявка · пара отменена · пара не прошла · уже «у» · «н» проставлен вручную старостой). Сейчас фронт джойнит расписание + отметки + (несуществующие) данные о тикетах — 3 источника на каждую смену диапазона, плюс N+1 | `[предложение по бэкенду]` | высокий |
| A-3 | **Правило «можно ли оспаривать» считает сервер, не клиент.** Ручное «н» (`headman` / `teacher_override`) — нельзя, автоматическое (`auto_scheduler`) — можно. Источник отметки может пополниться, две реализации разойдутся | `[предложение по бэкенду]` | высокий |
| A-4 | **Счётчик попыток захвата:** `attemptsUsed` / `attemptsLimit` (3 на семестр) + признак блокировки на пользователе. Фронту нужно **как данные**, а не как ошибка после отправки — иначе кнопка недоступна молча | `[нет API]` | высокий |
| A-5 | **Снятие блокировки старостой** — отдельная операция для экрана управления студентами группы | `[нет API]` | чат 4 |
| A-6 | **Мои заявки late-checkin** — личного разреза нет вообще, есть только `pending` и `group/{groupId}` для старосты | `[нет API]` | высокий |

| A-8 | **Отмена тикета студентом.** `PATCH /excuses/{id}/status` — сторона согласующего. Отмена **освобождает пары**: подать заново можно | `[нет API]` | высокий |

## Фактура для решения REST vs GraphQL

Собрано по разобранным экранам. Направление владельца: **эндпоинты под форму экрана + кэшируемость**, а не клиентская агрегация.

| Экран | Запросов | Проблема |
|---|---|---|
| 001 Вход | 3–4 | сборка контекста сессии из нескольких вызовов |
| 101 Главная | 6–8 | шесть независимых блоков |
| 102 Посещаемость | 4–5 **на каждое переключение режима** | переключение режима = новая сборка |
| 103 Статистика | 4–6, **три из них не существуют** | рейтинг, разбивка по типам, средняя по группе |
| 104 Домашнее задание | 1–3 | over-fetching: список за семестр ради одного дня |
| 105 Карта | 1–2 | нейтрален: схема — бинарный ассет вне транспорта в любом случае |
| **107 Тикеты** | **3 на каждую смену диапазона + N при подаче + 2–3 на входе** | худший случай: явный N+1 при склейке пар с отметками; пакетная подача невыразима |
| **108 Настройки** | **4–6, три из них не существуют** | экран собирается из пяти независимых источников |

**Общий вывод фактуры:** проблема не в объёме данных (over-fetching заметен только на 104), а в **количестве источников на один экран** и в отсутствии агрегатов под форму экрана. Это одинаково решается и «endpoint под экран», и GraphQL — выбор транспорта данной фактурой не предрешается.
