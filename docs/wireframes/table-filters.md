## 1. Правило: что фильтруется в колонке, что панелью

> **Фильтр живёт в заголовке колонки, если он убирает строки по значению, которое эта колонка
> показывает. Всё остальное живёт в панели.**

Проверка — три вопроса **в этом порядке**. Первый сработавший даёт ответ:

| # | Вопрос | Если «да» |
|---|---|---|
| 1 | Значение **одинаково у всех строк** набора? | **Панель.** Это параметр набора, а не свойство строки. Колонка из него не получится: фильтр по ней вернёт либо всё, либо ничего |
| 2 | Отбор **пересчитывает ячейки**, а не убирает строки? | **Панель.** Ни одна строка не исчезает, меняется содержимое всех |
| 3 | Есть колонка, чьи ячейки показывают **ровно это значение**? | **Заголовок этой колонки** |
| — | Ни один не сработал | **Панель**, и это сигнал: возможно, поле должно стать колонкой |

Два уточнения к правилу:

4. **Полнотекстовый поиск по записи** по построению не ложится ни на одну колонку — он всегда
   `SearchField` в панели. Обратное следствие: **поле, покрытое поиском, второго фильтра в своей
   колонке не получает.** Иначе два контрола делают одно и то же в разном объёме, и пользователь
   не может сказать, который победил.
5. **Разрез — не фильтр.** `Tabs` выбирает набор, а не сужает его: 133 «активные / черновики /
   архив» и 123 «по студентам / по моим группам» остаются вкладками и в это распределение
   не входят. Прочтение 134 (прим. 2: «статус — это фильтр, а не разрез») остаётся верным —
   меняется только место фильтра.

Две границы, без которых правило переедет дальше, чем решено:

- **Решение владельца определяет место фильтра, а не его наличие.** Таблица, у которой фильтров
  нет по прямому указанию скана (`GroupMembersTable` на 116, прим. 2), фильтров не получает.
- **«По всем полям» — это ожидание к бэкенду, а не разрешение фронту.** Правило §0 чата 4 в силе:
  набор колонок с сортировкой и фильтром приходит описанием. Фронт рисует то, что пришло,
  и не зашивает ни одной колонки.

### Что происходит с правилом «механизмы не смешиваются»

Правило спеки 132 («либо панель фильтров, либо фильтры в заголовках — не оба на одном экране»),
повышенное K1 до сквозного, **перестаёт быть запретом и становится правилом распределения**:
выбор делается не на уровне экрана, а по каждому фильтру отдельно. Экран с таблицей может нести
`SearchField` и фильтры в колонках одновременно — это и есть 132 и 133 после дельты.
Совпадение `FilterBar` и `TableColumnFilter` на одном экране правилом больше не запрещено,
но среди приложенных экранов не возникает (см. §6, вопрос 8).

### Пояснения к спорным строкам

**113 и 123 — почему предмет и типы занятий остаются панелью.** Это самая частая ошибка
при переносе: контрол выглядит фильтром и стоит рядом с таблицей. Но предмет одинаков
у каждой строки (п. 1), а типы занятий не убирают ни одной строки — они меняют знаменатель
в каждой ячейке (п. 2). Загнать их в заголовки нельзя: фильтровать нечего.

**123 — фильтрация клиентская.** Набор приходит целиком (≈25 строк), пагинации нет, сортировка
уже клиентская по решению чата 6. Фильтрация в колонках идёт тем же режимом. Условие переноса
на сервер — то же, что для сортировки (123, §7.8): рост набора.

**132 — колонки «Роль» и «Статус» многозначны.** Строка несёт несколько ролей, у каждой свой
статус (вариант Б). При переезде фильтра в колонку это даёт два следствия, которых не было
у панели: (а) нужна явная семантика совпадения по многозначной ячейке, (б) зависимость
«статус осмыслен только в паре с ролью» (§4.5) переезжает из дескриптора поля панели
в дескриптор колонки. См. §3 и §6, вопросы 2 и 3.

**132 — `GroupFilter context="filter"` перестаёт применяться.** Фильтр по группе теперь
живёт в колонке, а в поповер колонки доменные контролы не подставляются (§3). Повышение
владения `GroupFilter` до `domain (academic)` при этом **сохраняется**: на 132 остаются два
применения с `context="form"` — ветка «студент» в `UserCreateForm` и `StudentTransferForm`.
На 123 `GroupFilter` остаётся панельным без изменений.

**134 — красная таблица получает фильтр в заголовке.** Это не противоречие: «красный ≠ без
взаимодействия» уже зафиксировано в самой спеке (⋮ в красной таблице). Набор конечен, поэтому
фильтрация клиентская, сортировки по колонкам по-прежнему нет.

**116 — основная таблица фильтров не получает.** Прим. 2 задаёт алфавитный порядок и отсутствие
фильтров прямо; решение владельца места фильтра не создаёт там, где фильтра нет. См. §6, вопрос 1.

**119 — экран без таблиц, не трогаю.** Очередь заявок — `<ul>`/`<li>` с `TicketCard`. Фильтры
архива и поле типа `sort` остаются в `FilterBar` без изменений; именно нетабличность этого списка
и делает поле `sort` осмысленным (K1, §2.2).

## 3. Контракт колонки и дельта к строкам реестра

### 3.1 Дескриптор колонки

`filterable: boolean` из K2 разворачивается в дескриптор. Приходит с бэкенда вместе с описанием
колонок (§0 чат 4), фронт не достраивает.

```
ColumnDescriptor = {
  key, label, align?, sticky?, group?,
  sortable: boolean,
  filter?: ColumnFilterDescriptor        // отсутствует → колонка не фильтруется
}

ColumnFilterDescriptor = {
  type: 'enum' | 'text' | 'number' | 'numberRange' | 'date' | 'dateRange' | 'boolean',
  multiple?: boolean,          // мультивыбор → fieldset с чекбоксами
  options?: { value, label }[],// перечень внутри описания (малые закрытые списки)
  optionsSource?: string,      // ключ справочника, подгружается при открытии поповера
  searchable?: boolean,        // поиск по подстроке внутри перечня
  matchAny?: boolean,          // ячейка многозначна: строка подходит по любому значению
  enabledWhen?: { column: ColumnKey },   // фильтр осмыслен только вместе с другим
  disabledReason?: string,     // текстовая причина недоступности
  hint?: string
}
```

**Словарь `type` намеренно повторяет `FilterFieldDescriptor` из K1**, из него убраны два значения
и добавлены три:

- **убрано `'sort'`** — сортировка в таблице живёт в `sortable`, а не в описании фильтра;
- **убрано `'custom'`** — в поповер колонки доменные контролы **не подставляются**. Карты
  `controls` у `DataTable` нет: иначе примитив узнаёт домен, а это прямая граница K2
  («примитив знает строки, колонки и взаимодействия; сущности не знает никогда»). Большие
  справочники решаются `optionsSource` + `searchable`, а не подстановкой `GroupFilter`;
- **добавлены `'number'`, `'numberRange'`, `'boolean'`** — 🆕 относительно перечня K1. Нужны
  для колонок метрик на 113 и 123 («`%+` ниже 50») и для колонок-состояний на 132.

### 3.2 Откуда приходит перечень значений

> **Перечень значений enum-фильтра приходит с бэкенда и никогда не собирается из загруженной
> страницы.** При серверной пагинации страница не содержит всех значений набора — собранный
> из неё перечень молча скроет варианты, и пользователь не узнает, что фильтр неполон.

Две формы доставки: `options` внутри описания колонки (закрытые перечни — статус, тип, курс)
и `optionsSource` для перечней, которые не помещаются в описание (группа на 132 — сотни значений;
такой перечень подгружается при открытии поповера, с поиском по подстроке и собственной
постраничностью).

**Колонки-состояния фильтруются по состоянию, а не по значению.** Ячейка `InitialPasswordCell`
показывает происхождение (`initial` / `admin_reset` / `changed`), `TelegramIdCell` — значение либо
`not-linked`. Фильтр по такой колонке — `enum` по состоянию; фильтра по самому значению пароля
не существует (см. §6, вопрос 4).

### 3.4 Дельта к строке `TableColumnFilter` (§4 реестра, `shared`)

## 5. Потребности к бэкенду

Транспортно-нейтрально: решения REST/GraphQL не принимаю, формулирую как требования к операции
списка независимо от её формы.

| # | Потребность | Приоритет | Экраны |
|---|---|---|---|
| **B-1** | **Фильтрация выполняется там же, где пагинация.** Везде, где набор отдаётся страницами, фильтрация обязана быть серверной. Клиентская фильтрация загруженной страницы даёт неверный ответ **молча**: пользователь видит «ничего не найдено» при непустом наборе | **блокирующий** | 113, 132, 133 |
| **B-2** | **Порядок применения: фильтр → сортировка → страница.** `total` и счётчик результата считаются **по отфильтрованному набору**, иначе `Pagination` объявляет чужой объём, а состояние `filtered-empty` неотличимо от `empty` | **блокирующий** | 113, 132, 133 |
| **B-3** | **Описание колонок как данные — расширяется.** К уже требуемому §0 чата 4 составу добавляются: тип фильтра, признак мультивыбора, источник перечня значений, парные зависимости. Формат — §3.1. Добавление фильтра на бэкенде не должно требовать релиза фронта | высокий | все таблицы |
| **B-4** | **Справочники значений отдаются отдельно от страницы данных.** Перечень значений enum-фильтра не выводится из загруженной страницы. Малые перечни — внутри описания колонки; большие (группа на 132 — сотни значений) — отдельной операцией с поиском по подстроке и собственной постраничностью | высокий | 132, 133 |
| **B-5** | **Семантика комбинирования — одна на все списки.** Несколько значений внутри одной колонки — ИЛИ; фильтры по разным колонкам — И. Правило серверное и единое; расхождение между операциями вылезет как несогласованность внутри одного экрана | высокий | все |
| **B-6** | **Многозначные ячейки.** Строка 132 несёт несколько ролей и несколько статусов. Нужно определить: строка подходит, если совпало **любое** её значение. Плюс — парный фильтр «роль + статус»: отбор по статусу без роли двусмыслен по построению варианта Б | высокий | 132 |
| **B-7** | **Устойчивый порядок при пагинации.** Сортировка по неуникальной колонке (`%+`, курс, статус) требует вторичного ключа-разрешителя. Без него строки дублируются и пропадают между страницами, и это выглядит как потеря данных | высокий | 113, 132, 133 |
| **B-8** | **Фильтрация по вычисляемым значениям.** На 113 фильтруемые колонки — это агрегаты: проценты, счётчики тикетов, разбивка способа получения «+». Отбор по ним означает фильтрацию по вычисленному, а не по хранимому полю. **Смыкается с инкрементальным хранением (113, §4.1) и требует проверки**: если значения инкрементируются, а не считаются, по ним нужно уметь отбирать и сортировать | высокий | 113 |
| **B-9** | **Выгрузка принимает тот же набор фильтров.** `ExportButton` выгружает «текущий разрез со всеми активными фильтрами». После дельты активные фильтры — это фильтры колонок; параметры выгрузки обязаны принимать ту же структуру, что и список, а не собственную | средний | 113, 116, 123, 132, 133 |
| **B-10** | **Набор фильтров сериализуем.** Значения фильтров живут в URL (прямое требование 132 и 133). Структура, уходящая на сервер, и структура в адресе — одна и та же; невалидные значения сбрасываются к умолчанию **с пояснением** (правило уже есть на 132, 133, 134) | средний | 132, 133, 134 |
| **B-11** | **Клиентский режим — там, где набор приходит целиком.** 123 (≈25 строк, пагинации нет) и `StatsBySubjectTable` на 116 фильтруются на клиенте. Серверных требований не порождают; при росте набора переносятся вместе с сортировкой | низкий | 116, 123 |

**Чего эта дельта не меняет.** Требования к самим агрегатам, N+1 по названию группы и ФИО
старосты, границы данных, аудит по персональным данным — всё, что уже записано в спеках,
остаётся как есть. Новых источников данных дельта не создаёт: она меняет, **где** задаётся отбор,
и добавляет к списочной операции требования B-1…B-8.

## 6. A11y: фильтр в заголовке колонки

`aria-sort` уже описан и не меняется — он остаётся на `<th>`, а не на кнопке.

**Разметка заголовка.** В `<th>` **два контрола, не один**: подпись-кнопка сортирует, отдельная
кнопка открывает фильтр. Один контрол на оба действия неоднозначен — по клику невозможно понять,
что произойдёт, а с клавиатуры разделить их нечем. Оба попадают в порядок табуляции, у каждого
собственное доступное имя.

**Открытие.** Кнопка-триггер: `aria-haspopup="dialog"` (внутри форма с полями, не меню),
`aria-expanded`. Открытие — Enter или Space. Основа — `Popover` из реестра: Esc закрывает,
фокус переводится внутрь.

**Доступное имя триггера называет колонку и состояние фильтра:**
«Фильтр по колонке "Курс", не задан» / «Фильтр по колонке "Курс", активен: выбрано 2 значения».
Признак активного фильтра обязан быть **видимым и текстовым** одновременно — требование уже
записано в 113 (§5, состояние `filtered`), здесь у него появляется конкретный носитель.

**Содержимое поповера** по типу фильтра: мультивыбор — `fieldset` с чекбоксами и подписью-легендой
(перенесено из `FilterBar`); одиночный выбор — радиогруппа; диапазон — два поля с явными
подписями «от» и «до»; текст — одно поле.

**Момент применения.** ⚠️ Предложение фронта: **мультивыбор применяется по кнопке внутри поповера,
одиночный — сразу с закрытием.** Причина — на серверных таблицах применение по каждому чекбоксу
даёт запрос на щелчок; на клиентских это незаметно, но два разных поведения у одного контрола
хуже, чем одно предсказуемое. Требует подтверждения (§7, вопрос 5).

**Возврат фокуса — на кнопку-триггер**, а не «на заголовок колонки», как записано сейчас в 113
и 116. Это важнее, чем выглядит: после применения фильтра строки исчезают, и триггер — единственный
элемент, который гарантированно остался на месте. Проблемы потери фокуса, как при удалении строки,
здесь не возникает.

**Объявление результата.** После применения — `role="status"`: разрез, что отфильтровано, сколько
строк осталось («отфильтровано по колонке "Статус": активные; показано 12 из 340»). Молча
перестроившаяся таблица — тот же дефект, что молчаливая пересортировка, для которой объявление
уже требуется.

**Недоступный фильтр** (132: «Статус» до выбора роли, `enabledWhen`): `aria-disabled` **с текстовой
причиной, доступной скринридеру**, а не только тултипом, и **не скрыт** — общее правило продукта.

**Сброс.** Сброс одного фильтра — внутри его поповера. Сброс всех фильтров таблицы — контрол
уровня таблицы; на 116 он уже нарисован («Сбросить»), и состояния `filtered-empty` на 113, 132, 133
его прямо предполагают. Место в контракте `DataTable` (§3.3), имя — вопрос 6.

**Сводка активных фильтров.** На 132 девять колонок; просмотреть заголовки, чтобы понять, что
включено, — не сценарий. Нужна текстовая сводка активных фильтров над таблицей со сбросом каждого.
Предлагаю считать её регионом `DataTable`, а не новым компонентом (§7, вопрос 6).

**Режим крупной сетки.** Если таблица включает клавиатурный режим крупной сетки (K2: одна остановка
Tab, перемещение стрелками), две кнопки в заголовке достижимы **стрелками внутри ячейки**, а не
отдельными остановками Tab. Среди приложенных экранов режим не задействован, но контракт примитива
обязан это оговорить, иначе на 112/122 при добавлении фильтров заголовки станут недостижимы.

## 7. Вопросы

1. **Таблицы без фильтров.** `GroupMembersTable` (116, прим. 2 — алфавит, фильтров нет) и

   одна колонка», второе точнее отражает вариант Б. По умолчанию закладываю первое.

3. **132, многозначные ячейки.** Строка подходит, если совпало **любое** значение ячейки — это
   поведение по умолчанию (`matchAny`). Подтвердить: других вариантов («все значения», «ровно эти»)
   не закладываю.

4. **Колонки-состояния.** Фильтр по колонке «Пароль» — по происхождению (`initial` /
   `admin_reset` / `changed`), по «Tr id» — по признаку привязки. Фильтра по самому значению
   пароля или id не существует. Подтвердить, что «по всем полям» читается именно так.

5. **Момент применения фильтра** (§6): мультивыбор — по кнопке, одиночный — сразу. Принимается?

6. **Сброс и сводка активных фильтров.** Вопрос 7 из K1 (`reset` у `FilterBar`) остался открытым,
   и теперь тот же вопрос встал у таблицы. Предлагаю: сброс всех фильтров и текстовая сводка
   активных — регион `DataTable`, отдельного имени не заводить. Подтвердить или дать имя.

7. ✅ **`filterMode` — решено (владелец).** Заводится **симметрично `sortMode`**, отдельным пропом,
   с правилом валидации: **при серверной пагинации оба обязаны быть `'server'`** — клиентский отбор
   по неполной странице молча скроет строки. Внесено в строку `DataTable` реестра.

8. ✅ **123, 122 и 113: свободные контролы — решено (владелец).** Экземпляром `FilterBar` **не являются**
   и панельного компонента не образуют. Обоснование: `FilterBar` сужает уже полученный список, а здесь
   это **параметры запроса** — на 122 без выбора журнала не существует вовсе, на 113 и 123 предмет
   и типы занятий меняют знаменатель метрик. Регионы `StatsFilterBar` (123) и `JournalFilterBar` (122)
