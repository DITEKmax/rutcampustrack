## MVR03 — P2, new PNG scanline validation permits extreme synchronous CPU work

**Contract:** TASK-CONTRACT §4 requires upload stability and resource boundaries; this packet explicitly requires examination of CPU/inflated bounds and preservation of grayscale/indexed/interlaced/wide valid images. No arbitrary canvas-size policy is inferred.

**Location:** `services/academic-service/academic-app/src/main/java/ru/rutcampustrack/academic/map/CampusMapAdminService.java:536` (also 483–484, 535–540). The newly introduced scanline validator accepts any positive signed-int height and performs one Java row iteration plus filter read and `skipNBytes` per row. The 10 MiB limit applies to compressed input only. There is no accumulated inflated-byte/row-work budget or validation deadline; thread interruption at row start is not a request time/work limit.

**Concrete construction candidate:** valid noninterlaced PNG IHDR width=1, height=1,000,000,000, depth=1, color=0, compression/filter/interlace=0; IDAT is the zlib stream of 2,000,000,000 zero bytes; IEND and chunk CRCs are valid. Each row is filter byte 0 plus one packed grayscale byte 0. Long runs of zero bytes compress below 10 MiB, but this code must execute **one billion row iterations** before accepting the file. Fixed inflater buffers avoid a dimensions-sized raster allocation; they do not bound this CPU amplification. The author receipt honestly acknowledges no decompressed/work/time policy. The existing huge-incomplete test instead reaches EOF almost immediately, and the 100,000×1 positive is only one row, so neither checks this risk. **This reviewer did not generate/inflate this large stream or measure latency**; the finding is extreme source-level work without a practical validation budget, not an observed outage. Signed-int dimensions and the finite compressed-input bound do impose theoretical finite maxima; those maxima do not constitute a demonstrated service-safe work budget.

**Needed author correction:** introduce a defensible server validation work budget or bounded cancellable validation path before processing attacker-controlled rows; calculate per-pass expected bytes and row work with overflow-safe arithmetic. Treat it as a resource safeguard, not a guessed width/height canvas policy, and preserve the existing valid wide/grayscale/indexed/Adam7 cases. Demonstrate the accepted limit/control with a scaled high-compression, many-row synthetic input under an explicit bounded author lease and a positive control; do not run a billion-row attack as the first reproduction. If a product-facing upload limit changes, keep advertised limits and failure behavior consistent through the assigned contract owner.
