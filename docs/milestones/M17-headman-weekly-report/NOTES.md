## Ответы на open questions (зафиксировано 2026-04-28)

### Q1 — Структура подколонки (вертикаль)

Сверху вниз:
1. Дата дня (в шапке колонки-дня, формат ДД.ММ.ГГГГ).
2. Название предмета — **вертикально** в заголовке подколонки.
3. Тип пары (ЛК / ПЗ / ЛЗ) — прямо под названием предмета.
4. Клетка статуса (`+` / `н` / `у`) на пересечении студент × подколонка.

Это соответствует варианту (a) из предложений.

### Q2 — Разовые пары

`one_off_lessons` **включаются** в отчёт на общих правах с регулярным
расписанием.

### Q3 — Несколько пар одного предмета в день

Каждая пара = отдельная подколонка. Если матан в среду 1-я и 3-я пара,
будут две подколонки «Математика» в среду.

### Q4 — Больше 5 пар в день

**Падать с 422** + осмысленное сообщение. Не пытаться обрезать или
подвинуть — деканат должен знать о расхождении.

### Q5 — Больше 35 студентов

То же — 422 с ошибкой.

### Q6 — Имя файла

`понедельный-{group_name}-{дата_начала_недели}-{дата_конца_недели}.docx`
где конец недели — **календарное воскресенье** (даже если пар в субботу
и/или воскресенье нет).

Пример: `понедельный-УВПв-511-27.04.2026-03.05.2026.docx`.

### Q7 — Слияние нескольких недель

Вариант **(ε) — один многостраничный `.docx`**. Каждая неделя =
отдельная страница с page-break.

Имя файла при слиянии: `понедельный-{group_name}-{первая_дата}-{последняя_дата}.docx`.

### Q8 — Шапка группы

Текст шапки: `Группа: {group_name}, {N} семестр {YYYY/YYYY+1} года, {M} курс`

Пример: `Группа: УВПв-511, 2 семестр 2025/2026 года, 5 курс`.

- **Семестр** — число (1 или 2).
- **Учебный год** — формат `2025/2026`.
- **Курс** — вычисляется из имени группы по первой цифре после
  дефиса: `УВПв-511` → 5-й курс. Парсер тот же, что в backend
  (`group_name.match(/-(\d)\d{2}$/)[1]`).

### Q9 — Подпись внизу

Староста расписывается **от руки** на распечатке. ФИО старосты
**автоматически не подставляется** — оставляем пустое место для подписи
(как в эталоне).

### Q10 — Дата вверху страницы

Отдельной даты «над всем документом» нет. Все даты — это даты дней
недели в шапках колонок.

### Q11 — Библиотека для генерации `.docx` на JVM

- **Apache POI XWPF** — стандарт, тяжёлый, шаблонизация ручная.
- **docx4j** — мощнее POI, более удобный API для шаблонов.
- **`docx-stamper`** (https://github.com/thombergs/docx-stamper) —
  обёртка над docx4j с MVEL-плейсхолдерами `${student.lastName}`.

**Предварительный кандидат** — `docx-stamper`. Финальное решение
примем при реальной попытке встроить шаблон с merged cells (это
основной риск с любой библиотекой).

## Архитектурное решение: единый сервис, не выделяем

См. `DECISIONS.md` D3. Кратко: остаёмся в `attendance-service`,
потому что:
- Объём ~300-500 строк кода — не повод для микросервиса.
- Все данные уже у attendance (Mongo) или доступны через существующие
  gRPC-вызовы (academic, schedule).
- Выделение добавило бы лишний сетевой прыжок без выгоды.
- M18 (сводный семестровый отчёт) тоже про attendance — будет
  использовать ту же инфраструктуру.

Триггеры для будущего выделения в `report-service`:
- ≥3 разных типов отчётов.
- Долгая генерация (минуты) → нужна очередь / отдельный воркер.
- Batch-выгрузка по факультету → пул процессов.
- 10+ шаблонов с UI редактирования.

## Архитектурные заметки

### Источники данных

| Что нужно | Откуда |
|---|---|
| ФИО студентов группы | gRPC academic-service `GetGroupMembers` |
| Группа: имя, semester, year | gRPC academic-service `GetGroup` |
| Расписание недели (предметы + типы пар + дни/слоты) | gRPC schedule-service (нужен новый метод? проверить) |
| Attendance-cells | Mongo `attendance_db.attendance_records` через `AttendanceReadPort` |
| Дата перевода студента в группу | в `User` сейчас нет — нужно из event log / audit log? **Открытый вопрос** |

### Риски

- **Дата перевода студента** в БД явно не хранится. Проверка
  «зачёркивать ли фамилию» требует доступа к истории. Вариант обхода:
  смотреть на самый ранний `attendance_record` для пары в этой группе —
  если для студента нет ни одной отметки до даты X, значит его не было.
  Грубо, но работает для первой версии.

- **Шаблон со слиянием ячеек** в docx — болезненная штука.
  `colspan`/`rowspan` в Word устроен через `gridSpan`/`vMerge`, и любая
  ошибка в шаблоне → сломанный файл. Нужно тестировать на реальном
  Word, а не только на LibreOffice.

- **Локали в docx** — Word на Windows может по-разному рендерить
  кириллический шрифт по сравнению с LibreOffice. Тест на обоих.

- **Альбомная ориентация + таблица 6 столбцов × 5 подколонок** = 30
  колонок с очень узкими ячейками. Если шрифт по умолчанию — переполнение.
  Шаблон уже это решает (в эталоне 8pt примерно), просто помним.
