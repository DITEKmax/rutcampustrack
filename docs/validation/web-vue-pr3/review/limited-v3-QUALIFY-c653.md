## Почему403 является допустимым security outcome

- Gateway `JwtAuthenticationFilter.java:152` устанавливает expectations обычного ADMIN access bearer; `InternalJwtIssuerFilter.java:92–102` вызывает настоящий Auth admission и возвращает typed denial. `/api/auth/**` направляется в Auth (`application.yml:333–338`).
- Auth `JdbcSessionAuthority.java:862–880` очищает выбранную роль, когда grant больше не selectable. `SessionAdmissionService.java:116–138` проверяет отсутствие/невыбираемость роли **перед** stale-version сравнением: отозванная ADMIN приводит к `ROLE_NOT_SELECTABLE` либо `ROLE_NOT_GRANTED`, а не обязана давать401.
- Auth `GlobalExceptionHandler.java:144–169` возвращает для этих codes HTTP403 с typed `extras.code`; AUTHORITY_UNAVAILABLE даёт503. Gateway `InternalJwtIssuerClient.java:207–219` отображает именно typed role403 в public **403/WRONG_ROLE**; unavailable/malformed admission не маскируется этим mapping.
- Frontend `session.ts:136–145` для этого non401 ответа очищает snapshot, повышает generation и переводит session в error. `App.vue:53–72` заменяет защищённый RouterView состоянием «Сессия недоступна» с обычным retry. Наблюдаемое исчезновение через83ms соответствует этому fail-closed пути. Автоматический refresh обещан для401;403 не обязан автоматически выбирать Teacher.
- c653 `idleVerdict:337–339` разрешает лишь200/401 и объявляет любой session403 ENV. Поэтому его enum неверно квалифицирует предусмотренный server denial. **Это TEST classification gap.** Внешний raw outcome не переименовывается в exit0/PASS; узкий пользовательский критерий принимается по сохранённой причинной цепи.

Предел доказательства: raw403 problem body/code driver не сохранил. Поэтому exact actual `WRONG_ROLE` не заявляется прочитанным wire фактом; это source-consistent branch ожидаемого role denial. Достоверные wire facts — реальный HTTP403, его время и последующий withdrawal. Их вместе с known canonical revoke достаточно для принятия узкого idle criterion; признаков ENV outage в idle evidence нет.
