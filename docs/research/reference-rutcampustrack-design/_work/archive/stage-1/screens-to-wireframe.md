# Screens → Wireframe → Figma-spec

Превращает нарисованные на бумаге экраны в структурированные low-fidelity wireframe'ы и спеку, готовую для Figma. Это ПЕРВЫЙ этап фронта: структура и логика, БЕЗ цвета и красоты.

## Проект (контекст привязки)

**Репозиторий:** https://github.com/DITEKmax/rutcampustrack

Существующий бэкенд (на момент написания):
- Java 21 + Spring Boot 3.4, Gradle (Kotlin DSL), **микросервисы**: `auth-service`, `academic-service`, `schedule-service`, `attendance-service`, `notification-service`, `api-gateway`.
- **Contract-first:** публичные контракты в модулях `services/*/*-api-contract` — источник правды по данным.
- REST через API Gateway (`/api/{service}/...`), ошибки — **RFC 9457 Problem Details**, HATEOAS.
- Между сервисами — gRPC (`proto/`), события — RabbitMQ (`event-schemas/`).
- Хранилища: PostgreSQL (auth/academic/schedule), MongoDB (attendance/notification), Redis.
- **Роли:** `student`, `headman` (староста), `teacher`, `admin`.
- Существующие фронты: web-panel (Angular 19), pwa + mini-app (React 19 + Vite). Новый фронт — **Vue**.

Если репозиторий доступен — сверяйся с реальными `*-api-contract`, а не с этим описанием. Описание может устареть.

## Бэкенд НЕ заморожен (важно)

Бэкенд можно менять и подгонять под потребности фронта. Поэтому:

- Если экрану нужны данные, которых нет или которые неудобно получать текущим API — **не подгоняй экран под API**. Опиши, что реально нужно экрану, и поставь пометку `[предложение по бэкенду]`: какой эндпоинт/поле/агрегат добавить и почему.
- Все такие пометки собирай в отдельный файл — это вход для бэкенд-задач.
- Не выдумывай существующие эндпоинты. Либо ссылка на реальный контракт, либо явная пометка `[нет API]` / `[предложение по бэкенду]`.

## Транспорт API под вопросом (REST vs GraphQL)

Формат API может измениться — рассматривается переход на GraphQL. Описывай потребности в данных **транспортно-нейтрально**:

1. ЧТО нужно экрану: сущность, поля, фильтры, сортировка, пагинация, связи.
2. Только потом — ГДЕ это лежит сейчас (REST-эндпоинт/DTO), если есть.

Так спека переживёт смену транспорта: меняется доставка, требования к данным остаются. Не зашивай допущения вида «один экран = один REST-вызов».

Отдельно помечай экраны, где текущий REST **явно неудобен** (нужно 4+ запроса, over-fetching, N+1 на клиенте) — это фактура для решения по GraphQL.

## Вход

- Фото/сканы нарисованных экранов ИЛИ текстовые описания.
- Роль(и) пользователя для каждого экрана.
- Целевая платформа: мобильный PWA / десктоп-панель / оба.

Если экран непонятен на фото — задай ОДИН уточняющий вопрос, не выдумывай элементы.

## Процесс (по одному экрану)

### 1. Идентификация
Название экрана, роль(и), точка входа (откуда попадает), цель экрана.

### 2. Layout-регионы
Зоны без стилей: header / nav / content / list / detail / actions / footer. Иерархия вложенности.

### 3. Компоненты
Семантические имена: `AppHeader`, `ScheduleList`, `LessonCard`, `AttendanceButton`, `EmptyState`, `FilterBar`. Для каждого — назначение и ключевые данные.

### 4. Потребности в данных (транспортно-нейтрально)
Для каждого компонента с данными:
- **Нужно:** сущность + поля + фильтры/сортировка/пагинация.
- **Сейчас доступно:** контракт/эндпоинт из `*-api-contract`, если есть.
- **Пробел:** `[нет API]` или `[предложение по бэкенду]` с описанием.

### 5. Состояния (критично — часто забывают)
Для каждого экрана/списка: loading, empty, error, success + role-specific (что видит headman, но не student). Отметь, что было на бумаге, а что добавлено.

### 6. Навигация и действия
Куда ведёт каждая кнопка. Что происходит при действии (оптимистично? подтверждение для деструктивного — «отменить пару»?). Edge cases: неавторизованный доступ, нехватка прав роли.

### 7. Адаптив (заметки, не реализация)
Что меняется mobile vs desktop. Конкретные брейкпоинты — позже, в Figma.

## Вывод

- `wireframes/<screen-name>.md` — по файлу на экран, все 7 секций.
- `wireframes/00_overview.md` — список экранов, карта навигации, общие компоненты (кандидаты в переиспользуемый `components/`).
- `wireframes/figma-spec.md` — чеклист для Figma: frame-структура, переиспользуемые компоненты, состояния как variants, карта навигации для prototype.
- `wireframes/backend-requests.md` — **все пометки `[нет API]` / `[предложение по бэкенду]`** в одном месте, сгруппированные по сервису. Плюс список экранов, где текущий REST неудобен (фактура к решению по GraphQL).

Опционально: схематичный low-fi блочный wireframe каждого экрана (прямоугольники с подписями зон), БЕЗ цвета.

## Constraints

- НИКАКОГО визуального дизайна (цвета/тени/финальные шрифты). Только структура и логика.
- Не выдумывай данные/эндпоинты — привязывай к реальным контрактам или помечай пробел.
- Не пропускай non-happy состояния (loading/empty/error) — это половина ценности wireframe.
- Учитывай 4 роли: один экран может по-разному выглядеть для student/headman/teacher/admin.
- Не пиши код. Результат — вход для Figma, потом для скилла `vue-frontend-build`.
