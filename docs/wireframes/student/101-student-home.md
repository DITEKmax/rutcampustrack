# ПК-101 — Студент, Главная

> Этап 1, чат 1. Веб-десктоп 1920. Структура и логика, без визуала.
> Цветовые группы по скану: ЗЕЛЁНЫЙ — управляющие элементы, ЖЁЛТЫЙ — условное/наложенное, КРАСНЫЙ — фиксированное отображение.

## 2. Layout-регионы

```
AppShell                                       ← сквозной каркас всех страниц
├─ <header> AppHeader
│  ├─ RoleSwitcher               [ЗЕЛЁНЫЙ]   «староста | студент»
│  ├─ <nav> MainNav              [без цвета] главная · посещаемость · статистика ·
│  │                                          домашнее задание · карта · заявки и тикеты
│  └─ ProfileMenu                [ЗЕЛЁНЫЙ круг + ЖЁЛТЫЙ поповер «Настройки / Выход»]
└─ <main> dashboard-грид
   ├─ ряд 1
   │  ├─ LessonCard (featured)   [ЗЕЛЁНЫЙ]   «Пара "Название"» + отметка
   │  ├─ StatCard                [КРАСНЫЙ]   % посещаемости по предмету и типу этой пары
   │  └─ панель тренда
   │     ├─ AttendanceTrendChart [КРАСНЫЙ]   график недели в %, только «+»
   │     └─ Tabs + DatePager      [ЗЕЛЁНЫЙ] «Эта неделя | Весь период» + ◀ ▶
   └─ ряд 2
      ├─ ScheduleList            [КРАСНЫЙ]   расписание сегодняшнего дня с отметками
      ├─ late-checkin слой       [ЗЕЛЁНЫЙ]   действие «попросить поставить +»
      └─ HomeworkList            [КРАСНЫЙ]   дз дня + собственный DatePager
```

**Сверка со сканом.** Зелёные: переключатель ролей, круг профиля, карточка пары, полоса «Эта неделя / Весь период», блок про нажатие на пару со статусом «н». Жёлтый: только «Настройки / Выход» — выпадающее меню профиля. Красные: процент посещаемости, график недели, расписание дня, дз дня. Навигационный ряд не окрашен: по заметке 3 это «страницы под кнопками и профилем», в узких версиях уезжает в бургер-меню.

### Красный ≠ без взаимодействия

Два «красных» блока содержат точечные действия, и это следует из заметок скана:
- **расписание дня** — заметка 7: иконка справа отправляет заявку старосте;
- **дз дня** — заметка 8: галочка «сделано / не сделано» плюс листание дней.

Трактовка: красный = «блок не является управляющим элементом», но действия внутри строк есть.

### Три независимых контекста периода (уточнено владельцем)

Ключевое: на экране **не один период, а три независимых**.

| Блок | Контекст | Управление |
|---|---|---|
| `LessonCard` + `StatCard` | текущая/ближайшая пара; процент по её `предмет + тип занятия` | нет управления, следует за парой |
| `AttendanceTrendChart` | «Эта неделя» (листается) / «Весь период» | `Tabs` + `DatePager` — **только график** |
| `ScheduleList` | всегда сегодня | нет |
| `HomeworkList` | день, свой независимый | собственный `DatePager` |

**Состав вкладок и память разреза.** Полоса «Эта неделя / Весь период» — это `Tabs`; сам компонент состава не знает. Перечень вкладок, активный разрез и запомненная дата листания принадлежат странице `StudentHomePage` (K1), а не компоненту.

Следствия:
- `DatePager` присутствует **в двух экземплярах** (недели у графика, дни у дз). Компонент общий, состояние раздельное. В URL — два параметра, а не один.
- В режиме «Весь период» стрелки листания недоступны: они принадлежат только режиму недели.
- `StatCard` слева от графика — это **не общая посещаемость**, а процент по предмету текущей пары с её типом занятия, только по «+».

## 4. Потребности в данных

### 4.1. Текущая или ближайшая пара для отметки

- **Нужно:** одна `Lesson` со статусом `ACTIVE` (или ближайшая `PLANNED`): предмет, тип занятия, время, аудитория, **флаг блокировки геоотметки старостой**, мой текущий статус отметки, окно, в которое отметка ещё принимается.
- **Сейчас:** `GET /schedule/groups/{groupId}/lessons` (диапазон дат, все пары) + отдельно мои отметки. Блокировка ставится через `POST /schedule/lessons/{id}/blockage`.
- **Пробел:** `[уточнение по контракту]` — есть ли `geoBlocked` в представлении пары. Без него кнопка отметки врёт: студент нажмёт, а отметка запрещена (JS-HEADMAN-02, JS-STUDENT-12).
- **Пробел:** `[предложение по бэкенду]` — «моя ближайшая релевантная пара» как отдельная потребность, а не выборка из недельного списка на клиенте.

### 4.2. Отметка по геолокации и авто-эскалация

**Флоу, подтверждённый владельцем:**

| Ситуация | Путь | Итог |
|---|---|---|
| Пара идёт, студент нажал «Отметиться», гео прошло | подтверждение | `+` |
| Пара идёт, гео не прошло | заявка уходит **автоматически**, уведомление «отправлено старосте» | кнопка неактивна, `pending` |
| Пара закрыта со статусом «н», попытки отметки не было | иконка в строке расписания, вручную | кнопка неактивна, `pending` |

- Оба пути создают **одну и ту же заявку** и делят лимит «одна на пару».
- Отклонение старостой окончательно: повторить нельзя, «н» остаётся.
- Ручной кнопки в карточке текущей пары **нет** — прежняя механика JS-STUDENT-02 отменена.

- **Нужно:** `{lessonId, lat, lon, accuracy}` → результат `ok | out_of_range | geo_blocked | window_closed | already_marked` + новый статус. При неуспехе — автоматическое создание заявки старосте и возврат фронту `requestId` и статуса заявки.
- **Сейчас:** `POST /attendance/checkin`; отдельно `POST /attendance/late-checkin/{lessonId}`.
- **Пробел:** `[предложение по бэкенду]` — авто-эскалация выполняется на сервере **одной операцией** с неуспешным чекином. Если собирать на клиенте двумя вызовами, при обрыве между ними студент останется с «н» и без заявки, а повторить нечем — ручная кнопка на карточке убрана.
- **Пробел:** `[предложение по бэкенду]` — **идемпотентность по паре `(студент, пара)`** на сервере. Тогда «одна заявка на пару» гарантируется ключом, а не поведением фронта, и повторный запрос безопасен.
- **Пробел:** `[предложение по бэкенду]` — гарантия доставки старосте (сохранение + повторы на стороне сервера). Фронт различает «заявка создана» и «староста увидел»: студенту показываем первое.
- **Идея владельца (Wi-Fi МИИТ как дополнительный признак присутствия):** целиком серверная проверка. На структуру экрана не влияет — влияет только на текст в состоянии «не удалось».

### 4.3. Процент по паре и недельный тренд

- **Нужно (StatCard):** агрегат «мой % по конкретному `предмет + тип занятия` за семестр», только по «+».
- **Нужно (график):** разбивка по **дням недели** в %, только по «+»; будущие пары в знаменатель не входят; режим «весь период» как альтернативный разрез.
- **Сейчас:** `GET /attendance/reports/student/stats`; `GET /attendance/reports/student/dashboard` (по описанию — общий %, разбивка, недельный timeseries, топ пропущенных предметов).
- **Пробел:** `[уточнение по контракту]` — timeseries это «по неделям» или «по дням внутри недели»? Экрану нужно второе. И принимает ли dashboard произвольную неделю (заметка 6 — листание влево/вправо) или всегда текущую.
- **Пробел:** `[уточнение по контракту]` — даёт ли `student/stats` разрез именно по паре `предмет + тип занятия`, а не по предмету целиком.
- **Пробел:** `[предложение по бэкенду]` — режим «весь период» как параметр того же агрегата.

### 4.4. Расписание дня с отметками

- **Нужно:** пары сегодняшнего дня + **мой статус по каждой** в одном представлении: предмет, тип, время, аудитория, **признак смены аудитории**, статус пары (планируется / идёт / закрыта / отменена), статус отметки, для «у» — тип и комментарий причины, для «н» — есть ли заявка late-checkin и её статус.
- **Сейчас:** `GET /schedule/groups/{groupId}/lessons` + `GET /attendance/reports/student/records` + `GET /attendance/late-checkin/pending` — сшивание на клиенте по `lessonId`.
- **Пробел:** `[предложение по бэкенду]` — смена аудитории (`roomChanged` + прежнее значение). Владелец отметил это как новый функционал; со стороны старосты появится действие «изменить аудиторию».
- **Пробел:** `[предложение по бэкенду]` — статус моей заявки late-checkin **в составе строки пары**, иначе после перезагрузки страницы кнопка снова выглядит активной, хотя заявка уже подана.

### 4.5. Дз дня

- **Нужно:** задания на выбранную дату + мой флаг выполнения; переключение дней без ухода со страницы.
- **Сейчас:** `GET /academic/homeworks` (группа + семестр), `POST` / `DELETE /academic/homeworks/{id}/complete`.
- **Пробел:** `[уточнение по контракту]` — есть ли фильтр по дате или паре. Если нет, фронт грузит **все задания семестра**, чтобы показать три штуки за день.

### 4.6. Шапка

- **Нужно:** ФИО, аватар, группа, список ролей, активная роль.
- **Сейчас:** `GET /academic/users/me`.
- **Решено:** активная роль после входа — **базовая**: `student` вперёд `headman`, `teacher` вперёд `admin`. Расширенная включается вручную через `RoleSwitcher`.

### ⚠️ Фактура к решению о транспорте

Главная требует **6–8 запросов** до первого полного кадра: профиль → активный семестр → пары дня → мои отметки → pending-заявки → агрегат по паре → недельный тренд → дз. Плюс два клиентских join'а (по `lessonId`, по `subjectId`) и over-fetching дз. Самый нагруженный по числу вызовов экран из разобранных.

## 5. Состояния

Из нарисованного на бумаге есть только состояния отметки (заметка 7) и «на подтверждении». **Остальное добавлено при разборе.**

### Карточка пары (`LessonCard featured`) — ключевой автомат

| Состояние | Условие | Что показываем |
|---|---|---|
| `no-lesson` | сейчас пар нет | «Пар сейчас нет» + время ближайшей |
| `upcoming` | пара ещё не началась | отсчёт до начала, отметка недоступна |
| `ready` | пара идёт, не отмечен | кнопка «Отметиться» активна |
| `geo-permission` | браузер запрашивает доступ | подсказка |
| `geo-denied` | доступ к геолокации запрещён | инструкция, как включить, + путь через старосту. **Отдельная ветка, не ошибка сервера** |
| `checking` | проверка идёт | `aria-busy`, индикатор |
| `success` | отметка принята | «+», расписание ниже обновляется сразу |
| `failed-escalated` | гео не прошло | «Не удалось по геолокации. Староста уведомлён» + статус заявки, кнопка неактивна |
| `geo-blocked` | староста заблокировал геоотметку | отметка недоступна, объяснение почему. **Без этого состояния экран врёт** |
| `already-marked` | уже отмечен | статус + источник отметки |
| `cancelled` | пара отменена | «Отменена», отметка недоступна |
| `window-closed` | пара закрыта, отметки нет | «н» + путь через late-checkin |

### Остальные блоки

У каждого свои `loading` (скелетон) · `empty` (нет пар / нет дз / нет данных за период) · `error` (`title`/`detail` из RFC 9457 + повтор) · `success`. **Ошибка одного блока не роняет страницу** — блоки грузятся и падают независимо.

### Общие

- `offline` — предупреждение с пометкой, что данные могут быть устаревшими; отметка недоступна, кэш расписания показываем как есть.
- `forbidden` — `teacher` / `admin` по прямой ссылке: `ForbiddenState` без утечки данных.
- `no-active-semester` — семестр не активирован (JS-ADMIN-09): вырожденный, но реальный случай, весь дашборд пуст.

### По ролям

`student` и `headman` видят идентичный контент. У старосты дополнительно отрисован `RoleSwitcher`, а в `MainNav` появляются разделы старосты. Студенческих блоков, скрытых от старосты, нет.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| `RoleSwitcher` | Смена активной роли → перезагрузка `MainNav` и переход на главную выбранной роли; данные страницы инвалидируются |
| `MainNav` | «посещаемость» → ПК-102. «статистика», «домашнее задание», «заявки и тикеты» → экраны ещё не разобраны. **«карта» — назначение не определено**, отложено в отдельный чат |
| `ProfileMenu` | «Настройки» → профиль (там же смена пароля, JS-SYSTEM-04). «Выход» → `POST /auth/logout` → 001 |
| `AttendanceButton` | Запрос гео → проверка → одно из состояний выше. Подтверждения не требует. **Оптимистичного UI нет:** результат зависит от сервера, показывать «+» до ответа нельзя |
| `LateCheckInButton` | Заявка старосте. Кнопка гаснет, переходит в «на подтверждении» — **необратимо** (заметка 7: «всегда»), поэтому **требуется подтверждение перед отправкой**: случайный клик не откатить |
| `HomeworkItem` чекбокс | Отметка «сделано» / снятие. Оптимистично с откатом при ошибке (JS-STUDENT-WEB-04) |
| Вкладки разреза (`Tabs`) / `DatePager` | Смена периода без перезагрузки. Оба параметра — в URL, чтобы состояние переживало обновление страницы; память разреза держит страница, а не `Tabs` |

**Нехватка прав:** неавторизованный → 001 с `returnUrl`. Авторизованный не-студент → `ForbiddenState`.

### A11y (структурно)

- Один `h1` на странице, блоки — `<section>` с `h2`; skip-link на `#main`.
- `ScheduleList` — именно список, не таблица (табличная семантика нужна на 102).
- `AttendanceStatusBadge` доступен текстом: «+ / н / у» цветом не кодируем, символ разворачивается словом в `aria-label`.
- Смена статуса после отметки объявляется через `role="status"`, ошибка отметки — `role="alert"`.
- Тач-таргет `LateCheckInButton` не меньше 44×44, несмотря на то что это иконка.
- Всплывающая причина по «у» доступна с клавиатуры, а не только по hover.
- `prefers-reduced-motion` отключает анимацию проверки гео; текстовый статус остаётся.

## Решения задачи 4 — внесено 01.08.2026

Источник — `02-backend/backend-conflicts.md`. Правила ниже имеют приоритет над более ранними формулировками этой спеки.

**Механика отметки (§3 backend-conflicts, переносится как есть):**

- **Окно отметки** — с 5 минут до начала пары до 5 минут после её окончания. Всё это время ячейки **пусты по умолчанию**; пустота означает «ещё не решено», а не «нет данных».
- **Четыре пути получения «+»:** успешная геоотметка; подтверждение старосты по автоматическому запросу (он уходит сам при неудачной геопроверке и **не истекает** — подтвердить можно и через несколько дней); замена ручного «н» успешной геоотметкой; одобренное прошение по прошедшей паре (лимит — пять за семестр, Р-2).
- **Закрытие окна:** после конца пары и пятиминутного хвоста оставшиеся пустые ячейки становятся **«н»**; счётчики и агрегаты обновляются в этот момент.
- **«у» ставится только по тикету** и никаким другим путём. Одобрение тикета не заменяет уже проставленный «+».
- **Приоритет источников:** успешная геоотметка и подтверждение старосты **перекрывают ручное «н»**; тикет на «у» перекрывает любое состояние, кроме «+».
- **При заблокированной паре** (Р-11) недоступны все четыре пути — остаётся только тикет на «у». Блокировка запрещает **любое** взаимодействие с парой, а не только геоотметку.
