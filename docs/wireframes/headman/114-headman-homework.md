## 4. Потребности в данных

### 4.1 Предметы и их реальные типы занятий

- **Нужно:** предметы своей группы; у каждого — **фактически существующие** типы занятий.
- **Сейчас:** `GET /academic/subjects` (HEADMAN — только своя группа).
- **Пробел:** тот же `AC-4` из ПК-112 — третий потребитель. Без явного списка типов форма предложит тип, которого у предмета нет, и следующая пара не найдётся никогда.

### 4.2 Следующая подходящая пара (заметка 1 job, заметка 2 макета)

- **Нужно:** ближайшая пара по паре «предмет + тип занятия» после текущей даты — её дату календарь подсвечивает и делает единственной доступной в режиме привязки.
- **Сейчас:** только вычислением по `GET /schedule/groups/{groupId}/lessons`.
- **Пробел:** **это ровно `S-6` из ПК-111**, где он нужен для быстрой выдачи дз с главной. Второй потребитель усиливает запрос: клиент не знает, насколько далеко вперёд искать — предмет может не встретиться две недели.

### 4.3 Публикация задания

- **Нужно:** предмет, тип занятия, **привязка к паре** (`lessonId` либо явный признак «без привязки»), дата, **одна основная ссылка отдельным полем**, описание.
- **Сейчас:** `POST /academic/homeworks` (HEADMAN).
- **Пробел:** `[уточнение по контракту]` — есть ли в модели задания **поле привязки к паре** и **отдельное поле основной ссылки**. Без первого не работают ни ползунок, ни автоперенос, ни правило архивации; без второго ссылка утонет в описании и `AppLink` нечего рендерить.
- **Подтверждено владельцем:** прочие ссылки внутри описания — **ответственность отображения, а не модели данных**. Бэкенду хранить их отдельно не нужно, фронт делает их кликабельными при выводе (`LinkifiedText`).

### 4.4 Списки «Актуальное» и «Архив» — критерий подтверждён владельцем

- **Нужно:** задания группы с сортировкой по дате по возрастанию, фильтрами (предмет, тип занятия, диапазон дат), пагинацией; **признак принадлежности к актуальным или архивным**.
- **Критерий архива (подтверждено владельцем):** задание уходит в архив, **когда прошла пара, на которую оно было создано**.
- **Следствие для задания без привязки к паре:** пары нет, значит критерием служит дата, выбранная в календаре. Записано как необходимое дополнение, а не как самостоятельное решение — при разночтении поправить.
- **Отменённая пара (подтверждено владельцем):** задание уходит **в архив**. Закрывает вопрос реестра §9, открытый с чата 2.
- **Возврат из архива не проектируется (подтверждено владельцем):** «из архива мы не возвращаем, только создаём новое». Архив строго на чтение.
- **Сейчас:** `GET /academic/homeworks` — по группе и семестру, **без фильтра по датам и без разделения на актуальные и архивные**.
- **Пробел:** `AC-1` из ПК-111 (фильтр по диапазону дат) — третий потребитель того же требования.
- **Пробел:** `[предложение по бэкенду]` — признак актуальности приходит **с сервера**. Клиент не может вычислить его сам: правило опирается на время окончания пары и на её статус отмены, а не на одну дату в задании.

### 4.5 Право на правку — расходится с текущим API

- **Нужно:** признак «текущий пользователь может редактировать и удалять это задание» и **автор** задания для показа.
- **Решение владельца:** править может **каждый, у кого есть право выкладывать дз** — староста и помощники с `manage_homework`. Не только автор.
- **Сейчас:** `PUT /academic/homeworks/{id}` и `DELETE /academic/homeworks/{id}` — **только автор**.
- **Пробел:** `[предложение по бэкенду]` `D-1` — снять ограничение «только автор», заменить проверкой права в группе. **Без этого экран врёт:** кнопки будут активны, а сервер откажет.
- **Пробел:** `[уточнение по контракту]` — приходит ли автор в модели задания. Он нужен не для прав, а для показа и для истории: раз редакторов несколько, «кто выложил» становится значимой информацией (заметка 2 job).

### 4.6 История изменений (заметка 2 job) — **крупный пробел**

- **Нужно:** по заданию — хронология: кто, когда, что изменил (текст, ссылка, дата, привязка к паре), включая факт первой публикации.
- **Сейчас:** **нет.**
- **Пробел:** `[предложение по бэкенду]` — это **второй потребитель той же аудит-подсистемы, что `A-1` на ПК-111** (журнал действий по паре). Два независимых экрана требуют одного механизма — аргумент делать его общим, а не точечно.
- **Усиление после решения о правах:** раз править может любой обладатель права, история перестаёт быть удобством и становится единственным способом понять, кто изменил задание.

### 4.7 Перенос задания вместе с парой (заметка 3 job)

- **Нужно:** при переносе пары связанные с ней сущности переезжают следом — **автоматически**, без действия старосты.
- **Сейчас:** автопереноса нет; самой операции переноса пары тоже нет (JS-HEADMAN-21 — «требуется решение бэкенда»).
- **Пробел:** `[предложение по бэкенду]` — формулировка владельца шире дз: «дз и, может, ещё какие-то данные по паре».
- **Смысловой край:** задание **без** привязки к паре при переносе **не двигается** — в этом и состоит назначение ползунка.
- **Ручной перенос** отдельной операцией не проектируется: дата и привязка меняются в форме редактирования.

### 4.8 Удаление

`DELETE /academic/homeworks/{id}`. Действие необратимо и уже разослано группе уведомлением → **подтверждение обязательно**. Ограничение «только автор» снимается вместе с `PUT` (`D-1`) — по аналогии с редактированием; при разночтении подтвердить отдельно.

### 4.9 Несколько заданий на одну пару

**Подтверждено владельцем:** на одну пару может приходиться **несколько заданий**. Уникальности «пара → задание» нет.

- **Следствие для фронта:** список не схлопывается по паре, карточки показываются отдельно; на ПК-111 виджет «дз на сегодня» тоже должен допускать несколько записей на одну пару.
- **Пробел:** `[уточнение по контракту]` — порядок заданий внутри одной пары (время публикации?) должен быть детерминирован, иначе список будет перетасовываться между запросами.

### ⚠️ Фактура к решению о транспорте

| Действие | Запросов |
|---|---|
| Открытие экрана | профиль / права / семестр — **и всё**. Данных не запрашивается (заметка 1 макета) |
| Режим «Добавить» | предметы с типами + следующая подходящая пара → **2** |
| Режим «Актуальное» / «Архив» | список с фильтрами → **1** |
| Смена фильтра | **1** |
| История изменений | **1** на открытие |

**Самый лёгкий экран роли: 1–3 запроса.** И единственный, где экономия запросов — **осознанное продуктовое решение владельца** (заметка 1 макета), а не побочный эффект удачной структуры.

| `no-mode` | режим не выбран — **стартовое** | пояснение «выберите, что нужно сделать» + три кнопки. **Это не `EmptyState`:** данных не запрашивали, значит не «пусто», а «ещё не спросили». Одинаковый текст на оба случая — дефект (§6.2 реестра) |
| `mode-selected` | режим выбран | соответствующая секция; выбранная кнопка помечена **текстом и состоянием**, не только цветом |

### `HomeworkComposerForm`

| Состояние | Условие | Что показываем |
|---|---|---|
| `no-subject` | предмет не выбран | типы занятий и календарь недоступны |
| `no-type` | тип занятия не выбран | календарь недоступен |
| `bound-mode` | ползунок в «привязано к паре» | в календаре доступен **только день следующей подходящей пары**, он подсвечен |
| `no-next-lesson` | подходящей пары впереди нет (конец семестра, предмет закончился) | **доступных дней ноль.** Пояснить и предложить переключить ползунок. **Без этого состояния форма заходит в тупик** без объяснения |
| `free-mode` | ползунок в «все дни» | доступна любая дата; привязки к паре не будет, при переносе пары задание не поедет |
| `ready` | всё заполнено | «Опубликовать» активна |
| `editing` | форма открыта для правки существующего задания | поля заполнены текущими значениями; смена привязки и даты — здесь же |
| `submitting` | отправка | `aria-busy`, кнопка заблокирована |
| `submit-error` | сервер отказал | `role="alert"`, **введённое не теряется** |
| `forbidden-publish` | нет права `manage_homework` | режим «Добавить» недоступен с пояснением, форма не рендерится |

### Списки «Актуальное» и «Архив»

| Состояние | Условие | Что показываем |
|---|---|---|
| `loading` | грузится | скелетон карточек |
| `empty-actual` | актуальных нет | «активных заданий нет» — формулировка **про будущее** |
| `empty-archive` | архив пуст | «в архиве пока ничего нет» — формулировка **про прошедшее**. Разные тексты обязательны (§6.2 реестра) |
| `filtered-empty` | фильтры не оставили строк | «под выбранные фильтры ничего не подошло» + сброс. Отличать от «данных нет» |
| `archived` | режим «архив» | **все действия отсутствуют, кроме истории** (заметка 4 макета). Возврата в актуальные нет — решение владельца |
| `error` | список не пришёл | `ErrorState` + повтор |

### Общие

- `offline` — публикация, правка и удаление блокируются; просмотр по кэшу с пометкой об устаревании.
- `no-active-semester` — публиковать некуда, форма не рендерится, списки пусты с пояснением.
- `forbidden` — `student` без `is_headman` при прямом заходе по адресу.

### По ролям и помощникам

| Ситуация | Поведение |
|---|---|
| Староста | все режимы и действия |
| Помощник **с** `manage_homework` | **все режимы и действия, включая правку чужих заданий** — подтверждено владельцем |
| Помощник **без** `manage_homework` | режим «Добавить» недоступен с пояснением; «Актуальное» и «Архив» читаются; действия на карточках `aria-disabled` с пояснением |

⛔ **Состояние `not-author` отменено.** В первоначальном разборе оно предполагалось по ограничению API «только автор»; решением владельца авторство перестало влиять на права. Автор остаётся как **информация** («выложил ‹имя›»), а не как ограничение.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| Три кнопки режима | показывают свою секцию. **Предлагаю сделать режимы адресуемыми** (свой URL): иначе перезагрузка сбрасывает старосту на пустой экран посреди работы |
| `LessonBindingToggle` | переключает набор доступных дат в календаре. В режиме редактирования смена привязки **меняет судьбу задания при переносе пары и правило его архивации** — пояснить текстом рядом, а не оставлять на догадку |
| «Опубликовать» | создаёт задание, уведомляет группу (`homework.published`). Подтверждения не требует; при ошибке введённое сохраняется |
| «Редактировать» | открывает `HomeworkComposerForm` с текущими значениями. **Включает смену даты и привязки** — отдельной кнопки «Перенести» нет (решение владельца). Повторное уведомление `homework.updated` |
| «Удалить» | **подтверждение обязательно** — действие необратимо и уже разослано группе |
| «История изменения» | раскрывает `HomeworkHistoryPanel` внутри карточки. Доступна всем, включая архивные записи |
| Основная ссылка | внешняя, новая вкладка, видимый домен, доступное имя с предметом |
| Ссылка внутри описания | то же поведение: внешняя, видимый домен (`LinkifiedText`) |

**Нехватка прав.** Неавторизованный → вход с возвратом. Без `is_headman` → `ForbiddenState` без утечки данных группы. Помощник — по §5.

### A11y (структурно)

- **Три кнопки режима — не `tablist`.** ARIA требует, чтобы одна вкладка была выбрана всегда, а здесь пустой старт штатен. Это кнопки (или ссылки, если режимы адресуемые); смена режима объявляется через `role="status"`.
- `h1` «Домашнее задание — ‹код группы›», `h2` на активную секцию.
- **Календарь:** сетка с перемещением стрелками, `aria-current="date"` на сегодня, **недоступные дни объяснены текстом**, а не просто погашены. В режиме привязки доступен ровно один день — это надо озвучить, иначе календарь выглядит сломанным.
- **Ползунок — `role="switch"`** с видимой подписью обоих состояний. Переключение **обязательно объявляется**: оно молча меняет содержимое календаря.
- Форма — `FormField` из реестра: `label` / `for` / `id`, подсказки и ошибки через `aria-describedby`, ошибки **текстом, не цветом**. Проверка ссылки — текстовая.
- Список заданий — `<ul>`, каждая карточка `<li>` с `h3` (предмет + тип занятия). **Действия внутри карточки имеют доступные имена с предметом и датой** — иначе экран озвучится как «Удалить, Удалить, Удалить».
- **`LinkifiedText`:** автоматически распознанные ссылки должны получать осмысленное доступное имя и видимый домен; голый URL в качестве текста ссылки допустим, но не должен быть единственным ориентиром.
- Подтверждение удаления — `ConfirmDialog`: **единственный оверлей продукта**, `role="dialog"`, `aria-modal="true"`, ловушка фокуса, Esc, возврат фокуса на вызвавшую кнопку. `HomeworkHistoryPanel` — **не оверлей**: раскрывающийся регион в карточке, `aria-expanded` на кнопке «История изменения», фокус переводится и **не запирается**, Esc и повторное нажатие закрывают с возвратом фокуса на кнопку.
- История — `<ol>` в хронологическом порядке: записи разнородны, таблица навяжет ложную сетку.
- Заблокированные действия — `aria-disabled` **с текстовым пояснением рядом**, не скрытые.

## 7. Заметки на будущее

### Адаптив

Экран узкий по природе: форма в одну колонку, список карточек. До 1280 схлопывается почти без потерь.

- **Первым уходит** панель фильтров — в поповер.
- **Затем** действия карточки — в меню «ещё».
- **Нельзя потерять:** видимость пометки привязки к паре (от неё зависит поведение задания) и различие «актуальное / архив».

### Мобильная поверхность (не сейчас, отдельный цикл)

Публикация дз с телефона — реальный сценарий старосты (JS-HEADMAN-20). Календарь с одним доступным днём и ползунком — первое, что придётся переосмыслить: на мобильном это скорее «подтвердите дату следующей пары» с редким уходом в ручной выбор.

### Конфликты с уже разобранным

- **ПК-111** — форма выдачи дз там та же самая (`HomeworkComposerForm`, раскрываемая на странице). Все решения этого экрана (ползунок, один доступный день, одна основная ссылка) действуют и там. Файл 111 нужно синхронизировать при финальной сборке.
- **ПК-104** (студент) — решения «задание отменённой пары уходит в архив» и «ссылки в тексте кликабельны» действуют и на студенческом экране. Второе означает, что `LinkifiedText` сразу `shared`.
- **JS-HEADMAN-21** (перенос пары) — автоперенос задания превращает отсутствующую операцию переноса из «удобства» в зависимость двух экранов.
