### Отношение к ПК-101

На 101 уже есть `HomeworkList` / `HomeworkItem` — дз дня с переключателем выполнения. **Это та же сущность; новых имён не заводим**, 104 использует те же компоненты в других вариантах компоновки и с другими масштабами периода (правило «варианты вместо синонимов»).

**Открыто (предложение фронта, владельцем не подтверждено):** на 101 оставить дз только на сегодня без листания + ссылка «все задания» → 104. Причина: листание дней существует в двух местах — два независимых состояния одной сущности.

### Решение владельца по блоку «Сегодня»

Закреплённого блока «Сегодня» **нет**. Прим. 5 скана отменено. «Сегодня» — дефолтное значение `DatePager`; в режимах «Неделя» и «Месяц» сегодняшний день выделяется внутри периода. Из любой точки листания есть возврат к текущей дате одним действием (`showCurrentReset`).

## 2. Layout-регионы

```
AppShell
├─ header (AppHeader)                        [зелёный / жёлтый]
└─ main #main, h1 «Домашнее задание»
    ├─ toolbar                               [зелёный]
    │   ├─ Tabs                              «День / Неделя / Месяц»
    │   └─ DatePager                         unit по выбранному режиму + действие «Сегодня»
    └─ region: scoped (ровно один блок)      h2 «<период>»
        ├─ [День]    HomeworkList variant="flat"          [жёлтый]
        ├─ [Неделя]  HomeworkList groupBy="day"           [жёлтый] h3 на каждый день
        └─ [Месяц]   MonthCalendar + HomeworkList flat    [жёлтый] два h3: календарь и задания выбранного дня
```

**Состав вкладок и память режима.** Полоса «День / Неделя / Месяц» — это `Tabs`; сам компонент состава не знает. Перечень режимов, активный режим и **запомненная дата каждого режима** принадлежат странице `StudentHomeworkPage` (K1). Режимы взаимоисключающие (прим. 3).

**Про жёлтый на скане.** По легенде жёлтый = «условное / наложенное». Здесь карточки дз — не оверлей, а основной контент, зависящий от выбора в зелёной панели. Трактуем жёлтый как «зависит от выбора режима». Настоящий оверлей на экране один — поповер профиля.

## 4. Потребности в данных

**Сущность `homework`.** Поля: `id`, предмет (`id`, название, тип занятия), текст задания, ссылка(и), дата, на которую задано, признак «выполнено мной», порядок предмета в расписании этого дня, автор и время публикации / обновления.

**Фильтры:** диапазон дат (день / неделя / месяц), активный семестр, моя группа — подставляется сервером из контекста пользователя.
**Сортировка:** сервер отдаёт естественный порядок «по порядку пар дня»; перестановку выполненных вниз делает клиент — это состояние UI, не данных.
**Пагинация:** не нужна, объём ограничен периодом.

**Сейчас доступно:**
- `GET /academic/homeworks` — список заданий для группы и семестра;
- `GET /academic/homeworks/{id}` — деталь;
- `POST` / `DELETE /academic/homeworks/{id}/complete` — переключение выполнения (STUDENT). Ровно то, что нужно экрану.

**Пробелы:**

1. `[предложение по бэкенду]` — **признак выполнения текущим студентом в списке.** Из описания списка не видно, приходит ли он. Без него переключатель не с чего инициализировать, а деталь на каждое задание — N+1.
2. `[предложение по бэкенду]` — **фильтр по диапазону дат.** Сейчас список отдаётся за семестр целиком: ради одного дня тянется весь семестр, режим месяца без диапазона нереализуем разумно.
3. `[предложение по бэкенду]` — **привязка задания к паре или порядковый номер предмета в дне.** Без этого требование «раньше пара — раньше задание» невыполнимо: клиент тянет расписание каждого дня и джойнит (×7 в неделе, ×30 в месяце).
4. `[предложение по бэкенду]` — **лёгкий агрегат для календаря:** по каждой дате есть ли задания, сколько, краткие названия предметов. Иначе календарь тянет полные тексты всех заданий месяца ради подписей под датами.
5. `[уточнение по контракту]` — **ссылка: одна или несколько**, отдельное поле или внутри текста. От этого зависит макет ячейки: иконка против списка.
6. `[уточнение по контракту]` — **что происходит с дз отменённой пары.** Пара показывается, но не считается; про её задание правил нет.

## 5. Состояния

На бумаге нет ни одного. Всё добавлено при разборе.

| Блок | Состояния |
|---|---|
| День | `loading` (скелетон, `aria-busy`) · `empty` с **разными формулировками** для будущего дня («ещё не задано») и прошедшего («не было задано») · `error` (RFC 9457 + повтор) · `out-of-range` — граница семестра, стрелка недоступна с пояснением |
| Неделя | те же + `partial`: пустые дни **показываются с пометкой**, а не выбрасываются, иначе неделя выглядит рваной |
| Месяц | `loading` календаря отдельно от `loading` панели дня · `empty` — в месяце заданий нет · день без заданий выбирается и показывает пустое состояние, ячейка не блокируется |
| Переключатель выполнения | оптимистичное обновление с откатом при ошибке сервера; при откате — `role="alert"` с текстом ошибки, отметка возвращается назад |
| Экран | `no-active-semester` · `offline` — переключение выполнения недоступно с пояснением, данные из кэша помечены как возможно устаревшие · `forbidden` — если у пользователя нет группы |

**Ролевых различий нет.** Староста видит тот же экран; управление заданиями — на его собственном.

**A11y на уровне структуры:**
- переключатель выполнения — настоящий чекбокс с `<label>`, не кликабельный div; текст задания связан через `aria-describedby`;
- **перестановка выполненного вниз не уводит фокус**: фокус остаётся на переключателе перемещённого задания, факт перемещения объявляется через `role="status"`;
- ячейка календаря — `<button>` с `aria-pressed` / `aria-current`, доступное имя = дата + количество заданий; наличие заданий передаётся не только визуальной меткой;
- неделя — список дней с заголовками, не таблица: содержимое дня не табличное;
- смена периода объявляется через `role="status"`.

## 6. Навигация и действия

| Элемент | Действие |
|---|---|
| `MainNav` / `RoleSwitcher` / `ProfileMenu` | как на 103 |
| Вкладки режима (`Tabs`) | выбор режима. Позицию другого режима **не сбрасывают** — каждый режим помнит свою дату в пределах сессии экрана; память держит страница, а не `Tabs` |
| `DatePager` ◀ ▶ | листание дня / недели / месяца в границах семестра; на границе стрелка недоступна с пояснением |
| «Сегодня» у пейджера | возврат к текущей дате из любой точки листания, одним действием |
| Ячейка календаря | выбор дня → обновление панели заданий. По умолчанию выбран сегодняшний день, если он в показанном месяце |
| Иконка ссылки | внешний переход в новой вкладке, домен виден |
| Переключатель выполнения | оптимистично, обратимо в обе стороны («можно как снять, так и поставить»). **Подтверждения не требует** — действие не деструктивно. Выполненное задание остаётся видимым, меняются подача и позиция |

Создания, редактирования и удаления заданий нет ни в каком состоянии — даже у пользователя с ролью `headman`.

## 7. Заметки на будущее

**Адаптив (без брейкпоинтов):**
- 1920: панель периода во всю ширину; в режиме месяца календарь слева, задания выбранного дня справа (как на скане).
- Уже: календарь и панель дня переходят в вертикальный порядок — календарь сверху, задания под ним.
- Неделя: при сужении заголовок дня переезжает над карточками вместо колонки слева.
- Карточка задания: основная нагрузка — текст; при сужении первым сжимается блок статуса, не текст.
- Календарь: краткие названия предметов под датой уходят первыми, остаётся маркер количества.

**Открытые вопросы по экрану:**
- убирать ли листание дз с главной в пользу 104;
- ссылка одна или массив;
- судьба дз отменённой пары;
- сбрасывается ли отметка выполнения, когда староста правит текст задания (предполагается, что нет — иначе правка запятой обнуляет прогресс группы; требует подтверждения).

**Для следующих этапов:**
- Три режима + отсутствие закреплённого блока на мобильной поверхности почти наверняка дадут другую компоновку — это отдельный цикл, не адаптив десктопа.
- Число запросов: **1–3 в зависимости от режима**, но без фильтра по датам каждый режим тянет задания всего семестра — фактура к решению REST/GraphQL, см. `backend-requests.md`.
