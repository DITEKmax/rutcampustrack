## Focal Points

Explicit primary focal point per feature area:

**`/headman/dashboard`**
Primary focal point: the 4-card stat grid (member count + today's lesson + ticket count + late check-in count). The dashboard is purely informational — no primary CTA. The most actionable element if counts > 0 is the pending ticket/late-checkin count chip, which links to the relevant page. The today's lesson card is the visual anchor of the center row.

**`/headman/group`**
Primary focal point: the "Назначить помощника" button in `.page-header__actions`. The student list below is read-only information; the actionable path is adding or removing an assistant. Existing assistant cards appear below the student table in a separate "Помощники" section, each with a "Удалить" icon button.

**`/headman/subjects`**
Primary focal point: the "Добавить предмет" button in `.page-header__actions`. The subject list is the secondary weight. Each row has an edit icon button; the primary new-subject action tops the page.

## Component Inventory

New components and behavior introduced in Phase 54. All are isolated to the `features/headman/` directory. Guard changes touch `studentGuard` and `headmanGuard` (behavior only — no new files).

### 0. Guard fix — HEAD-WEB-01

`studentGuard` already allows `user.role === 'STUDENT'` regardless of `isHeadman`. Headmen already pass this guard. **No guard code change required for HEAD-WEB-01** — the guard is correct as implemented in `student.guard.ts`. The `headmanGuard` also correctly requires `role=STUDENT && isHeadman`. The only change needed is to ensure the sidebar `NavItem` role filter includes headman in STUDENT-role items — headman users display all student nav items plus headman-specific items.

**Sidebar change — headman nav section:**

Add to `SidebarComponent`:

1. A new headman primary item (alongside the student "Главная"):
```
{ label: 'Кабинет старосты', icon: 'ph-crown-simple', route: '/headman/dashboard', roles: ['STUDENT'] }
```
Only rendered when `user.isHeadman === true`. The sidebar computed `filteredPrimaryItems` must be extended to check `user.isHeadman`.

2. New headman secondary items rendered below the existing student section, inside a new sidebar section labelled "Старостат", visible only when `user.isHeadman === true`:
```
{ label: 'Группа',    icon: 'ph-users-three',   route: '/headman/group',    isHeadman: true }
{ label: 'Предметы',  icon: 'ph-books',          route: '/headman/subjects', isHeadman: true }
```

Icon weight: `regular` (inactive), `fill` when `routerLinkActive`. Icon size: 22px (existing `--sidebar__icon` rule).

The `NavItem` interface must be extended with an optional `isHeadman?: boolean` field. `filteredNavItems` computed must additionally filter headman-gated items through `user.isHeadman === true`.

### 1. `/headman/dashboard` — HeadmanDashboardComponent

Layout: `.page-stack` with greeting header (same time-based pattern as admin and student dashboards).

**Header:**
- Greeting: `{Доброе утро / Добрый день / Добрый вечер}, Иван` (uses `auth.currentUser().fullName` first name).
- Eyebrow: "Кабинет старосты" in `--text-xs` / uppercase / `--tracking-wide` / `--text-muted`.
- Date: same `dateLabel` computed pattern as existing dashboards.
- Sub-heading: "Группа {groupName}" (resolved from `auth.currentUser().groupId` → headman API) in `--text-sm` / `--text-secondary`.

**Stat grid (4 cards using existing `StatCardComponent`):**

Row 1 — two cards side by side (CSS grid, `grid-template-columns: repeat(2, 1fr)`, `gap: var(--space-5)`):
- Card 1: `value=studentCount`, `label="Студентов в группе"`, `icon="ph ph-users"`, `accent="primary"`. Links to `/headman/group` via `routerLink` on card click.
- Card 2: `value=pendingExcuses`, `label="Тикеты о пропуске"`, `icon="ph ph-file-text"`, `accent="warning"`. Badge style: if `pendingExcuses > 0`, show count as number; if 0, show "0". Links to `/headman/excuses` (Phase 55 route — render the link but use `[disabled]="true"` styling until Phase 55 is shipped; alternatively omit link and keep card non-interactive for Phase 54).

Row 2 — two cards side by side:
- Card 3: Today's lesson card — NOT a `StatCardComponent`. Custom component `HeadmanTodayLessonCardComponent`. See below.
- Card 4: `value=pendingLateCheckins`, `label="Запросы поздней отметки"`, `icon="ph ph-clock-countdown"`, `accent="info"`. Same disabled-link treatment as Card 2 until Phase 55.

**Grid responsive:** on < 600px breakpoint, switch to `grid-template-columns: 1fr` (single column, cards stack).

**HeadmanTodayLessonCardComponent** (new, Phase 54):

If today has an ACTIVE or earliest PLANNED lesson:
```
.page-card with border-left: 4px solid var(--accent-warning)
  [ ph-chalkboard-teacher 24px duotone --accent-warning ]
  [ Subject name — --text-base / 600 / --font-heading ]
  [ HH:MM – HH:MM — --text-xs / --font-mono / --text-secondary ]
  [ Room / location if available — --text-xs / --text-muted ]
  Status chip: "Идёт" (ACTIVE, --status-present) or "Запланирована" (PLANNED, --accent-warning)
```

If no lesson today (empty):
```
.page-card with --border-subtle
  [ ph-calendar-x 24px duotone --text-muted ]
  [ "Нет пары сегодня" — --text-base / 600 / --text-secondary ]
```

**Dashboard loading state:**
4× skeleton stat card placeholders (`--bg-elevated` shimmer, using existing `dashboard-shimmer` keyframe, 100px height each, `--radius-md`).

**Dashboard error state:**
`.page-error` inline: `ph-warning-circle` 20px + "Не удалось загрузить данные группы. Попробуйте обновить страницу."

**Data sources:**
- `GET /api/academic/headman/group/members` → student count
- `GET /api/schedule/lessons?groupId={groupId}&date={today}` → today's lesson (reuse `StudentApiService.getWeekLessons` or headman equivalent)
- `GET /api/academic/headman/excuses?status=pending` → pending excuse count
- `GET /api/academic/headman/late-checkins?status=pending` → pending late check-in count

All four loaded in parallel via `forkJoin`. Signals: `loading`, `error`, `memberCount`, `todayLesson`, `pendingExcuses`, `pendingLateCheckins`.

- Subtitle: "{groupName}" in `--text-sm` / `--text-secondary`

- Empty: `.page-empty` with `ph-users` 32px duotone + "Группа пуста" heading + "В вашей группе пока нет студентов." body.

If no assistants: inline muted message "Помощники не назначены" in `--text-sm` / `--text-muted` / centered.

```

[ Permission chips row ]

```

Permission chips (inline pill chips per granted permission, `--radius-full`, `--bg-elevated` background, `--text-secondary` text, `--text-xs` / 600):
- `excuse_approve` → chip label "Одобрение пропусков"
- `late_checkin_approve` → chip label "Поздние отметки"
- `subject_manage` → chip label "Управление предметами"
- `attendance_mark` → chip label "Проставление посещаемости"

**AssignAssistantDialog — MatDialog:**

Trigger: "Назначить помощника" button.
Dialog width: 520px max; 100vw - 32px on < 600px.
Dialog heading: "Назначить помощника старосты"

Form sections:
1. **Выберите студента** — `MatSelect` or searchable list of group students (excluding existing assistants and the headman themselves). Each option: full name + login. Required.
2. **Права помощника** — four `MatCheckbox` rows with labels and 44px min-height per row:
   - `excuse_approve` — "Одобрять тикеты о пропусках"
   - `late_checkin_approve` — "Одобрять запросы поздней отметки"
   - `subject_manage` — "Управлять предметами группы"
   - `attendance_mark` — "Проставлять посещаемость"
   Helper text below checkboxes: "Можно выбрать несколько прав. Права можно изменить позже через переназначение." in `--text-xs` / `--text-secondary`.
3. **Кнопки** — right-aligned row: `[Отмена — mat-stroked-button]` `[Назначить помощника — .btn-brand]`.

Validation: student must be selected. At least one permission must be checked (show inline error "Выберите хотя бы одно право" below checkboxes if submit attempted with none checked).

Submit behavior:
- Disable form + spinner inside "Назначить помощника" button.
- On success: close dialog + MatSnackBar "Помощник назначен." (duration: 4000ms).
- On API error: keep dialog open + `.page-error` inline below permissions: "Не удалось назначить помощника. Попробуйте ещё раз."

Trigger: trash icon button on assistant list item.
Pattern: `MatDialog` confirm (same pattern as existing admin "Revoke Headman" dialog — no new pattern needed).

Body: "Студент {fullName} потеряет все права помощника старосты."
Buttons: `[Отмена — mat-stroked-button]` `[Удалить — mat-flat-button color="warn" / --accent-danger styled]`.

On confirm:
- On success: close dialog + MatSnackBar "Помощник удалён." (duration: 4000ms). Reload assistant list.
- On API error: close dialog + MatSnackBar "Не удалось удалить помощника." (duration: 6000ms).

Dialog heading (create): "Новый предмет"
Dialog heading (edit): "Редактировать предмет"

Form fields:

- Validate: subject name required.
- On submit: disable form + spinner inside submit button.
- On success (create): close dialog + MatSnackBar "Предмет создан." (duration: 4000ms). Reload subject list.
- On success (edit): close dialog + MatSnackBar "Предмет обновлён." (duration: 4000ms). Reload subject list.
- On API error: keep dialog open + `.page-error` inline below teacher select: "Не удалось сохранить предмет. Попробуйте ещё раз."

**Delete subject — confirmation:**

Dialog heading: "Удалить предмет?"

Buttons: `[Отмена — mat-stroked-button]` `[Удалить — .btn-brand` with `--accent-danger` override background]`.

On confirm:
- On success: MatSnackBar "Предмет удалён." Reload list.
- On API 409 (subject has attendance records): MatSnackBar "Нельзя удалить предмет с записями посещаемости." (duration: 6000ms). No deletion.
- On other API error: MatSnackBar "Не удалось удалить предмет." (duration: 6000ms).

## Accessibility

All patterns follow WCAG 2.1 AA minimum. Consistent with prior phases.

- Stat cards: each `<article>` has `role="region"` with `aria-label="{stat label}"`.
- Clickable stat cards: add `role="link"` and `tabindex="0"` with keyboard `Enter`/`Space` handling, or wrap in `<a [routerLink]>` instead of `(click)`.
- Trash icon buttons: `aria-label="Удалить помощника {fullName}"` / `aria-label="Удалить предмет {subjectName}"`.
- Edit icon buttons: `aria-label="Редактировать предмет {subjectName}"`.
- `MatDialog` provides `role="dialog"` and `aria-modal="true"` automatically; set `ariaLabel` on each dialog config:
  - Assign assistant: `ariaLabel: "Назначить помощника старосты"`
  - Subject create: `ariaLabel: "Новый предмет"`
  - Subject edit: `ariaLabel: "Редактировать предмет"`
  - Delete confirmations: `ariaLabel: "Подтверждение удаления"`
- Permission checkboxes: each has an associated `<label>` wrapping both checkbox and text.
- Student select in dialog: `aria-label="Выберите студента"`.
- Teacher select in dialog: `aria-label="Выберите преподавателя"`.
- Loading skeletons: `aria-hidden="true"` with an `aria-live="polite"` region announcing "Загрузка..." while `loading()` is true and cleared when data arrives.

## Backend Fix — WPAN-13

This is a backend-only change (Java, `academic-service`). No UI contract is needed. The fix extends the `@RequireRole` AOP aspect to permit assistant management operations when the JWT carries `X-Is-Headman: true` AND `X-Group-Id` matches the target group. The Angular `HeadmanApiService` sends both headers via the existing `AuthInterceptor` which already forwards all claims from the JWT access token as `X-*` headers.

Verify: if the interceptor does NOT already forward `X-Is-Headman` and `X-Group-Id`, it must be updated to do so. Check `auth.interceptor.ts` before implementing the backend fix.
